\chapter{Discussion, Limitations and Future Work}\label{ch:discussion}

This chapter interprets the evaluation results, states the prototype's limitations, and identifies
priorities for completing, deploying, and extending DUET.

% ============================================================================
\section{Discussion}\label{sec:disc-discussion}

For honestly established and monitored conversations, DUET provides automatic in-band
key-substitution detection by adding conversation-specific peer warnings through additional
label-bound lookups without changing the lookup-proof format. The
detection mechanism combines domain-separated labels, proof-verified absence, warning persistence,
and transition auditing. When the directory is honest, comparison with the global VRF-bound identity
entry detects the \hyperref[sc:threat-a3]{A3 network man-in-the-middle substitution}, while
peer-slot absence provides supporting evidence.

The evaluation shows that key-substitution detection reuses the existing proof format through
additional lookups, while windowed catch-up reduces the proof count from $W$ to one in the defined
synthetic baseline (\cref{ssec:eval-catchup}). DUET's measured lookup proof remains in the same
sub-kilobyte class as the matched CONIKS quantity in \cref{sec:eval-compare}. These are local
component results and do not measure production throughput.

DUET could extend beyond Signal to a messenger with a provider-operated key directory and a shared
secret between the messaging parties. Continuous mode also requires public ratchet keys and secret
state for each epoch. Session mode requires fewer integration points and directory writes, while
continuous mode authenticates each ratchet epoch at a higher write rate. Both remain subject to
trust on first use, endpoint security, and independent head comparison for split-view detection.

\section{Limitations}\label{sec:disc-limitations}

DUET's monitoring guarantee begins only after a client pins an initial directory binding and
therefore cannot establish whether that binding was authentic. Timely detection also assumes active
peer participation as an absent peer slot may mean that the peer has not run the client. Monitoring
applies only to retained conversations. Deleting a conversation stops its monitoring, while
archiving it preserves monitoring. The prototype retains the signed-head checkpoint, peer-key pins,
and per-label monitor state only while the application process is running. An application restart
establishes a new trust-on-first-use baseline and cannot retrospectively detect a substitution
introduced during the gap. The design also does not cover groups, MLS, Sender Keys, complete
multi-device warning propagation, or compromised endpoints.

For third-party auditing, transition validation assumes at least one honest auditor. G4 (Fork
Detection) additionally requires signed heads obtained from independent vantage points. A client can
reject a head that does not extend its retained baseline, but it cannot independently expose two
internally consistent histories. Therefore, before production deployment, the system must define
authenticated epoch disclosures, signed-head freshness and failure policies, and a source of
independently observed heads.

The prototype also does not hide lookup queries from the operator. Published VRF-derived global
identity labels resist offline enumeration by observers without the VRF secret key or corresponding
proof~\cite[Sections~1, 3.4, and 7.6]{rfc9381}, but the public interface permits online tests of
known identifiers. Moreover, a valid warning MAC shows only that a holder of the conversation
secret created the payload. It neither identifies the writer nor establishes that the report is
true. Write-rate limits, signed-head freshness checks, gossip for detecting withheld proofs, and
warning attribution also remain unimplemented.

The key directory server is an in-memory, single-machine prototype that
clones the directory tree at each epoch commit. The Signal Desktop integration uses a deterministic
substitute for the conversation secret and a seeded Double Ratchet simulation. These demonstrate
the label derivation and CEA state transitions but do not establish label unpredictability or the
security of Signal's live Double Ratchet. The identity-key verification path runs at Signal
Desktop's peer-key-retrieval integration point. However, if a signed head or proof is invalid, or the fetched
identity key does not match the verified directory binding, the prototype reports a rejecting
verdict without blocking session establishment. Warning persistence checks are implemented and
tested but are not called by the live monitor. Continuous mode also uses the raw Diffie--Hellman
output as a substitute for the chain key and does not model skipped ratchet epochs. A production
integration must obtain the live chain key and support explicit epoch indices and bounded skipped
state.

Finally, the supporting security evidence consists of an informal proof sketch, definitions, the
same-head lemma, and the adversarial suite. The adversarial suite also does not model separate
first-contact sessions for both parties or a fabricated pre-key bundle made consistent with a
malicious directory entry. Moreover, the timings cover local components instead of complete
networked monitoring or auditing. M11 excludes the Signal Desktop peer-key-retrieval path, while
M12 excludes network transfer, epoch-delta retrieval, persistent state, and full transition replay.
The committed results contain aggregate statistics instead of raw Criterion samples. Therefore, these
results cannot be interpreted as end-to-end deployment measurements.

\section{Future Work}\label{sec:disc-future}

\subsection{Completing the Protocol and Security Argument}

First, production integration must replace the deterministic conversation and ratchet inputs with
the live X3DH or PQXDH conversation secret and Double Ratchet chain key obtained from libsignal.
Continuous mode must also support explicit epoch indices and bounded skipped state.

Second, the public registration and raw-label write interfaces must authenticate the account or
conversation party making the first write. This prevents an unauthorised client from registering a
global binding or occupying an empty conversation slot. Later replacement and deletion remain
subject to transition auditing and persistence evidence.

Finally, the security analysis needs a formal detection game combining the KDF, VRF, signed heads,
warning authentication, CEA fingerprints, and append-only verification. Symbolic analysis and
independent verification of the client proof checker would provide additional assurance.

\subsection{Groups, Devices, and Directory Privacy}

Group messaging support would require epoch-scoped labels and a warning policy covering membership
changes and every current device, potentially using domain-separated MLS exporter
secrets~\cite[Section~8.5]{rfc9420}. Multi-device continuity could build on ELEKTRA-style device
cross-signing, together with device-scoped labels, warning propagation, and reset
handling~\cite[Sections~2.1 and 3]{len2023elektra}.

Stronger directory privacy is another research direction. OPRF-based identity blinding could
conceal the raw lookup identity from the OPRF server~\cite[Sections~1 and 7.1]{rfc9497}. However,
private retrieval and network anonymity would still be needed to hide the requested entry and the
requester. The design would need to specify whether the OPRF role is separate or distributed.

\subsection{Deployment and Cryptographic Scale}

Persistent copy-on-write nodes should replace full snapshot cloning without changing the proof
format. This would avoid the full-tree copy currently performed at each epoch commit. Integration
with Signal's existing key-transparency service~\cite{signal-kt-server} would require immutable raw
writes, authenticated ownership, transition disclosures, client integration points, and an
independent auditor or gossip federation.

CONIKS allows clients to monitor their own bindings with logarithmic proofs without relying on a
third-party monitor for that task~\cite[Sections~1 and 4.1.3]{melara2015coniks}. DUET could evaluate
client-assisted transition checking and signed-head exchange. However, G4 still requires
independently observed heads.

Post-quantum operation also requires replacements for the ECVRF and signed-head signatures,
although PQXDH secrets already fit the label KDF~\cite[Sections~2.2 and 3.3]{pqxdh}. Even with
PQXDH-derived labels, end-to-end post-quantum security would continue to depend on the messenger's
authentication and ratchet mechanisms. This thesis does not select or implement those replacements.

Concurrency, serialization, reclamation, and memory use require measurement under realistic
deployment loads.

\subsection{Evaluation, Operations, and Usability}

A usability study should determine whether users correctly interpret and act on the red warning and
amber notice. It should also examine accessibility, escalation, and alarm fatigue, continuing the
verification-ceremony research that motivated the design~\cite{vaziripour2017}.

Production warning records should contain the recorded verdict, relevant epoch, signed heads, and
proofs needed for operator or auditor review while avoiding unnecessary metadata. An operational
policy must define how to respond to a rejected proof, when to request key rotation, and when to
escalate a warning.

Moreover, future evaluation should cover persistent storage, concurrent requests, wide-area delay,
different epoch and catch-up policies, mobile CPU and energy use, and archived raw samples. Applying
the design in clinical, emergency-response, or industrial settings would require domain-specific
identity models, device-enrolment and revocation procedures, availability requirements, and regulatory
controls.
