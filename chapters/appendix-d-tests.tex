\chapter{Test Catalogue}\label{app:tests}

This appendix summarizes the complete test corpus that backs the conformance claims of \cref{sec:impl-tests}.
The Rust core contains \num{134} tests: \num{97} unit and invariant tests across nine modules, the
\num{8}-scenario adversarial integration suite, \num{25} tests in the \texttt{kt\_auditor} binary, and
\num{4} clean-session regression tests in \texttt{tests/clean\_path\_coverage.rs}
(\cref{ssec:eval-detection}), all run under \texttt{cargo test}. The TypeScript client has \num{180}
standalone Jest tests in thirteen suites and a further \num{35} embedded electron-mocha tests in six
Signal Desktop suites that drive realistic account identifier (ACI) strings through the integration boundary. A fixed set
of cross-language vectors additionally requires the two implementations to produce byte-identical
outputs.

The \num{25} \texttt{kt\_auditor} tests comprise the delta-replay test, six \texttt{classify\_head}
rollback/fork cases, five \texttt{commit\_decision} transaction cases, an end-to-end
partial-fetch-failure test, and twelve \texttt{PollStatus} tests covering every poll verdict,
including the missing, unparseable, and failing consistency-proof cases that return
\textsc{ConsistencyUnverified}, and the exact status-line mapping.

\Cref{tab:impl-t5a} lists representative correctness tests and the requirement each protects, and
\cref{tab:tests-adversarial} lists the adversarial scenarios with their expected and observed
verdicts. The unit, cross-language, and TypeScript tests are catalogued in the tables that follow. The
\texttt{kt\_auditor} binary tests are summarized by category above rather than listed individually.
\Cref{fig:impl-testing} summarizes the five evidence classes.

\section{TypeScript (Signal Desktop) Jest Suite}\label{sec:tests-ts}

The standalone \texttt{signal-desktop-kt} harness covers the verifier with \num{180} Jest tests in
thirteen suites: a live-server wire-parity suite, an in-process integration suite, a source-parity
suite, and ten unit suites.
Some catalogue rows represent parameterized cases (twelve decoder mutations, three status mappings,
three VRF vectors), and the totals count executed tests.
The \emph{wire-parity} suite runs the full client verification chain against a \emph{live} Rust directory
server over the network. It is a separate, opt-in test target (\texttt{npm run test:wire}) that requires the server
to be running, and its five tests early-return as no-ops when the server is absent, so a bare
\texttt{npm test} run does not by itself establish wire parity. The \emph{source-parity} suite
(\texttt{tree\_parity}) asserts that the shared verifier sources are byte-identical between the two
TypeScript trees, one parameterized case per file across the twenty-seven shared files. The integration suite and the
cryptographic unit suites (\texttt{remote\_kt\_client}, \texttt{cea}, \texttt{secret\_store}) run
the verifier against a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle log, ECVRF,
and Ed25519 signer). The remaining unit suites use test doubles by design: \texttt{background\_monitor}
and \texttt{getKeysForServiceId\_status} inject stub clients to check verdict-to-event routing,
\texttt{decoder\_validation} drives the DTO decoders through a mocked transport to check
malformed-response rejection, \texttt{kt\_log} checks the structured screenshot-readable log format,
and the \texttt{canonical\_service\_id}, \texttt{display\_string}, and
\texttt{pni\_silence} suites cover the ACI canonical-bytes boundary, display-string preservation, and
phone-number identifier (PNI) event-silence added with the canonical-identity fix. \Cref{tab:tests-jest-wire} lists the
wire-parity and integration tests, and
\cref{tab:tests-jest-unit,tab:tests-jest-unit-b,tab:tests-jest-canonical} list nine of the ten unit suites (\texttt{kt\_log} is described above but not separately tabulated).
Beyond the standalone harness, \num{35} embedded electron-mocha tests run in six suites under Signal
Desktop's own test runner (\cref{tab:tests-embedded}). They drive realistic ACI strings through the
same integration boundary the live preload callers use, so a regression at that boundary fails an
embedded test rather than passing silently.

\section{Evidence Structure and Cross-Implementation Parity}\label{sec:tests-evidence}

This section provides the detailed testing evidence summarized in \cref{sec:impl-tests}. Testing
provides five forms of evidence: specification grounding states the required behaviour. Unit and
invariant tests assess individual components. Cross-language vectors check agreement between the
implementations. The adversarial scenario suite evaluates the combined system against the threat
model. Performance benchmarks support the cost claims in \cref{ch:eval}.

On the \textbf{Rust} side, the core is covered by unit tests run under \texttt{cargo test}.
The Merkle log is tested exhaustively (every inclusion proof and every $(m,n)$ consistency
pair up to size 64, together with forgery attempts) so the RFC~9162 verifiers are checked
against their full small-input space rather than on a handful of cases. The prefix tree is
tested by recomputing the root from the compressed proof. The dual-index derivation is checked
against the cross-implementation HKDF vectors, and the VRF against the RFC~9381 suite-\texttt{0x03}
vectors. The server's signed tree head is tested for correct acceptance and for rejection of a tampered
or wrong-key signature. The auditor is tested for both honest audit and fork detection, including
the two cases that matter for soundness: that a genuine equivocation (one signer, two roots
at one epoch) is reported as a fork, and that a divergent head with an invalid signature is
correctly rejected rather than misclassified as a fork.

On the \textbf{TypeScript} side, the standalone verifier harness contains \num{180} Jest tests. Live
Rust--TypeScript wire parity is a separate opt-in target that requires the Rust directory server, and a normal
Jest run alone does not establish wire parity. When enabled, the wire-parity suite runs the client's
full verification chain against the live Rust directory server, confirming multi-entry inclusion, proven
non-inclusion, the Ed25519 signed-tree-head check (and its rejection of a tampered head), the VRF
path, and windowed consistency. The integration suite and the cryptographic unit suites run the
verifier against a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle log, ECVRF, and
Ed25519 signer), so the client is checked against the implemented components rather than stubs, while
the remaining unit suites use controlled test doubles. Together they cover key-substitution detection (the
lookup verdicts \texttt{SAFE}, key mismatch, and proven not-in-log), the own-key self-check
against a server overwrite, man-in-the-middle detection on a replaced lookup slot, and the
availability-versus-integrity routing. Beyond this harness, thirty-five embedded tests in six Signal Desktop suites run under the
client's own test runner and drive realistic ACI strings through the same integration boundary the
live callers use (\cref{sec:tests-ts}).

The adversarial scenario suite runs the attack taxonomy of \cref{ch:threat} against the
implemented crate. Implemented as the Rust integration test \texttt{tests/adversarial.rs}, it
covers A0, A1a, A1b, A2--A5, and X1 and asserts the
expected security outcome for each, with the A1 variants additionally pinning the warning epoch. The
standalone Jest, embedded electron-mocha, and opt-in wire-parity totals are separate figures, each
counted independently.
