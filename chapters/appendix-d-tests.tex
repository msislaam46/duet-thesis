\chapter{Test Catalogue}\label{app:tests}

This appendix summarizes the complete set of tests supporting the conformance claims in
\cref{sec:impl-tests}. The \texttt{duet} crate contains \num{86} tests: \num{61} unit and invariant
tests across nine modules, the \num{8}-case adversarial integration suite, \num{13} tests in the
\texttt{kt\_auditor} binary, and \num{4} clean-workflow regression tests in
\texttt{tests/clean\_path\_coverage.rs} (\cref{ssec:eval-detection}). All crate tests run using
\texttt{cargo test}. The \texttt{signal-desktop-kt} client verifier harness contains \num{93} Jest
tests in thirteen suites, along with \num{13} embedded electron-mocha tests in six Signal Desktop
suites. The embedded tests pass realistic account identifiers through the client integration. Fixed
vectors also require the crate and client component to produce byte-identical outputs.

The totals report all tests executed by the runners. Some catalogue rows group related tests.
Parameterized tests, including the RFC~9381 vectors, decoder mutations, and shared-source parity
files, check several internal cases but count as one executed test.

The \num{13} \texttt{kt\_auditor} tests consist of the wrong-leaf replay rejection test, the
\texttt{classify\_head} verdict table, the \texttt{commit\_decision} transaction table, two
configuration-mismatch tests (primary and comparison head), the exact status-line mapping, five
remaining poll-outcome tests, the partial-fetch retry, and the check-ordering test. The five
poll-outcome tests cover availability failures, withheld or invalid consistency proofs on the
primary chain and on the comparison head, an inadmissible vantage, and a malformed head. The
check-ordering test also pins the consistent, transition-failed, and rollback outcomes. These tests
are summarized by category here instead of being listed individually.

\Cref{tab:impl-t5a} lists representative correctness tests and the requirement each protects, and
\cref{tab:tests-adversarial} lists the adversarial scenarios with their expected and observed
verdicts. The unit, crate--client agreement, and client-component tests are catalogued in the tables
that follow. \Cref{fig:impl-testing} summarizes the five evidence classes.

The complete per-test listing is held in the test sources.

\paragraph{Running the tests.}
\begin{itemize}
  \item From \texttt{crate/}, \texttt{cargo test} runs the Rust tests and prints every test name.
  \item From \texttt{signal-desktop-kt/}, \texttt{npm test} runs the Jest suites.
  \item With a directory server running, \texttt{npm run test:wire} runs the opt-in wire-parity
  suite from \texttt{signal-desktop-kt/}.
  \item From \texttt{signal-desktop/}, \texttt{pnpm run test-node} runs the embedded
  electron-mocha tests, including the six key-transparency suites.
\end{itemize}

\texttt{signal-desktop-kt/\allowbreak \_\_tests\_\_/}, and

\section{Client Verifier and Signal Desktop Tests}\label{sec:tests-ts}

The \texttt{signal-desktop-kt} client verifier harness contains \num{93} Jest tests in thirteen
suites: a live-server wire-parity suite, an in-process integration suite, a source-parity suite,
and ten unit suites. The \emph{wire-parity} suite runs the full client verification chain against a
\emph{live} DUET directory server over the network. A normal Jest run permits its five live paths to
return without assertions when the server is unavailable. The dedicated \texttt{npm run test:wire}
command requires the server and fails if it cannot be reached. The \emph{source-parity} suite
(\texttt{tree\_parity}) asserts that the shared verifier sources are byte-identical between the two
verifier source trees across the twenty shared implementation files. The integration suite and the
cryptographic unit suites (\texttt{remote\_kt\_client}, \texttt{cea}, \texttt{secret\_store}) run
the verifier against a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle log, ECVRF,
and Ed25519 signer). The remaining unit suites use test doubles by design: \texttt{background\_monitor}
and \texttt{getKeysForServiceId\_status} inject stub clients to check verdict-to-event routing,
\texttt{decoder\_validation} drives the DTO decoders through a mocked transport to check
malformed-response rejection, \texttt{kt\_log} checks the structured log format used by the screenshots,
and the \texttt{canonical\_service\_id}, \texttt{display\_string}, and
\texttt{pni\_silence} suites cover the ACI canonicalization, display-string preservation, and
phone-number identifier (PNI) event-silence added with the canonical-identity fix.
\Cref{tab:tests-jest-wire} lists the suites and the properties each establishes.
Beyond this harness, \num{13} embedded electron-mocha tests run in six suites under Signal
Desktop's own test runner (\cref{tab:tests-embedded}). They pass realistic ACI strings through the
integration point used by the live preload callers. Therefore, a regression at that point fails an
embedded test instead of passing silently.

\section{Evidence Structure and Cross-Implementation Parity}\label{sec:tests-evidence}

This section provides the detailed testing evidence summarized in \cref{sec:impl-tests}. The
evidence covers standards conformance, unit and invariant behaviour, agreement between the crate and
client component, adversarial outcomes, and measured component costs.

The \texttt{duet} crate's tests cover the cryptographic primitives, prefix tree, Merkle log, signed
heads, server, auditor, warning monitor, and continuous mode. Every Merkle-log inclusion proof and
consistency pair up to size 64 is tested, together with forged-proof rejection, so the RFC~9162
verifiers are checked across their complete small-input
space~\cite[Sections~2.1.3--2.1.4]{rfc9162}. The prefix-tree tests reconstruct the root from compressed
proofs. Fixed vectors check the dual-index derivation, while the VRF tests use the RFC~9381
ECVRF-EDWARDS25519-SHA512-TAI vectors~\cite[Appendix~B.3]{rfc9381}. Signed-head tests cover valid,
tampered, and wrong-key signatures. Auditor tests cover honest transitions, genuine equivocation,
and rejection of a divergent head carrying an invalid signature.

The \texttt{signal-desktop-kt} client verifier harness contains \num{93} Jest tests. Its opt-in
wire-parity suite requires the running directory server and checks the complete client verification
chain against live responses. The checked paths include multi-entry inclusion, proven
non-inclusion, signed-head verification and tamper rejection, VRF verification, and windowed
consistency. A normal Jest run does not by itself establish live wire parity. The \texttt{npm run
test:wire} command requires the server and fails if it is unreachable. In addition,
\num{13} embedded tests in six Signal Desktop suites pass realistic account identifiers through the
client's integration path (\cref{sec:tests-ts}).

The adversarial suite is implemented in \texttt{tests/adversarial.rs} within the \texttt{duet}
crate. It covers A0, A1a, A1b, A2--A5, and X1 and asserts the expected security outcome for every
case. The A1 variants also assert the warning epoch. The Jest, embedded electron-mocha, and opt-in
wire-parity totals describe separate test classes and are counted independently.
