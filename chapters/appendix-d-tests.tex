\chapter{Test Catalogue}\label{app:tests}

This appendix lists the full test suite that backs the conformance claims of \cref{sec:impl-tests}.
The test corpus comprises the following groups. The Rust core is covered by \num{97} unit and property tests across
nine modules, the \num{8}-scenario adversarial integration suite, and \num{22} tests in the
\texttt{kt\_auditor} binary (the delta-replay test, six \texttt{classify\_head} rollback/fork cases,
five \texttt{commit\_decision} transaction cases, an end-to-end partial-fetch-failure test, and nine
\texttt{PollStatus} tests covering every poll verdict and the exact status-line mapping),
\num{127} tests in total, run under \texttt{cargo test}; the TypeScript
client is covered by \num{106} Jest tests in eight suites,
and a fixed set of cross-language vectors ties the two implementations together byte-for-byte. The
representative excerpt and the scenario summary are in \cref{tab:impl-t5a,tab:impl-t5b}; the
complete listing follows. Tables are placed exactly where they are discussed.

\section{TypeScript (Signal Desktop) Jest Suite}\label{sec:tests-ts}

The standalone \texttt{signal-desktop-kt} harness covers the verifier with \num{106} Jest tests in
eight suites: a live-server wire-parity suite, an in-process integration suite, and six unit suites.
The \emph{wire-parity} suite runs the full client verification chain against a \emph{live} Rust
server over the network; it is a separate, opt-in test target (\texttt{npm run test:wire}) that requires the server
to be running, and its five tests early-return as no-ops when the server is absent, so a bare
\texttt{npm test} run does not by itself establish wire parity. The integration suite and the
cryptographic unit suites (\texttt{remote\_kt\_client}, \texttt{cea}, \texttt{secret\_store}) exercise
the verifier against a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle log, ECVRF,
and Ed25519 signer). The remaining unit suites use test doubles by design: \texttt{background\_monitor}
and \texttt{getKeysForServiceId\_status} inject stub clients to check verdict-to-event routing, and
\texttt{decoder\_validation} drives the DTO decoders through a mocked transport to check
malformed-response rejection. \Cref{tab:tests-jest-wire} lists the wire-parity and integration tests;
\cref{tab:tests-jest-unit,tab:tests-jest-unit-b} list the six unit suites.

\section{Cross-Language Equivalence Vectors}\label{sec:tests-xlang}

A fixed set of test vectors pins the HKDF dual-index derivation, the sealed warning MAC, and the
CEA construction byte-for-byte across the Rust and TypeScript implementations: on the Rust side,
\texttt{dual\_index::cross\_impl\_test\_vectors}, \texttt{dual\_index::warn\_mac\_cross\_impl\_vector},
and \texttt{cea::cross\_impl\_test\_vectors}, the last pinning three ratchet epochs, not just the
first (\cref{tab:tests-rust-prim,tab:tests-rust-system}); on the TypeScript side, the
\texttt{kt\_integration} vectors v1, v3, and the warn-MAC vector, and the \texttt{cea} vector test
(\cref{tab:tests-jest-wire,tab:tests-jest-unit}). The Ed25519 and Merkle computations are checked to
agree by the wire-parity suite, which verifies the Rust server's live outputs with the TypeScript
verifiers. Together these are the contract that licenses the TypeScript client as a faithful
verifier of the Rust server's outputs (\cref{sec:impl-tests}).

\section{Adversarial Scenario Suite}\label{sec:tests-adversarial}

The suite exercises each in-scope threat scenario of \cref{ch:threat} end to end against the real
\texttt{duet} crate, asserting both the verdict and the epoch at which detection occurs, so it
provides machine-checkable coverage of the threat model rather than of isolated components. The
detection epochs it reports are the schedule of this scripted demonstration, not a protocol-wide
latency bound.
