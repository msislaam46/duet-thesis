\chapter{Background}\label{ch:background}

This chapter establishes the background needed to understand the design of DUET. It begins with
Signal's asynchronous key-distribution model and then examines key-transparency systems and
continuous-authentication research to derive the requirements carried into \cref{ch:design}.

% ============================================================================
\section{The Signal Protocol Stack}\label{sec:bg-signal}

Signal is a widely used end-to-end encrypted
messenger~\cite{signal-home,dowling2020nocompromise}. Its cryptographic stack, known as the Signal
Protocol, provides confidentiality, authentication, forward secrecy, and post-compromise security for
asynchronous communication. Its server-hosted pre-key model allows a user to initiate a conversation
while the intended recipient is offline. The Signal Protocol has also influenced other large-scale
messaging systems, including WhatsApp~\cite{whatsapp2023whitepaper}.

The Signal Protocol combines the Extended Triple Diffie--Hellman (X3DH) key-agreement protocol for
session establishment~\cite{x3dh} with the Double Ratchet algorithm for ongoing
communication~\cite{doubleratchet}. These mechanisms provide confidentiality and support recovery
from compromise through continuous key evolution.

This construction still depends on the provider distributing authentic public keys during session
establishment. Signal's server supplies those keys for X3DH~\cite{signaldocs}. A completed Safety
Number comparison can authenticate the parties' long-term identity keys, but its protection depends
on users carrying out a separate out-of-band ceremony. Signal therefore provides both the case study
and the integration setting for this thesis.

\subsection{Key Material, Safety Numbers, and What They Cover}\label{ssec:bg-keymat}

To support asynchronous communication, Signal requires users to publish several
types of public key material. A user $U$ generates a long-term identity key pair
$(\pkid{U},\skid{U})$, retains the secret key $\skid{U}$ locally, and publishes
the corresponding public identity key $\pkid{U}$. The user also publishes a
medium-term signed pre-key $\spk{U}$ together with a signature $\sig{\spk{U}}$
produced under $\skid{U}$, and a batch of single-use one-time pre-keys
$\opk{U}{i}$. These public values are uploaded to the server so that a sender
can initiate a session while the recipient is offline.

Signal's original built-in defence against key substitution is the Safety Number. It is a 60-digit
fingerprint derived from the parties' long-term identity keys and stable account identifiers. Users
can compare it out of band by scanning a QR code in person or reading the digits over a separate
channel~\cite{safetynumbers}. Signal has since introduced Automatic Key Verification (AKV), a
key-transparency mechanism discussed in \cref{ssec:bg-gap}. The Safety Number remains the baseline
against which the automated approaches are considered.

The Safety Number covers the parties' long-term identity keys and account identifiers. A signed
pre-key is authenticated indirectly through its signature under the identity key, but it is not
included in the Safety Number itself. One-time pre-keys are unsigned and have no individual
authentication, although the identity-key and signed-pre-key terms still bind the handshake to the
intended parties~\cite{x3dh}. The Safety Number therefore does not directly authenticate all the key material
used together in a particular session. This limitation in per-session coverage motivates the
construction developed later in the thesis.

X3DH consumes this published key material to establish the initial shared secret used by the
subsequent protocol stages.

\subsection{The Extended Triple Diffie--Hellman (X3DH) Protocol}\label{ssec:bg-x3dh}

The Extended
Triple Diffie--Hellman (X3DH) protocol allows Alice to derive a shared secret
(denoted by $\sharedS$) with Bob even when Bob is offline, by combining Alice's
keys with the identity, signed pre-key, and one-time pre-key material published
by Bob.

Following the X3DH specification~\cite[Section~2.4]{x3dh}, this thesis denotes identity keys by
$\xIK{}$, signed pre-keys by $\xSPK{}$, one-time pre-keys by $\xOPK{}$, and ephemeral keys by
$\xEK{}$. Thus, $\xIK{U}=\pkid{U}$, $\xSPK{U}=\spk{U}$, and
$\xOPK{U}=\opk{U}{i}$. Each notation denotes a public key whose corresponding private key is held by
its owner. Alice generates an ephemeral key $\xEK{A}$ and computes the following Diffie--Hellman
values.
\begin{equation}\label{eq:bg-x3dh}
\begin{aligned}
\mathrm{DH1}    &= \DH{\xIK{A}}{\xSPK{B}}, \\
\mathrm{DH2}    &= \DH{\xEK{A}}{\xIK{B}}, \\
\mathrm{DH3}    &= \DH{\xEK{A}}{\xSPK{B}}, \\
\mathrm{DH4}^{*} &= \DH{\xEK{A}}{\xOPK{B}}
   \qquad\text{(if the bundle contains a one-time pre-key)}, \\
\sharedS &= \KDF\!\left(\mathrm{DH1}\concat\mathrm{DH2}\concat\mathrm{DH3}
   \concat\mathrm{DH4}^{*}\right).
\end{aligned}
\end{equation}
Here, $\DH{X}{Y}$ denotes the Diffie--Hellman shared secret derived from the key pairs associated
with $X$ and $Y$, following the X3DH specification. The notation omits whether a party uses the
public or private component of each pair. $\KDF$ denotes a key-derivation function, $\concat$
denotes byte-string concatenation, and $\sharedS$ is the resulting shared secret. \Cref{ch:design}
uses this secret as an input to DUET's label derivation. Key authenticity must hold at this point.

The identity keys enter the shared secret through $\mathrm{DH1}$ and
$\mathrm{DH2}$: $\mathrm{DH1}$ combines Alice's identity key with Bob's signed
pre-key, and $\mathrm{DH2}$ combines Bob's identity key with Alice's ephemeral
key, so that both parties' long-term identities are bound into session
establishment. $\mathrm{DH3}$ and $\mathrm{DH4}^{*}$ incorporate Bob's signed
pre-key and one-time pre-key material, contributing forward secrecy, and the
fourth term is omitted when no one-time pre-key is
available~\cite[Section~3.3]{x3dh}.

The resulting $\sharedS$ depends on Alice's identity and ephemeral keys and on Bob's identity key,
signed pre-key, and optional one-time pre-key. A substitution therefore affects the resulting
session differently depending on which value is replaced.

When Bob's genuine one-time pre-key is absent or withheld, an attacker who substitutes Bob's identity
key and a signed pre-key valid under that identity can derive the resulting shared secret and
impersonate Bob. DUET is designed to detect this coordinated substitution.
Substituting only the signed pre-key causes Alice's signature check to fail because she verifies
$\spk{B}$ under $\pkid{B}$ and aborts on failure~\cite[Section~3.3]{x3dh}. Substituting only the
one-time pre-key normally causes Alice and Bob to derive different secrets, so the session fails
rather than enabling impersonation. Omitting the one-time pre-key weakens the initial
forward-secrecy contribution but does not by itself enable impersonation.

The coverage of these values by Signal's authentication mechanisms is examined in
\cref{ssec:bg-gap}. \Cref{fig:bg-x3dh} shows the protocol sequence from publication of Bob's pre-key
bundle to Alice's initial message.

Signal's post-quantum variant, PQXDH, additionally mixes in a key-encapsulation
secret so that traffic recorded today cannot be decrypted by a future quantum
adversary (a ``harvest-now, decrypt-later'' attacker)~\cite{pqxdh}.

Signal does not use $\sharedS$ directly to encrypt application data. Instead, $\sharedS$
initializes the Double Ratchet, which evolves the cryptographic state throughout the conversation
and derives the per-message encryption keys.

\subsection{The Double Ratchet Protocol}\label{ssec:bg-ratchet}

Once the shared secret $\sharedS$ has been established by X3DH or PQXDH, Signal
hands control to the Double Ratchet protocol. Whereas X3DH is responsible for
bootstrapping trust and deriving an initial secret, the Double Ratchet protocol
is responsible for maintaining confidentiality throughout the remainder of the
conversation. It combines a Diffie--Hellman ``ratchet'', in which the parties
periodically exchange new ephemeral public keys, with symmetric key-derivation
chains that advance a root key into per-message keys~\cite{doubleratchet}. This construction provides
forward secrecy and post-compromise security. \emph{Forward secrecy} means that compromise of a current key
does not expose past messages, because the chain only moves forward. \emph{Post-compromise
security} means that the session can heal after a compromise once the attacker stops
interfering, because a fresh Diffie--Hellman ratchet step re-randomizes the state. This
healing is guaranteed only against an adversary who becomes passive after the compromise. It
offers no guarantee against one who remains active. This active-adversary
setting returns in \cref{sec:bg-acka}. \Cref{fig:bg-ratchet} shows how the Diffie--Hellman
ratchet and the symmetric-key chains interact.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-bg-ratchet}
\caption[Double Ratchet key schedule.]{Double Ratchet key schedule. Each party maintains
sending and receiving chains, and the figure follows one direction. $\KDF_{RK}$ combines the current
root key with a fresh Diffie--Hellman output to produce the next root key and a chain

temporarily for out-of-order delivery.}
\label{fig:bg-ratchet}
\end{figure}

The Double Ratchet continuously evolves the encryption state but does not re-authenticate the public
keys used during session establishment. Its guarantees therefore depend on those keys having been
authentic when the session began. Signal addresses this dependency through Safety Numbers and AKV,
whose coverage and usability limitations are examined next.

\subsection{Safety Numbers and the Verification Gap}\label{ssec:bg-gap}

The preceding mechanisms establish confidential communication and continuously update the encryption
keys, but they do not by themselves establish that the public keys supplied during session initiation
were authentic. Signal therefore provides two verification mechanisms. The first is the Safety
Number ceremony introduced in \cref{ssec:bg-keymat}, through which users compare a fingerprint
derived from their long-term identity keys over an independent channel. The second is Automatic Key
Verification (AKV). When a user selects ``Verify automatically'' from the Safety Number screen, the
client checks the public keys held for a contact against Signal's transparency log and displays an
``Encryption verified'' indicator when the check succeeds~\cite{signal-akv}.

Signal's deployment of AKV shows that key transparency can be integrated into a deployed messaging
service. Its documentation also identifies limitations relevant to this thesis. AKV is unavailable for chats
initiated through usernames, contacts that cannot be discovered through phone numbers, and devices
holding outdated contact information~\cite{signal-akv}. It does not verify real-world identity or
prevent impersonation and account compromise~\cite{signal-akv}. AKV verifies the requesting client's
view of a contact's key binding, but it does not provide a channel through which that client can warn
the contact after detecting a substitution.

Two limitations therefore remain. The first concerns the key material and protocol state covered by
authentication. The second concerns whether users complete the required verification ceremony.

Dowling and Hale observe that authentication based on long-term identity keys authenticates the
protocol state at session initiation but not its subsequent evolution~\cite[p.~4]{dowling2023acka}.
The same limitation applies to trust-on-first-use systems, which establish authenticity once and
then assume it thereafter~\cite[p.~4]{dowling2023acka}. Their earlier MoDUSA construction derives
authentication values throughout a conversation, allowing a user-initiated comparison to cover
ratchet epochs rather than only session initiation~\cite{dowling2021meta}. This allows the parties
to detect state divergence caused by an active man-in-the-middle attacker. MoDUSA still depends on
users initiating the comparison, so continuous key agreement alone does not provide automatic
re-authentication during a long-lived conversation.

Dowling and Hale illustrate the consequence with a three-year scenario in which compromise occurs
after the first year. Under their assumptions, the adversary may remain undetected for up to two
years, compared with the single one-hour session assumed for a TLS
deployment~\cite[p.~3]{dowling2023acka}.

Where AKV is unavailable, users still depend on a manual verification ceremony. A study of user
pairs across WhatsApp, Viber, and Facebook Messenger found that only two of twelve pairs succeeded
in locating and completing the ceremony in at least one application when asked to ensure that no one
else could read their messages. Across all unguided pair--application trials, the overall success
rate was 14\%~\cite[p.~30]{vaziripour2017}. Brief, application-independent instructions about the need to
compare keys raised the overall success rate to 79\%, reaching 96\% for
Viber~\cite[p.~29]{vaziripour2017}. Even with instructions, users took an average of 3.2 minutes to
find the ceremony and a further 7.8 minutes to complete it~\cite[p.~36]{vaziripour2017}.

Respondents also showed limited understanding of the threat model. Among responses that did not
mention key verification, 88\% referred instead to features of the other person, such as voice,
appearance, or shared knowledge~\cite[p.~39]{vaziripour2017}. The man-in-the-middle attacker was not
explicitly identified as a possible attack vector~\cite[p.~40]{vaziripour2017}. The authors conclude
that a system such as CONIKS could automate key discovery without relying on one trusted party while
making inconsistent directory views detectable~\cite[p.~40]{vaziripour2017}.

The literature therefore leaves several requirements unresolved. A malicious provider may
substitute a coordinated identity-key and signed-pre-key bundle during session establishment.
Directory-based verification depends on consistent views and effective auditing. Signal's deployed
authentication mechanisms concentrate on key bindings rather than evolving protocol state, while
manual verification remains uncommon in practice. The following
sections examine secure transparency logs and verifiable key directories before turning to ACKA and
the requirements summarized in \cref{ssec:bg-implications}.

\section{Secure Transparency Logs}\label{sec:bg-logs}

The server distributing session-establishment keys must be accountable for the values it serves. Key
transparency provides this accountability by binding directory responses to publicly auditable
commitments. To make a forged binding pass client verification, the server must incorporate it into
a committed directory state, where subsequent monitoring can expose it.

\subsection{Commitments and Merkle Log Trees}\label{ssec:bg-merkle}

The transparency systems examined throughout this chapter are built from a
collision-resistant hash function, which enables commitments: compact
values that bind a publisher to a larger body of data. Merkle trees then
organize many such commitments into a structure that supports efficient
verification, and transparency logs use Merkle trees to make server
behaviour publicly auditable. The notion of a commitment therefore comes first.

A commitment is a short fingerprint of a body of data: small enough to publish
or repeat widely, yet so tightly bound to the data that altering any part of it
(adding, deleting, or modifying even a single entry) changes the
fingerprint. A collision-resistant hash function $\Hash$ makes this precise.
$\Hash$ maps an input of arbitrary length to a fixed-length output, and
collision resistance means that no efficient adversary can find two distinct
inputs that produce the same output. Publishing $\Hash(D)$ therefore commits the
publisher to $D$. To later substitute a different $D'\neq D$ while retaining the
same commitment would require producing a hash collision, which collision
resistance is assumed to prevent.

This binding property supports accountability in transparency systems. A server cannot alter a
committed state while retaining the same commitment without finding a hash collision. If it presents
conflicting commitments for the same state, the divergence can be exposed when those commitments are
compared.

A single hash binds an entire directory state, but it does not support efficient
verification of individual entries nor efficient evolution over time. Merkle
trees address both problems simultaneously. A Merkle tree is a binary tree in
which each leaf contains the hash of one record and each internal node contains
the hash of its two children, $\Hash(\text{left}\concat\text{right})$, where
$\concat$ denotes concatenation. The value at the root, commonly called the tree
head or root hash, is therefore a commitment to the entire
collection~\cite{rfc6962,rfc9162}. Because every internal node depends
recursively on the values beneath it, the root depends on every record in the
tree while remaining only a single hash long.

The specifications used by transparency systems deliberately distinguish leaves
from internal nodes by prepending different one-byte prefixes before hashing.
This form of domain separation prevents a leaf from ever being interpreted as an
internal node and vice versa, eliminating an otherwise subtle class of
structural ambiguities. This structure, due originally to Merkle, is the backbone
of Certificate Transparency, discussed in the following section, and of the RFCs
that specify it, RFC~6962 and its revision RFC~9162~\cite{rfc6962,rfc9162}.

Merkle trees support two verification operations used throughout this chapter. An inclusion proof
establishes that a record is included at a specified position under a committed tree head without
requiring the verifier to download the entire log. The proof contains the sibling hashes along the
path from the leaf to the root. The verifier combines the record with those hashes, recomputes the
root, and compares it with the published tree head. For a tree of $N$ leaves, the path contains at
most $\lceil\log_2 N\rceil$ siblings, with the exact number determined by the leaf position and tree
size~\cite[Section~2.1.3]{rfc9162}.

A consistency proof establishes that a later tree is an append-only extension of an earlier one. It
reveals the internal nodes needed to show that the earlier tree is contained within the later tree
without modifying, deleting, or reordering previously committed leaves. Its size is also logarithmic
in the size of the log~\cite[Section~2.1.4]{rfc9162}. Inclusion and consistency proofs answer
different questions. The first proves that a claimed record occurs under a committed root. The
second proves that the committed history has not been rewritten between observations.
\Cref{fig:bg-merkle} illustrates an inclusion proof and the copath used to recompute the root.

\caption[A Merkle log tree and inclusion proof.]{A Merkle log tree on four records. The shaded

The logarithmic size of inclusion and consistency proofs is one of the principal
reasons Merkle trees are practical for scalability across the Internet. However,
these costs are measured per proof. A client that has been offline for an
extended period may need to validate a sequence of updates accumulated during
its absence, causing the total verification cost to grow with the number of
missed epochs. Offline clients accumulate verification work across the epochs they miss, which motivates the
monitoring mechanisms examined later.

\subsection{Key Transparency Requirements}\label{ssec:bg-ct2kt}

Key transparency applies the broader transparency-overlay model~\cite{chase2016overlays} to
identity-to-key bindings~\cite{melara2015coniks}. It adapts Certificate Transparency's append-only
Merkle log~\cite{rfc6962,rfc9162} so that inconsistent key presentation can leave cryptographic
evidence.

A messaging directory must also protect information about its users. Publishing the directory
contents directly would expose service membership, while observing client queries may reveal which
identities are being looked up. A KT system should therefore reveal only the information needed to
verify the queried binding~\cite[p.~2]{melara2015coniks}.

Predictable labels, such as usernames or simple hashes of usernames, would still allow an adversary
to enumerate the directory by testing candidate identities. KT systems address this problem with
deterministic but unpredictable labels derived through a verifiable random function (VRF),
standardized in RFC~9381~\cite{rfc9381}. The directory operator maps an identity to a pseudorandom
label and returns a proof of correct evaluation. A client can verify that proof under the operator's
public key but cannot compute labels for unevaluated identities without the VRF secret key.
Determinism is also necessary because otherwise the provider could place multiple bindings for one
user at different locations~\cite[p.~5]{melara2015coniks}.

The VRF makes labels for unevaluated identities computationally unpredictable to parties that do not
possess the secret key. It also verifiably binds each evaluated identity to one label under a fixed
VRF key. It does not hide a query from the operator that evaluates the VRF, nor does it conceal the
directory's overall scale. Query privacy against the operator is a separate problem and is outside
the scope of this thesis.

A consistency proof establishes that one log state extends another, but it does not establish that
every observer received the same state. A malicious server may maintain two internally consistent
histories, presenting tree head $\logroot{A}$ to Alice and a different $\logroot{B}$ to Bob while
supplying each with a different key for the other. Their local inclusion and consistency checks may
all succeed. Detecting this split view requires commitments observed from different vantage points
to be compared through client gossip, an independent transparency log, or external auditors. This
distinction between local verifiability and global consistency motivates the equivocation requirement
in \cref{ssec:bg-implications}. \Cref{fig:bg-splitview} depicts the two divergent views.

\subsection{The IETF KeyTrans Architecture}\label{ssec:bg-keytrans}

The IETF Key Transparency (KEYTRANS) working group defines a reference architecture for
key-transparency systems, although several deployments predate or differ from it. The architecture
combines a VRF-indexed prefix tree with a log tree that commits successive directory states. It
includes deployment modes for contact monitoring and third-party
auditing~\cite{ietf-keytrans-architecture}. The associated protocol specifies the construction and
defines update, search, monitor, and audit operations~\cite{ietf-keytrans-protocol}. Signal's
production server implements the protocol draft with modifications~\cite{signal-kt-server}.

The Merkle log and its inclusion and consistency proofs follow RFC~6962 and
RFC~9162~\cite{rfc6962,rfc9162}. Label derivation uses the VRF standardized in
RFC~9381~\cite{rfc9381}. DUET later uses HKDF, standardized in RFC~5869~\cite{rfc5869}, to derive
conversation-specific labels from a shared session secret. The KeyTrans draft also calls for
reasonable monitoring windows so that intermittently connected clients need not replay every missed
update, but it does not specify the mechanism~\cite{ietf-keytrans-protocol}. DUET's windowed
consistency construction addresses that open efficiency requirement.

\section{Verifiable Key Directories for Key Transparency}\label{sec:bg-vkd}

The surveyed systems differ in data structure, privacy guarantees, and performance, but they
implement a common abstraction known as a verifiable key directory (VKD). A VKD is an authenticated
key--value directory whose responses can be verified without trusting the operator. Each returned
value is accompanied by a proof linking it to a publicly committed directory state. Commitments to
successive states allow clients and auditors to verify that updates follow the directory's transition
rules.

SEEMless formalized this abstraction through completeness, soundness, and
privacy~\cite[p.~4]{chase2019seemless}. Completeness requires honest proofs to verify. Soundness
prevents contradictory valid answers for one label. Privacy is defined by simulation against an
explicit leakage function. ELEKTRA later extended the abstraction to multi-device key histories and
formalized the keychain model used by Keybase since 2014~\cite[p.~1, p.~4]{len2023elektra}. These
constructions provide the principal comparison point for DUET, and their recurring limitations
motivate the design in \cref{ch:design}.


\subsection{Cryptographic Building Blocks: Merkle Prefix Trees and Zero-Knowledge Sets}\label{ssec:bg-vkd-blocks}

Although VKD constructions differ in their design details, most are assembled from the same building
blocks. Beyond the VRF of \cref{ssec:bg-ct2kt}, which keys the directory by storing bindings under
VRF-derived labels rather than usernames, two components recur: authenticated Merkle-tree directories
and zero-knowledge sets (ZKS).

\paragraph{Merkle Prefix Trees.} Most VKDs store bindings in a sparse
authenticated dictionary indexed by these labels. Conceptually the structure is
a sparse binary Merkle tree whose leaves correspond to the whole space of
possible labels. Because only a tiny fraction of labels are occupied,
implementations represent it as a \emph{Merkle prefix tree}, materializing only
the nodes on paths to existing entries. A label's bits give the path from the
root to its leaf, so a membership proof is the authentication path to that leaf
and a non-membership proof is the path to an empty (default) position. CONIKS
introduced this representation for key transparency~\cite[Section~3.1]{melara2015coniks}.
Later systems commonly add \emph{Patricia-style path compression}, collapsing
chains of single-child internal nodes into a single edge. This preserves the
tree's authentication properties while reducing storage. The terms \emph{Merkle
prefix tree}, \emph{Patricia trie}, \emph{Merkle Patricia trie}, and \emph{sparse
Merkle tree} thus name closely related authenticated dictionaries that differ
chiefly in whether, and how, the tree is path-compressed.

\paragraph{Zero-Knowledge Sets.} Merkle trees provide authenticated membership
and non-membership proofs, but they do not by themselves provide directory
privacy. That role is played by the \emph{zero-knowledge set} (ZKS): a committed
key--value map whose membership and non-membership queries can be answered
without revealing anything further about the directory's contents. Several VKD systems refine the ZKS primitive. SEEMless introduces an append-only ZKS
(aZKS)~\cite{chase2019seemless}. Parakeet uses an ordered ZKS (oZKS)~\cite{malvai2023parakeet}.
ELEKTRA builds on a rotatable ZKS (RZKS)~\cite{chen2022rzks,len2023elektra}. These constructions
differ mainly in how they encode update history and preserve privacy after server compromise.

\subsection{Academic VKD Constructions for KT}\label{ssec:bg-vkd-academic}

The academic VKD literature did not arrive as a set of independent proposals but
as a sequence of refinements to a shared design space, each construction
addressing a limitation of its predecessors. CONIKS introduced the basic
architecture of a privacy-preserving, auditable key directory. SEEMless
formalized the VKD abstraction and strengthened both privacy and history
verification. Parakeet improved storage efficiency and deployability, a design line
since deployed at scale by WhatsApp and independently reviewed~\cite{nccgroup2023akd}. ELEKTRA
extended the model to multi-device accounts and added privacy recovery after
server compromise, and OPTIKS, PRISM, and Merkle\textsuperscript{2} explored
alternative trade-offs between monitoring cost, auditing, and scalability. The
comparison focuses on the limitation each construction addresses and the
trade-off it leaves unresolved.

\subsubsection{CONIKS}
CONIKS introduced the transparency-based key-verification design that the subsequent literature builds
on, and it established design principles that later VKDs
retained~\cite{melara2015coniks}. Although CONIKS predates the formal VKD
abstraction that SEEMless would later introduce, the VKD constructions that
follow inherit its core architecture of VRF-derived labels, authenticated
directory commitments, and auditable epoch-by-epoch evolution. It stands as
the direct precursor of the VKD line rather than a VKD itself. Its motivation
was to automate the key verification that the manual fingerprint ceremonies of
\cref{sec:bg-signal} had failed to deliver, without reintroducing a single
trusted party. Its construction stores identity bindings in a Merkle prefix tree
whose leaves sit at VRF-derived labels, and each epoch the provider publishes a
\emph{Signed Tree Root} (STR): a signed snapshot of the tree root that
hash-chains to its predecessor~\cite[Section~3.3]{melara2015coniks}. A client then
audits only its own entry, downloading a logarithmic-size proof each
epoch (under 20\,kB per day even for a provider with billions of
users~\cite[p.~1]{melara2015coniks}) and checking that the key bound to its name
is the one it expects. Its security contribution is twofold. Lookups are
privacy-preserving, revealing nothing about which other users exist, and the
hash-chained STRs support \emph{non-equivocation} once views are compared: to show two clients
different directories a provider would have to maintain two divergent STR chains
indefinitely, so any auditor or client that compares STRs obtains publicly verifiable
evidence of the fork, attributable to the provider's signing key~\cite[p.~3]{melara2015coniks}. The directory records
identity-key bindings and their evolution across epochs, and nothing more. Three
limitations are significant. First, monitoring is linear in the offline period: a
client absent for $\ell$ epochs must perform $\Theta(\ell)$ work, because a
provider could insert a malicious binding and later revert it, so inspecting only
the latest STR is unsound. The proposed remedy, a per-leaf version history, would
require an auditor to perform $\Theta(n)$ work each epoch, where $n$ is the
number of changes in that epoch. The authors themselves doubt that a party
willing to perform this auditing for free will exist in every
deployment~\cite[p.~12]{melara2015coniks}. Second,
the client-to-client gossip that would let peers cross-check STRs is left as
future work~\cite[p.~7]{melara2015coniks}. Third, CONIKS exposes an attack but cannot deter a provider
willing to attack its users openly~\cite[p.~2]{melara2015coniks}.

\subsubsection{SEEMless}
SEEMless turned CONIKS's design pattern into a formally defined \emph{verifiable key directory}
primitive, with precise completeness, soundness, and simulation-based privacy
definitions~\cite[p.~2]{chase2019seemless}. Its \emph{append-only zero-knowledge set} (aZKS) stores
versioned labels so that proving a key is the current version costs only logarithmically in the number
of epochs, and it makes auditing a public role checkable by any party~\cite[Section~4.2]{chase2019seemless}.
Detection nonetheless remains self-monitoring: through \texttt{KeyHistory} the client retrieves its
verified key-version history and must reconcile it against the updates it actually made, and commitment
consistency is deferred to an external gossip or blockchain mechanism~\cite[p.~5]{chase2019seemless}.

\subsubsection{Parakeet}
Parakeet introduces compaction to bound the storage growth caused by append-only
history~\cite[Sections~III--IV]{malvai2023parakeet}. It replaces blockchains and gossip with a
consensusless witness protocol. Each epoch commitment is accepted after receiving $2f+1$ signatures
from a set of $3f+1$ witnesses. Under the assumption that at most $f$ witnesses are faulty and honest
witnesses do not sign conflicting commitments, intersecting quorums prevent the provider from
obtaining valid support for two conflicting states~\cite[Section~V]{malvai2023parakeet}. This design
adds a distributed witness set as a trust and operational assumption, while substitution
detection still depends on self-monitoring~\cite[p.~14]{malvai2023parakeet}.

\subsubsection{ELEKTRA}
ELEKTRA extended key transparency to multi-device accounts, representing each account as a
\emph{keychain} in which device additions and removals are cross-signed by an existing device key, so
a malicious provider cannot insert a fabricated key without forging a device signature or compromising
a device~\cite[Section~3]{len2023elektra}. Built over a \emph{rotatable zero-knowledge set} (RZKS) that
periodically rotates the VRF key to restore directory privacy after a server compromise, it formalizes
a \emph{multi-device VKD}~\cite[pp.~2--3]{len2023elektra}. Its unsuppressible account-reset warning is
the closest the academic line comes to an in-band peer warning, but it is raised only on a full account
reset, not on the substitution of an individual key~\cite[p.~2]{len2023elektra}.

\subsubsection{OPTIKS}
OPTIKS reduces client-side monitoring cost by removing SEEMless's second (``old'') tree: instead of
proving a version absent from an old set, it shows a key is the latest version in the single remaining
tree, combining a membership proof for the current version with a non-membership proof for the next,
roughly halving storage and update costs~\cite[p.~4356]{optiks2024}. It is the most
scalability-focused of the surveyed academic systems, yet soundness still requires the key's owner to
run history checks, and it shares the no-in-band-peer-warning gap common to every system surveyed
(\cref{ssec:bg-implications})~\cite[pp.~4357, 4360]{optiks2024}.

\subsubsection{PRISM}
PRISM departs furthest from per-user monitoring: a \emph{zero-knowledge rollup} (a zkVM over a
Jellyfish Merkle tree) produces a succinct proof of each epoch's state transition and posts it to a
data-availability layer, so every user verifies the whole directory through that proof rather than by
monitoring their own entry~\cite[Section~4]{pusch2025prism}. Its diagnostic observation frames this review:
every existing KT system assumes \emph{someone else will check}, whether the user, gossiping clients, a
blockchain, or third-party auditors~\cite[p.~6]{pusch2025prism}. It is presented as an overview rather
than a full specification and introduces substantial new trust dependencies in the data-availability
layer, the zkVM toolchain, and a single sequencer/prover~\cite[pp.~10--11]{pusch2025prism}.

\subsubsection{Merkle\texorpdfstring{$^2$}{2}}
Merkle\textsuperscript{2} provides an alternative transparency-log design rather than a complete
key-transparency directory. It nests a chronological Merkle tree with lexicographic prefix trees
attached to its nodes. This gives $O(\log^2 n)$ append cost while allowing a data owner to download
only polylogarithmic data for monitoring over the system's
lifetime~\cite[pp.~1--2]{hu2021merkle2}. The paper notes that the CONIKS VRF technique can reduce
identifier leakage, but its evaluation disables VRFs because privacy is not its focus.
Merkle\textsuperscript{2} therefore illustrates how the transparency-log substrate can be optimized
for low-latency monitoring when directory privacy is not the primary objective.

\medskip\noindent
Despite substantial differences in implementation, these constructions converge on a common
architecture: VRF-derived labels, an authenticated directory supporting membership and non-membership
proofs, an append-only history, and verifiable auditing. Across all of them, \emph{detection remains
external to the conversation}, resting on the user, an auditor, or a witness set rather than an in-band
channel to the peer.

\subsection{Deployed VKDs in Production Systems}\label{ssec:bg-vkd-deployed}

Several of these constructions have influenced deployed systems. Their operation at scale provides
evidence about which design choices are practical and which limitations remain relevant to this
thesis.

\subsubsection{WhatsApp Key Transparency (AKD)}
WhatsApp deploys an Auditable Key Directory at production scale, with signed directory roots and
retained audit material for independent consistency checking~\cite[pp.~4, 7, 8, 11, 12]{whatsapp2023whitepaper}.
The cited deployment does not enable client key-history monitoring~\cite[p.~5]{whatsapp2023whitepaper},
and a failed automatic check directs the user to verify the session manually with the
contact~\cite[pp.~10, 13]{whatsapp2023whitepaper}. It therefore demonstrates that key transparency and
public auditing can operate at messaging scale, but it does not provide the automatic in-band peer
warning targeted by this thesis.

\subsubsection{Signal Key Transparency}
Signal's key-transparency deployment closely follows the emerging IETF standard and exposes Search,
Monitor, and public audit interfaces~\cite{signal-kt-server}. Its directory covers the account identity
key, the phone-number mapping, and a username-hash mapping. Its wire format pads every prefix proof to
the full 256-sibling copath with stand-in hashes, giving a fixed-size 8{,}192-byte proof regardless of
directory occupancy, the deployed baseline that \cref{ch:eval} compares against. Detection nevertheless
relies on account monitoring and optional user-triggered verification rather than a
conversation-specific warning delivered to the peer.

\subsubsection{Proton Mail Key Transparency}
ProtonKT applies a verifiable directory to email and reuses Certificate Transparency to support
consistency checking~\cite[pp.~35, 37]{goebel2023proton}. It supports owner and external auditing but
does not notify a communication partner when a key is substituted~\cite[pp.~8, 47, 67]{goebel2023proton}.
Its evaluation also identifies the communication of verification failures to users as an unresolved
usability problem~\cite[p.~88]{goebel2023proton}.

\subsubsection{Google KT and Apple CKV}
Google KT~\cite{google-kt} is a historical CONIKS-derived transparency service. Apple Contact Key
Verification~\cite{apple-ckv} provides automatic device-level verification. Their relevant properties
are summarized in \cref{tab:bg-compare}.

The deployed systems converge on the same operational model: detection rests on
self-monitoring, auditor verification, or consistency checking, none of it reaching
the peer in band.

\section{The ACKA (Authenticated Continuous Key Agreement) Framework}\label{sec:bg-acka}

ACKA, proposed by Dowling and Hale~\cite{dowling2023acka}, extends a line of work in which
authentication evolves alongside continuous key agreement~\cite{dowling2020nocompromise}. It
complements verifiable key directories rather than replacing them. ACKA addresses an active channel
adversary and supplies continuous authentication, while assuming an abstract secure log of the kind
that key transparency can provide.

A continuous key agreement (CKA) is the component of a ratcheting protocol in which two parties
exchange fresh public key-shares and derive a new shared symmetric key after each exchange. The Double
Ratchet in \cref{ssec:bg-ratchet} is the principal example. Formally, a CKA is a multi-stage
key-exchange protocol that continually produces fresh symmetric keys from exchanged public
key-shares~\cite[p.~9]{dowling2023acka}.

ACKA (Authenticated Continuous Key Agreement) is composed of three
primitives~\cite[p.~7]{dowling2023acka}. First, the \emph{CKA} is the
key-exchange protocol just defined. Second, \emph{Continuous Entity
Authentication} (CEA), with its security notion CEAsec, is, informally, a
per-epoch authenticator: each epoch it derives a label and a fingerprint from a
chained secret state and the new public key-share, so that the two parties can
check, epoch by epoch, that they are talking to each other and not to an injected
key~\cite[pp.~13--14, 18]{dowling2023acka}. Finally, the \emph{secure logging
scheme} ($\Log$), with security notion $\Logsec$, is an append-only, immutable log to which fingerprints are
posted and from which they are queried~\cite[p.~10]{dowling2023acka}. An adversary who injects a forged
key-share must either collide on the honest party's label (producing two
fingerprints at one label, which alerts all communicating parties) or post
under a label the impersonated party never generates, which that party detects on
lookup~\cite[p.~7]{dowling2023acka} (\cref{fig:bg-acka} summarizes the
composition).

ACKA requires append-only immutability but leaves the log construction abstract. It notes that the
log could be a blockchain or another distributed-ledger protocol and specifies the interface
generically~\cite[p.~10]{dowling2023acka}.

ACKA and VKDs address different adversarial capabilities. ACKA considers an active
man-in-the-middle controlling the communication channel. This adversary may learn the pre-shared
state, control the sender's randomness, inject forged ratchet key-shares, and possess the long-term
authentication secrets~\cite[pp.~5, 19--20, 23]{dowling2023acka}.

Its detection result is conditional on CEAsec security and a log satisfying the $\Logsec$
definition~\cite[p.~7]{dowling2023acka}. A malicious log operator therefore lies outside ACKA's
theorem. ACKA specifies the required log interface but does not provide a construction that resists
an equivocating server. It also assumes a pre-shared state that is common and globally unique across
honest pairwise sessions, although it need not remain secret. The authors associate this assumption
with trust on first use~\cite[p.~6]{dowling2023acka}.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-bg-acka}
\caption[ACKA composition]{ACKA composes CKA and CEA with the abstract
secure-log interface $\Log$, whose required security notion is $\Logsec$. Adapted from Dowling and

\label{fig:bg-acka}
\end{figure}

Implementing ACKA's abstract log against an untrusted server is the component developed in
\cref{ch:design}, since the servers distributing keys are themselves targets of compromise
(\cref{sec:bg-vkd}). Three limitations remain in ACKA's construction. Only the receiver detects a
forgery, so no signal reaches the peer~\cite[p.~21]{dowling2023acka}. Verification proceeds
sequentially each epoch and provides no windowed catch-up. Its consistency mechanism is not used for
third-party auditing, which can instead be provided through the standard cross-vantage comparison in
\cref{sec:design-acka}.

ACKA and key transparency address complementary adversaries. ACKA assumes a secure log and provides
continuous authentication against an active channel adversary even after key compromise. Key
transparency builds a log that resists a malicious, equivocating server. Combining them is the
synthesis proposed in this thesis.

\subsection{Implications for the Design}\label{ssec:bg-implications}

The survey and the ACKA framework identify three requirements for key authentication in asynchronous
messaging.

First, detection must reach the peer. The surveyed systems assign discovery of a substitution to the
key owner, an auditor, or a witness set (\cref{tab:bg-compare}). ELEKTRA produces a warning only
after a full account reset~\cite[p.~2]{len2023elektra}. The cited WhatsApp deployment disables
self-monitoring and falls back to manual verification after a failed automatic
check~\cite[pp.~5, 10]{whatsapp2023whitepaper}. The design therefore requires an in-band peer signal
that remains available when one party is offline.

Second, catch-up cost must not grow linearly with the number of missed epochs. Under per-epoch
monitoring, a client that misses $W$ epochs must verify $W$ transitions. The IETF draft calls for
reasonable monitoring windows but leaves their construction
unspecified~\cite{ietf-keytrans-protocol}. CONIKS similarly identifies linear catch-up as an open
problem~\cite[p.~11]{melara2015coniks}. The required mechanism should therefore cover the missed
interval without fetching one proof for every epoch.

Third, equivocation must be detectable from outside the affected session. A malicious server may
present Alice and Bob with different append-only histories, each supported by locally valid proofs.
Neither party can expose that fork through its own view alone. Detection therefore requires an
independent vantage from which directory commitments can be compared. This is an established
key-transparency requirement and can be met through cross-vantage comparison.

Proof construction also involves a trade-off between compactness and structural privacy. Signal uses
fixed-length \num{8192}-byte proofs that conceal directory occupancy~\cite{signal-kt-server}. CONIKS
transmits only the authentication path required for the queried
entry~\cite[p.~10]{melara2015coniks}. \Cref{ch:eval} places DUET's proof construction within this
design space.

These requirements define the design developed in \cref{ch:design} and underlie the contributions
stated in \cref{ch:intro}. ACKA supplies continuous authentication under an assumed secure log,
while DUET provides the directory, peer-warning, catch-up, and cross-vantage mechanisms needed in
the malicious-server setting.
