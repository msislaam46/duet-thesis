\chapter{Background}\label{ch:background}

This chapter introduces the building blocks the rest of the thesis assembles and places the work among
existing systems. Key transparency and verifiable key directories authenticate what a directory
serves; the Authenticated Continuous Key Agreement (ACKA) framework~\cite{dowling2023acka} models
continuous authentication assuming a logging scheme that meets its Logsec security definition while
leaving its implementation open. This thesis composes the two, implementing the log ACKA assumes as a
directory designed for a malicious operator.

\section{The Signal Protocol Stack}\label{sec:bg-signal}

\subsection{What Signal Is and Why It Matters}\label{ssec:bg-whatis}

Signal is an end-to-end encrypted messaging protocol designed to provide
confidentiality, authentication, forward secrecy, and post-compromise security
for asynchronous communication. Unlike traditional secure channels, where both
parties must be online simultaneously, Signal allows users to initiate
conversations while recipients are offline through the use of server-hosted
pre-keys. The protocol has become influential well beyond the Signal
application itself: variants of its design have been adopted by large-scale messaging platforms,
including WhatsApp~\cite{whatsapp2023whitepaper}.

Signal is not a single cryptographic primitive but a protocol stack. Session
establishment is performed using the Extended Triple Diffie--Hellman (X3DH) key
agreement protocol~\cite{x3dh}, while ongoing communication is protected using the Double
Ratchet algorithm~\cite{doubleratchet}. Together these mechanisms provide strong confidentiality
guarantees against passive adversaries and support recovery from compromise
through continuous key evolution.

As \cref{ch:intro} argues, the security of this construction depends on one assumption external to the
cryptographic protocols: that users receive authentic public keys when initiating communication.
Signal's server distributes those keys for X3DH~\cite{signaldocs}, and the manual Safety Number does
not on its own guarantee they are authentic. Signal is thus both the case study and the deployment
context for this thesis.

\subsection{Key Material, Safety Numbers, and What They Cover}\label{ssec:bg-keymat}

To support asynchronous communication, Signal requires users to publish several
types of public key material. A user $U$ generates a long-term identity key pair
$(\pkid{U},\skid{U})$, retains the secret key $\skid{U}$ locally, and publishes
the corresponding public identity key $\pkid{U}$. The user also publishes a
medium-term signed pre-key $\spk{U}$ together with a signature $\sig{\spk{U}}$
produced under $\skid{U}$, and a batch of single-use one-time pre-keys
$\opk{U}{i}$. These public values are uploaded to the server so that a sender
can initiate a session while the recipient is offline.

Historically, Signal's principal built-in defence against a server that
substitutes one of these keys is the Safety Number: a 60-digit fingerprint,
derived from the two parties' long-term identity keys together with their stable
account identifiers, that users are expected
to compare out of band, by scanning a QR code in person, or reading digits
aloud over a separate channel~\cite{safetynumbers}. More recently, Signal has introduced Automatic
Key Verification (AKV), a key-transparency-based mechanism discussed in
\cref{ssec:bg-gap}. Understanding the scope of the Safety Number remains
important because it illustrates the original authentication model on which much
of the literature was based.

The gap that \cref{ssec:bg-gap} develops is one of
\emph{coverage}. The Safety Number is a function of the identity keys
$\pkid{A}$ and $\pkid{B}$ and the parties' account identifiers only, and
therefore authenticates the long-term
identities of the communicating parties and nothing else directly. The signed
pre-key is authenticated only \emph{indirectly}, by its signature
$\sig{\spk{}}$ under the identity key, so it is authentic relative to an
authentic identity key but is not itself covered by the Safety Number. The
one-time pre-keys are unsigned and carry no individual authentication (they are not signed under the
identity key), though the identity and signed-pre-key terms still bind the handshake to the true
parties. What no part of
this mechanism provides is authentication of the particular \emph{session}: the
specific keys actually combined in a given handshake are never checked together.
This per-session gap, rather than a mere shortfall in the number of keys
fingerprinted, is what the remainder of the thesis addresses.

The key material described above is consumed directly by Signal's
session-establishment protocol. The next step, therefore, is to examine how the X3DH
protocol combines these keys to derive the initial shared secret from which all
subsequent communication keys are generated.

\subsection{The Extended Triple Diffie--Hellman (X3DH) Protocol}\label{ssec:bg-x3dh}

Having introduced the public key material that Signal users publish, the section now
turns to how that material is used during session establishment. The Extended
Triple Diffie--Hellman (X3DH) protocol allows Alice to derive a shared secret
(denoted by $\sharedS$) with Bob even when Bob is offline, by combining Alice's
keys with the identity, signed pre-key, and one-time pre-key material published
by Bob.

Following the notation used in the X3DH specification~\cite[\S2.4]{x3dh}, this thesis
denotes identity keys by $\xIK{}$, signed pre-keys by $\xSPK{}$, one-time
pre-keys by $\xOPK{}$, and ephemeral keys by $\xEK{}$. Hence $\xIK{U}$ denotes a
user's identity key, $\xEK{A}$ for Alice's ephemeral key, $\xSPK{U}$ for a
signed pre-key, and $\xOPK{U}$ for a one-time pre-key, each a public key with a
corresponding private key held by its owner, so that $\xIK{U}=\pkid{U}$,
$\xSPK{U}=\spk{U}$, and $\xOPK{U}=\opk{U}{i}$. Alice generates an ephemeral key
$\xEK{A}$ and computes four Diffie--Hellman values:
\begin{equation}\label{eq:bg-x3dh}
\begin{aligned}
\mathrm{DH1}    &= \DH{\xIK{A}}{\xSPK{B}}, \\
\mathrm{DH2}    &= \DH{\xEK{A}}{\xIK{B}}, \\
\mathrm{DH3}    &= \DH{\xEK{A}}{\xSPK{B}}, \\
\mathrm{DH4}^{*} &= \DH{\xEK{A}}{\xOPK{B}}
   \qquad\text{(if the bundle contains a one-time pre-key)}, \\
\sharedS &= \KDF\!\left(\mathrm{DH1}\concat\mathrm{DH2}\concat\mathrm{DH3}
   \concat\mathrm{DH4}^{*}\right).
\end{aligned}
\end{equation}
Here $\DH{X}{Y}$ denotes the Diffie--Hellman shared secret derived from the key
pairs associated with $X$ and $Y$, following the notation of the X3DH
specification. The notation suppresses whether the public or private component
of each key pair is used by a given party during the computation. $\KDF$ is a
key-derivation function, $\concat$ is byte-string concatenation, and $\sharedS$
is the resulting shared secret, which will later serve as an input to the
constructions developed in \cref{ch:design}. The derivation of \cref{eq:bg-x3dh}
is the point at which key authenticity must hold: if an adversary substitutes
$\xIK{B}$, every downstream secret is computed against the wrong party.

The identity keys enter the shared secret through $\mathrm{DH1}$ and
$\mathrm{DH2}$: $\mathrm{DH1}$ combines Alice's identity key with Bob's signed
pre-key, and $\mathrm{DH2}$ combines Bob's identity key with Alice's ephemeral
key, so that both parties' long-term identities are bound into session
establishment. $\mathrm{DH3}$ and $\mathrm{DH4}^{*}$ incorporate Bob's signed
pre-key and one-time pre-key material, contributing forward secrecy, and the
fourth term is omitted when no one-time pre-key is
available~\cite[\S3.3]{x3dh}.

The property that matters for this thesis is that $\sharedS$ depends on all of
the public key material used during session establishment, not only the identity
keys: three distinct classes of key material (identity keys, signed pre-keys,
and one-time pre-keys) contribute directly to its derivation. Consequently, the
authenticity of every key in Bob's published bundle affects the resulting
session, but the effect of a substitution depends on which value is replaced.
Substituting the identity key, together with a signed pre-key valid under that substituted identity,
can interpose an attacker-controlled key, the case this thesis targets. Substituting only the signed
pre-key fails Alice's signature verification, since she verifies the signature on Bob's signed pre-key
$\spk{B}$ under his identity key $\pkid{B}$ and aborts on failure~\cite[\S3.3]{x3dh}. Substituting only
the one-time pre-key, whose optional DH term both peers must agree on, normally causes Alice and Bob to
derive different secrets and the session to fail rather than enabling impersonation, and omitting it
weakens the initial forward-secrecy contribution without enabling impersonation by itself.
\cref{ssec:bg-gap} develops this gap when it evaluates the scope of Signal's authentication mechanisms. \Cref{fig:bg-x3dh}
shows the message sequence, from Bob publishing his bundle to Alice's initial
message.

Signal's post-quantum variant, PQXDH, additionally mixes in a key-encapsulation
secret so that traffic recorded today cannot be decrypted by a future quantum
adversary (a ``harvest-now, decrypt-later'' attacker)~\cite{pqxdh}.

In Signal, the shared secret $\sharedS$ is not used directly to encrypt
application data. Instead, it serves as the starting point for the Double
Ratchet protocol, which continuously evolves cryptographic state throughout the
lifetime of the conversation. How Signal transforms this initial
shared secret into per-message encryption keys comes next.

\subsection{The Double Ratchet Protocol}\label{ssec:bg-ratchet}

Once the shared secret $\sharedS$ has been established by X3DH or PQXDH, Signal
hands control to the Double Ratchet protocol. Whereas X3DH is responsible for
bootstrapping trust and deriving an initial secret, the Double Ratchet protocol
is responsible for maintaining confidentiality throughout the remainder of the
conversation. It combines a Diffie--Hellman ``ratchet'', in which the parties
periodically exchange new ephemeral public keys, with symmetric key-derivation
chains that advance a root key into per-message keys~\cite{doubleratchet}. This
gives two properties: forward secrecy, meaning that compromise of a current key
does not expose past messages, because the chain only moves forward, and
post-compromise security, meaning that the session can heal after a compromise
once the attacker stops interfering, because a fresh Diffie--Hellman ratchet
step re-randomizes the state. Post-compromise security, however, is guaranteed
only against an adversary who becomes passive after the compromise. It offers no
guarantee against one who remains active. This active-adversary
setting returns in \cref{sec:bg-acka}. \Cref{fig:bg-ratchet} shows how the Diffie--Hellman
ratchet and the symmetric-key chains interact.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-bg-ratchet}
\caption[Double Ratchet key schedule.]{Double Ratchet key schedule. Each participant maintains
sending and receiving chains, and the figure follows one direction. $\KDF_{RK}$ combines the current

Although the Double Ratchet algorithm continuously refreshes encryption keys, it
does not continuously re-authenticate the public keys from which the session
originated. The security guarantees it provides therefore assume that the key
material used during session establishment was authentic in the first place.
This returns to the question left open in \cref{ssec:bg-keymat}: how do users
know that the public keys supplied by the server were genuine? Signal's answer
is the Safety Number mechanism, whose limitations motivate the remainder of this
chapter.

\subsection{Safety Numbers and the Verification Gap}\label{ssec:bg-gap}

The mechanisms described in the preceding subsections establish confidential
communication and continuously refresh encryption keys, but they do not
themselves establish that the public keys used during session initiation were
authentic. Signal therefore provides two verification mechanisms. The first is
the traditional Safety Number ceremony introduced in \cref{ssec:bg-keymat}, in
which users compare a fingerprint derived from their long-term identity keys
over an independent channel. The second is Automatic Key Verification (AKV), a
more recent, optional feature built on key transparency: when the user selects
``Verify automatically'' from the safety-number screen, the client checks the
public keys it holds for a contact against Signal's transparency log and
displays an ``Encryption verified'' indicator when that check
succeeds~\cite{signal-akv}.

The introduction of AKV is significant because it demonstrates that key
transparency has moved beyond research prototypes and into large-scale
deployment. Signal's own documentation, however, highlights limitations that are
directly relevant to this thesis. AKV is unavailable in several situations,
including chats initiated through usernames, contacts that are not discoverable
through phone numbers, and cases where a device stores outdated contact
information~\cite{signal-akv}. More fundamentally, AKV does not verify real-world
identity and cannot prevent impersonation or account compromise~\cite{signal-akv}.
Like other key-transparency deployments discussed later in this chapter, it
verifies a user's own view of a binding rather than providing a mechanism
through which one user can actively warn another that a key substitution has been
detected.

Despite these mechanisms, authentication remains incomplete. The
remaining gap has two dimensions: a structural gap arising from the protocol's
authentication model and a human gap arising from the usability of verification
ceremonies.

On the structural side, Dowling and Hale observe that authentication based on
long-term identity keys authenticates only the state of the protocol at session
initiation and not its subsequent evolution~\cite[p.~4]{dowling2023acka}. The
same limitation applies to trust-on-first-use systems, where authenticity is
established once and then assumed thereafter~\cite[p.~4]{dowling2023acka}. Their
earlier MoDUSA (Modified Device-to-User Signal Authentication) construction
strengthens the ceremony by deriving authentication values throughout the lifetime of the
conversation, so a user-initiated comparison covers ratchet epochs rather than only session
initiation; this lets participants detect state divergence caused by an
active man-in-the-middle attacker~\cite{dowling2021meta}. However, MoDUSA still
depends on user-initiated verification. Authentication information exists, but
users must actively compare it. As a result, a continuous key agreement provides
no automatic re-authentication during long-lived conversations. Dowling and Hale
argue that this can leave an active adversary undetected for years: in a stylized
three-year scenario in which the compromise occurs after the first year, this
exposes up to two years of communication, against the single (assumed one-hour)
session that a TLS deployment would expose~\cite[p.~3]{dowling2023acka}.

The human dimension of the problem is equally important because, in the many
chats where AKV is unavailable, verification still falls back to a manual user
ceremony. In practice, users rarely
perform it correctly. In a paired-participant usability study of the
authentication ceremony across WhatsApp, Viber and Facebook Messenger, only two
of twelve pairs located and completed the ceremony when simply
asked to make sure no one else could read their messages, an overall success
rate of 14\% across all pairs and applications (pair--application trials)~\cite[p.~30]{vaziripour2017}.
Brief, app-generic instructions about the need to compare keys raised the
overall success rate to 79\%, as high as 96\% for Viber~\cite[p.~29]{vaziripour2017},
but even when prompted the ceremony was slow: 3.2 minutes to find and a further
7.8 minutes to complete, on average~\cite[p.~36]{vaziripour2017}, which the
authors call unsatisfactory. Users also lacked the threat model the ceremony
defends: of the responses that did not mention key verification, 88\% relied
on recognizing features of their partner such as voice, appearance, or shared
knowledge~\cite[p.~39]{vaziripour2017}, and across the attacker types they
named, the man-in-the-middle ``was not explicitly mentioned as a possible attack
vector''~\cite[p.~40]{vaziripour2017}. The study's own authors draw the
conclusion this thesis starts from, that a system like CONIKS ``may help to
automate the process of discovering another person's key without relying on a
single trusted party, while also providing non-equivocation so that key servers
cannot deceive users''~\cite[p.~40]{vaziripour2017}.

In conclusion, these findings reveal a persistent authentication gap. The public
keys used during session establishment are distributed by a party that could
substitute them. Verification mechanisms remain dependent on assumptions about
the consistency of directory views and the availability of auditing
infrastructure. Authentication is tied primarily to key bindings rather than the
evolving protocol state, and manual user verification remains uncommon in
practice. The remainder of this chapter examines the principal approaches
proposed to address these limitations, beginning with key transparency and
verifiable key directories before turning to the complementary perspective
offered by the Authenticated Continuous Key Agreement (ACKA) framework, and
finally to the contributions of this thesis, which propose a unified system
bridging the KT and ACKA frameworks.

\section{Secure Transparency Logs}\label{sec:bg-logs}

Since the keys for session establishment are distributed by a server that could
substitute them, the server must be made accountable for what it hands out. Key
transparency meets this demand with one organizing idea, that the server should
be forced to publish an irrevocable, public record of the keys it serves, so
that handing Alice a forged key for Bob becomes an act the server can be caught
having committed in writing.

\subsection{Commitments and Merkle Log Trees}\label{ssec:bg-merkle}

The transparency systems examined throughout this chapter are built from a
collision-resistant hash function, which enables commitments: compact
values that bind a publisher to a larger body of data. Merkle trees then
organize many such commitments into a structure that supports efficient
verification, and transparency logs use Merkle trees to make server
behaviour publicly auditable. The notion of a commitment therefore comes first.

A commitment is a short fingerprint of a body of data: small enough to publish
or repeat widely, yet so tightly bound to the data that altering any part of it
(adding, deleting, or modifying even a single entry) changes the
fingerprint. A collision-resistant hash function $\Hash$ makes this precise.
$\Hash$ maps an input of arbitrary length to a fixed-length output, and
collision resistance means that no efficient adversary can find two distinct
inputs that produce the same output. Publishing $\Hash(D)$ therefore commits the
publisher to $D$. To later substitute a different $D'\neq D$ while retaining the
same commitment would require producing a hash collision, which collision
resistance is assumed to prevent.

This binding property is the source of accountability in transparency systems.
Once a server publishes a commitment to a directory state, any later attempt to
rewrite that state requires either producing a hash collision or presenting a
different commitment, both of which are detectable.

A single hash binds an entire directory state, but it does not support efficient
verification of individual entries nor efficient evolution over time. Merkle
trees address both problems simultaneously. A Merkle tree is a binary tree in
which each leaf contains the hash of one record and each internal node contains
the hash of its two children, $\Hash(\text{left}\concat\text{right})$, where
$\concat$ denotes concatenation. The value at the root, commonly called the tree
head or root hash, is therefore a commitment to the entire
collection~\cite{rfc6962,rfc9162}. Because every internal node depends
recursively on the values beneath it, the root depends on every record in the
tree while remaining only a single hash long.

The specifications used by transparency systems deliberately distinguish leaves
from internal nodes by prepending different one-byte prefixes before hashing.
This form of domain separation prevents a leaf from ever being interpreted as an
internal node and vice versa, eliminating an otherwise subtle class of
structural ambiguities. This structure, due originally to Merkle, is the backbone
of Certificate Transparency, discussed in the following section, and of the RFCs
that specify it, RFC~6962 and its revision RFC~9162.

Merkle trees become useful because they support two verification operations that
recur throughout the remainder of this chapter: proving that an entry exists and
proving that history has not been rewritten. An inclusion proof answers the
question ``is this record in the log, at this position?'' without shipping the
whole log: it consists of the sibling hashes along the path from the record's
leaf up to the root, and the verifier recomputes the root from the record and
those siblings and compares it against the published tree head. For a tree of
$N$ leaves that path has length at most $\lceil\log_2 N\rceil$, the exact length depending on the
leaf's position and the tree size, so the proof is logarithmic in the size of the directory rather
than linear~\cite[\S2.1.3]{rfc9162}.
A consistency proof answers a different question (``is the log I see now an
append-only extension of the one I saw before?'') by revealing the few
internal nodes that let a verifier confirm that an earlier tree head is
contained in a later one, with nothing previously committed modified, deleted,
or reordered. A consistency proof is also logarithmic in the size of the
log~\cite[\S2.1.4]{rfc9162}. The two proofs serve the client in equally
important ways: an inclusion proof convinces a client that its own key is
recorded correctly now, while a consistency proof convinces it that the server
has not quietly rewritten the past between visits. \Cref{fig:bg-merkle}
illustrates an inclusion proof and the copath a verifier recomputes from.

The logarithmic size of inclusion and consistency proofs is one of the principal
reasons Merkle trees are practical for scalability across the Internet. However,
these costs are measured per proof. A client that has been offline for an
extended period may need to validate a sequence of updates accumulated during
its absence, causing the total verification cost to grow with the number of
missed epochs. This distinction between per-proof efficiency and long-term
monitoring cost becomes important later, when discussing mobile clients and the
monitoring mechanisms used by key-transparency systems.

\subsection{Key Transparency Requirements}\label{ssec:bg-ct2kt}

Key transparency (KT) adapts the append-only Merkle log of Certificate
Transparency~\cite{rfc6962,rfc9162} from public certificates to user identity bindings: a server
should be unable to present different keys to different users without leaving cryptographic evidence.
The general framework of transparency overlays formalizes this reuse across
applications~\cite{chase2016overlays}. Moving from certificates to messaging introduces two
requirements that Certificate Transparency was never designed to satisfy.

The first requirement is privacy. Certificate Transparency logs
are intentionally public because certificates are public objects. A messaging
directory, by contrast, contains user identities and associated public keys. A
transparency mechanism that exposed the entire directory would reveal
information about who uses the service and potentially who communicates with
whom. KT systems therefore require proofs that reveal information only about the
queried entry rather than the directory as a whole~\cite[p.~2]{melara2015coniks}.

The second requirement follows directly from the first. If entries were stored
under predictable labels such as usernames or simple hashes of usernames, an
adversary could enumerate the directory by generating candidate names and
checking whether they exist. KT systems therefore require labels that are
deterministic yet unpredictable. This is achieved via verifiable random
functions (VRF), standardized in RFC~9381~\cite{rfc9381}. A VRF is a keyed function whose
outputs appear pseudorandom to anyone without the secret key while
simultaneously producing publicly verifiable proofs of correct evaluation. The
directory operator, holding the VRF secret key, maps a username to a
pseudorandom label and produces a proof that the label was computed correctly.
Clients can verify that proof against the operator's public key without being
able to compute or predict any other label~\cite{rfc9381}. The mapping must be
deterministic, ``or else the identity provider could insert multiple bindings
for a user at different locations''~\cite[p.~5]{melara2015coniks}.

The VRF's role is narrower than it might seem, and precision here matters for the
threat model that follows. The VRF conceals the identity-to-label mapping from parties without the VRF
secret, which gives directory privacy, and deterministically and verifiably binds an identity to its
label under a fixed VRF key, which gives label integrity. It does not provide query privacy against the
operator, which computes the label and so learns the queried identity, and the directory
representation may still reveal pseudorandom occupied positions and its overall scale. No
deployed system surveyed in this chapter hides the queried identity from the
server, and query privacy against the operator is a separate problem, beyond the
scope of this work.

The split-view, or fork, attack is a problem inherited from CT that constrains
every design that follows. A consistency proof certifies only
that a log grew in an append-only way. It says nothing about whether everyone is
shown the same log. A malicious server can therefore keep two internally
consistent logs at once, presenting tree head $\logroot{A}$ to Alice and a
different $\logroot{B}$ to Bob and serving each a different key for the other,
with every local check on both sides passing. Exposing the fork requires
comparing tree heads observed from different vantage points, whether through
client gossip, anchoring tree heads in an independent transparency log, or
cross-checking by external auditors.

The split-view attack exposes a fundamental limitation of local verification. A
client can verify that a particular directory view is internally consistent, yet
still be unable to determine whether other clients are seeing the same view.
Resolving this tension between local verifiability and global consistency
becomes a central design challenge for every verifiable key directory examined
in the next section, and motivates several of the open problems discussed later
in this chapter. \Cref{fig:bg-splitview} depicts the two divergent views a
malicious server maintains.

\subsection{The IETF KeyTrans Architecture}\label{ssec:bg-keytrans}

The IETF's Key Transparency (KEYTRANS) working group provides a common reference model for
key-transparency systems, though several deployments predate or diverge from
it~\cite{ietf-keytrans-protocol}. It assembles three pieces already introduced: an append-only Merkle
log tree records the directory's history; a per-epoch prefix tree, a sparse Merkle tree whose leaves
are the VRF-derived labels, represents the directory's state at one epoch (one published snapshot); and
the VRF maps identities to their labels in that tree. Around these the draft defines a small interface
(update, search, monitor, and audit) and a role for third-party auditors who cross-check tree heads to
catch the forks of the previous subsection. Signal's production server implements this draft ``with
some modifications''~\cite{signal-kt-server}.

The construction grounds each primitive in its specification: the Merkle log and its inclusion and
consistency proofs are those of RFC~6962 and RFC~9162~\cite{rfc6962,rfc9162}, the verifiable random
function is that of RFC~9381~\cite{rfc9381}, and the later label derivation from a session secret uses
HKDF, RFC~5869~\cite{rfc5869}. The draft leaves one question open: it calls for ``reasonable monitoring
windows'' so that intermittently connected clients need not replay every missed update, but leaves the
mechanism unspecified~\cite{ietf-keytrans-protocol}. That efficiency gap is what this thesis's windowed
consistency proof addresses.

This work hardens the standard head in one respect. The server signs each head with
Ed25519~\cite{rfc8032} over the epoch number, tree size, log root, and a timestamp, so a single
consistency proof certifies append-only growth against an earlier head in $O(\log n)$. Because neither
a signed head nor a consistency proof catches equivocation on its own, a second vantage compares heads
to expose the split-view attack of \cref{fig:bg-splitview}, which is the cross-vantage auditor's job
(\cref{sec:design-acka}). Borrowing one element of CONIKS's signed root that a bare head omits, the
signed message additionally binds a hash of the provider's \emph{policy} (the VRF public key, the
signing key, the ciphersuite, the protocol version, and the epoch cadence), so a malicious server
cannot silently substitute these parameters between epochs, or serve different ones to different
clients, without detection.

\section{Verifiable Key Directories for Key Transparency}\label{sec:bg-vkd}

This section surveys the verifiable key directories built on transparency logs: the context in which
this thesis sits and the benchmark against which its contributions are assessed. The limitations that
recur across these systems motivate the designs of \cref{ch:design}.

\subsection{The Verifiable Key Directory (VKD) Abstraction}\label{ssec:bg-vkd-abstraction}

The systems surveyed here differ substantially in their data structures, privacy guarantees, and
performance, yet all implement the same abstraction: a \emph{verifiable key directory} (VKD).
Informally, a VKD is an authenticated key--value directory that lets clients verify the correctness of
directory responses without trusting the operator: the directory returns each value with a proof that
it is consistent with a publicly committed state, and by publishing commitments to successive states it
lets clients and auditors check that the directory evolves according to its update rules. SEEMless
formalized the abstraction with three security goals~\cite[p.~4]{chase2019seemless}: \emph{completeness}
(honest proofs verify), \emph{soundness} (no two contradictory yet valid answers for one label), and
\emph{privacy} (formalized by simulation against an explicit leakage function). ELEKTRA later
generalized it to a \emph{multi-device} VKD, extending the model to device-key histories and
formalizing the multi-device keychains Keybase had run in production since
2014~\cite[p.~1, p.~4]{len2023elektra}. The abstraction leaves the implementation unspecified; the
primitives that recur across constructions are introduced next.

\subsection{Cryptographic Building Blocks: Merkle Prefix Trees and Zero-Knowledge Sets}\label{ssec:bg-vkd-blocks}

Although VKD constructions differ in their design details, most are assembled from the same building
blocks. Beyond the VRF of \cref{ssec:bg-ct2kt}, which keys the directory by storing bindings under
VRF-derived labels rather than usernames, two components recur: authenticated Merkle-tree directories
and zero-knowledge sets (ZKS).

\paragraph{Merkle Prefix Trees.} Most VKDs store bindings in a sparse
authenticated dictionary indexed by these labels. Conceptually the structure is
a sparse binary Merkle tree whose leaves correspond to the whole space of
possible labels; because only a tiny fraction of labels are occupied,
implementations represent it as a \emph{Merkle prefix tree}, materializing only
the nodes on paths to existing entries. A label's bits give the path from the
root to its leaf, so a membership proof is the authentication path to that leaf
and a non-membership proof is the path to an empty (default) position. CONIKS
introduced this representation for key transparency~\cite[\S3.1]{melara2015coniks}.
Later systems commonly add \emph{Patricia-style path compression}, collapsing
chains of single-child internal nodes into a single edge. This preserves the
tree's authentication properties while reducing storage. The terms \emph{Merkle
prefix tree}, \emph{Patricia trie}, \emph{Merkle Patricia trie}, and \emph{sparse
Merkle tree} thus name closely related authenticated dictionaries that differ
chiefly in whether, and how, the tree is path-compressed.

\paragraph{Zero-Knowledge Sets.} Merkle trees provide authenticated membership
and non-membership proofs, but they do not by themselves provide directory
privacy. That role is played by the \emph{zero-knowledge set} (ZKS): a committed
key--value map whose membership and non-membership queries can be answered
without revealing anything further about the directory's contents. Several VKD
systems refine this primitive (SEEMless introduces an \emph{append-only} ZKS
(aZKS), Parakeet an \emph{ordered} ZKS (oZKS), and ELEKTRA a \emph{rotatable} ZKS
(RZKS)~\cite{chen2022rzks}), differing mainly in how they encode update history
and how they preserve privacy under server compromise. How each is used within a
complete system is taken up in the next subsection.

\subsection{Academic VKD Constructions for KT}\label{ssec:bg-vkd-academic}

The academic VKD literature did not arrive as a set of independent proposals but
as a sequence of refinements to a shared design space, each construction
addressing a limitation of its predecessors. CONIKS introduced the basic
architecture of a privacy-preserving, auditable key directory. SEEMless
formalized the VKD abstraction and strengthened both privacy and history
verification. Parakeet improved storage efficiency and deployability, a design line
since deployed at scale by WhatsApp and independently reviewed~\cite{nccgroup2023akd}. ELEKTRA
extended the model to multi-device accounts and added privacy recovery after
server compromise, and OPTIKS, PRISM, and Merkle\textsuperscript{2} explored
alternative trade-offs between monitoring cost, auditing, and scalability. We
review the systems in roughly the order they appeared, in each case identifying
the problem the system set out to solve, its main construction, its security
contribution, and the limitations that remained: a reading that makes the
residual, common gap visible.

\subsubsection{CONIKS}
CONIKS introduced the transparency-based key-verification design that the subsequent literature builds
on, and it established design principles that later VKDs
retained~\cite{melara2015coniks}. Although CONIKS predates the formal VKD
abstraction that SEEMless would later introduce, the VKD constructions that
follow inherit its core architecture of VRF-derived labels, authenticated
directory commitments, and auditable epoch-by-epoch evolution; it stands as
the direct precursor of the VKD line rather than a VKD itself. Its motivation
was to automate the key verification that the manual fingerprint ceremonies of
\cref{sec:bg-signal} had failed to deliver, without reintroducing a single
trusted party. Its construction stores identity bindings in a Merkle prefix tree
whose leaves sit at VRF-derived labels, and each epoch the provider publishes a
\emph{Signed Tree Root} (STR): a signed snapshot of the tree root that
hash-chains to its predecessor~\cite[\S3.3]{melara2015coniks}. A client then
audits only its own entry, downloading a logarithmic-size proof each
epoch (under 20\,kB per day even for a provider with billions of
users~\cite[p.~1]{melara2015coniks}) and checking that the key bound to its name
is the one it expects. Its security contribution is twofold. Lookups are
privacy-preserving, revealing nothing about which other users exist, and the
hash-chained STRs provide \emph{non-equivocation}, since to show two clients
different directories a provider would have to maintain two divergent STR chains
indefinitely, and any auditor comparing STRs would then obtain publicly verifiable
evidence of the fork, attributable to the provider's signing key~\cite[p.~3]{melara2015coniks}. The directory records
identity-key bindings and their evolution across epochs, and nothing more. Three
limitations are significant. First, monitoring is linear in the offline period: a
client absent for $\ell$ epochs must perform $\Theta(\ell)$ work, because a
provider could insert a malicious binding and later revert it, so inspecting only
the latest STR is unsound. The proposed remedy, a per-leaf version history, would
require an auditor to perform $\Theta(n)$ work each epoch, where $n$ is the
number of changes in that epoch; the authors themselves doubt that a party
willing to perform this auditing for free will exist in every
deployment~\cite[p.~12]{melara2015coniks}. Second,
the client-to-client gossip that would let peers cross-check STRs is left as
future work~\cite[p.~7]{melara2015coniks}. Third, the guarantee is detective
rather than preventive: CONIKS exposes an attack but cannot deter a provider
willing to attack its users openly~\cite[p.~2]{melara2015coniks}.

\subsubsection{SEEMless}
SEEMless turned CONIKS's design pattern into a formally defined \emph{verifiable key directory}
primitive, with precise completeness, soundness, and simulation-based privacy
definitions~\cite[p.~2]{chase2019seemless}. Its \emph{append-only zero-knowledge set} (aZKS) stores
versioned labels so that proving a key is the current version costs only logarithmically in the number
of epochs, and it makes auditing a public role checkable by any party~\cite[\S4.2]{chase2019seemless}.
Detection nonetheless remains self-monitoring: through \texttt{KeyHistory} the client retrieves its
verified key-version history and must reconcile it against the updates it actually made, and commitment
consistency is deferred to an external gossip or blockchain mechanism~\cite[p.~5]{chase2019seemless}.

\subsubsection{Parakeet}
Parakeet addressed SEEMless's storage overhead with an \emph{ordered zero-knowledge set} (oZKS) that
collapses SEEMless's two trees into one, moves storage onto a persistent backend, and adds
\emph{compaction} to bound the growth that append-only storage
implies~\cite[\S\S III--IV]{malvai2023parakeet}. For consistency it replaces blockchains and gossip
with a \emph{consensusless} protocol in which a set of $3f+1$ \emph{witnesses} counter-signs each
epoch commitment, a $2f+1$ quorum proving the provider could not have
equivocated~\cite[\S V]{malvai2023parakeet}. Its trade-offs are explicit: the witness set is a new,
professionally operated trust assumption, and detection remains
self-monitoring~\cite[p.~14]{malvai2023parakeet}.

\subsubsection{ELEKTRA}
ELEKTRA extended key transparency to multi-device accounts, representing each account as a
\emph{keychain} in which device additions and removals are cross-signed by an existing device key, so
a malicious provider cannot insert a fabricated key without forging a device signature or compromising
a device~\cite[\S3]{len2023elektra}. Built over a \emph{rotatable zero-knowledge set} (RZKS) that
periodically rotates the VRF key to restore directory privacy after a server compromise, it formalizes
a \emph{multi-device VKD}~\cite[pp.~2--3]{len2023elektra}. Its unsuppressible account-reset warning is
the closest the academic line comes to an in-band peer alarm, but it is raised only on a full account
reset, not on the substitution of an individual key~\cite[p.~2]{len2023elektra}.

\subsubsection{OPTIKS}
OPTIKS reduces client-side monitoring cost by removing SEEMless's second (``old'') tree: instead of
proving a version absent from an old set, it shows a key is the latest version in the single remaining
tree, combining a membership proof for the current version with a non-membership proof for the next,
roughly halving storage and update costs~\cite[p.~4356]{optiks2024}. It is the most
scalability-focused of the surveyed academic systems, yet soundness still requires the key's owner to
run history checks, and it shares the no-in-band-peer-warning gap common to every system surveyed
(\cref{sec:bg-open})~\cite[pp.~4357, 4360]{optiks2024}.

\subsubsection{PRISM}
PRISM departs furthest from per-user monitoring: a \emph{zero-knowledge rollup} (a zkVM over a
Jellyfish Merkle tree) produces a succinct proof of each epoch's state transition and posts it to a
data-availability layer, so every user verifies the whole directory through that proof rather than by
monitoring their own entry~\cite[\S4]{pusch2025prism}. Its diagnostic observation frames this review:
every existing KT system assumes \emph{someone else will check}, whether the user, gossiping clients, a
blockchain, or third-party auditors~\cite[p.~6]{pusch2025prism}. It is presented as an overview rather
than a full specification and introduces substantial new trust dependencies in the data-availability
layer, the zkVM toolchain, and a single sequencer/prover~\cite[pp.~10--11]{pusch2025prism}.

\subsubsection{Merkle\texorpdfstring{$^2$}{2}}
Merkle\textsuperscript{2} (Hu et al.) is included not as a key-transparency system but as an
alternative transparency-log design: it \emph{nests two kinds of Merkle tree}, a chronological tree
(as in Certificate Transparency) whose nodes each carry a lexicographic prefix tree (as in CONIKS), so
that an append costs $O(\log^2 n)$ while a data owner monitors with only polylogarithmic
download~\cite[pp.~1--2]{hu2021merkle2}. Its emphasis is throughput rather than the directory privacy
messaging demands; it does not aim for strong key privacy and so leaks update
patterns~\cite[p.~14]{len2023elektra}. It is therefore evidence that the shared transparency-log
substrate can be optimized for very different objectives once privacy is not a first-order goal.

\medskip\noindent
Despite substantial differences in implementation, these constructions converge on a common
architecture (VRF-derived labels, an authenticated directory supporting membership and non-membership
proofs, an append-only history, and verifiable auditing). Most consequentially for this thesis,
\emph{detection remains external to the conversation}: almost every system relies on the user, an
auditor, or a witness set to notice a malicious directory, and none provides an in-band channel by
which one participant could warn the other that a substitution has occurred. This is the gap the
contributions of this thesis address.

\subsection{Deployed VKDs in Production Systems}\label{ssec:bg-vkd-deployed}

The constructions above have shaped several deployed systems, which show which design choices proved
practical at scale and which limitations remained after deployment, the constraints against which this
work is judged.

\subsubsection{WhatsApp Key Transparency (AKD)}
WhatsApp deploys a VKD at the scale of its user base: an Auditable Key Directory
(AKD), an open-source Rust implementation inspired by SEEMless with extensions
adapted from Parakeet~\cite[p.~4]{whatsapp2023whitepaper}. It hashes with Blake3,
publishes an epoch every five minutes, derives leaf positions from a VRF over the
phone number, key version, and a latest-key flag, tombstones removed devices in
production, and signs each directory root with a key whose public half ships
inside the WhatsApp client binary, a deployed signed tree head that hardens
against split views~\cite[pp.~4, 7, 8, 12]{whatsapp2023whitepaper}. Audit proofs
are published on Amazon S3 under a write-once retention policy of five years,
allowing independent parties to audit the directory
state~\cite[p.~11]{whatsapp2023whitepaper}, and the directory logs identity keys
only. Two aspects of the deployment are particularly relevant to the problem this
thesis considers. First, client self-monitoring is not enabled (``key history
requests are not yet enabled in the current version of WhatsApp's
clients''~\cite[p.~5]{whatsapp2023whitepaper}), so detection rests on
infrastructure auditing and the peer-and-self lookups performed when a chat is
opened, not on continuous monitoring. Second, when a lookup fails the client
falls back to the manual ceremony rather than an automatic alarm: the session
``should be verified manually with the contact in
question''~\cite[p.~10]{whatsapp2023whitepaper}, and the whitepaper frames key
transparency as a supplement to, not a replacement for, the manual fingerprint
check~\cite[p.~13]{whatsapp2023whitepaper}. (The whitepaper's claims are kept
separate from the Meta engineering blog~\cite{lawlor2023whatsapp}, the actual
source of the throughput and third-party-auditor figures.)

\subsubsection{Signal Key Transparency}
Signal's deployment is notable because it closely tracks the emerging IETF Key
Transparency standard: its \texttt{key-transparency-server} implements the draft
with some modifications, exposing Search and Monitor endpoints, public audit
endpoints, and auditor interoperability test vectors (the auditor's deployment
operator is not documented), and it keys the directory
with an elliptic-curve VRF (ECVRF) from the suite family the standard
recommends~\cite{signal-kt-server}. It stores three lookup keys: an identity key
indexed by the account identifier (ACI), which is the per-account identity Signal
assigns independently of the phone number, together with the phone number itself and a
username hash. Its wire format pads every prefix proof to the full 256-sibling
copath with stand-in hashes, giving a fixed-size 8{,}192-byte proof regardless of
directory occupancy. As with the other deployed systems reviewed here, detection
ultimately relies on self-monitoring rather than any peer-warning mechanism.
Tracking the IETF draft as it does, Signal's deployment also is a useful
indicator of the direction in which standardized key-transparency deployments are
heading.

\subsubsection{Proton Mail Key Transparency}
ProtonKT is both deployed and formally analysed~\cite{goebel2023proton,proton2023ktdeck}: it is a VKD
whose values are \emph{Signed Key Lists} and whose consistency reuses Certificate Transparency,
embedding each epoch's chain hash into a CT-logged TLS certificate rather than a blockchain, gossip, or
witness quorum~\cite[pp.~35, 37]{goebel2023proton}. It targets email under a different threat model
and, like the academic constructions, notifies only the key's owner, defining no peer-warning path to
the conversation partner~\cite[pp.~8, 47, 67]{goebel2023proton}. G\"obel also flags communicating KT
failures to end users as an open usability problem, since the interface presents a generic
verification failure without the exportable technical evidence a user would need to
investigate~\cite[p.~88]{goebel2023proton}.

\subsubsection{Google KT, Apple CKV, and Keybase}
Three further deployments complete the survey. Google Key Transparency is a CONIKS-derived VKD on Trillian that
snapshots a CONIKS-style map into a CT-style log and records, per account,
\emph{who} changed each record, an early precursor of ELEKTRA's device
cross-signing, but it is a general key-discovery service, self-monitoring, and
has been archived since October 2024, making it a design precedent rather than a
live deployment~\cite{google-kt}. Apple Contact Key Verification (iMessage) is a
CONIKS-style design that keeps verification state
device-local~\cite[p.~4355]{optiks2024}\cite{apple-ckv}. Keybase, in production
since 2014, is the deployed multi-device-keychain ancestor, but it targets no
user-key privacy. ELEKTRA later added precisely that privacy
mechanism~\cite[p.~2]{len2023elektra}.

Despite substantial differences in architecture, consistency mechanisms, and
deployment environments, the deployed systems converge on a common operational
model. Detection rests on self-monitoring, auditor verification, or consistency
checking. None provides a general in-band mechanism through which one user can
automatically warn another about a suspected key substitution. This is the gap
that the remainder of the chapter takes up.

\section{The ACKA (Authenticated Continuous Key Agreement) Framework}\label{sec:bg-acka}

This section introduces the ACKA framework of Dowling and
Hale~\cite{dowling2023acka}, the culmination of a line of work arguing that
authentication must itself be ratcheted alongside the key
agreement~\cite{dowling2020nocompromise}, and makes precise how this work bridges it to key
transparency. This matters because ACKA is not another verifiable key directory
to be slotted into the comparison of \cref{sec:bg-vkd}: it works in a
\emph{different model}, against a \emph{different adversary}, and it contributes
the continuous-authentication component that a complete solution needs while
leaving abstract exactly the component, a secure log, that key transparency
supplies.

Before ACKA can be stated, the object it authenticates must be named. A
\emph{continuous key agreement} (CKA) is, informally, the part of a ratcheting
protocol in which the two parties keep exchanging fresh public key-shares and,
after each exchange, derive a new shared symmetric key; the Double Ratchet of
\cref{ssec:bg-ratchet} is the canonical example. Formally, it is a multi-stage
key-exchange protocol whose participants continually exchange public key-shares
and, after each message, output a fresh symmetric key~\cite[p.~9]{dowling2023acka}.

ACKA (Authenticated Continuous Key Agreement) is composed of three
primitives~\cite[p.~7]{dowling2023acka}. First, the \emph{CKA} is the
key-exchange protocol just defined. Second, \emph{Continuous Entity
Authentication} (CEA), with its security notion CEAsec, is, informally, a
per-epoch authenticator: each epoch it derives a label and a fingerprint from a
chained secret state and the new public key-share, so that the two parties can
check, epoch by epoch, that they are talking to each other and not to an injected
key~\cite[pp.~13--14, 18]{dowling2023acka}. Finally, the \emph{secure logging
scheme} (Logsec) is an append-only, immutable log to which fingerprints are
posted and from which they are queried~\cite[p.~10]{dowling2023acka}. The
detection mechanism is then simple to state: an adversary who injects a forged
key-share must either collide on the honest party's label (producing two
fingerprints at one label, which alerts all communicating parties) or post
under a label the impersonated party never generates, which that party detects on
lookup~\cite[p.~7]{dowling2023acka} (\cref{fig:bg-acka} summarizes the
composition).

The framework's treatment of Logsec needs care. It is left
\emph{deliberately abstract}: ACKA notes that the logging scheme could use a blockchain or another
distributed-ledger protocol and therefore specifies the interface generically~\cite[p.~10]{dowling2023acka}.
ACKA specifies what
the secure log must guarantee, append-only immutability, without committing
to how those guarantees are implemented, leaving the construction of Logsec
deliberately open.

The adversary ACKA defends against is different from, and along its own axis
stronger than, the malicious-server adversary of the VKD line, and that
difference determines how the two mechanisms compose. ACKA's adversary is a full-compromise
active man-in-the-middle on the \emph{channel}: it may learn the pre-shared
secret state, control the sender's randomness, and actively inject its own forged
ratchet key-share~\cite[pp.~19--20]{dowling2023acka}, and, per Remark~4, may even
hold all long-term authentication secrets~\cite[p.~23]{dowling2023acka}, so that
the construction covers not only full compromise but an unrestricted
adversary~\cite[p.~5]{dowling2023acka}.
ACKA treats the log's security as a separate, conditional assumption: detection holds only
under CEAsec security and a log satisfying its Logsec definition~\cite[p.~7]{dowling2023acka}. The malicious, equivocating server that the VKD
line defends against (one that can substitute keys, censor writes, and serve
divergent views) therefore lies \emph{outside} ACKA's detection theorem, which assumes a log
already satisfying its Logsec definition (append-only, with consistency and exclusion proofs) and
does not specify its malicious-server-resistant implementation. The construction also bootstraps from a
pre-shared state that must be shared and globally unique across honest pairwise
sessions, though not secret, which the authors equate with a correctly assumed
trust-on-first-use scenario~\cite[p.~6]{dowling2023acka}, a caveat any
construction built on ACKA inherits. CEAsec itself reduces to the
collision-resistance of the hash function~\cite[p.~26]{dowling2023acka}, precisely
because the adversary is assumed to hold all secret keys, so that collision
resistance must extend to the keying material itself~\cite[p.~23]{dowling2023acka}.

ACKA acknowledges this openness: it asks whether a second channel the adversary cannot fully control
could enable detection, and leaves that channel abstract as its Logsec-secure
log~\cite[p.~2]{dowling2023acka}. Implementing such a log against an \emph{untrusted} server is exactly
the problem practical messaging faces, since the servers distributing keys are themselves targets of
compromise (\cref{sec:bg-vkd}). ACKA's own construction also carries three limitations this thesis
addresses in \cref{ch:design}: detection is one-sided, since only the receiver detects a forgery and
there is no channel to warn the peer~\cite[p.~21]{dowling2023acka}; verification is sequential every
epoch, with no windowed catch-up; and the consistency mechanism, though defined, is left unused for
third-party auditing. Answering the framework's own question about a second vantage, this thesis
supplies that vantage as part of its systems contribution: a cross-vantage auditor that compares signed
heads to expose split views (\cref{sec:design-acka}), reusing gossip and split-view detection from
prior work rather than claiming them as new primitives.

ACKA and key transparency address complementary adversaries. ACKA assumes a secure log and provides
continuous authentication against an active channel adversary even after key compromise. Key
transparency builds a log that resists a malicious, equivocating server. Combining them is the
synthesis proposed in this thesis.

to the key owner or to an external auditor, and none propagates that evidence in-band
to the communicating peer. This recurring blind spot is the gap that the open problems of
\cref{sec:bg-open} and the contribution of this thesis target, developed as the fifth of the findings
below.

Where \cref{tab:bg-compare} compares complete directory systems, \cref{tab:bg-x3dh-coverage} compares
the cryptographic material authenticated within Signal itself, where the proposed scheme intervenes,
contrasting Signal's current coverage (\cref{tab:bg-coverage}) with that
of the proposed design. Signal authenticates one key, manually. The proposed scheme directly logs and
monitors the identity binding. The signed pre-key is authenticated by its signature under that
verified identity key rather than logged individually. The one-time and ephemeral keys are not
independently logged or authenticated by the directory, though they contribute to $\sharedS$ and
therefore to the conversation-derived labels once a session has been established honestly. In outline,
it logs the identity binding in a verifiable directory and derives per-conversation lookup and warning
labels from the session secret. The comparison is intentionally a forward reference, with the full
construction developed in \cref{ch:design}.

The survey establishes five findings.

\paragraph{Finding 1 (Consistency Mechanisms).} There is no convergence on a
consistency mechanism: the field spans client
gossip~\cite[p.~7]{melara2015coniks}, CT-anchored map roots (Google),
$2f{+}1$ signatures from $3f{+}1$ witnesses (Parakeet)~\cite[p.~11]{malvai2023parakeet},
CT-certificate piggybacking (Proton)~\cite[p.~45]{goebel2023proton}, and
zero-knowledge whole-directory verification (PRISM)~\cite[p.~11]{pusch2025prism}.

\paragraph{Finding 2 (Monitoring Cost).} Client monitoring cost has fallen
steadily: from CONIKS's per-epoch self-check~\cite[p.~6]{melara2015coniks}, to
SEEMless and Parakeet charging per user update rather than per
epoch~\cite[p.~2]{chase2019seemless}, to OPTIKS's single non-membership proof in
the common case~\cite[p.~4356]{optiks2024}.

\paragraph{Finding 3 (Key Coverage).} VKDs differ not only in their consistency
mechanisms but in the cryptographic material they authenticate: identity keys
only (CONIKS, SEEMless, Signal), multi-device keychains (ELEKTRA,
Keybase)~\cite[p.~1]{len2023elektra}, and email key lists
(Proton)~\cite[p.~33]{goebel2023proton}; \cref{ch:design} extends this comparison
with per-session authenticated labels.

\paragraph{Finding 4 (Proof Construction).} Proof construction trades compactness
against structural privacy: Signal deliberately transmits fixed-length
8{,}192-byte proofs that hide the directory's occupancy, whereas leaner
constructions such as CONIKS transmit only the authentication path actually
required, about 1{,}216 bytes~\cite[p.~10]{melara2015coniks}, yielding
smaller proofs at the cost of revealing limited structural information. SEEMless's
measured ${\approx}8{,}600$ bytes~\cite[p.~12]{chase2019seemless} place it at the high
end of the reported proof-size range even in the academic line, and \cref{ch:eval} places the
proposed construction within this design space.

\paragraph{Finding 5 (Detection).} Despite all these differences, every system
ultimately relies on self-monitoring or external auditing, and none provides a
general in-band peer-warning channel. The closest prior art is ELEKTRA's
reset-only warning~\cite[p.~2]{len2023elektra} and PRISM's passing suggestion that
commitments could be embedded ``in-band within encrypted
messages''~\cite[p.~5]{pusch2025prism}; PRISM states the diagnosis plainly:
``all existing KT systems assume that someone else will
check''~\cite[p.~6]{pusch2025prism}, while the largest deployed system ships
with self-monitoring disabled and a manual fallback on
failure~\cite[pp.~5, 10]{whatsapp2023whitepaper}. This recurring design choice
motivates the problem formulated in \cref{sec:bg-open}. The question, therefore,
is not whether existing VKDs can detect directory equivocation or malicious key
substitution; they can. It is how that evidence reaches the affected
communicating parties in time to influence the security of a conversation.

\section{Open Problems for Key Transparency in Asynchronous Messaging}\label{sec:bg-open}

The comparison of \cref{sec:bg-compare} and the ACKA limitations of
\cref{sec:bg-acka} leave three problems open for the asynchronous-messaging
setting.

\paragraph{Problem 1 (No In-Band Peer Warning).} No system surveyed in
\cref{sec:bg-compare} propagates a detection to the affected peer in band: whether detection is
self-monitoring or an automatic lookup check, only the party performing the check learns the result,
and a peer who could detect the substitution has no channel by which to warn the key's owner.
Concretely, a malicious server shows Bob a key for Alice that Bob's own monitor
never examines (Bob monitors his own entry, not Alice's) while Alice, whose
entry is untouched from her own vantage point, has nothing to report through any
channel Bob reads. The closest prior art does not close this: ELEKTRA's
unsuppressible warning is raised only on an account reset, not on a key
substitution~\cite[p.~2]{len2023elektra}, and WhatsApp's deployed client does not
even enable self-monitoring, falling back to the manual ceremony on a failed
check~\cite[pp.~5, 10]{whatsapp2023whitepaper}. No existing VKD provides a
peer-to-peer warning channel, a gap PRISM states in general terms~\cite[p.~6]{pusch2025prism}.

\paragraph{Problem 2 (Linear Offline Catch-Up).} A mobile,
intermittently connected client faces an efficiency gap that the per-epoch
protocol does not address. Under the sequential baseline evaluated in \cref{ch:eval}, a client that
misses $W$ epoch commitments verifies $W$ successive transitions. The surveyed systems implement
per-epoch monitoring differently, through replayed monitoring views, history transitions, or
per-period checks. The benchmark represents those transitions uniformly as RFC~9162 consistency
proofs, a synthetic stand-in rather than a claim about any one system's format. Each proof is
taken over the append-only \emph{epoch log}, which appends one directory root per
committed epoch, so its size is $O(\log E)$ in the number of committed epochs $E$
and is independent of the directory's user count $N$. The sequential total is
therefore $O(W \cdot \log E)$, linear in the missed-epoch count $W$. As a concrete case,
with hourly epoch commitments a client offline for 30 days misses $W = 720$
epochs and re-verifies 720 transitions in sequence. This is a linear, avoidable overhead that grows with the gap. \Cref{ssec:eval-catchup}
measures the synthetic current-head-anchored sequential baseline for this window at \num{222528} raw
consistency-path hash bytes (serialized transfer was not measured), which the windowed
proof replaces with a single proof. The
IETF draft leaves ``reasonable monitoring windows'' for mobile clients
unspecified~\cite{ietf-keytrans-protocol}, and CONIKS identifies the linear offline
cost as an open extension, conceding that its own remedy ``may not be realistic in
all deployments''~\cite[p.~11]{melara2015coniks}.

\paragraph{Problem 3 (Split-View Equivocation).} Append-only is not the same as
globally consistent. As \cref{ssec:bg-ct2kt} explained, a malicious server can
maintain two internally consistent logs and serve Alice and Bob divergent heads,
each backed by valid consistency proofs, so that neither detects the substitution
from local checks alone. \Cref{sec:bg-compare} showed the field has no single
answer to this: client gossip, CT-anchoring, a witness quorum, and zero-knowledge
whole-directory verification are all in use. What unites them is that detecting
equivocation at all requires an independent mechanism that observes the directory
from outside the victim's own session.

Of these three, the first two (an absent peer-warning channel and a linear offline
catch-up cost) are the client-facing gaps this thesis sets out to close directly;
the third (a split-view that local checks cannot expose) is an inherited
key-transparency requirement that any untrusted-directory design must meet,
addressed here with a standard cross-vantage auditor rather than a new primitive.
The contributions of \cref{sec:bg-contrib} take up all three.

\section{Research Gap and Contributions}\label{sec:bg-contrib}

The open problems of \cref{sec:bg-open} leave key transparency for asynchronous
messaging without an in-band peer-warning channel, without an efficient offline
catch-up, and without local detection of server equivocation; ACKA, conversely,
supplies continuous authentication but only under the assumption of a log satisfying its Logsec security definition. The
research gap is therefore the absence of a single system that closes both
client-facing gaps (in-band peer warning and efficient offline catch-up) while
remaining resistant to a malicious directory server and continuously authenticated
across the ratchet. No system surveyed in \cref{sec:bg-compare} does so.

These limitations motivate the four principal contributions announced in
\cref{ch:intro} (conceptual, cryptographic, systems, and empirical), which this section develops.
The \emph{conceptual} contribution is the dual-index warning scheme, together with its framing as a
concrete instantiation of the ACKA append-only-log component. The \emph{cryptographic} contribution
is the windowed consistency proof, with the dual-index same-head consistency lemma as supporting
analysis of the conceptual scheme. The \emph{systems}
contribution is the Rust and TypeScript implementation, cross-checked by shared test vectors, with its cross-vantage auditor.
The \emph{empirical} contribution is the benchmark and security evaluation. Not every
mechanism is equally novel, and the text is careful to say which: the windowed proof and the
cross-vantage auditor reuse ideas established in prior work (\S6.3 of CONIKS; CT/CONIKS gossip) and
are claimed as instantiation-and-measurement, not as new primitives. Together they strengthen key
transparency for asynchronous messaging by adding automatic peer notification, efficient offline
recovery, transparent equivocation detection, and continuous authentication over an untrusted
directory. The mechanisms are parallel, not layered: the log-based warning scheme does not depend on
the ACKA continuous-mode instantiation, which provides one operating mode of the system rather than
its foundation. The mechanisms developed below implement these four contributions; each heading names
its parent category, so the number of mechanisms is not a count of separate contributions.

\paragraph{Mechanism 1 (Conceptual): Dual-Index Warning Scheme.} This addresses Problem~1
(the absent in-band peer-warning channel; \cref{sec:bg-open}) by
providing automatic, bidirectional, in-band detection of a man-in-the-middle. Alice and
Bob derive from their shared secret $S$ not only a lookup label but a shared
\emph{warning} label $\ell_{\mathsf{warn}}$, an initially empty leaf in the same log. If
either party detects a key mismatch, it writes to that leaf. Since the label is derived
from $S$, which the server does not hold, the server can neither pre-position a
value on the slot nor predict where a warning will land. Once a warning is committed, a
write-once update policy, a per-epoch transition audit, and a writer-side persistence
check (\cref{ch:design}) together ensure that removing it is a detectable and provable
act rather than a silent one, leaving outright denial of service (itself observable)
as the server's only remaining suppression strategy. This is the in-band peer-warning channel the
literature lacks. The closest related work is KTACA (Yadav et al.), which achieves
client-side detection but relies on anonymous
lookups~\cite{yadav2020poster,yadav2022fakekey}, a cost Parakeet explicitly objects
to~\cite[p.~14]{malvai2023parakeet} and which DUET's derived labels, unpredictable before first use, avoid.

\paragraph{Mechanism 2 (Cryptographic): Windowed Consistency Proofs.} These address Problem~2
(linear offline catch-up; \cref{sec:bg-open}),
reducing the offline catch-up from $W$ sequential consistency proofs (one per missed
epoch) to a \emph{single} RFC~9162 consistency proof spanning the whole window. The saving
is in the number of proofs (one rather than $W$): the client verifies one proof from the
epoch-log head it last saw to the current one, of size $O(\log E_1)$ in the current epoch-log
length $E_1$ (\cref{lem:windowed-size}), logarithmic in the log length and independent of the
directory's user count $N$, rather than linear in the window $W$. It does not make the proof
size independent of the current head.

\paragraph{Mechanism 3 (Systems): Cross-Vantage Auditor.} This addresses Problem~3
(split-view equivocation; \cref{sec:bg-open}), the inherited key-transparency requirement: it
cross-checks tree heads observed from a second vantage point and flags two validly signed
heads at one epoch as an equivocation, detecting the split-view that local checks cannot.
Mechanisms~1 through~3 are the transparency-log half of the work.

\paragraph{Mechanism 4 (Conceptual): ACKA Instantiation (Continuous Mode).} ACKA itself gives a modular
construction and a specific Signal add-on but leaves its logging component (Logsec) an
\emph{abstract} primitive~\cite[p.~10]{dowling2023acka}. To the author's knowledge, this is the first
instantiation of that component over a concrete, \emph{malicious-server-resistant}
key-transparency log: a per-ratchet-epoch fingerprint and label chain that authenticates the
Double Ratchet epoch by epoch. The claim rests on a survey of the published key-transparency
literature (CONIKS~\cite{melara2015coniks}, SEEMless~\cite{chase2019seemless},
Parakeet~\cite{malvai2023parakeet}, OPTIKS~\cite{optiks2024}, ELEKTRA~\cite{len2023elektra}, the
WhatsApp and Apple deployments~\cite{lawlor2023whatsapp,apple-ckv}, and
draft-ietf-keytrans~\cite{ietf-keytrans-protocol}) and open-source implementations
as of July~2026. Its scope is narrow. What is new is the concrete log
instantiation and its measurement, not the ACKA construction. In the prototype the ratchet is driven
deterministically from the shared secret; the in-protocol libsignal hook is future work
(Chapter~7).

\paragraph{Mechanism 5 (Conceptual): Reconciliation of ACKA and Key Transparency.} The principal
conceptual contribution of this thesis is the reconciliation of ACKA and key
transparency, which are usually treated separately: ACKA authenticates the
continuous key agreement per epoch but treats its logging component as an \emph{abstract}
primitive with a security definition (Logsec), leaving the concrete malicious-server-resistant
implementation unspecified, whereas the academic VKD literature builds exactly such a directory but
authenticates only a session or identity binding. They differ in granularity (per-epoch versus
per-session) and, more to the point, in what each makes concrete: ACKA specifies what the log must
guarantee, key transparency shows how to build it. This thesis reconciles them by instantiating ACKA's abstract
logging component with a concrete key-transparency log that need not be trusted, supporting both as
operating modes and measuring the trade between them. No system in the surveyed
corpus (\cref{sec:bg-compare}) combines per-ratchet continuous entity authentication with a publicly
auditable, untrusted-server key directory in one implemented design. Throughout, the coverage trade is explicit: DUET logs identity keys
and per-session labels, not the per-user version chains of SEEMless, Parakeet and OPTIKS
or the multi-device keychains of ELEKTRA, different coverage, leaner proofs, and
automatic in-band detection.

\paragraph{Mechanism 6 (Systems, Empirical): Implementation and Evaluation.} This is the engineering
core of the thesis and a contribution in its own right. The core is a Rust \texttt{duet}
crate whose library modules implement the
sparse-Merkle-tree directory, the RFC~9162
append-only log with its inclusion and consistency proofs, the Ed25519 signed tree head,
the ECVRF lookup (RFC~9381)~\cite{rfc9381}, the dual-index warning, the windowed catch-up,
and the cross-vantage auditor, alongside the server, auditor, and benchmark binaries (\cref{ch:impl}). It is integrated into the Signal Desktop client, where the
verification is hooked into the key-upload and key-fetch paths. A standalone networked
directory server and an independent auditor service back a two-client, cross-process
demonstration of substitution and equivocation being caught in band, and the Rust and
TypeScript builds produce byte-identical outputs on the shared cross-implementation test
vectors. The prototype is deliberately single-machine and in-memory, with the genuine X3DH binding and the
live-ratchet hook scoped as deployment work (\cref{ch:discussion}); within those boundaries it
delivers the two-client demonstration just described. \Cref{ch:threat} next fixes the adversary
model against which these mechanisms are evaluated.
