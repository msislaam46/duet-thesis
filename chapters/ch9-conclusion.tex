\chapter{Conclusion}\label{ch:conclusion}

End-to-end encryption is only as trustworthy as the keys it runs on, and in every deployed messaging
system those keys are handed out by a server that users must simply trust. The traditional
defence, the manual safety-number comparison, detects a substituted key only if both parties carry
out an out-of-band ritual that only about one in seven complete without guidance~\cite{vaziripour2017}, and the
key-transparency deployments that have begun to automate it (\cref{ssec:bg-gap}) still warn only
the key's owner, never the peer. This thesis set out to close that gap: to make
key substitution automatically detectable, in band, and at a cost a real messaging service could
afford.

To do so it instantiated the abstract log component of the ACKA framework as a concrete verifiable
directory: an append-only Merkle log over a path-compressed sparse prefix tree, with ECVRF-derived
labels and an Ed25519 signed tree head, following the IETF KeyTrans draft. On top of it, it added two
mechanisms. The dual-index warning scheme (\cref{ch:design}) gives each conversation a shared
warning slot that either party can raise and that the server can neither forge in advance nor censor
undetectably after the fact, turning a silent substitution into a detectable one. The windowed consistency proof lets a
client that has been offline for a long window catch up with a single short proof rather than one per
missed epoch. Both were realized in a standalone Rust reference implementation and exercised through a
verifier embedded in Signal Desktop (\cref{ch:impl}), and both were evaluated against the threat model
of \cref{ch:threat}.

The evaluation (\cref{ch:eval}) shows that this detection is added without changing the asymptotic
complexity of the lookup proof, using additional lookups of the shape the client already verifies. The
implemented (VRF-indexed) lookup proof is at size parity with CONIKS, while the scheme adds a warning
channel CONIKS lacks.
Median full client verification stays below \SI{150}{\micro\second} through $10^7$ labels and grows
far more slowly than $N$ (\SIrange{128.1}{147.1}{\micro\second}), about
\num{3.8} times faster than CONIKS at matched scale even though it includes the VRF check that CONIKS's
figures omit (both totals include the signature check, and the cross-hardware comparison is
indicative only). A month-long offline catch-up is one distant-head consistency proof rather than $W$
of them, a few hundred raw path bytes against the hundreds of kilobytes a synthetic baseline that
re-fetches a current-head-anchored proof for each missed epoch would instead spend. The marginal
warning-slot read costs microseconds on top of a lookup the client already verifies, with no false
alarms observed over a thousand clean deterministic sessions, and the cross-vantage auditor's local
fork check runs at a median \SI{27.9}{\micro\second} (p95 \SI{34.2}{\micro\second}) against one
observed head. The adversarial suite detects the full substitution and
equivocation taxonomy, and a STRIDE analysis leaves four residual risks: one the label-to-user
mapping inherent to any semi-trusted-server directory, the other three availability functions left to
a production deployment.

Read against the research questions of \cref{sec:intro-aims}, the evidence is direct. RQ1 (in-band
detection) is answered by the dual-index warning and its clean pass across the full
adversarial suite, with no false alarms observed in the clean deterministic trials. RQ2 (cost) is
answered by the \num{817}\,byte VRF-indexed lookup proof at parity with CONIKS and the
$\approx$\SI{128}{\micro\second} verification at $N\le10^4$, rising only to $\approx$\SI{147}{\micro\second} at $10^7$. RQ3 (offline) is answered by
the \num{320}\,byte month-long catch-up, whose size is bounded by the endpoint log sizes rather than
the window's length. RQ4 (client-integration feasibility) is answered by the
verifier running inside a fork of the real Signal Desktop client at that measured local cost; the
integration is a prototype with an advisory hook and deterministic stand-ins, so it establishes
feasibility of hook placement and proof verification rather than enforced session blocking. The thesis
statement, that this detection can be added without changing the asymptotic complexity of the
proofs the directory already serves using additional lookups of the existing shape, is thereby
supported on every axis it claimed. The full chain from each research question and contribution kind
to its supporting evidence is tabulated in \cref{app:traceability}
(\cref{tab:trace-rq,tab:trace-contrib}).

The result is a design that detects rather than prevents (a server can still substitute a key, but
it can no longer do so silently) and that presents a deployment such as Signal with a narrow,
well-defined addition rather than a wholesale change: a write path for warning and per-session labels
alongside the identity directory it already maintains, at a client cost of microseconds per
conversation. The clearest remaining step, binding the labels to the live X3DH secret in place of the
prototype's stand-in (\cref{ch:discussion}), is a necessary security-integration step whose
correctness and operational cost remain to be evaluated. Key
transparency has, until now, told users that they must check their keys themselves; this work shows
that, by reusing the directory's existing proof form while incurring additional lookups and
deployment work, it can check them for the users instead.
