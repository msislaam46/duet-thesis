\section{Signed-Head Fields and Verification Details}\label{sec:design-detail-sth}

\paragraph{Domain separation and structure roles.} Hashing uses the domain tags defined in
RFC~6962~\cite[Section~2.1]{rfc6962}:
$\Hash_{\mathsf{leaf}}(x)=\Hash(\mathtt{0x00}\concat x)$ and
$\Hash_{\mathsf{node}}(l,r)=\Hash(\mathtt{0x01}\concat l\concat r)$, with $\Hash$
instantiated as SHA-256. DUET currently uses these tags in both the prefix tree and the log. The IETF KeyTrans construction
separates the two structures differently. For log-tree parent hashing, it prefixes leaf-child and
parent-node child values with \texttt{0x00} and \texttt{0x01}, respectively. Prefix-tree leaves use
\texttt{0x02}, while prefix-tree parents use
\texttt{0x03}~\cite[Sections~11.8--11.9]{ietf-keytrans-protocol}. Although the two roots occupy
different positions in DUET's verification chain, separate per-structure tags would provide clearer
domain separation in a production design.

The prefix tree maps each 256-bit label to a value. For a user-identity entry, the value is an
identity public key, while the label is derived from the user identifier through the VRF. Labels
belong to two types. The first is a global slot computed server-side as a VRF over the user
identifier. The second comprises the client-derived raw slots, which include the dual-index lookup
and warning slots and, in continuous mode, the per-epoch CEA slots. Each committed prefix-tree root
is appended to the Merkle log as one leaf. Therefore, the log records every committed directory
state, while a consistency proof verifies that the sequence of committed roots is append-only. At
each epoch, the log root is signed with Ed25519 and published as the signed tree head against which
every lookup is ultimately checked.

\paragraph{Signed-head field rationale.} Each field of the signed-head message
(\cref{eq:design-sth}) supports a different part of verification. The
$\mathit{tree\_size}$ is required by the inclusion and consistency verifiers. Signing the
$\mathit{timestamp}$ prevents it from being altered without invalidating the signature. Enforcing
freshness additionally requires a client-side maximum-age or publication-interval policy, which
the DUET prototype does not implement. The trailing $\Hash(\mathit{config})$ is the configuration
commitment. It corresponds to the field CONIKS calls $P$~\cite[Section~3.3]{melara2015coniks}. In DUET, this commitment binds the VRF and signing keys,
suite, protocol version, epoch interval, and raw-label policy into the signature. A client
recomputes the commitment from its expected keys and constants and rejects a mismatch. A client or
auditor rejects a signed head whose configuration commitment differs from its expected keys and
parameters. Therefore, the heads admitted to the A4 comparison already carry the expected commitment.
The comparison then checks their tree sizes and roots and, for different tree sizes, requires a valid
consistency proof.

\paragraph{Verification-chain current-snapshot binding.} The verification chain in
\cref{ssec:design-verify} has three properties that the figure does not make explicit. First,
global lookups require the VRF check, while client-derived raw labels omit it and rely on the
requested-label binding. Second, the response must be anchored to the root in the verified signed head returned with that
response. During catch-up, the current head must also be verified as an append-only extension of
the retained trusted head. The client rejects a proof chain bound to a different signed head. Third,
inclusion is pinned to the latest leaf. Since each commit appends the new
directory root as the log's last leaf, verification requires
$\mathit{leaf\_index}=\mathit{tree\_size}-1$ at exactly the signed tree size. An RFC~9162
inclusion proof can authenticate any indexed leaf in a
tree~\cite[Section~2.1.3.2]{rfc9162}. It does not by itself establish that the leaf represents the
current directory snapshot. Therefore, this current-snapshot binding prevents acceptance of an earlier
committed directory root from the same log history.

\section{Continuous-Mode Operation and ACKA Correspondence}\label{sec:design-detail-cea}

The ordering of operations within an epoch follows ACKA's composed construction~\cite[Figure~8]{dowling2023acka} in three aspects. First, the label $L_t$ is computed from the
current pre-update CEA state, while the fingerprint $F_t$ binds that state to the public ratchet key
$T_t$. Only after the fingerprint has been committed and verified is the secret epoch input $I_t$
mixed into the CEA chain. Using the secret epoch input rather than the public ratchet key means that
an honest, uncompromised $I_t$ contributes fresh secret material to the chain. Before it is mixed
into the CEA state, the input is domain-separated as
$\KDF(I_t,\text{\texttt{"CEA"}})$. In ACKA's mapping to Signal, $T_t$ corresponds to the public
ratchet key and $I_t$ corresponds to the chain key $ck$~\cite{dowling2023acka}. The separate \texttt{"CEA"} and \texttt{"CKA"} tags distinguish
the CEA state update from the session-key output. A production Signal integration would obtain
$I_t$ from the live Double Ratchet state. The DUET prototype instead uses the simulated epoch input
described in \cref{sec:impl-strategy}.

Second, before posting, the sender verifies that $L_t$ is unoccupied. ACKA states that an existing
fingerprint at the expected label indicates impersonation and should cause the sender to take
appropriate, likely out-of-band, action~\cite{dowling2023acka}. Therefore, when the label is
already occupied, the DUET sender procedure rejects the registration and leaves the CEA state
unchanged. After writing to an empty label, the sender advances its chain only after a verified
read-back confirms the committed fingerprint. Third, the receiver advances only after a
\textsc{Consistent} verdict. A \textsc{Fork} verdict leaves the chain unchanged over the disputed
epoch and causes the client to attempt to publish an in-band warning. A \textsc{NotPosted} verdict means that the per-epoch entry
is absent. It also leaves the receiver's state unchanged so that the lookup can be retried without
desynchronizing the chain. Note that this verdict is distinct from the user interface's grey
pending state.

An important distinction is that ACKA and DUET represent values at a label differently. ACKA's log
stores a vector of fingerprints for each label and requires exactly one value when the receiver
verifies an update~\cite[Figure~8]{dowling2023acka}. DUET stores one immutable value at each label
and implements the same detection objective through two checks. First, if an adversary occupies the
label before the honest sender writes, the sender's pre-write lookup detects the occupied slot and
rejects the write. Second, transition auditing rejects a later overwrite because the raw-label
policy marks the entry as immutable. A receiver that has already accepted the epoch does not repeat
its per-epoch lookup, so detecting an overwrite attempted afterwards depends on the transition
audit. Proving formally that ACKA's security argument carries over to this single-value directory
representation remains future work.

For per-epoch CEA verification, detection follows ACKA's method. An active man-in-the-middle that
injects a forged ratchet key $T'$ either leads to a label the impersonated party does not derive or
produces a fingerprint mismatch at the shared label. In the second case, \textsf{CeaVerify} returns
\textsc{Fork}, leaves the chain unchanged, and causes an attempt to write to the shared warning slot. This CEA verdict
is different from the \hyperref[sc:threat-a4]{A4 split-view equivocation scenario}, which requires
comparison of signed heads obtained from independent vantage points.

\section{Windowing Soundness and Supporting Argument}\label{sec:design-detail-window}

Windowed catch-up must account for a substitution introduced and reverted between the retained and
current heads. CONIKS requires a returning client to perform a series of checks after missed
epochs~\cite{melara2015coniks}. A malicious provider could insert a false binding and
later revert it before the client returns~\cite[Section~4.2]{chase2019seemless}. A client that verifies only endpoint consistency and the
current value of its binding would not detect such a transient substitution. The same limitation
applies to DUET's windowed check.

A transient substitution affects a conversation only if an online peer retrieves and uses the
substituted key. An online peer running DUET's monitor checks the dual-index slots and writes to the
shared warning slot when it detects a mismatch (\cref{ssec:design-detection}). Detection of an
in-window substitution therefore depends on that warning being committed. Once committed, the
write-once policy prevents replacement through the public interface, the transition audit rejects a
later invalid change, and the persistence check can retain evidence of a deletion. If the directory
operator censors the warning before it commits, as considered by
\hyperref[sc:threat-a2]{A2 warning censorship}, the endpoint consistency proof still verifies
append-only growth between the retained and current heads but cannot reveal the transient
substitution. Windowed catch-up therefore relies on the warning channel for evidence of an
in-window substitution. The warning channel itself does not depend on windowing.

\section{Design Alternatives}\label{sec:design-detail-alternatives}

\paragraph{Directory structure.} DUET retains a path-compressed sparse binary Merkle prefix tree
because the warning channel requires direct inclusion and non-inclusion proofs, including proof that
a warning slot is empty. An $n$-ary trie would reduce the number of levels but require up to $n-1$
sibling hashes at each $n$-ary node and a wider proof encoding. Path compression collapses
single-child chains, leaving sibling hashes only at populated branching points. Therefore, binary
branching matches the implemented proof format while retaining direct non-inclusion proofs.

\paragraph{Global-label derivation.} Global slots use
ECVRF-EDWARDS25519-SHA512-TAI rather than a bare hash for the directory-privacy reason described in
\cref{ssec:design-structures}. The selected suite is defined by
RFC~9381~\cite[Section~5.5]{rfc9381} and matches Signal's key-transparency implementation~\cite{signal-kt-server}. This avoids introducing a second, incompatible VRF suite.

\paragraph{Combined prefix-plus-log stack.} The prefix tree alone authenticates current lookup
results but does not authenticate their history. The append-only log records the committed
prefix-tree roots and supplies the consistency proofs used by windowed catch-up and the auditor.
Therefore, each lookup includes one additional log-inclusion path. With $E$ committed epochs, this
path contains at most $\lceil\lg E\rceil$ sibling hashes of 32 bytes, giving a maximum of
$32\lceil\lg E\rceil$ bytes, which follows from the RFC~9162 inclusion-proof
construction~\cite[Section~2.1.3]{rfc9162}. The measured cost is reported in
\cref{ch:eval}.
