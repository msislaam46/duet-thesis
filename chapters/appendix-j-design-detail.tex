\section{Signed-Head Fields and Verification Details}\label{sec:design-detail-sth}

\paragraph{Domain separation and structure roles.} Hashing is domain-separated in the manner of
RFC~6962~\cite[Section~2.1]{rfc6962}: $\Hash_{\mathsf{leaf}}(x) = \Hash(\mathtt{0x00} \concat x)$ and
$\Hash_{\mathsf{node}}(l, r) = \Hash(\mathtt{0x01} \concat l \concat r)$, with $\Hash$ instantiated as
SHA-256. The prefix tree and the log use these same leaf and node tags. Cross-tree confusion is not
exploitable here, since prefix roots appear only as log leaf data and log roots only in signed tree
heads, but a production deployment should apply distinct per-structure tags as defence in depth.

The prefix tree maps each 256-bit label to a value. For a user-identity entry the value is an identity
public key, and the label is derived rather than chosen. Labels come in two families: a global slot,
computed server-side as a VRF over the user identifier, and the client-derived raw slots (the
dual-index lookup and warning slots and, in continuous mode, the per-epoch CEA slots). Each committed
prefix-tree root is appended to the Merkle log as a single leaf, so the log records every committed
directory state and a consistency proof certifies that history has only ever grown. Each epoch the log
root is signed with Ed25519 and published as the signed tree head, the single authenticated value
against which every lookup is ultimately checked.

\paragraph{Signed-head field rationale.} Each field of the signed-head message
(\cref{eq:design-sth}) is necessary for a different aspect of verification. The $\mathit{tree\_size}$
is required by the inclusion and consistency verifiers. Signing the $\mathit{timestamp}$ means it
cannot be altered without invalidating the signature. Enforcing freshness additionally requires a
client-side maximum-age or publication-cadence policy, which the prototype does not implement. The
trailing $\Hash(\mathit{config})$ is a CONIKS-style policy commitment (the field CONIKS calls $P$)~\cite[Section~3.3]{melara2015coniks}
that binds the provider's parameters into the signature. With it, the server cannot silently swap its
VRF key, its signing key, the ciphersuite, the protocol version, or the epoch cadence, nor serve
different parameters to different clients, because any client that recomputes $\Hash(\mathit{config})$
from the parameters it expects will reject the mismatch. A parameter substitution thus becomes a
signed, monitorable act: a uniform mismatch is rejected by any client that recomputes the commitment,
and serving different parameter sets to different clients is equivocation on the configuration
commitment, exposed by the same cross-vantage comparison used to detect \hyperref[sc:threat-a4]{A4} split-view equivocation.

\paragraph{Verification-chain current-snapshot binding.} The verification chain of \cref{ssec:design-verify} has three
properties the figure does not make evident. First, global lookups require the VRF check, while
client-derived raw labels omit it and the requested-label binding stands on its own. Second, the
signed head used for verification must be identical to the head the client independently obtained and
verified, either the latest head it fetched or, during catch-up, the new head whose append-only
consistency with its last trusted head it has just checked. The client rejects any response anchored
to a different head, even one carrying a valid signature, which prevents stale-snapshot acceptance and
an equivocating server from substituting another signed view. Third, inclusion is pinned to the latest
leaf: because each commit appends the new directory root as the log's last leaf, verification requires
$\mathit{leaf\_index} = \mathit{tree\_size} - 1$ at exactly the signed tree size. Inclusion proves
membership, not current-snapshot binding (RFC~9162~\cite[Section~2.1.3.2]{rfc9162}), and the current-snapshot check closes that
gap.

\section{Continuous-Mode Operation and ACKA Correspondence}\label{sec:design-detail-cea}

The ordering of operations within an epoch follows ACKA's composed construction (their
Figure~8~\cite{dowling2023acka}) in three respects, each of which matters for correctness. First, the
label and fingerprint are computed over the current (pre-update) state and the public key, and only
then is the secret $I_t$ mixed into the chain. Mixing the secret epoch key rather than the public
ratchet key keeps the chain unpredictable to an adversary that has compromised the pre-shared state,
the property the pre-use unpredictability and forgery-resistance arguments need. Before the secret is
folded into the CEA chain, it is domain-separated as $\KDF(I_t, \text{\texttt{"CEA"}})$. In a faithful
Signal integration $I_t$ is Signal's chain key $ck$, which also feeds the session-key derivation (the
paper's $\KDF(I_t, \text{\texttt{"CKA"}})$). The distinct \texttt{"CEA"} and \texttt{"CKA"} tags keep
the transparency-chain value independent of the session key. Second, before posting, the sender checks
that the label $L_t$ is unoccupied, since ACKA specifies that ``the sender will also check if the
label has already been uploaded to the log with a fingerprint, which would indicate an
impersonation''~\cite{dowling2023acka}, and the sender advances its chain only after its write is
confirmed in a committed head. Third, the receiver advances its chain only when a verification returns
\textsc{Consistent}. A \textsc{Fork} verdict leaves the chain unadvanced over the disputed epoch and
reports an in-band warning, and a \textsc{NotPosted} verdict (the per-epoch entry is absent, distinct
from the UI's grey pending state) leaves the receiver's state untouched so the check can be retried
without desynchronizing the chain.

The two designs represent label history differently. ACKA's log stores a vector of fingerprints for
each label, and its receiver treats two fingerprints at one label as evidence of impersonation. DUET
stores one value at each label and implements the same detection objective through two checks: if the
adversary posts first, the honest sender's pre-post check finds the label occupied and rejects the
write. If the adversary later attempts to replace a committed fingerprint, the transition audit
rejects the update, because each leaf hash records whether the leaf is mutable or immutable. The
receiver's per-epoch check cannot detect this overwrite when the adversary controls the pre-shared
state, so that case depends on the transition audit. Proving that ACKA's security argument carries
over to this directory representation remains future work.

For per-epoch CEA verification, detection follows ACKA. An active man-in-the-middle that injects a
forged ratchet key $T'$ either posts under a label the impersonated party never derives (a different
chain produces a different $L_t$) or causes the committed fingerprint to differ from the verifier's
expected fingerprint at the shared label, in which case \textsf{CeaVerify} returns \textsc{Fork},
leaves the chain unchanged, and writes to the shared warning slot. This CEA verdict is distinct from
split-view equivocation (A4), which requires the cross-vantage auditor. \Cref{tab:design-x3dh-coverage}
sets session-mode X3DH coverage against Signal's manual Safety Number.

\section{Windowing Soundness and Supporting Argument}\label{sec:design-detail-window}

The key-transparency literature identifies a soundness risk when clients skip intermediate epochs.
CONIKS's monitoring cost is linear in the offline period precisely because a malicious provider could
insert a false binding at some epoch inside the window and revert it before the client
returns~\cite[pp.~7--8]{melara2015coniks}. A
client that verifies only the consistency of the two endpoint heads and the current value at its own
label would miss such a transient substitution, which is why CONIKS concludes that inspecting only the
latest signed root is unsound (\cref{sec:ext-vkd-survey}). That objection applies verbatim to any
windowed check, including this one. A transient in-window substitution is profitable to the adversary
only if it is used. A peer who initiates or continues the conversation during the window performs
pinned-key lookups at the dual-index slots (\cref{ssec:design-detection}) and, on a mismatch, writes
to the shared warning slot. DUET preserves detection only when that warning commits. The write-once
policy blocks replacement through the honest interface. Once committed, the warning either remains
available for the returning client to read or its removal causes the transition audit to reject the
epoch transition, and the separately specified persistence check can retain evidence of that removal.
If the server censors the write (the \hyperref[sc:threat-a2]{A2} threat), the distant-head proof still
establishes append-only consistency but cannot exclude every transient substitution. Windowed catch-up
therefore relies on the warning channel, although the warning channel does not depend on windowing.

\section{Design Alternatives and Requirement Mapping}\label{sec:design-detail-alternatives}

\paragraph{Directory structure.} An accumulator would shorten membership proofs but make the
non-membership proofs the warning channel needs substantially more expensive, and an $n$-ary trie
would reduce the number of levels but widen every node's copath ($k-1$ siblings per level) and
complicate the encoding. With path compression the transmitted proof is already governed by the
populated prefix depth, so binary branching keeps the simplest node semantics at no asymptotic cost in
proof size.

\paragraph{Global-label derivation.} Global slots are addressed by an ECVRF over the user identifier
rather than a bare hash, for the directory-privacy reason given in \cref{ssec:design-structures}. The
design selects ECVRF-EDWARDS25519-SHA512-TAI (RFC~9381) because it matches Signal's deployed keytrans
VRF, avoiding a second, incompatible VRF suite~\cite{rfc9381,signal-kt-server}.

\paragraph{Combined prefix-plus-log stack.} One tree alone would authenticate the present state but
not its history, leaving append-only violations undetectable. The log supplies exactly the consistency
proofs that windowed catch-up and the cross-vantage auditor depend on. The cost is one extra
log-inclusion path per lookup, up to $32\lceil\lg E\rceil$ bytes, quantified in \cref{ch:eval}.
