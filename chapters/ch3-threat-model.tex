\chapter{Threat Model and Problem Statement}\label{ch:threat}

This chapter defines the actors, adversaries, assumptions, and four security requirements that govern
the design and evaluation. The model combines a potentially malicious directory operator with an
active network adversary, then states the substitution, censorship, and equivocation scenarios
together with the endpoint-compromise boundary.

% ============================================================================
\section{System Model and Actors}\label{sec:threat-system}

DUET considers asynchronous communication between Alice and Bob over
infrastructure operated by a service provider (\cref{sec:bg-signal}). Either party
may be offline while the other sends a message or updates key material. The system
model comprises four actors: the
communicating clients, the messaging infrastructure, the key-transparency
service, and independent auditors. Their respective responsibilities and trust
assumptions define the attack surface considered throughout the remainder of this
chapter.

The \textbf{clients}, Alice ($A$) and Bob ($B$), run the messaging application on
their own devices. They generate and hold their own secret keys, publish the
corresponding public key material, and perform all verification locally. They are
assumed honest: their devices are not under adversarial control (the boundary
where this fails is scenario X1 in \cref{sec:threat-adversary}). Clients may be
resource-constrained and intermittently connected, which is why the cost of
catching up after an offline period is a primary concern.

The \textbf{message-delivery and key-distribution server} is part of the provider's
infrastructure. It stores and serves the X3DH pre-key bundles that Alice needs to
start a session with Bob (\cref{ssec:bg-x3dh}) and relays ciphertext between the
parties. A malicious provider can substitute a key through this delivery path or through the
directory state it controls. A network attacker can separately alter the bundle while it is in
transit (scenario A3, \cref{sec:threat-adversary}).

The \textbf{key-transparency log server} maintains the verifiable directory and
its append-only log, answers lookup and monitoring queries with cryptographic
proofs, and publishes a signed tree head each epoch. It may be operated by the
same party as the message-delivery server. The analysis assumes the worst case
throughout: that the two are a single, possibly malicious, operator, which avoids
relying on any assumption that they do not collude.

The \textbf{auditors} observe the log from an independent vantage point. They compare signed
tree heads and replay each epoch's declared updates against the committed directory root (the
per-epoch transition audit of \cref{ch:design}). These checks detect split-view equivocation
and undeclared mutations between epochs. The dual-index warning mechanism itself does not
require an auditor, as clarified in \cref{sec:threat-assumptions}.

The interactions between these actors define three trust boundaries (\cref{fig:threat-arch}). The
client--server boundary is semi-trusted. The client depends on the server to answer requests but
verifies each response rather than assuming honest behaviour. This follows the semi-trusted-directory
model used by CONIKS and the IETF Key Transparency architecture (\cref{sec:bg-vkd,ssec:bg-keytrans}).
The client--network boundary is untrusted. The design adopts the full active network adversary
described below, the same adversary ACKA defends against in its continuous mode (\cref{sec:bg-acka}).
The server--auditor boundary is independent. The auditor's value is that its view of the log is
obtained separately from the client's. The network and infrastructure adversaries are modelled
separately, and a deployment may face either or both at once.

The design supports two authentication modes, defined in \cref{ch:design}. Session mode uses
per-conversation dual-index entries to authenticate session keys. Continuous mode uses a
fingerprint at each ratchet epoch to authenticate the evolving Double Ratchet state
(\cref{ssec:bg-ratchet}). The threat model applies to both modes, and mode-specific conditions
are identified where necessary.

\section{Adversary Model}\label{sec:threat-adversary}

\paragraph{The Network Attacker (Dolev--Yao).} Following Dolev and
Yao~\cite{dolevyao1983}, the network adversary has maximal control of the wire:
it can intercept, modify, inject, delete, and replay any message, and it can
impersonate any party in transit. It does not, on its own, control the server's
directory. This models the active man-in-the-middle that the Double Ratchet's
post-compromise security does not defend against once the adversary remains active
(\cref{ssec:bg-ratchet}), and that ACKA's continuous mode is designed to catch
(\cref{sec:bg-acka}).

\paragraph{The Infrastructure Attacker (Malicious Server).} The server is semi-trusted. Clients
depend on the server to answer requests but verify its cryptographic responses rather than
assuming honest behaviour. A malicious operator may substitute a key, censor a log write, or
present different internally consistent directory views to different clients. This is the
malicious-directory threat considered by the key-transparency systems surveyed in
\cref{sec:bg-vkd} and by the IETF Key Transparency
architecture~\cite{ietf-keytrans-architecture}. Documented fake-key attacks show why compromise
or coercion of a key-distribution service is a practical concern~\cite{yadav2022fakekey}.

\paragraph{What the Adversary Cannot Do.} The model assumes that the underlying cryptographic
mechanisms remain secure. An external attacker cannot find SHA-256 collisions, compute the honest
parties' X25519 shared secret without either party's private key, forge signatures under keys it
does not control, or produce valid VRF proofs without the corresponding secret key. The malicious
operator does hold the directory's VRF and signing keys, so it can evaluate global identity
labels and sign new directory states. It cannot, however,
produce a valid inclusion proof for a value absent from the root of the signed head being
verified without violating the collision-resistance assumption underlying the authenticated
data structure. Equivocation is detected when an
honest auditor compares two conflicting, validly signed heads for the same epoch. Endpoint
compromise remains outside the model and is represented by X1.

The implications of these adversary capabilities for the design are developed in
\cref{ch:design}.

\subsection{Attack Scenarios}\label{ssec:threat-scenarios}

The scenarios below turn the adversary model of \cref{tab:threat-attacks} into attack scenarios,
ordered from the primary key-substitution threat through its network and equivocation variants to the
endpoint-compromise boundary.

\paragraph{A1: Key Substitution.} A1 is the primary server-side substitution attack. A
compromised or coerced operator commits an attacker-controlled key under the victim's identity
and returns a valid inclusion proof for that malicious directory state. The proof establishes
that the key belongs to the signed state, not that it is the victim's authentic key. The
affected client detects the unexpected binding, and an established peer can learn of it through
the shared warning slot. The evaluation (\cref{ch:eval}) instantiates A1a at the global
identity slot and A1b at an immutable dual-index session slot.

\paragraph{A2: Warning Censorship.} A2 concerns censorship before the warning commits. After
detecting a key mismatch, the client verifies the warning slot. A proof-verified empty slot raises the
compound A2 alarm. If a committed warning later disappears, the transition audit detects the invalid
directory transition. For a client using windowed catch-up, an in-window substitution is detected only
if the warning commits and remains present at the catch-up read (\cref{ssec:design-catchup}).

\paragraph{A3: Network Man-in-the-Middle.} With no server collusion, a Dolev--Yao adversary may
replace Bob's identity key and signed pre-key with an attacker-controlled pair whose signature
verifies under the substituted identity. The attacker also replaces or withholds the optional
one-time pre-key. The attacker can then derive the X3DH secret for the session it establishes
with Alice. By establishing separate sessions with Alice and Bob, the attacker causes the
legitimate parties to hold different conversation secrets and derive disjoint dual-index
labels. The substituted bundle also differs from the identity entry stored under Bob's global
VRF-derived label. The affected client can therefore detect A3 through both label divergence
and the comparison with the honest directory entry.

A post-compromise variant of A3 motivates continuous mode. An adversary that has already
compromised a session may inject a forged ratchet key while the directory itself continues to
operate correctly. The transition audit alone cannot identify the semantic mismatch because the
directory operations remain internally valid. Continuous mode instead authenticates the ratchet
key at each epoch. The forged key then produces either a label the other party does not derive
or a conflicting fingerprint at the expected label, causing the client to report a warning.

\paragraph{A4: Equivocation (Split-View).} Inherited from Certificate
Transparency (\cref{ssec:bg-ct2kt}), the server signs two heads at one epoch, one
for the victim and one for the auditor, and no single client can distinguish the
two views. The cross-vantage comparison of the two heads exposes the fork.

\paragraph{A5: Malicious Key Rotation.} A legitimate rotation also changes the identity key, so a
changed key is not by itself malicious. A malicious server exploits this by substituting its own key
inside a rotation. The peer re-fetches the identity entry at the global VRF-derived label. If the identity key has changed, a valid cross-signature from the trusted predecessor binds the
new key to that predecessor and distinguishes an authorized rotation from an unauthorized
replacement. In the demonstrated A5 control, a missing
or invalid predecessor cross-signature causes rejection. The live client path currently relies on the
identity re-fetch and warning, while the cross-signature check is exercised by the adversarial suite.

\paragraph{X1: Endpoint Compromise (Boundary).} Once the adversary controls the victim's
private state, it can derive the same conversation secrets and labels and can query the same
directory entries. The protocol can no longer distinguish the attacker from the victim. X1
therefore marks the endpoint boundary of key-transparency protection.
\Cref{fig:eval-attacktree} separates the key-substitution routes A1, A3, and A5 from the
concealment attempts A2 and A4 and from the endpoint-compromise boundary X1.

\section{Assumptions}\label{sec:threat-assumptions}

The guarantees of the later chapters rest on the following assumptions.

The assumptions for the cryptographic primitives used by the model are stated in
\cref{app:definitions}. The same appendix separately defines the RFC~9162 consistency property used
by the append-only log. These assumptions and properties bound the adversary's capabilities in
\cref{sec:threat-adversary}.

The \textbf{endpoint assumption} is that honest clients' devices are not
compromised. This is the X1 boundary, and lifting it places the situation outside
the scope of any key-transparency guarantee.

The \textbf{auditor assumption} is that at least one honest auditor observes the log. It is required
only for fork detection (A4) and the per-epoch transition audit (\cref{ch:design}), not for the
dual-index warning mechanism. Detection of server-side substitution (A1) and network
man-in-the-middle (A3) is performed by the communicating clients and depends on no auditor.

The model uses trust on first use (TOFU) for the initial binding supplied by the
directory.\label{sec:threat-fair} A malicious operator that substitutes the first directory
entry before any authentic baseline exists can poison that initial binding. Later monitoring
can detect changes from the pinned value but cannot establish that the original value was
authentic. First-contact A3 remains detectable when the directory is honest because comparison
with the global VRF-bound identity entry exposes the substituted bundle. The limitation of the
initial directory binding is revisited in \cref{ch:discussion}.

\section{Security Requirements}\label{sec:threat-goals}

The adversary model and assumptions give four security requirements, denoted G1--G4.

\paragraph{G1: Key-Substitution Detection.} If a server (A1, A5) or network adversary (A3)
substitutes a key, the relevant client reports the substitution after completing the
scenario-specific verified lookups. For an established pair affected by A1 or A5, the detecting
client writes a warning to the shared warning slot. Peer notification is completed when that
warning commits and the other client's monitor reads and verifies it.

\paragraph{G2: Consistency Across Offline Windows.} A returning client obtains one consistency
proof between the last verified log size and the current log size. It verifies that the current
state extends the earlier state without requesting one proof for every missed epoch. Proof size
depends on the two log sizes and does not grow linearly with the number of missed epochs.

\paragraph{G3: Directory Privacy.} The global directory label derived from a user's identity is
computationally unpredictable to parties that do not hold the operator's VRF secret key.

\paragraph{G4: Fork Detection.} An equivocating server (A4) that signs two different heads for
the same epoch is detected when an honest auditor obtains and compares the client-observed head
with a valid head from an independent vantage. G4 is the only security requirement that depends
on the auditor's independent vantage (\cref{sec:threat-assumptions}).

\section{Out of Scope}\label{sec:threat-scope}

A malicious operator may still serve a substituted key. After an authentic baseline has been
established, the requirement is that completed verification exposes a later substitution. The
design does not guarantee service availability.
Endpoint compromise, query privacy from the operator, group messaging, and multi-device
keychains are outside the model. A refusal or dropped response produces an unavailable or
incomplete check rather than successful verification. These boundaries and possible extensions
are examined in \cref{ch:discussion}.
