\chapter{Evaluation}\label{ch:eval}

This chapter evaluates the implementation described in \cref{ch:impl} against the requirements and
threats defined in \cref{ch:threat}. It examines proof size and verification cost, offline catch-up,
scalability, the trade-off between session and continuous modes, comparisons with existing systems, and
the coverage of the security controls.

% ============================================================================
\section{Methodology}\label{sec:eval-method}

The evaluation asks whether detection enlarges an individual proof, how verification changes with
directory size, and whether offline catch-up can use one proof. It also tests whether each scenario
in \cref{sec:threat-scenarios} produces its required outcome and whether the seven clean workflows
in \cref{tab:bench-m17} complete without warnings. Seventeen metric families measure proof size,
latency, catch-up, scale, operating modes, and security outcomes.

The benchmark harness in the \texttt{duet} crate measures local cryptographic and data structure
operations within one process. It excludes HTTP, Electron, persistent storage, and network costs.
For the per-lookup latency and detection microbenchmarks, the reported medians and 95th percentiles
are calculated over \num{2000} sequential iterations. The heavier maintenance and scale experiments
use fewer samples, because each iteration is far more expensive. For example, the M7 large-directory
experiment samples \num{1000} randomly selected lookups at each directory size, and the M9 epoch
commit uses \num{200} iterations.

All DUET timings reported in this chapter were measured on the Windows x86\_64 machine described in
Appendix~\ref{sec:bench-env} (12th Gen Intel Core i7-12700H, 31.7\,GiB RAM). Under the worked
parameterization established in \cref{ssec:design-param}, epochs are hourly, so a window of $W=720$
epochs spans 30 days. Proof-size values are exact for the fixed seeds used in the recorded runs.
Timing values that are close to the timer resolution are treated as approximate. Cross-system timing
comparisons are also approximate as the published implementations and hardware differ.
Appendix~\ref{app:benchmarks} defines the metric families and baseline configurations and provides
the complete tables, measurement environment, and reproduction instructions.

\section{Measured Results}\label{sec:eval-micro}

\subsection{Proof Size and Verification (M1--M3, M14)}\label{ssec:eval-sizes}\label{ssec:eval-latency}

A VRF-indexed lookup proof carries a prefix copath, a log-inclusion path, and fixed-size VRF and
encoding fields. Let $\pi^{\mathsf{lookup}}$ denote the serialized lookup-proof body:

\begin{equation}\label{eq:eval-proofsize}
  |\pi^{\mathsf{lookup}}| \;=\; 32h \;+\; 32h_{\mathrm{log}} \;+\; 177 \ \text{bytes},
  \qquad \mathbb{E}[h]\approx\lceil\lg N\rceil,\quad
  h_{\mathrm{log}}\le\lceil\lg E\rceil.
\end{equation}

In \cref{eq:eval-proofsize}, $N$ is the number of populated directory labels, $E$ is the number of
committed epochs in the append-only log, $h$ is the number of non-empty siblings on the queried
label's path, and $h_{\mathrm{log}}$ is the log-inclusion path length. The \num{177}-byte constant
consists of the \num{80}-byte ECVRF proof, a \num{32}-byte label, a \num{32}-byte value, a one-byte
leaf-kind commitment, and a \num{32}-byte sibling bitmap. Raw-label warning responses omit the
\num{80}-byte VRF proof because the client supplies the derived label directly. The median lookup
proof is \num{817} bytes at $N=10^{6}$ and \num{945} bytes at $N=10^{7}$. This \num{128}-byte
increase corresponds to four additional non-empty prefix siblings, while the fixed component
remains unchanged. Appendix~\ref{sec:bench-sizes} gives the complete single-epoch proof-size table,
while \cref{tab:bench-scale} reports the sampled distribution.

Key-substitution detection uses additional verified lookups but does not change the lookup-proof
format. The dual-index and CEA checks each carry their own directory and signed-head evidence,
increasing the number of lookups without enlarging an individual proof.

The M14 history-depth experiment isolates the $32h_{\mathrm{log}}$ log-inclusion term by holding
$N$ fixed while varying $E$. Across $E\in\{1,16,256,1024\}$, the corresponding values of
$h_{\mathrm{log}}$ are \num{0}, \num{4}, \num{8}, and \num{10} sibling hashes. The log-inclusion
path therefore adds \num{0}, \num{128}, \num{256}, and \num{320} bytes, matching
$32h_{\mathrm{log}}$ in \cref{eq:eval-proofsize}. Median full verification remains below
\SI{150}{\micro\second} throughout the grid, with a maximum of
\SI{143.2}{\micro\second}. These results confirm the measured effect of increasing log history while
the $32h$ prefix-copath term remains unchanged.

Full client verification checks the VRF derivation, prefix proof, log-inclusion proof, and STH
signature. Its median is \SI{128.7}{\micro\second} at $N=10^{3}$ in the manual harness. In the M7
large-directory scale experiment (\cref{tab:bench-scale}), the median increases from
\SI{133.6}{\micro\second} at $N=10^{6}$ to \SI{139.2}{\micro\second} at $N=10^{7}$. A tenfold
increase in directory size therefore produces an increase of \SI{5.6}{\micro\second}, or 4.2
percent, across these two measured sizes. Prefix-only verification changes from
\SI{26.3}{\micro\second} to \SI{26.4}{\micro\second} over the same range and accounts for little of
the full-verification increase. The benchmark does not isolate the cause of the remaining increase,
and these two directory sizes do not establish an asymptotic trend.

At $N=10^{7}$, server-side search has a median of \SI{441.7}{\micro\second} and a 95th percentile of
\SI{4581.9}{\micro\second} (\cref{tab:bench-scale}). The cause of this tail remains unexplained. The
harness did not record operating-system paging activity and therefore cannot determine whether
memory pressure caused it. The tail is reported as observed implementation behaviour without
assigning an unmeasured cause.

\subsection{Offline Catch-Up (M4)}\label{ssec:eval-catchup}

A client that has been offline for $W$ epochs must verify that the current head is consistent with
the head it last verified. The M4 offline catch-up experiment measures the raw consistency-path hash
bytes required for this verification. Its synthetic baseline generates $W$ proofs, each connecting
a missed-epoch position to the current head. DUET's windowed construction instead uses one
consistency proof from the retained head to the current head. At $W=720$, the windowed proof
contains \num{320} raw hash bytes, compared with \num{222528} bytes across the synthetic baseline,
giving a ratio of \num{695.4}. \Cref{fig:eval-catchup-plot} shows how the two results change as the
offline window increases.

The synthetic baseline models this implementation without windowing and does not represent a
deployed system. Both byte totals count raw consistency-path hashes and exclude serialization and
transport. Proofs between adjacent epochs would be smaller, so the \num{695.4} ratio is specific to
the defined baseline. Nevertheless, the windowed construction reduces the proof count from $W$ to
one. Appendix~\ref{sec:bench-sizes} reports the corresponding proof-generation timings.

\subsection{Detection Costs and Clean-Run Results (M16, M17)}\label{ssec:eval-detection}

The M16 detection-path experiment reconstructs two execution paths through the key-substitution
detector in the \texttt{duet} crate at $N=10^{4}$. The mismatch path performs one verified
owner-slot lookup and value comparison before returning, with a median of
\SI{27.8}{\micro\second}. The clean path verifies owner-slot inclusion followed by warning-slot
non-inclusion, with a median of \SI{31.1}{\micro\second}. These are local, in-process component
timings. They exclude the Signal Desktop client, HTTP transport, background polling, registration,
and warning publication. Thus, they do not represent end-to-end detection latency.

M17 evaluates clean-workflow outcomes without measuring their latency. All seven specified clean
workflows produce their expected clean verdicts, and none produces a warning, as shown in
\cref{tab:bench-m17}. The corresponding adversarial outcomes are evaluated in
\cref{sec:eval-security}.

\section{Scalability, Maintenance, and Authentication Modes}\label{sec:eval-scale}

\subsection{Scale, Maintenance, and Auditing (M7, M9, M12)}\label{ssec:eval-scale}\label{ssec:eval-throughput}\label{ssec:eval-auditor}

The M7 large-directory scale experiment records directory-build time and resident set size after
build. Building the $N=10^{7}$ directory takes approximately 26 minutes, with a resident set size
of \SI{20.8}{\gibi\byte} after build. The single-process benchmark keeps the complete directory in
memory. Therefore, its memory requirement is a major constraint for deployment at this scale.

The M9 maintenance experiment measures key rotation and the epoch-commit path at
$N\in\{10^3,10^4\}$. Key-rotation medians change from \SI{138.7}{\micro\second} to
\SI{140.3}{\micro\second} across these sizes, but these two measurements do not establish
independence from $N$. The measured path for epoch commit, which includes one fixed-key update,
increases from \SI{451.0}{\micro\second} at $N=10^3$ to \SI{6.73}{\milli\second} at $N=10^4$.
The implementation's full-tree cloning step is described in \cref{ssec:impl-core-state}. Although
the benchmark does not isolate this step from the remaining commit work, the measured increase
identifies it as a major maintenance constraint at larger $N$.

Finally, the M12 auditor experiment measures two local operations at $N=10^4$ and does not
represent a complete networked audit. The first combines an STH signature check with the generation
and verification of one consistency proof. The second measures fork detection after the auditor has
stored one signed head and is given another validly signed head for the same epoch with a different
root. Their medians are \SI{28.6}{\micro\second} and \SI{27.1}{\micro\second}, with 95th
percentiles of \SI{34.7}{\micro\second} and \SI{33.1}{\micro\second}, respectively. Both
measurements exclude network transfer, scheduling, persistent storage, and full transition replay.
A further limitation is that the fork-check benchmark begins with one stored head, so it does not
show how the cost changes as signed heads accumulate.

\subsection{Session and Continuous Modes (M13, M15)}\label{ssec:eval-modes}

The M13 mode experiment compares two local label-bound lookup paths at $N=10^4$. Session mode
verifies a raw-label lookup proof and compares the returned identity-key value, while continuous
mode verifies the same proof format and compares the returned CEA fingerprint. Their median costs
are \SI{27.3}{\micro\second} and \SI{27.7}{\micro\second}, respectively. Both measurements
include server-side proof generation. The \SI{0.4}{\micro\second} difference is within run-to-run
variation. Thus, the measurements do not establish that either mode is faster, and equivalence was
not tested.

The directory-write count comparison in M13 assumes one continuous-mode write per modelled hourly
epoch and one session-mode write every $R=720$ epochs, where $R$ is the assumed interval between
new session-mode conversation secrets. Across $E\in\{24,168,720,4320\}$ modelled epochs, the
resulting ratio ranges from 24 to
720. These counts follow from the assumed intervals and do not represent measured Signal traffic or
a fixed deployment value. Appendix~\ref{sec:bench-modes} gives the complete write-count table.

The M15 ratchet-depth experiment evolves independent simulated continuous-mode chains through
$K\in\{1,10,100,720\}$ epochs and then measures verification of the final epoch. A session-mode raw
lookup is timed on the same resulting directory, controlling for directory and log depth. Across
the tested values of $K$, the continuous-mode medians range from
\SI{27.1}{\micro\second} to \SI{27.5}{\micro\second}, while the session-mode medians range from
\SI{27.0}{\micro\second} to \SI{27.5}{\micro\second}. These results show that final-state
verification remains stable across the tested ratchet depths. Note that the experiment does not
measure the cost of replaying the preceding epochs.

At $N\approx10^6$, DUET's \num{817}-byte median and the derived

excluded. Signal's fixed \num{8192}-byte sibling copath provides structural context but is not a

Signal copath length is independent of directory occupancy, while DUET's bitmap reveals which
levels on the queried path have non-empty siblings.

The timing comparison is less closely matched. CONIKS reports
\SI{159}{\micro\second} for authentication-path verification and approximately
\SI{400}{\micro\second} for signature verification, giving a derived total of approximately
\SI{559}{\micro\second}. The cost of verifying its private-index proof is not reported separately.
DUET's
\SI{139.2}{\micro\second} result includes VRF and signed-head verification, but it was measured with
a different implementation and on different hardware. Therefore, these values provide published
context and do not establish a controlled speed comparison.

CONIKS already makes routine owner self-monitoring efficient by allowing a client to check only its
own binding with a logarithmic proof. Under its stated model, daily monitoring requires less than
20\,kB~\cite[Section~5.3 and Table~1]{melara2015coniks}. However, after missing several epochs, a
returning client performs a series of checks until its previously verified inclusion proofs and
signed tree roots are consistent with the more recent proofs~\cite{melara2015coniks}.
DUET's M4 experiment evaluates this returning-client case with one endpoint consistency proof.
Since CONIKS does not publish a matched byte total for $W=720$, no direct catch-up byte ratio is
reported in \cref{tab:eval-compare}.

The systems also differ in their detection scope. CONIKS automatically monitors the owner's
binding~\cite[Sections~2 and 4.1.3]{melara2015coniks}, while Signal provides a monitoring endpoint and optional user-triggered
AKV~\cite{signal-kt-server,signal-akv}. Neither cited workflow describes DUET's
conversation-specific shared peer-warning channel. \Cref{tab:bg-compare} provides the broader
qualitative comparison, while \cref{sec:eval-security} reports DUET's evaluated security outcomes.

Endpoint compromise (X1) is not included in \cref{tab:eval-security} because it is a threat-model
boundary, not an additional security requirement. Its adversarial-suite case shows that an attacker
holding the endpoint's shared secret derives the same labels as the client and therefore produces
the expected out-of-scope outcome.

The functional results support the tested aspects of G1, G2, and G4 for the specified inputs but do
not constitute a formal proof of the requirements. For G3 (Directory Privacy), the RFC~9381 test
vectors check ECVRF implementation conformance~\cite[Appendix~B.3]{rfc9381}. They do not measure
resistance to offline enumeration, which depends on the VRF security
assumption~\cite{rfc9381}.

The client-side results assume uncompromised endpoints. The A4 split-view equivocation fixture
stages two validly signed views on the same test server to evaluate the signed-head comparison
logic. Additionally, meeting G4 (Fork Detection) in deployment requires a comparison head obtained
from an independent vantage.

\section{Implications for Deployment}\label{sec:eval-deploy}

The results indicate that local proof verification is not the main deployment constraint at the
tested scales. Key-substitution detection reuses the existing proof format through additional
lookups, while windowed catch-up reduces the number of consistency proofs from $W$ to one. However,
the measurements do not include complete background-monitoring and network costs.

The major implementation constraints are server-side memory use and the full-tree clone performed
at each epoch commit. Therefore, deployment would require persistent storage, an epoch-commit design
that avoids full-tree cloning, concurrent request handling, crash recovery, and end-to-end networked
evaluation. The choice between session and continuous modes
also affects the directory write load according to the selected update interval.

Finally, M12 does not establish the deployment cost of independent auditing because it excludes
network transfer, persistent state, epoch-delta retrieval, and full transition replay.
Client-assisted and independent auditing are discussed in \cref{ch:discussion}.
