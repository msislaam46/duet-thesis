\chapter{Evaluation}\label{ch:eval}

This chapter evaluates the system implemented in \cref{ch:impl} against the goals and threats of
\cref{ch:threat}. It sets out the measurement methodology and baselines (\cref{sec:eval-method}),
reports the microbenchmarks for proof size, verification latency, catch-up bandwidth, and detection
(\cref{sec:eval-micro}), examines behaviour at scale together with the session-versus-continuous
mode trade (\cref{sec:eval-scale}), places the results beside prior key-transparency systems
(\cref{sec:eval-compare}), and finally evaluates the security of the system against the attack
taxonomy (\cref{sec:eval-security}). The principal findings are that the dual-index lookup proof is
at size parity with CONIKS while adding automatic detection, that offline catch-up needs one proof
rather than $W$ (\num{695}-fold fewer raw path-hash bytes at a one-month window against this
chapter's synthetic baseline), and that median full client verification stays below
\SI{150}{\micro\second} through $10^7$ labels and grows far more slowly than $N$.

% ============================================================================
\section{Methodology}\label{sec:eval-method}

In this section we describe what was measured, against which baselines, and on what apparatus, so
that every number that follows can be read against a fixed reference. This matters because the
value of a transparency system is not any single cost but the trade between proof size, verification
time, and the bandwidth a client must spend to stay synchronized.

The evaluation is organized around four questions, one per design claim, each stated so that it could
be falsified. \emph{Is detection free in proof size?} Falsified if the dual-index proof were
materially larger than a single-index proof at the same $N$ (\cref{ssec:eval-sizes}). \emph{Does client
verification remain inexpensive as the directory grows?} Falsified if the full-chain verify grew in
proportion to $N$, or exceeded the sub-millisecond target (\cref{ssec:eval-latency,ssec:eval-scale}).
\emph{Can an offline client re-synchronize in a single proof, rather than one per missed epoch?}
Falsified if the windowed client still had to fetch a proof per epoch, or if that single proof's size
grew linearly with $W$ (\cref{ssec:eval-catchup}). \emph{Is substitution detected, with no false alarms?} Falsified by any
missed attack in the adversarial suite or a non-zero clean-session false-positive rate
(\cref{ssec:eval-detection,sec:eval-security}). Each question is answered against the baselines below.

Measurements are grouped into thirteen metric families, \emph{M1}--\emph{M13}. Rather than define
them in prose, \cref{tab:eval-map} is the measurement map for the whole chapter: it states what each
metric measures, the baseline it is read against, and where it is reported. The reader can consult it
once and refer back, instead of holding thirteen definitions in mind. The metrics are numbered in the
order this chapter presents them (size, then latency, then bandwidth, then detection, then scale,
maintenance, and modes) which is the order the questions above are answered, not the order of the
benchmark harness that produces them.\footnote{The Rust harness (\cref{app:benchmarks}) emits the
same metric numbering, so each metric family reported here can be traced directly to the harness
group of the same name.}

Baselines are referred to by name throughout this chapter, and each name denotes the same
configuration wherever it appears: the \emph{no-KT floor} (a session
setup with no key transparency: a single hash, the cost a deployment pays anyway), the
\emph{single-index} path (log-inclusion only), the \emph{dual-index} path (the prefix-tree lookup that
carries the warning slot), and the \emph{windowed} full scheme (dual-index plus windowed consistency
proofs). These form an ablation: the no-KT floor isolates the cost of key transparency at all,
single-index removes the dual-index warning, dual-index removes windowing, and windowed is the
complete client verification. Read together with the session-versus-continuous comparison (M13), they
let the contribution of each mechanism be attributed directly.

Timings are collected two ways. Criterion provides the confidence intervals and regression plots;
in parallel, a manual harness of \num{2000} timed iterations per operation records the median, the
95th percentile, and a 95\% confidence half-width to \texttt{results/rust\_benchmark\_timings.csv},
and it is the manual-harness medians that are quoted here, the harness producing uniformly formatted
rows across every metric family. Two properties of those rows bound how they may be read. The median
and 95th percentile are descriptive sample statistics, carrying no interval. The $\pm$ column is a
\num{95}\,\% confidence half-width \emph{of the mean} under a normal approximation
($1.96\,s/\sqrt{n}$): it quantifies the precision of the mean, so it licenses no inference about the
medians quoted beside it, and none is drawn. Where a timing falls near the platform's timer
resolution (the sub-microsecond M4 windowed generation figures, \SIrange{0.1}{0.3}{\micro\second}),
it is a coarse hot-path observation and is treated as one. Proof sizes are computed exactly and are seed-deterministic,
so they carry no confidence interval; the scale figures (M7) are distributions over \num{1000}
random lookups per $N$. All runs use fixed cryptographic and sampling seeds and are reproducible by
the procedure of \cref{sec:impl-repro}; the full per-parameter tables, at the resolution the CSVs
record, are collected in \cref{app:benchmarks}
(\cref{tab:bench-env,tab:bench-m1,tab:bench-m4,tab:bench-latency,tab:bench-detection,tab:bench-maint,tab:bench-auditor,tab:bench-scale,tab:bench-modes,tab:bench-repro}). Timing medians are quoted in the body to one decimal
place ($0.1\,\si{\micro\second}$): finer precision would be spurious for a wall-clock median, and
sub-microsecond digits vary between runs (for example, the VRF-verify median reads
\SI{76.0}{\micro\second} in \cref{tab:eval-latency} and \SI{81.5}{\micro\second} in the separate
scale run of \cref{tab:eval-scale}). The isolated VRF rows of \cref{app:benchmarks} show the same
sensitivity more strongly, and in both directions: isolated verify reads
\SI{78.5}{\micro\second} against an in-path \SI{76.0}{\micro\second}, while isolated prove reads
\SI{117.4}{\micro\second} against a prove-inclusive in-path generation of
\SI{119.5}{\micro\second}. The isolated figure is therefore the slower one for verify and the faster one
for prove. Measuring the same primitive in a different benchmark context, and at a different point in
the run order, therefore shifts it by a few percent in whichever direction; the harness records
execution times but no clock-frequency, power, or temperature telemetry, so this is reported as
context and run-order sensitivity without attributing it to a mechanism. The in-path figures are the
ones this chapter quotes, since they are the cost a client actually pays.

Three limitations bound the interpretation of the numbers. First, the server is in-memory and
single-machine, so absolute latencies exclude the database and network costs a distributed
deployment would add. Second, every proof is measured on a single-epoch log, so the log-inclusion
component is \num{0}\,bytes; a deployed log of $E$ epochs adds up to $32\lceil\lg E\rceil$\,bytes to every
lookup proof. Third, the operation-rate figures are single-thread per-operation costs, not parallel
scaling. Cross-system numbers in \cref{sec:eval-compare} come from different hardware, scales, and
storage models and are treated as order-of-magnitude only.

\section{Microbenchmarks (M1--M6)}\label{sec:eval-micro}

In this section we report the core per-lookup costs on a directory of up to $10^6$ labels: how large
a proof is, how long it takes to produce and to check, how much bandwidth an offline client must
spend to catch up, and how quickly and reliably an attack is detected.

\subsection{Lookup Proof Size (M1)}\label{ssec:eval-sizes}

The size of a lookup proof determines the bandwidth cost of every key fetch, so it is the first
quantity to pin down. \Cref{tab:eval-sizes} reports two measured objects as the directory grows: the
implemented (VRF-indexed) DUET lookup proof, which bundles a prefix proof, an 80-byte VRF proof, and a
log-inclusion component, and, as a reference point, a dense Merkle-log inclusion proof over $N$ user
entries. The table therefore compares the implemented VRF-indexed lookup against a plain log
inclusion at the same $N$; it is not a measurement of the raw dual-index path (which calls
\texttt{search(label)} and carries no VRF proof) and it does not isolate a like-for-like single-
versus dual-index directory overhead. Each row is one seed-deterministic path; M7
(\cref{ssec:eval-scale}) supplies the sampled distribution. A prefix proof carries one hash per
non-empty sibling on the label's path, whose number $h$ has expected value $\approx\lceil\lg N\rceil$,
so both objects grow logarithmically in $N$ as the sparse-tree design predicts
(\cref{ssec:design-structures}).

The dual-index proof decomposes as a fixed \num{177}\,byte constant (an \num{80}\,byte
ECVRF proof (RFC~9381)~\cite{rfc9381} plus \num{97}\,bytes of metadata: a \num{32}\,byte label, a
\num{32}\,byte value, a \num{1}\,byte C2 leaf-kind commitment (\cref{ssec:design-detection}), and a
\num{32}\,byte sibling bitmap) on
top of $32$ bytes per prefix hash, giving
\begin{equation}\label{eq:eval-proofsize}
  |\pi| \;=\; 32h \;+\; 32h_{\mathrm{log}} \;+\; 177 \ \text{bytes},
  \qquad \mathbb{E}[h]\approx\lceil\lg N\rceil,\quad h_{\mathrm{log}}\le\lceil\lg E\rceil,
\end{equation}
where $h$ is the number of non-empty siblings on the queried label's path (the ``dual-index prefix
hashes'' column of \cref{tab:eval-sizes}) and $h_{\mathrm{log}}$ is the length of the current root's
log-inclusion path. Because the current directory root is always the \emph{last} log leaf (the
currency pin, \cref{ssec:design-verify}), $h_{\mathrm{log}}$ is the number of complete subtrees to its
left: $\mathrm{popcount}(E-1)$, at most $\lceil\lg E\rceil$ and often smaller (one hash at $E=5$,
not three). The $O(\lg N + \lg E)$ scaling of \cref{eq:eval-proofsize} is plotted in
\cref{fig:eval-sizes-plot}. The $10^6$ row reads \num{913}\,bytes because the single seeded leaf's
path carries $h=\num{23}$ non-empty siblings; the distribution median over \num{1000} random lookups
at $10^6$ is \num{817}\,bytes (\cref{ssec:eval-scale}). We
therefore report the distribution median in the remainder of this chapter, since it reflects the
proof size a typical lookup incurs rather than the depth of one particular seeded leaf. Crucially,
the ECVRF proof and the warning slot add nothing beyond this
formula: \emph{the dual-index detection mechanism does not enlarge the per-lookup proof} (a warning
check is a second lookup of the same shape, not a larger proof).

prefix-root recompute, the VRF verify, and the full five-step chain of \cref{ssec:design-verify}.

The most important result is the last row, M3: the full signed-head lookup verification path, referred to more generally as full client verification (VRF label binding, value binding, prefix
root recompute, log inclusion, and the Ed25519 signed-tree-head signature) costs about
\SI{128}{\micro\second} and does not grow with the directory, because its two cost centres, the
prefix recompute (\SI{25.9}{\micro\second}) and the VRF verify (\SI{76.0}{\micro\second}), are both
$N$-independent: the first is a fixed \num{256}-level bitmap walk and the second is a constant-time
elliptic-curve operation. The system therefore meets its sub-millisecond client-verify target with
roughly sevenfold headroom, and does so while including the VRF verification that comparable systems
exclude from their reported figures. The server-side full search is likewise flat rather than
growing, and this is a direct consequence of the compressed-leaf chain memo (\cref{sec:impl-modules}).
Before that optimization, proof generation grew with directory depth (from \SI{107}{\micro\second} to
\SI{159}{\micro\second} across $N=10^3$--$10^4$) because each non-inclusion co-path recomputed a
compressed leaf's \num{256}-level hash chain. Memoizing that chain top removes the $N$-dependent
component, leaving generation dominated by the constant-time VRF prove: it reads \SI{119.5}{\micro\second}
at $N=10^3$ and \SI{119.7}{\micro\second} at $N=10^4$, while the scale run's search median reads
\SI{117.6}{\micro\second} at $N=10^6$ and \SI{141.2}{\micro\second} at $N=10^7$
(\cref{ssec:eval-scale}): flat through $10^6$, then rising at $10^7$, the same shape verification
shows and with the same two candidates behind it, the wider proof and the change of measurement
context between the harnesses.

\subsection{Offline Catch-Up Bandwidth (M4)}\label{ssec:eval-catchup}

The bandwidth a client spends after being offline is where the windowed-consistency policy of
\cref{ssec:design-catchup} yields its largest saving over a repeated-proof workload. The baseline
here is synthetic: it re-fetches one current-head-anchored consistency proof for each of the $W$
missed epochs. The windowed client instead verifies a single distant-head proof spanning the whole
gap, which standard RFC~9162 already supports directly; the saving is therefore in the number of
proofs a monitoring policy chooses to fetch, not a cost RFC~9162 forces on an offline client.
\Cref{tab:eval-catchup} reports both as the offline window $W$ grows. Because catch-up proofs are
taken over the epoch log, one leaf per epoch, their size is independent of the number of users
$N$; the table therefore holds for every $N$ measured.

Two properties of the comparison must be stated before the ratio is read, because both bound what it
means. First, the baseline is \emph{synthetic}: the harness issues $W$ current-head-anchored
consistency proofs, which models a client that re-fetches a fresh proof against the latest head on
each of $W$ occasions.\footnote{It is one baseline among several, not the cost of generic sequential
catch-up. A client verifying adjacent $e \to e+1$ transitions is an equally reasonable naïve
strategy, and its per-proof size is smaller, so the \num{695}-fold constant is specific to this
construction. What does not depend on the choice is the proof \emph{count}: $O(1)$ against $O(W)$.}
Second, the byte figures are \emph{raw consistency-path hash bytes}: the harness counts path
length times the \num{32}-byte hash size. A deployment serializes these (the reference server sends
hex-encoded JSON with framing and length fields), so serialized network bandwidth was not measured
and would be larger on both sides of the comparison.

sends a \num{320}\,byte proof in place of \num{222528}\,bytes, a \num{695}-fold reduction, and the
generation-time counterpart is similar in magnitude (\SI{0.3}{\micro\second} windowed versus
\SI{184.8}{\micro\second} sequential at $W=720$: medians over the log alone, which the prefix-tree
memoization does not touch). The two ratios are separate measurements and should not be conflated:
the \num{695}-fold figure is a computed count of raw path hash bytes, whereas the generation-time figure is timed,
and the windowed median sits at the \SI{0.1}{\micro\second} resolution this chapter quotes to, so
their quotient is only good to a couple of significant figures ($\approx$\num{600}-fold). Both say the
same thing about the mechanism: one proof replaces $W$ of them. This directly addresses the monitoring-bandwidth problem that CONIKS lists as
an open extension.

\subsection{Warning-Slot Lookup Cost and False Positives (M5, M6)}\label{ssec:eval-detection}

Finally, we measure the warning-slot read that carries detection, and how
often a clean session is wrongly flagged. The check comprises the dual-index label
derivation (pure HKDF, one extract and three expands, independent of directory size) and an
unverified read of the warning slot. The read's underlying cost is \emph{data-dependent}: the
co-path of a non-inclusion proof almost always meets a compressed leaf, whose subtree hash is a
chain of up to \num{256} hash evaluations. The implementation memoizes the top of that chain per
leaf (\cref{sec:impl-modules}), so the check costs a median \SI{1.6}{\micro\second} (95th percentile
\SI{2.0}{\micro\second}), independent of $N$; only the first touch of a cold leaf pays the full chain once, a worst case
bounded by the fixed tree depth rather than by $N$. The benchmark samples \num{1000} random
conversations and reports the distribution (median and 95th percentile) rather than any
single label's path,\footnote{An earlier revision of the harness timed one fixed conversation and,
before the chain memo, read \SI{1.4}{\micro\second} or ${\sim}$\SI{40}{\micro\second} depending on
where that one label happened to sit; a single-label figure is not robust, because re-seeding the
directory relocates every label.}
Both branches have microsecond-scale marginal cost, and no claim of timing indistinguishability is
made between them. The run does not support one. The clean branch reads
\SI{1.62}{\micro\second} against the attacked branch's \SI{1.72}{\micro\second} at $N=10^3$, and the
two Criterion intervals do not overlap. That separation is not offered as a leak either: a
side-channel claim in either direction needs a dedicated adversarial and statistical analysis that
this benchmark, which was built to size a cost rather than to test a hypothesis, does not attempt.
The point is only that indistinguishability cannot be asserted here. Either way, this is the
\emph{marginal} cost of the warning-slot read on top
of a lookup the client already verifies; it is an unverified read, so the security-bearing detection
cost is that of the full verified chain the client runs regardless: the \SI{26}{\micro\second}
prefix verify and the remainder of the \SI{128}{\micro\second} chain of \cref{ssec:eval-latency}. Over \num{1000} clean
sessions the false-positive rate (M6) is \num{0}; this is a sanity check rather than independent
evidence, since a spurious collision at a 256-bit HKDF-derived warning label is cryptographically
negligible. What M5 times must not be mistaken for the detector. The reference detector
(\texttt{detectMitm}, \cref{sec:impl-signal}) performs \emph{two} proof-carrying lookups: the client's
own slot must still verifiably equal its key, and the warning slot must be verifiably \emph{empty},
a non-inclusion proof, since an unproven ``empty'' would let the server censor the warning. M5 times
neither. It times the marginal, unverified read of the warning slot, in clean state. Each of the two
verified lookups is of the shape M3 measures ($\approx$\SI{128}{\micro\second} median locally), which
bounds one of them; no two-request total is derived from that here, because the workflow those
requests belong to (including the network round-trips a deployment adds) was not measured, and
end-to-end detection latency is therefore not a figure this thesis reports. Detection remains
automatic and silent, in sharp contrast to the manual safety-number ceremony it replaces, which only
about 14\% of users complete without guidance~\cite{vaziripour2017}.

\section{Scalability and the Mode Trade (M7--M13)}\label{sec:eval-scale}

Having established per-lookup costs at moderate size, we now push the directory to production scale,
measure server-side operation rates and maintenance costs, and quantify the price of the continuous
operating mode.

\subsection{Scale to CONIKS Size (M7)}\label{ssec:eval-scale}

To show the design holds at deployment scale, the size and verification measurements were repeated at
$N=10^6$ and $N=10^7$: the latter the scale at which CONIKS reports its figures.
\Cref{tab:eval-scale} gives the distribution over \num{1000} random lookups per $N$.

The measured constancy of prefix verification across five orders of magnitude ($10^2$ to $10^7$),
\SI{25.9}{\micro\second} at $10^3$ and \SI{26.0}{\micro\second} at $10^7$, is strong empirical
evidence that the tree walk is bounded by the fixed \num{256}-level height rather than by $N$. Full client
verification is not quite as flat: its median reads \SI{131.9}{\micro\second} at $10^6$ and
\SI{147.1}{\micro\second} at $10^7$. These M7 figures are medians of the randomized \num{1000}-lookup
distribution recorded to the CSV, whose proof shape varies with the sampled label; the fixed-target
Criterion group, which repeatedly times a single fixed lookup path, is exploratory and is not the
reported scale figure. Against the manual-harness M3 figure of $\approx$\SI{128}{\micro\second} at
$N\le10^4$ (\cref{tab:eval-latency}), the full check rises by roughly \num{15}\,\%
(about \SI{19}{\micro\second}) while $N$ grows by four orders of magnitude. The two components that
could carry a depth-driven increase, the prefix walk and the constant-time VRF, are themselves flat
across the same range, so the residual is not a tree-depth effect. The experiment does not isolate its
source; possible contributors include the larger proof representation and differences between the two
measurement contexts (\cref{sec:eval-method}). The claim the data supports is that the check grows far
more slowly than the directory, not that it is invariant. The build-time and memory rows expose the single-machine limit: constructing a $10^7$-label
tree takes about 26 minutes and leaves a \SI{20.8}{\giga\byte} resident set, which is why a production
deployment would move to the persistent, sharded storage this prototype deliberately does not model.
$^{\dagger}$The $10^7$ full-search 95th percentile of \SI{2404.5}{\micro\second} (an order of magnitude
above its \SI{141.2}{\micro\second} median) shows that a small fraction of lookups are far slower than
the typical one. The proof structure does not account for it: the client-side steps that consume the
proof (prefix and VRF verify) show no comparable tail. The harness records no paging or
memory-pressure counters, so the source of the tail was not instrumented; a \SI{20.8}{\giga\byte}
resident set on a \SI{31.7}{\giga\byte} machine makes memory pressure a plausible candidate, but that

\subsection{Auditor Cost (M12)}\label{ssec:eval-auditor}

The cross-vantage auditor (\cref{sec:design-acka}) that detects split-view equivocation must be
cheap enough to run continuously. It is, in the local append-only cryptographic kernel this metric
covers: an STH signature check plus consistency-proof generation and verification, and a fork
check against \emph{one} observed head. The per-epoch audit costs \SI{28.5}{\micro\second} median at
$N=10^4$, and the fork check \SI{27.9}{\micro\second} median (p95 \SI{34.2}{\micro\second}), so the
equivocation-detection kernel is cheap per epoch in local computation. Two scoping caveats matter.
The audit figure times proof generation and verification together, so as a \emph{verify-only} cost it
is a conservative over-estimate; but it measures only the auditor's \emph{local} per-epoch work (the
signature check and the append-only consistency check). It
does \emph{not} include the networked, proof-carrying exchange a deployed auditor runs: fetching
each epoch's disclosed update set together with the committed-root log-inclusion proof
(\cref{sec:design-acka}) and verifying that proof against the signed head, whose transfer and
verification cost is not captured here, nor the full \texttt{audit\_epoch} transition replay, which
re-applies every disclosed update into a scratch mirror rather than checking a signature and a
consistency proof. The fork figure needs a further caveat, and it is not a constant. The
implementation's \texttt{detect\_fork} compares the presented head against \emph{every} head it has
observed (a linear scan of the observed vector), so its cost grows with the number of accumulated
heads; the benchmark seeds exactly one, so \SI{27.9}{\micro\second} is the one-head case and not the
steady-state cost of a mature auditor holding many vantages over a long log. The number is therefore
the compute floor of the audit, not the end-to-end cost of the protocol.

\subsection{Session versus Continuous Mode (M13)}\label{ssec:eval-modes}

The design offers two operating modes (\cref{ssec:design-modes}): session mode writes one directory
entry per signed-pre-key rotation, and continuous mode writes one per ratchet epoch for finer-grained,
ACKA CEA-style detection. The cost of that granularity is not verification time. A per-check operation
costs \SI{27.2}{\micro\second} in session mode and \SI{27.5}{\micro\second} in continuous mode (medians, \cref{app:benchmarks}; both include
server-side proof generation). The two medians differ by \SI{0.3}{\micro\second}, and no ordering
conclusion is drawn from that gap: the $\pm$ column is a confidence half-width of the \emph{mean}
(\cref{sec:eval-method}) and licenses no inference about the medians, which are reported as
descriptive statistics. The chain memoization flattens the compressed-leaf cost that previously
separated the two modes. Both
figures require a precise statement of what they measure: each benchmarked check comprises the
server-side proof generation and the client-side verification of the value, prefix-root, and
log-inclusion steps, both under the same label-bound verifier. Client-side label derivation (a fixed
sub-microsecond HKDF/hash) is performed once in setup and excluded from both timed bodies, so the two
medians compare like for like. One residual asymmetry is disclosed: continuous mode appends one log
leaf per registered epoch (here $K$ epochs) whereas session mode commits once, so the continuous
log-inclusion proof is over a marginally deeper log; the effect is within the reported precision and
does not change the conclusion that granularity costs write rate, not verification time. Neither figure includes a VRF step, because the
dual-index and CEA paths use client-derived rather than VRF-derived labels
(\cref{ssec:design-verify}), and neither includes the signed-tree-head signature verification that
the full specified check of \cref{app:algorithms} performs; \cref{ssec:eval-latency} shows that the
complete five-step chain, including that signature, costs $\approx$\SI{128}{\micro\second}. The cost
of the granularity is instead the number of directory writes. \Cref{tab:eval-modes} reports the write
counts over a conversation of $E$ hourly epochs, with a signed-pre-key rotation every 30 days
($R=720$).

neither path gains an artificial edge from skipping the label-binding check.

First, the implemented (VRF-indexed) lookup proof is at \emph{size parity} with CONIKS at matched

and the raw dual-index lookup used elsewhere in DUET carries no VRF proof and is correspondingly
smaller. CONIKS publishes \num{1216}\,bytes at $N = 2^{32}$; instantiating CONIKS's own per-lookup accounting
(one \num{32}-byte hash per tree level plus one, a \num{96}-byte VRF proof, and the \num{64}-byte
signed-tree-root signature~\cite[\S5.3, Table~1]{melara2015coniks}) at $N = 10^6$ gives
$32 \cdot 21 + 96 + 64 = 832$\,bytes, a figure we derive; the paper itself states no number at
$10^6$. Our measured median at the same $N$ is \num{817}\,bytes. The two accountings differ in one
respect: CONIKS counts its \num{64}-byte signature inside each proof, whereas our signed tree head is
transmitted once per epoch rather than inside each lookup proof. Parity holds under either
convention: \num{817} versus \num{832}\,bytes with the signature counted on CONIKS's side, or
\num{817} versus \num{768}\,bytes with it excluded from both. Both of our medians also sit
\num{22}--33\% under CONIKS's published \num{1216}-byte figure (\num{817}\,bytes at $10^6$ is 33\%
under it; \num{945}\,bytes at $10^7$ is 22\% under it), and our proof, unlike CONIKS's, carries the
automatic-detection mechanism of \cref{sec:design-dual} at no additional size.

Second, the proof is roughly $9\times$ smaller than Signal's deployed wire format
($8192/945 = 8.7\times$ at our $10^7$ median; $8192/817 = 10.0\times$ at $10^6$). This is a
verified property of the deployed code, not an estimate: Signal's key-transparency server pads every
prefix proof to the full \num{256}-sibling copath with seed-derived stand-in hashes, and its verifier
(\texttt{evaluateProof} in \texttt{tree/prefix/verify.go}) rejects any proof that does not contain
exactly \num{256} siblings of \num{32}\,bytes each~\cite{signal-kt-server}. The padding is a
deliberate trade of bandwidth for the hiding of tree density, which our \num{32}-byte bitmap instead
reveals; the comparison is therefore $\sim$$9\times$ bandwidth in exchange for
$\sim\lceil\lg N\rceil$ bits of density metadata. SEEMless's measured $\approx$8.6\,kB lookup proofs
at $10^7$~\cite[p.~12]{chase2019seemless} confirm that both deployed-lineage systems ship $\sim$8\,kB
proofs.

Third, offline catch-up at $W = 720$ costs \num{320}\,bytes against approximately \num{530}\,kB for
CONIKS-style per-epoch monitoring over the same window. The \num{530}\,kB figure is derived from
CONIKS's published per-epoch monitoring proof of $\approx$\num{736}\,bytes~\cite[Table~1]{melara2015coniks}:
$720 \times 736 = 529{,}920$\,bytes, equivalently thirty times its published \num{17.6}\,kB daily
cost. The per-epoch figure assumes CONIKS's own parameterization ($\approx 2^{21}$ directory changes
per epoch at $N \approx 2^{32}$), so the derived total is indicative rather than exact; under any
plausible churn it remains over three orders of magnitude larger than the windowed proof
($529{,}920/320 \approx 1{,}656\times$).

Fourth, full client verification stays below \SI{150}{\micro\second} through $10^7$ labels. CONIKS
reports \SI{159}{\micro\second} to verify the authentication path at $N = 10^7$ and approximately
\SI{400}{\micro\second} to verify the signed-tree-root signature, and reports no VRF-verification
time~\cite[\S5.3]{melara2015coniks}; the total of \SI{559}{\micro\second} is our sum of their two
published figures. The comparison must be taken at matched scale, so it is our $10^7$ median of
\SI{147.1}{\micro\second} that belongs beside it, not the $\approx$\SI{128}{\micro\second} we measure
at $N \le 10^4$: our figure is therefore about $3.8\times$ lower while covering a strictly larger
check, since it \emph{includes} the VRF verification that CONIKS's figures omit, in addition to the
signature verification that both totals include. Because the two measurements come from different
hardware (CONIKS's 2015 2\,GHz laptop CPU against our 2022 mobile CPU; see the comparability note),
the $3.8\times$ factor is indicative only; the claim that stands on our hardware alone is the
sub-\SI{150}{\micro\second} median cost of the full five-step chain across the whole measured range.

Xeon through to 2023 cloud instances), different scales ($10^6$ versus $2^{32}$), and database-backed

proof-verified \emph{absence} of the warning, is a strong indication of compromise. Deleting a
warning \emph{after} it commits is tampering rather than censorship, and is separately closed by the
write-once policy, the per-epoch transition audit, and the writer's persistence evidence.)

\subsection{Residual Risks and Posture}\label{ssec:eval-posture}

The overall posture follows from the preceding artefacts. The marginal in-memory warning-slot read
costs tens of microseconds of client work; end-to-end detection latency, which additionally requires
the verified lookups, network transport, monitor polling, and epoch timing that M5 does not measure,
was not quantified. No false alarms were observed over
\num{1000} clean deterministic sessions, so the warning channel raised no spurious alarms in that run. The residual
risks of \cref{ssec:eval-stride} are one semi-trusted-server limitation (the label$\leftrightarrow$user
mapping, outside what any transparency layer removes) and three availability functions left to a
production deployment. This is the gap the design set out to close: where the deployed WhatsApp
AKD ships with client key-history monitoring not yet enabled and directs the user to verify the
session \emph{manually} with the contact when an automatic check fails~\cite[pp.~5,
10]{whatsapp2023whitepaper}, and where unprompted users rarely locate and complete such a manual
ceremony (\cref{ssec:eval-detection}), DUET delivers the same detection in-band and without user
action.

\section{Implications for Deployment}\label{sec:eval-deploy}

The measurements above bear directly on whether a design of this kind could be adopted by a
production messenger such as Signal, whose own key-transparency server this work was built
against~\cite{signal-kt-server}. This section draws out those implications as measured comparisons
with their caveats attached, not as recommendations.

On the client, the cost is small and grows far more slowly than the service. Full verification is
$\approx$\SI{128}{\micro\second} at $N\le10^4$ and \SI{147.1}{\micro\second} at $10^7$
(\cref{ssec:eval-latency,ssec:eval-scale}),
and a lookup proof is \num{817}\,bytes median at $10^6$ labels (\cref{ssec:eval-scale}): at parity
with CONIKS and roughly $9\times$ smaller than Signal's deployed, density-hiding wire format
(\cref{sec:eval-compare}). A client offline for a month catches up in a single \num{320}\,byte proof
rather than the approximately \num{222}\,kB that one-proof-per-epoch verification costs over the same
window (\cref{ssec:eval-catchup}); for comparison, CONIKS's published per-epoch monitoring costs
imply approximately \num{530}\,kB for the same month (\cref{sec:eval-compare}). This matters most for
the intermittently connected mobile clients a messenger must serve. The per-conversation overhead a
deployment pays is therefore microseconds of client work and a few hundred bytes of bandwidth, in
exchange for automatic in-band detection that replaces a manual ceremony which, as
\cref{ssec:eval-detection} records, only about 14\% of unprompted users locate and
complete~\cite{vaziripour2017}.

On the server, the picture is more qualified, and the qualifications are exactly what a production
deployment would have to engineer away. Two costs stand out. First, the epoch commit is the one
operation that grows with $N$ ($\approx O(N)$, \SI{5.92}{\milli\second} at $10^4$,
\cref{ssec:eval-throughput}), because the current server deep-clones its committed snapshot; a
copy-on-write tree would reduce this to $O(\lg N)$ and is the single most valuable server-side change.
Second, the per-lookup and per-rotation VRF prove (\SI{117.4}{\micro\second} measured in isolation,
\cref{tab:bench-maint}) dominates those
paths only because the benchmark re-evaluates the VRF for an unchanged identifier; a deployed server
would cache the label and pay it once. Beyond compute, the scale run exposes the memory limit: a
$10^7$-label tree leaves a $\approx$\num{20.8}\,GB resident set on one machine (\cref{ssec:eval-scale}), so a real
deployment must move to the persistent, sharded storage of the SEEMless--Parakeet lineage that this
in-memory prototype deliberately does not model.

Finally, the two operating modes bound the deployment choice rather than forcing it. Session mode is
the deployable default (one directory write per signed-pre-key rotation, at parity with existing
key-transparency systems) while continuous mode offers finer-grained, ACKA CEA-style detection at a
write amplification of $\approx 720\times$ under the hourly-epoch benchmark model. The ratio scales
with ratchet cadence rather than sitting at a fixed cap (\cref{ssec:eval-modes}). The measured
verification path meets the latency target, but the $O(N)$ epoch commit, the memory footprint,
persistence, and networked operation remain deployment limitations rather than solved problems.
Before a design of this kind could ship it would need the engineering work stated plainly in
\cref{ch:discussion}: authenticated writes on the directory API, persistent sharded storage, and
closing the operator's label$\leftrightarrow$user query-privacy residual (\cref{ssec:eval-stride})
with an oblivious lookup. The numbers above show the cryptographic core is within a deployable
budget, while these items remain open.
