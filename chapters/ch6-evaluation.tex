\chapter{Evaluation}\label{ch:eval}

This chapter evaluates the system implemented in \cref{ch:impl} against the goals and threats of
\cref{ch:threat}. It sets out the measurement methodology and baselines (\cref{sec:eval-method}),
reports the microbenchmarks for proof size, verification latency, catch-up bandwidth, and detection
(\cref{sec:eval-micro}), examines behaviour at scale together with the session-versus-continuous
mode trade (\cref{sec:eval-scale}), places the results beside prior key-transparency systems
(\cref{sec:eval-compare}), and finally evaluates the security of the system against the attack
taxonomy (\cref{sec:eval-security}). The headline findings are that the dual-index lookup proof is
at size parity with CONIKS while adding automatic detection, that offline catch-up is three orders
of magnitude cheaper than naïve monitoring, and that full client verification is sub-\SI{150}{\micro\second}
and independent of directory size.

% ============================================================================
\section{Methodology}\label{sec:eval-method}

In this section we describe what was measured, against which baselines, and on what apparatus, so
that every number that follows can be read against a fixed reference. This matters because the
value of a transparency system is not any single cost but the trade between proof size, verification
time, and the bandwidth a client must spend to stay synchronised.

The evaluation is organised around four questions, one per design claim, each stated so that it could
be falsified. \emph{Is detection free in proof size?} --- falsified if the dual-index proof were
materially larger than a single-index proof at the same $N$ (\cref{ssec:eval-sizes}). \emph{Is client
verification cheap and scale-independent?} --- falsified if the full-chain verify grew with $N$ or
exceeded the sub-millisecond target (\cref{ssec:eval-latency,ssec:eval-scale}). \emph{Is offline
catch-up independent of the offline window?} --- falsified if the windowed proof grew linearly with $W$
(\cref{ssec:eval-catchup}). \emph{Is substitution detected, with no false alarms?} --- falsified by any
missed attack in the adversarial suite or a non-zero clean-session false-positive rate
(\cref{ssec:eval-detection,sec:eval-security}). Each question is answered against the baselines below.

Measurements are grouped into thirteen metric families, \emph{M1}--\emph{M13}. Rather than define
them in prose, \cref{tab:eval-map} is the measurement map for the whole chapter: it states what each
metric measures, the baseline it is read against, and where it is reported. The reader can consult it
once and refer back, instead of holding thirteen definitions in mind. The metrics are numbered in the
order this chapter presents them (size, then latency, then bandwidth, then detection, then scale,
maintenance, and modes) which is the order the questions above are answered, not the order of the
benchmark harness that produces them.\footnote{The Rust harness (\cref{app:benchmarks}) emits the
same metric numbering, so each metric family reported here can be traced directly to the harness
group of the same name.}

Baselines are referred to by name throughout this chapter, and each name denotes the same
configuration wherever it appears: the \emph{no-KT floor} (a session
setup with no key transparency --- a single hash, the cost a deployment pays anyway), the
\emph{single-index} path (log-inclusion only), the \emph{dual-index} path (the prefix-tree lookup that
carries the warning slot), and the \emph{windowed} full scheme (dual-index plus windowed consistency
proofs). These form an ablation: the no-KT floor isolates the cost of key transparency at all,
single-index removes the dual-index warning, dual-index removes windowing, and windowed is the
complete client verification. Read together with the session-versus-continuous comparison (M13), they
let the contribution of each mechanism be attributed directly.

Timings are collected two ways. Criterion provides the confidence intervals and regression plots;
in parallel, a manual harness of \num{2000} timed iterations per operation records the median, the
95th percentile, and a 95\% confidence half-width to \texttt{results/rust\_benchmark\_timings.csv},
and it is the manual-harness medians that are quoted here (they carry less measurement overhead than
Criterion's per-iteration accounting). Proof sizes are computed exactly and are seed-deterministic,
so they carry no confidence interval; the scale figures (M7) are distributions over \num{1000}
random lookups per $N$. All runs use fixed cryptographic and sampling seeds and are reproducible by
the procedure of \cref{sec:impl-repro}; the full per-parameter tables, at the resolution the CSVs
record, are collected in \cref{app:benchmarks}. Timing medians are quoted in the body to one decimal
place ($0.1\,\si{\micro\second}$): finer precision would be spurious for a wall-clock median, and
sub-microsecond digits vary between runs (for example, the VRF-verify median reads
\SI{76.8}{\micro\second} in \cref{tab:eval-latency} and \SI{74.9}{\micro\second} in the separate
scale run of \cref{tab:eval-scale}). The isolated VRF rows of \cref{app:benchmarks} show the same
effect more strongly: measured late in the suite on a warm machine, they read
\SI{134.8}{\micro\second} (prove) and \SI{92.9}{\micro\second} (verify) against in-path figures of
$\approx$\SI{120}{\micro\second} (generation including the prove) and \SI{76.8}{\micro\second}
(verify); the in-path figures are the ones this chapter quotes.

Three limitations bound the interpretation of the numbers. First, the server is in-memory and
single-machine, so absolute latencies exclude the database and network costs a distributed
deployment would add. Second, every proof is measured on a single-epoch log, so the log-inclusion
component is \num{0}\,bytes; a deployed log of $E$ epochs adds $32\lceil\lg E\rceil$\,bytes to every
lookup proof. Third, the throughput figures are single-thread per-operation costs, not parallel
scaling. Cross-system numbers in \cref{sec:eval-compare} come from different hardware, scales, and
storage models and are treated as order-of-magnitude only.

\section{Microbenchmarks (M1--M6)}\label{sec:eval-micro}

In this section we report the core per-lookup costs on a directory of up to $10^6$ labels: how large
a proof is, how long it takes to produce and to check, how much bandwidth an offline client must
spend to catch up, and how quickly and reliably an attack is detected.

\subsection{Lookup proof size (M1)}\label{ssec:eval-sizes}

The size of a lookup proof determines the bandwidth cost of every key fetch, so it is the first
quantity to pin down. \Cref{tab:eval-sizes} reports the single-index and dual-index proof
sizes as the directory grows. Both scale as $\lceil\lg N\rceil$, exactly as the sparse-tree design
predicts (\cref{ssec:design-structures}).

The dual-index proof decomposes as a fixed \num{176}\,byte constant (an \num{80}\,byte
ECVRF proof (RFC~9381)~\cite{rfc9381} plus \num{96}\,bytes of metadata (a \num{32}\,byte bitmap,
leaf data, and depth)) on top of $32$ bytes per prefix hash, giving the closed form
\begin{equation}\label{eq:eval-proofsize}
  |\pi| \;=\; 32\lceil\lg N\rceil \;+\; 32\lceil\lg E\rceil \;+\; 176 \ \text{bytes},
\end{equation}
where the middle term is the log-inclusion cost a deployed $E$-epoch log adds. The logarithmic
scaling of \cref{eq:eval-proofsize} in $N$ is plotted in \cref{fig:eval-sizes-plot}. The $10^6$ row reads
\num{912}\,bytes because the single seeded leaf happens to sit at depth \num{23}; the distribution
median over \num{1000} random lookups at $10^6$ is \num{816}\,bytes (\cref{ssec:eval-scale}). We
therefore report the distribution median in the remainder of this chapter, since it reflects the
proof size a typical lookup incurs rather than the depth of one particular seeded leaf. Crucially,
the ECVRF proof and the warning slot add nothing beyond this
formula: \emph{automatic detection adds no proof-size overhead}.

\subsection{Generation and verification latency (M2, M3)}\label{ssec:eval-latency}

A proof that is small is of little use if it is slow to check on the client. \Cref{tab:eval-latency}
reports the server-side generation cost and the client-side verification cost, broken into the
prefix-root recompute, the VRF verify, and the full five-step chain of \cref{ssec:design-verify}.

\midrule
Server full search (gen, incl.\ VRF prove) & \SI{119.6}{\micro\second} & \SI{119.8}{\micro\second} & VRF-dominated, independent of $N$ \\
Prefix-root verify (client) & \SI{26.0}{\micro\second} & \SI{26.0}{\micro\second} & independent of $N$ \\

The most important result is the last row: full client verification (VRF label binding, value binding, prefix
root recompute, log inclusion, and the Ed25519 signed-tree-head signature) costs about
\SI{132}{\micro\second} and does not grow with the directory, because its two cost centres, the
prefix recompute (\SI{26}{\micro\second}) and the VRF verify (\SI{77}{\micro\second}), are both
$N$-independent: the first is a fixed \num{256}-level bitmap walk and the second is a constant-time
elliptic-curve operation. The system therefore meets its sub-millisecond client-verify target with
roughly sevenfold headroom, and does so while including the VRF verification that comparable systems
exclude from their reported figures. The server-side full search is likewise flat rather than
growing, and this is a direct consequence of the compressed-leaf chain memo (\cref{sec:impl-modules}).
Before that optimization, proof generation grew with directory depth --- from \SI{107}{\micro\second} to
\SI{159}{\micro\second} across $N=10^3$--$10^4$ --- because each non-inclusion co-path recomputed a
compressed leaf's \num{256}-level hash chain. Memoizing that chain top removes the $N$-dependent
component, leaving generation dominated by the constant-time VRF prove: it reads \SI{119.6}{\micro\second}
at $N=10^3$, \SI{119.8}{\micro\second} at $N=10^4$, and \SI{141.6}{\micro\second} at $N=10^7$
(\cref{ssec:eval-scale}) --- essentially independent of $N$, exactly like verification.

\subsection{Offline catch-up bandwidth (M4)}\label{ssec:eval-catchup}

The bandwidth a client spends after being offline is where the windowed-consistency contribution of
\cref{ssec:design-catchup} pays off. A naïve client verifies one consistency proof per missed epoch
(the sequential baseline) --- in the benchmark, $W$ separate proofs, each anchored to the current head
rather than chained epoch-to-epoch, at the same $O(W\log N)$ cost; the windowed client verifies a
single proof spanning the whole gap.
\Cref{tab:eval-catchup} reports both as the offline window $W$ grows. Because catch-up proofs are
taken over the epoch log, one leaf per epoch, their size is independent of the number of users
$N$; the table therefore holds for every $N$ measured.

sequential at $W=720$; both are Criterion medians over the log alone, which the prefix-tree
memoization does not touch). This directly addresses the monitoring-bandwidth problem that CONIKS lists as
an open extension.

\subsection{Detection latency and false positives (M5, M6)}\label{ssec:eval-detection}

Finally, we measure the detection mechanism itself: how fast a substitution is detected, and how
often a clean session is wrongly flagged. The detection check comprises the dual-index label
derivation --- pure HKDF, one extract and three expands, independent of directory size --- and an
unverified read of the warning slot. The read's underlying cost is \emph{data-dependent}: the
co-path of a non-inclusion proof almost always meets a compressed leaf, whose subtree hash is a
chain of up to \num{256} hash evaluations. The implementation memoizes the top of that chain per
leaf (\cref{sec:impl-modules}), so the check costs a median \SI{1.6}{\micro\second} (95th percentile
\SI{2.2}{\micro\second}), independent of $N$; only the first touch of a cold leaf pays the full chain once, a worst case
bounded by the fixed tree depth rather than by $N$. The benchmark samples \num{1000} random
conversations and reports the distribution --- median and 95th percentile --- rather than any
single label's path,\footnote{An earlier revision of the harness timed one fixed conversation and,
before the chain memo, read \SI{1.4}{\micro\second} or ${\sim}$\SI{40}{\micro\second} depending on
where that one label happened to sit; a single-label figure is not robust, because re-seeding the
directory relocates every label.}
and a clean session and an attacked session are indistinguishable in cost, so detection leaks
nothing through timing. Either way, this is the \emph{marginal} cost of the warning-slot read on top
of a lookup the client already verifies; it is an unverified read, so the security-bearing detection
cost is that of the full verified chain the client runs regardless --- the \SI{26}{\micro\second}
prefix verify and the remainder of the \SI{132}{\micro\second} chain of \cref{ssec:eval-latency}. Over \num{1000} clean
sessions the false-positive rate (M6) is \num{0}; this is a sanity check rather than independent
evidence, since a spurious collision at a 256-bit HKDF-derived warning label is cryptographically
negligible. Detection is thus effectively free and silent, in sharp contrast to the manual
safety-number ceremony it replaces, which only about 14\% of users complete without
guidance~\cite{vaziripour2017}.

\section{Scalability and the mode trade (M7--M13)}\label{sec:eval-scale}

Having established per-lookup costs at moderate size, we now push the directory to production scale,
measure server-side throughput and maintenance costs, and quantify the price of the continuous
operating mode.

\subsection{Scale to CONIKS size (M7)}\label{ssec:eval-scale}

To show the design holds at deployment scale, the size and verification measurements were repeated at
$N=10^6$ and $N=10^7$ --- the latter the scale at which CONIKS reports its figures.
\Cref{tab:eval-scale} gives the distribution over \num{1000} random lookups per $N$.

The measured constancy of prefix verification across five orders of magnitude ($10^2$ to $10^7$) is
the empirical proof that verification is bounded by the fixed \num{256}-level tree height rather than
by $N$, and full client verification stays at $\approx$\SI{132}{\micro\second} at both $10^6$ and
$10^7$. The build-time and memory rows expose the single-machine limit: constructing a $10^7$-label
tree takes about 26 minutes and \SI{23.5}{\giga\byte} of RAM, which is why a production deployment would move to the
persistent, sharded storage this prototype deliberately does not model. $^{\dagger}$The $10^7$
full-search 95th percentile of \SI{2186}{\micro\second} --- against a \SI{142}{\micro\second} median ---
reflects this same memory pressure: as the \SI{23.5}{\giga\byte} working set approaches available RAM,
occasional lookups stall on page faults, a tail the deterministic proof structure does not itself
produce and that persistent storage would remove.

\subsection{Throughput, rotation, and epoch commit (M8--M11)}\label{ssec:eval-throughput}

Server-side maintenance costs decide how large a deployment one machine can sustain.
\Cref{tab:eval-server} collects them. Single-thread throughput is about \num{8340} lookups and
\num{6710} updates per second at $N=10^4$. Key rotation (overwriting an existing binding) costs
\SI{148.7}{\micro\second} at both $10^3$ and $10^4$ --- flat in $N$ for the same reason proof
generation is flat (\cref{ssec:eval-latency}), and dominated by the per-rotation VRF evaluation of
the unchanged user identifier, which a production server would cache, leaving only tens of
microseconds of tree work. The verifiable random function, measured in isolation, is constant-time
to prove and to verify, confirming its $N$-independence; its isolated rows in \cref{app:benchmarks}
read hotter than the in-path figures for the thermal reason noted in \cref{sec:eval-method}. The
per-handshake key-transparency overhead a deployment pays is exactly the
$\approx$\SI{132}{\micro\second} full client verify, against a no-KT floor of a single hash ---
microseconds of client work per conversation.

The one cost that does grow with $N$ is the epoch commit (\SI{465.6}{\micro\second} at $10^3$ rising to
\SI{5.80}{\milli\second} at $10^4$, a $\approx$$12\times$ increase for a $10\times$ growth, i.e.\ roughly

each leaf's chain memo, which is the deliberate space-for-time trade that makes reads flat
(\cref{sec:impl-modules}); a copy-on-write
tree would reduce it to $O(\lg N)$, and this is noted as future work in \cref{ch:discussion}.

\subsection{Auditor cost (M12)}\label{ssec:eval-auditor}

The cross-vantage auditor (\cref{sec:design-acka}) that detects split-view equivocation must be
cheap enough to run continuously. It is: a per-epoch audit, an Ed25519 signature verify plus an
append-only consistency check, costs \SI{28.3}{\micro\second} at $N=10^4$, and the cross-vantage
fork-detection check costs \SI{27.7}{\micro\second}. Both are under \SI{30}{\micro\second}, so the
equivocation-detection machinery is cheap per epoch in local computation. Two scoping caveats matter.
The audit figure times proof generation and verification together, so as a \emph{verify-only} cost it
is a conservative over-estimate; but it measures only the auditor's \emph{local} per-epoch work (the
signature check and the append-only consistency check). It
does \emph{not} include the networked, proof-carrying exchange a deployed auditor runs --- fetching
each epoch's disclosed update set together with the committed-root log-inclusion proof
(\cref{sec:design-acka}) and verifying that proof against the signed head --- whose transfer and
verification cost is not captured here. The number is therefore the compute floor of the audit, not
the end-to-end cost of the protocol.

\subsection{Session versus continuous mode (M13)}\label{ssec:eval-modes}

The design offers two operating modes (\cref{ssec:design-modes}): session mode writes one directory
entry per signed-pre-key rotation, and continuous mode writes one per ratchet epoch for finer-grained,
ACKA-faithful detection. The cost of that granularity is not verification time. A per-check operation
costs \SI{28.0}{\micro\second} in session mode and \SI{27.7}{\micro\second} in continuous mode (medians, \cref{tab:bench-repro}; both include
server-side proof generation, and are near-identical because the chain memoization flattens the compressed-leaf cost that previously separated them). Both
figures require a precise statement of what they measure: each benchmarked check comprises the
client-side label derivation, the server-side proof generation, and the client-side verification of
the value, prefix-root, and log-inclusion steps. Neither figure includes a VRF step, because the
dual-index and CEA paths use client-derived rather than VRF-derived labels
(\cref{ssec:design-verify}), and neither includes the signed-tree-head signature verification that
the full specified check of \cref{app:algorithms} performs; \cref{ssec:eval-latency} shows that the
complete five-step chain, including that signature, costs $\approx$\SI{132}{\micro\second}. The cost
of the granularity is instead the number of directory writes. \Cref{tab:eval-modes} reports the write
counts over a conversation of $E$ hourly epochs, with a signed-pre-key rotation every 30 days
($R=720$).

\begin{table}[ht]

\label{tab:eval-modes}
\small
\begin{tabular}{@{}lrrr@{}}
\toprule
$E$ (epochs) & Continuous (one/epoch) & Session (one/rotation) & Ratio \\

a conversation spans several rotations, session-mode writes tick up in proportion, so continuous mode

This bounds the deployment choice cleanly --- fine-grained detection is available, at a write-amplification
cost that is capped, not unbounded. One limitation applies: because real ratchet cadence is
message-driven rather than hourly, the continuous-mode write counts here are an under-count for a
chatty conversation.

Four claims follow from the comparison; for each cross-system figure we state explicitly whether it
is published or derived, and from what.

First, the dual-index lookup proof is at \emph{size parity} with CONIKS at matched directory size.
CONIKS publishes \num{1216}\,bytes at $N = 2^{32}$; instantiating CONIKS's own per-lookup accounting
(one \num{32}-byte hash per tree level plus one, a \num{96}-byte VRF proof, and the \num{64}-byte
signed-tree-root signature~\cite[\S5.3, Table~1]{melara2015coniks}) at $N = 10^6$ gives
$32 \cdot 21 + 96 + 64 = 832$\,bytes --- a figure we derive; the paper itself states no number at
$10^6$. Our measured median at the same $N$ is \num{816}\,bytes. The two accountings differ in one
respect: CONIKS counts its \num{64}-byte signature inside each proof, whereas our signed tree head is
transmitted once per epoch rather than inside each lookup proof. Parity holds under either
convention: \num{816} versus \num{832}\,bytes with the signature counted on CONIKS's side, or
\num{816} versus \num{768}\,bytes with it excluded from both. Both of our medians also sit
\num{22}--33\% under CONIKS's published \num{1216}-byte figure (\num{816}\,bytes at $10^6$ is 33\%
under it; \num{944}\,bytes at $10^7$ is 22\% under it), and our proof, unlike CONIKS's, carries the
automatic-detection machinery of \cref{sec:design-dual} at no additional size.

Second, the proof is roughly $9\times$ smaller than Signal's deployed wire format
($8192/944 = 8.7\times$ at our $10^7$ median; $8192/816 = 10.0\times$ at $10^6$). This is a
verified property of the deployed code, not an estimate: Signal's key-transparency server pads every
prefix proof to the full \num{256}-sibling copath with seed-derived stand-in hashes, and its verifier
(\texttt{evaluateProof} in \texttt{tree/prefix/verify.go}) rejects any proof that does not contain
exactly \num{256} siblings of \num{32}\,bytes each~\cite{signal-kt-server}. The padding is a
deliberate trade of bandwidth for the hiding of tree density, which our \num{32}-byte bitmap instead
reveals; the comparison is therefore $\sim$$9\times$ bandwidth in exchange for
$\sim\lceil\lg N\rceil$ bits of density metadata. SEEMless's measured $\approx$8.6\,kB lookup proofs
at $10^7$~\cite[p.~12]{chase2019seemless} confirm that both deployed-lineage systems ship $\sim$8\,kB
proofs.

Third, offline catch-up at $W = 720$ costs \num{320}\,bytes against approximately \num{530}\,kB for
CONIKS-style per-epoch monitoring over the same window. The \num{530}\,kB figure is derived from
CONIKS's published per-epoch monitoring proof of $\approx$\num{736}\,bytes~\cite[Table~1]{melara2015coniks}:
$720 \times 736 = 529{,}920$\,bytes, equivalently thirty times its published \num{17.6}\,kB daily
cost. The per-epoch figure assumes CONIKS's own parameterization ($\approx 2^{21}$ directory changes
per epoch at $N \approx 2^{32}$), so the derived total is indicative rather than exact; under any
plausible churn it remains over three orders of magnitude larger than the windowed proof
($529{,}920/320 \approx 1{,}656\times$).

Fourth, full client verification is $\approx$\SI{132}{\micro\second} and independent of $N$. CONIKS
reports \SI{159}{\micro\second} to verify the authentication path at $N = 10^7$ and approximately
\SI{400}{\micro\second} to verify the signed-tree-root signature, and reports no VRF-verification
time~\cite[\S5.3]{melara2015coniks}; the total of \SI{559}{\micro\second} is our sum of their two
published figures. Our figure is therefore about $4.2\times$ lower while covering a strictly larger
check: it \emph{includes} the VRF verification that CONIKS's figures omit, in addition to the
signature verification that both totals include. Because the two measurements come from different
hardware (CONIKS's 2015 2\,GHz laptop CPU against our 2022 mobile CPU; see the comparability note),
the $4.2\times$ factor is indicative only; the claims that stand on our hardware alone are the
sub-\SI{150}{\micro\second} cost of the full five-step chain and its measured independence of $N$.

\begin{quote}\small\noindent\textbf{Comparability note.} Published numbers come from different hardware (a 2015
Xeon through to 2023 cloud instances), different scales ($10^6$ versus $2^{32}$), and database-backed
versus in-memory implementations. All cross-system figures are order-of-magnitude; our own benchmarks
are single-machine and in-memory (\cref{sec:eval-method}).\end{quote}

Spoofing, tampering, repudiation, and elevation of privilege are closed cryptographically --- ECVRF

only operational rate limiting blunts (a denial-of-service residual); an operator that withholds
epochs or writes is caught by auditor timeouts and the compound signal of A2, at the cost of
delayed detection. Both residuals are acknowledged by the standard key-transparency literature and
neither is addressed by ACKA~\cite{dowling2023acka}, which abstracts the log behind a security definition rather than realising a distrusted one; they bound what
transparency can offer rather than revealing a flaw in this construction.

\subsection{Residual risks and posture}\label{ssec:eval-posture}

The overall posture follows from the preceding artefacts. Detection is automatic and fast (tens of
microseconds of client work, a verdict within one to two epochs) and the false-positive rate over
\num{1000} clean sessions is \num{0}, so the warning channel raises no spurious alarms. The residual
risks are the two semi-trusted-server limitations of \cref{ssec:eval-stride}, both outside what any
transparency layer removes. This is the gap the design set out to close: where the deployed WhatsApp
AKD ships with client key-history monitoring not yet enabled and directs the user to verify the
session \emph{manually} with the contact when an automatic check fails~\cite[pp.~5,
10]{whatsapp2023whitepaper}, and where unprompted users rarely locate and complete such a manual
ceremony (\cref{ssec:eval-detection}), DUET delivers the same detection in-band and without user
action.

\section{Implications for deployment}\label{sec:eval-deploy}

The measurements above bear directly on whether a design of this kind could be adopted by a
production messenger such as Signal, whose own key-transparency server this work was built
against~\cite{signal-kt-server}. This section draws out those implications as measured comparisons
with their caveats attached, not as recommendations.

On the client, the cost is small and does not grow with the service. Full verification is
$\approx$\SI{132}{\micro\second} and independent of $N$ (\cref{ssec:eval-latency,ssec:eval-scale}),
and a lookup proof is \num{816}\,bytes median at $10^6$ labels (\cref{ssec:eval-scale}) --- at parity
with CONIKS and roughly $9\times$ smaller than Signal's deployed, density-hiding wire format
(\cref{sec:eval-compare}). A client offline for a month catches up in a single \num{320}\,byte proof
rather than the approximately \num{222}\,kB that one-proof-per-epoch verification costs over the same
window (\cref{ssec:eval-catchup}); for comparison, CONIKS's published per-epoch monitoring costs
imply approximately \num{530}\,kB for the same month (\cref{sec:eval-compare}). This matters most for
the intermittently connected mobile clients a messenger must serve. The per-conversation overhead a
deployment pays is therefore microseconds of client work and a few hundred bytes of bandwidth, in
exchange for automatic in-band detection that replaces a manual ceremony which, as
\cref{ssec:eval-detection} records, only about 14\% of unprompted users locate and
complete~\cite{vaziripour2017}.

On the server, the picture is more qualified, and the qualifications are exactly what a production
deployment would have to engineer away. Two costs stand out. First, the epoch commit is the one
operation that grows with $N$ ($\approx O(N)$, \SI{5.80}{\milli\second} at $10^4$,
\cref{ssec:eval-throughput}), because the current server deep-clones its committed snapshot; a
copy-on-write tree would reduce this to $O(\lg N)$ and is the single most valuable server-side change.
Second, the per-lookup and per-rotation VRF prove ($\approx$\SI{106}{\micro\second}) dominates those
paths only because the benchmark re-evaluates the VRF for an unchanged identifier; a deployed server
would cache the label and pay it once. Beyond compute, the scale run exposes the memory limit: a
$10^7$-label tree needs $\approx$\num{23.5}\,GB on one machine (\cref{ssec:eval-scale}), so a real
deployment must move to the persistent, sharded storage of the SEEMless--Parakeet lineage that this
in-memory prototype deliberately does not model.

Finally, the two operating modes bound the deployment choice rather than forcing it. Session mode is
the deployable default (one directory write per signed-pre-key rotation, at parity with existing
key-transparency systems) while continuous mode offers finer-grained, ACKA-faithful detection at a
write amplification that is capped at $\approx 720\times$, not unbounded (\cref{ssec:eval-modes}). What
remains before a design of this kind could ship is not performance but three engineering gaps stated
plainly in \cref{ch:discussion}: authenticated writes on the directory API, persistent sharded
storage, and closing the operator's label$\leftrightarrow$user query-privacy residual
(\cref{ssec:eval-stride}) with an oblivious lookup. These are implementation questions, not
limitations of the measured design; the numbers above show the cryptographic core is comfortably
within a deployable budget.
