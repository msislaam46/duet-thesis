\chapter{Evaluation}\label{ch:eval}

This chapter evaluates the system implemented in \cref{ch:impl} against the goals and threats of
\cref{ch:threat}. It sets out the measurement methodology and baselines (\cref{sec:eval-method}),
reports the microbenchmarks for proof size, verification latency, catch-up bandwidth, and detection
(\cref{sec:eval-micro}), examines behaviour at scale together with the session-versus-continuous
mode trade (\cref{sec:eval-scale}), places the results beside prior key-transparency systems
(\cref{sec:eval-compare}), and finally evaluates the security of the system against the attack
taxonomy (\cref{sec:eval-security}). The principal findings are four. First, the implemented VRF-indexed lookup proof is
at rough size parity with CONIKS. Second, detection is obtained through additional lookups
of the same shape rather than any enlargement of that proof. Third, offline catch-up needs one proof
rather than $W$ (\num{695}-fold fewer raw path-hash bytes at a one-month window against this
chapter's synthetic baseline). Finally, median full client verification stays below
\SI{150}{\micro\second} through $10^7$ labels and grows far more slowly than $N$.

\section{Methodology}\label{sec:eval-method}

This section sets out what was measured, against which baselines, and on what apparatus, so
that every number that follows can be read against a fixed reference. This matters because the
value of a transparency system is not any single cost but the trade between proof size, verification
time, and the bandwidth a client must spend to stay synchronized.

The evaluation is organized around four questions, one per design claim, each stated so that it could
be tested. \emph{Does detection change individual proof size?} This separates into three claims.
\emph{Structurally}, the warning check is a separate lookup that reuses the same prefix-tree and
log-proof structure as a key lookup (without the VRF component), so enabling detection changes neither
the format nor the size of any single lookup proof; falsified if turning detection on enlarged or
restructured an individual proof. \emph{Empirically}, the measured VRF-indexed lookup is close in size
to the like-for-like VRF-indexed baseline (CONIKS), \num{817} against \num{768} derived bytes at
$N=10^6$ (a \num{6.4}\% difference), rather than to a non-VRF single-index log, which is necessarily
smaller by the VRF proof; this cross-paper comparison (\cref{sec:eval-compare}; \cref{ssec:eval-sizes}
separates the single-index and VRF-indexed components of the proof size) is descriptive, not a falsification criterion.
\emph{Operationally}, detection's cost is in requests and writes, not proof bytes. The request count
is source-verified from the isolated in-process \texttt{KTClient.detectMitm} helper: every check
performs one label-bound owner-slot lookup and, only when that slot verifies (matching the client's
key, or verifiably empty on first registration), a second label-bound warning-slot lookup, so a check
costs one or two raw-label lookups (two on the clean, first-registration, and warning-carrying paths,
one when the owner slot already shows substitution), plus one directory write per ratchet epoch in
continuous mode. The latency of those verified lookups is measured directly by the detector-branch
benchmark (M16, \cref{ssec:eval-detection}), which times each branch as the security-bearing verified
operation rather than the earlier unverified read; the continuous-mode write and per-epoch
verification trade is measured by M13 and M15. \emph{Does client verification remain inexpensive as
the directory grows?} Falsified if full client verification grew in
proportion to $N$, or exceeded the sub-millisecond target (\cref{ssec:eval-latency,ssec:eval-scale}).
\emph{Can an offline client re-synchronize in a single proof, rather than one per missed epoch?}
Falsified if the windowed client still had to fetch a proof per epoch, or if that single proof's size
grew linearly with $W$ (\cref{ssec:eval-catchup}). \emph{Is substitution detected?} Falsified by any
missed attack in the enumerated adversarial suite; separately, every enumerated clean-session workflow
is checked to produce the expected non-alarm verdict (M17, a coverage check rather than a rate)
(\cref{ssec:eval-detection,sec:eval-security}). Each question is answered against the baselines below.

them in prose, \cref{tab:eval-map} is the measurement map for the whole chapter: it states what each

Baselines are referred to by name throughout this chapter, and each name denotes the same
configuration wherever it appears: the \emph{single-index} path (log-inclusion only), the
\emph{dual-index} path (the prefix-tree lookup that carries the warning slot), and the \emph{windowed}
full scheme (dual-index plus windowed consistency proofs). These are benchmark configurations rather
than a full mechanism-level ablation: single-index is a plain log inclusion, dual-index is the
prefix-tree lookup, and windowed adds windowed consistency. One further reference point, the
\emph{no-KT floor} (a synthetic identity-hash comparison standing in for session setup without key
transparency), is used only by the handshake-hook microbenchmark M11 (\cref{ssec:eval-throughput}) and
is a synthetic local comparison, not a mechanism-level baseline. In the size, latency, and rotation
families the dual-index configuration is measured through the \emph{VRF-indexed}
\texttt{search\_by\_user\_id} lookup the client actually runs (recorded under the harness's historical
label \texttt{dual\_index}), which carries an \num{80}-byte VRF proof that the raw
\texttt{search(label)} path omits; the tables therefore report it as the VRF-indexed lookup, the
like-for-like counterpart to CONIKS. This configuration measures the identity-lookup proof, not the
raw dual-index warning path: the warning mechanism's own detector cost is exercised separately by the
detector-branch benchmark (M16), and the session-versus-continuous write trade by M13 and M15. The configurations thus
bound each cost rather than attributing a clean mechanism-level contribution.

Timings are collected two ways. Criterion provides bootstrap confidence intervals and regression
plots in its own reports; in parallel, a manual harness of \num{2000} timed iterations per operation
records the median and the 95th percentile, from sequential in-process iterations (no randomized
interleaving), to \texttt{results/rust\_benchmark\_timings.csv}. The thesis reports the median and,
where the tail matters, the 95th percentile; both are descriptive sample statistics, quoted without a
confidence interval, and no inference about the precision of a mean is drawn from them. Where a timing
falls near the platform's timer resolution (the sub-microsecond M4 windowed generation figures,
\SIrange{0.1}{0.3}{\micro\second}), it is a coarse hot-path observation and is treated as one. Proof
sizes are computed exactly and are seed-deterministic; the scale figures (M7) are distributions over
\num{1000} random lookups per $N$. All runs use fixed cryptographic and sampling seeds and are reproducible by
the procedure of \cref{sec:impl-repro}; the full per-parameter tables, at the resolution the CSVs
record, are reported in \cref{app:benchmarks}
(\cref{tab:bench-env,tab:bench-m1,tab:bench-m4,tab:bench-latency,tab:bench-detection,tab:bench-maint,tab:bench-auditor,tab:bench-scale,tab:bench-modes,tab:bench-repro}). Timing medians are quoted in the body to one decimal
place ($0.1\,\si{\micro\second}$): finer precision would be spurious for a wall-clock median, and
sub-microsecond digits vary between runs (for example, the VRF-verify median reads
\SI{76.0}{\micro\second} in \cref{tab:eval-latency} and \SI{81.5}{\micro\second} in the separate
scale run of \cref{tab:eval-scale}). The isolated VRF rows of \cref{app:benchmarks} show the same
sensitivity more strongly, and in both directions: isolated verify reads
\SI{78.5}{\micro\second} against an in-path \SI{76.0}{\micro\second}, while isolated prove reads
\SI{117.4}{\micro\second} against a prove-inclusive in-path generation of
\SI{119.5}{\micro\second}. The isolated figure is therefore the slower one for verify and the faster one
for prove. Measuring the same primitive in a different benchmark context, and at a different point in
the run order, therefore shifts it by a few percent in whichever direction; the harness records
execution times but no clock-frequency, power, or temperature telemetry, so this is reported as
context and run-order sensitivity without attributing it to a mechanism. The in-path figures are the
ones this chapter quotes, since they are the cost a client actually pays.

Three limitations bound the interpretation of the numbers. First, the server is in-memory and
single-machine, so absolute latencies exclude the database and network costs a distributed
deployment would add. Second, the single-epoch microbenchmarks of \cref{sec:eval-micro} carry a
\num{0}-byte log-inclusion component by construction; the history-depth sweep (M14,
\cref{ssec:eval-sizes}) measures how a deployed log of $E$ epochs adds its log-inclusion path,
confirming the $32\lceil\lg E\rceil$-byte growth the single-epoch figures would otherwise only
predict. Third, the operation-rate figures are single-thread per-operation costs, not parallel
scaling. Cross-system numbers in \cref{sec:eval-compare} come from different hardware, scales, and
storage models and are treated as order-of-magnitude only.

\section{Microbenchmarks}\label{sec:eval-micro}

This section reports the core per-lookup costs on a directory of up to $10^6$ labels: how large
a proof is, how long it takes to produce and to check, how much bandwidth an offline client must
spend to catch up, and how quickly and reliably an attack is detected.

\subsection{Lookup Proof Size and History Depth (M1, M14)}\label{ssec:eval-sizes}

The size of a lookup proof determines the bandwidth cost of every key fetch, so it is the first
quantity to pin down. \Cref{tab:eval-sizes} reports two measured objects as the directory grows: the
implemented (VRF-indexed) DUET lookup proof, which bundles a prefix proof, an 80-byte VRF proof, and a
log-inclusion component, and, as a reference point, a dense Merkle-log inclusion proof over $N$ user
entries. The table therefore compares the implemented VRF-indexed lookup against a plain log
inclusion at the same $N$; it is not a measurement of the raw dual-index path (which calls
\texttt{search(label)} and carries no VRF proof) and it does not isolate a like-for-like single-
versus dual-index directory overhead. Each row is one seed-deterministic path; M7
(\cref{ssec:eval-scale}) supplies the sampled distribution. A prefix proof carries one hash per
non-empty sibling on the label's path, whose number $h$ has expected value $\approx\lceil\lg N\rceil$,
so both objects grow logarithmically in $N$ as the sparse-tree design predicts
(\cref{ssec:design-structures}).

The VRF-indexed lookup proof decomposes as a fixed \num{177}\,byte constant (an \num{80}\,byte
ECVRF proof (RFC~9381)~\cite{rfc9381} plus \num{97}\,bytes of metadata: a \num{32}\,byte label, a
\num{32}\,byte value, a \num{1}\,byte leaf-kind commitment (\cref{ssec:design-detection}), and a
\num{32}\,byte sibling bitmap) on
top of $32$ bytes per prefix hash, giving
\begin{equation}\label{eq:eval-proofsize}
  |\pi| \;=\; 32h \;+\; 32h_{\mathrm{log}} \;+\; 177 \ \text{bytes},
  \qquad \mathbb{E}[h]\approx\lceil\lg N\rceil,\quad h_{\mathrm{log}}\le\lceil\lg E\rceil,
\end{equation}
where $h$ is the number of non-empty siblings on the queried label's path (the ``VRF prefix
hashes'' column of \cref{tab:eval-sizes}) and $h_{\mathrm{log}}$ is the length of the current root's
log-inclusion path. Because the current directory root is always the \emph{last} log leaf (the
currency pin, \cref{ssec:design-verify}), $h_{\mathrm{log}}$ is the number of complete subtrees to its
left: $\mathrm{popcount}(E-1)$, at most $\lceil\lg E\rceil$ and often smaller (one hash at $E=5$,
not three). Raw-label warning responses omit the \num{80}-byte VRF component, and their value field
varies with the stored warning-payload length, so this fixed constant applies to the key-lookup shape,
not to every response. The $O(\lg N + \lg E)$ scaling of \cref{eq:eval-proofsize} is plotted in
\cref{fig:eval-sizes-plot}. The $10^6$ row reads \num{913}\,bytes because the single seeded leaf's
path carries $h=\num{23}$ non-empty siblings; the distribution median over \num{1000} random lookups
at $10^6$ is \num{817}\,bytes (\cref{ssec:eval-scale}). The distribution median is
therefore reported in the remainder of this chapter, since it reflects the
proof size a typical lookup incurs rather than the depth of one particular seeded leaf. The
ECVRF proof and the warning slot add nothing beyond this
formula: \emph{the dual-index detection mechanism does not enlarge the per-lookup proof} (a warning
check is a second lookup of the same shape, not a larger proof).

The history term $32\,h_{\mathrm{log}}$ of \cref{eq:eval-proofsize}, zero on the single-epoch
microbenchmark log, is measured directly by the history-depth sweep (M14). Holding the directory at
$N$ and growing the committed log through $E\in\{1,16,256,1024\}$ epochs, the observed log-inclusion
path is $h_{\mathrm{log}}=\{0,4,8,10\}$ hashes---exactly $\lceil\lg E\rceil$ at these powers of two,
where $\mathrm{popcount}(E-1)$ attains its maximum---so the serialized proof grows by
$\{0,128,256,320\}$\,bytes on top of the directory-path component. The sweep runs at both $N=10^3$ and
$N=10^4$ and the two axes add independently (\cref{app:benchmarks}), so proof size grows
logarithmically in both directory size and history depth, now measured rather than derived from
\cref{eq:eval-proofsize}. The single-epoch convention used for the CONIKS size comparison
(\cref{sec:eval-compare}) is unchanged; M14 supplies the deployed history term that the convention sets
aside, and does not replace the convention-matched headline figure.

M3, the last row, measures the complete signed-head lookup-verification path, also called full
client verification: VRF label binding, value binding, prefix-root recomputation, log inclusion, and
verification of the Ed25519-signed tree head. Its median cost is about
\SI{128}{\micro\second} over the measured $10^3$--$10^4$ range and grows only weakly with the
directory (\cref{ssec:eval-scale}): its dominant cost centre, the VRF verify (\SI{76.0}{\micro\second}),
is an elliptic-curve operation whose cost is independent of directory size, and the prefix recompute (\SI{25.9}{\micro\second}) grows
only with proof depth ($\sim\lg N$). The system therefore meets its sub-millisecond client-verify target with
roughly sevenfold headroom, and does so while including the VRF verification that comparable systems
exclude from their reported figures. The server-side full search is likewise near-flat over this
range, and this is a direct consequence of the compressed-leaf chain memo (\cref{sec:impl-modules}).
Before that optimization, proof generation grew with directory depth (from \SI{107}{\micro\second} to
\SI{159}{\micro\second} across $N=10^3$--$10^4$) because each non-inclusion co-path recomputed a
compressed leaf's \num{256}-level hash chain. Memoizing that chain top removes the $N$-dependent
component, leaving generation dominated by the fixed-cost VRF prove: it reads \SI{119.5}{\micro\second}
at $N=10^3$ and \SI{119.7}{\micro\second} at $N=10^4$, while the scale run's search median reads
\SI{117.6}{\micro\second} at $N=10^6$ and \SI{141.2}{\micro\second} at $N=10^7$
(\cref{ssec:eval-scale}): flat through $10^6$, then rising at $10^7$. Verification shows the same
shape. Two factors sit behind the rise, the wider proof at larger $N$ and the change of measurement
context between the moderate-scale and scale-up harnesses.

\subsection{Offline Catch-Up Bandwidth (M4)}\label{ssec:eval-catchup}

The bandwidth a client spends after being offline is where the windowed-consistency policy of
\cref{ssec:design-catchup} yields its largest saving over a repeated-proof workload. The baseline
here is synthetic: it re-fetches one current-head-anchored consistency proof for each of the $W$
missed epochs. The windowed client instead verifies a single distant-head proof spanning the whole
gap, which standard RFC~9162 already supports directly; the saving is therefore in the number of
proofs a monitoring policy chooses to fetch, not a cost RFC~9162 forces on an offline client.
\Cref{tab:eval-catchup} reports both as the offline window $W$ grows. Because catch-up proofs are
taken over the epoch log, one leaf per epoch, their size is independent of the number of users
$N$; the table therefore holds for every $N$ measured.

Two properties of the comparison bound what the ratio means. First, the baseline is \emph{synthetic}: the harness issues $W$ current-head-anchored
consistency proofs, which models a client that re-fetches a fresh proof against the latest head on
each of $W$ occasions.\footnote{It is one baseline among several, not the cost of generic sequential
catch-up. A client verifying adjacent $e \to e+1$ transitions is an equally reasonable naïve
strategy, and its per-proof size is smaller, so the \num{695}-fold constant is specific to this
construction. What does not depend on the choice is the proof \emph{count}: $O(1)$ against $O(W)$.}
Second, the byte figures are \emph{raw consistency-path hash bytes}: the harness counts path
length times the \num{32}-byte hash size. A deployment serializes these (the reference server sends
hex-encoded JSON with framing and length fields), so serialized network bandwidth was not measured
and would be larger on both sides of the comparison.

The saving grows approximately linearly with the window (measured $\approx 0.97\,W$), as \cref{fig:eval-catchup-plot}
makes visible on a log axis. A client offline for a month
sends a \num{320}\,byte proof in place of \num{222528}\,bytes, a \num{695}-fold reduction, and the
generation-time counterpart is similar in magnitude (\SI{0.3}{\micro\second} windowed versus
\SI{184.8}{\micro\second} sequential at $W=720$: medians over the log alone, which the prefix-tree
memoization does not touch). The two ratios are separate measurements.
The \num{695}-fold figure is a computed count of raw path-hash bytes, whereas the generation-time figure is timed,
and the windowed median sits at the \SI{0.1}{\micro\second} resolution this chapter quotes to, so
their quotient is good to only a couple of significant figures ($\approx$\num{600}-fold). One windowed
proof thus replaces the $W$ per-epoch proofs, directly addressing the monitoring-bandwidth problem that CONIKS lists as
an open extension.

\subsection{Detector-Branch Latency and Clean-Session Coverage (M16, M17)}\label{ssec:eval-detection}

Finally, the evaluation measures the cost of the detector itself and confirms that it does not fire on
honest sessions. The isolated in-process \texttt{KTClient.detectMitm} helper (\cref{sec:impl-signal})
takes one of two branches, and M16 times each as the security-bearing \emph{verified} operation, using
the raw-label verifier (the prefix-tree and log path checked \emph{without} the VRF component, since
the VRF-indexed path is what M3 already times). On the \emph{early-return} branch a present owner slot
already shows a substituted key, so one verified owner-slot lookup settles the verdict, at a median
\SI{28.3}{\micro\second} (95th percentile \SI{30.2}{\micro\second}) at $N=10^4$. On the
\emph{clean-matching} branch the owner slot verifies against the client's key and the check proceeds to
a verified \emph{non-inclusion} of the warning slot---an unproven ``empty'' would let the server censor
the warning---costing a median \SI{31.9}{\micro\second} (95th percentile \SI{39.1}{\micro\second}) for
the two verified lookups. These are local, in-process component costs: they exclude the TypeScript
runtime, HTTP transport, background polling, and registration, and they exclude the network round-trips
a deployment adds, so this thesis does not report an end-to-end detection latency.

Measuring the verified branch directly retires an earlier scoping caveat. The superseded M5 figure
timed only one \emph{unverified} warning-slot read (a median \SI{1.6}{\micro\second}), a
verification-free lower bound that was explicitly not a detector-latency measurement; that row is
retained in \cref{app:benchmarks} for provenance but no longer carries a headline. The warning-slot
step is the same non-inclusion co-path whose cost is data-dependent: it almost always meets a
compressed leaf whose subtree hash is a chain of up to \num{256} evaluations, memoized per leaf
(\cref{sec:impl-modules}), so the benchmark samples \num{1000} conversations and reports the
distribution rather than one label's path.\footnote{An earlier revision timed one fixed conversation
and, before the chain memo, read \SI{1.4}{\micro\second} or ${\sim}$\SI{40}{\micro\second} depending on
where that one label sat; a single-label figure is not robust, because re-seeding the directory
relocates every label.} The request count is source-verified from the same helper: a present owner-slot
mismatch returns after the first lookup, while a matching or verifiably empty owner slot proceeds to
the warning-slot lookup, so the clean, first-registration, and warning-carrying paths perform two
verified lookups and the substituted path one. This count does not describe the complete networked
background-monitor pass, which performs registration and additional catch-up, owner-, peer-, and
warning-slot checks separately.

M17 turns the former clean-session false-positive rate into functional coverage. Every enumerated
honest state---a first registration into an empty owner slot, an established session with the expected
key, a proven-empty warning slot, repeated re-verification of a valid state, valid log growth under a
correct consistency proof, multiple honest continuous-mode epochs, and agreeing cross-vantage
heads---is asserted to produce the expected non-alarm verdict, rather than sampled for a rate. The
result is therefore a coverage statement: every enumerated clean workflow produced the expected
non-alarm verdict. This replaces the earlier ``zero false positives over \num{1000} sessions'' figure,
whose statistical framing added nothing a coverage check does not, a spurious collision at a
\num{256}-bit HKDF-derived warning label being cryptographically negligible in any case.

Detection runs automatically and requires no manual safety-number comparison, in contrast to the
ceremony it is designed to replace, which most users fail to complete without
guidance~\cite{vaziripour2017}. When it reports a problem, the prototype's advisory hook surfaces a
warning, although it does not yet block session establishment.

\subsection{Auditor Cost (M12)}\label{ssec:eval-auditor}

The cross-vantage auditor (\cref{sec:design-acka}) that detects split-view equivocation must be
cheap enough to run continuously. M12 measures only the auditor's \emph{local} append-only
verification kernel: an STH signature check, consistency-proof generation and verification, and a
fork check against \emph{one} observed head. The per-epoch audit costs \SI{28.5}{\micro\second}
median at $N=10^4$, and the fork check \SI{27.9}{\micro\second} median (p95 \SI{34.2}{\micro\second}),
so the kernel is cheap per epoch in local computation. Because the benchmark times proof generation
and verification together, it provides a conservative upper bound on verification alone. It excludes
network transfer, epoch-delta retrieval, committed-root inclusion verification, and the full
\texttt{audit\_epoch} transition replay, which re-applies every disclosed update into a candidate
replica rather than checking a signature and a consistency proof. The reported fork-check cost is
also specific to one observed head: \texttt{detect\_fork} scans every retained head, so its cost
grows with the number of observations. The benchmark seeds exactly one, so \SI{27.9}{\micro\second}
is the one-head case, not the steady-state cost of a mature auditor holding many vantages over a long
log.

\subsection{Session versus Continuous Mode (M13, M15)}\label{ssec:eval-modes}

The design offers two operating modes (\cref{ssec:design-modes}): session mode writes one directory
entry per signed-pre-key rotation, and continuous mode writes one per ratchet epoch for finer-grained,
ACKA CEA-style detection. The two modes have effectively indistinguishable per-check verification
costs; their difference is in write frequency. A per-check operation
costs \SI{27.2}{\micro\second} in session mode and \SI{27.5}{\micro\second} in continuous mode (medians, \cref{app:benchmarks}; both include
server-side proof generation). The two medians differ by \SI{0.3}{\micro\second}, within run-to-run
variation, and no ordering conclusion is drawn from that gap; the medians are reported as descriptive
statistics. The chain memoization flattens the compressed-leaf cost that previously
separated the two modes. Both
figures require a precise statement of what they measure: each benchmarked check comprises the
server-side proof generation and the client-side verification of the value, prefix-root, and
log-inclusion steps, both under the same label-bound verifier. Client-side label derivation (a fixed
sub-microsecond HKDF/hash) is performed once in setup and excluded from both timed bodies, so the two
medians compare like for like. One residual asymmetry is disclosed: continuous mode appends one log
leaf per registered epoch (here $K$ epochs) whereas session mode commits once, so the continuous
log-inclusion proof is over a marginally deeper log; the effect is within the reported precision,
leaving the two modes' per-check verification costs effectively equal. This depth-independence is
measured directly by the deep-chain experiment (M15), which isolates it from the directory-growth
confound: evolving a conversation through $K\in\{1,10,100,720\}$ ratchet epochs and timing the
final-epoch transparency check against a session-mode raw lookup on the \emph{same} log---so both paths
see the identical log depth and directory size---the two medians track each other to within
\SI{0.1}{\micro\second} at every $K$, through the full sweep to $K=720$ ratchet epochs on a log that
grows past ten thousand committed entries. The
component attributable to chain depth is therefore below the timer resolution: continuous-mode
verification stays flat through \num{720} ratchet epochs, because the CEA chain state is a
constant-size fold that adds no per-epoch verification work. What continuous mode does add is directory
writes, quantified next. Neither figure includes a VRF step, because the
dual-index and CEA paths use client-derived rather than VRF-derived labels
(\cref{ssec:design-verify}), and neither includes the signed-tree-head signature verification that
the full specified check of \cref{app:algorithms} performs; \cref{ssec:eval-latency} shows that the
full client verification, including that signature, costs $\approx$\SI{128}{\micro\second}. The modes
differ instead in the number of directory writes. \Cref{tab:eval-modes} reports the write
counts over a conversation of $E$ hourly epochs, with a signed-pre-key rotation every 30 days
($R=720$).

ratcheting the ratio is the number of ratchet epochs per signed-pre-key rotation, which has no fixed
cap. Two limitations follow from this. First, because real ratchet cadence is
message-driven rather than hourly, the continuous-mode write counts here are an under-count for a
chatty conversation and an over-count for a quiet one; the governing ratio is ratchet epochs per

the ratchet's own key agreement. To keep the two medians honestly comparable, both modes are timed
under the \emph{same} label-bound proof verifier (\texttt{verify\_search\_result\_raw\_for}), so
neither path gains an artificial edge from skipping the label-binding check.

First, the implemented (VRF-indexed) lookup proof is at rough size parity with CONIKS at matched
directory size, the like-for-like comparison since CONIKS lookups are likewise VRF-indexed; the raw
dual-index lookup used elsewhere in DUET carries no VRF proof and is correspondingly smaller. The
measured \num{817}-byte median at $N = 10^6$ (max \num{945}) is the prefix-proof payload plus the
\num{80}-byte ECVRF proof, measured under a single-epoch log. It excludes the signed tree head, the
JSON serialization framing, and the epoch-log inclusion path, which is empty at one epoch and grows
to at most $32\lceil\lg E\rceil$ bytes over $E$ epochs in a deployment. CONIKS publishes \num{1216}\,bytes at
$N = 2^{32}$; instantiating CONIKS's own per-lookup accounting (one \num{32}-byte hash per tree level
plus one, a \num{96}-byte VRF proof, and its \num{64}-byte signed-tree-root
signature~\cite[\S5.3, Table~1]{melara2015coniks}) at $N = 10^6$ gives $32 \cdot 21 + 96 + 64 =
832$\,bytes, or \num{768}\,bytes with the signature excluded; the paper itself states no number at
$10^6$. On the same convention as this chapter's measurement, proof and VRF without a signature, DUET's
\num{817}\,bytes sits within \num{7}\% of CONIKS's \num{768}\,bytes: rough parity, with DUET
marginally larger on the raw proof. This VRF-indexed identity lookup does not itself carry the
dual-index warning mechanism; detection is supplied separately through additional raw-label lookups
that reuse the same prefix-tree and log-proof structure without the VRF component (\cref{sec:design-dual}),
none of which enlarges an individual proof. No
wire-format advantage is claimed here: a full DUET lookup response also returns the signed tree head \emph{per
lookup} (\cref{sec:impl-signal}), which this proof-body comparison excludes on both sides.

Second, restricted to the prefix-proof sibling representation, DUET's bitmap-compressed proof carries
roughly one-ninth the sibling-hash bytes of Signal's fixed \num{256}-sibling copath at the measured
sizes. This is a like-for-like comparison of one component, not a whole-response wire-format claim.
Signal's key-transparency server pads every prefix proof to the full \num{256}-sibling copath
($256 \times 32 = \num{8192}$\,bytes) with seed-derived stand-in hashes, and its verifier
(\texttt{evaluateProof} in \texttt{tree/prefix/verify.go}) rejects any proof that does not contain
exactly \num{256} siblings of \num{32}\,bytes each~\cite{signal-kt-server}; DUET's prefix proof
instead ships only the non-empty siblings plus a \num{32}-byte bitmap. Taking DUET's \emph{whole}
lookup proof (prefix payload plus the \num{80}-byte VRF proof) as a conservative upper bound on its
prefix component gives $8192/945 = 8.7\times$ at the $10^7$ median and $8192/817 = 10.0\times$ at
$10^6$, so the prefix-only advantage is at least this large. The padding is a deliberate trade of
bandwidth for the hiding of tree density, which DUET's bitmap instead reveals, so the comparison is
$\sim$$9\times$ sibling-hash bytes in exchange for $\sim\lceil\lg N\rceil$ bits of density metadata;
it does not net against the signed tree head, which a full DUET response carries per lookup
(\cref{sec:impl-signal}) and which Signal's \num{8192}-byte copath figure excludes on both sides.
SEEMless's measured $\approx$8.6\,kB lookup proofs at $10^7$~\cite[p.~12]{chase2019seemless} confirm
that both deployed-lineage systems ship $\sim$8\,kB prefix proofs.

Third, offline catch-up at $W = 720$ costs \num{320}\,bytes against approximately \num{530}\,kB for
CONIKS-style per-epoch monitoring over the same window. The \num{530}\,kB figure is derived from
CONIKS's published per-epoch monitoring proof of $\approx$\num{736}\,bytes~\cite[Table~1]{melara2015coniks}:
$720 \times 736 = 529{,}920$\,bytes, equivalently thirty times its published \num{17.6}\,kB daily
cost. The per-epoch figure assumes CONIKS's own parameterization ($\approx 2^{21}$ directory changes
per epoch at $N \approx 2^{32}$), so the derived total is indicative rather than exact; at CONIKS's
stated parameterization it is over three orders of magnitude larger than the windowed proof
($529{,}920/320 \approx 1{,}656\times$).

Finally, full client verification stays below \SI{150}{\micro\second} through $10^7$ labels. CONIKS
reports \SI{159}{\micro\second} to verify the authentication path at $N = 10^7$ and approximately
\SI{400}{\micro\second} to verify the signed-tree-root signature, and reports no VRF-verification
time~\cite[\S5.3]{melara2015coniks}. The comparison must be taken at matched scale, so it is the $10^7$
median of \SI{147.1}{\micro\second} that belongs beside CONIKS's published figures, not the
$\approx$\SI{128}{\micro\second} measured at $N \le 10^4$. At that scale DUET's measured value is lower
than the published CONIKS figure while additionally performing the VRF verification CONIKS omits;
differing hardware (CONIKS's 2015 2\,GHz laptop CPU against the 2022 mobile CPU used here; see the
comparability note) and methodology prevent a direct performance comparison, so no ratio is offered in
the body.\footnote{For reference, the published CONIKS total is \SI{559}{\micro\second}, the sum
computed here of its \SI{159}{\micro\second} authentication-path and $\approx$\SI{400}{\micro\second}
signature figures, so the \SI{147.1}{\micro\second} DUET median is roughly $3.8\times$ lower; the
quotient is kept to this note because a cross-hardware, cross-methodology comparison is indicative
only.} The claim that stands on this hardware alone is the
sub-\SI{150}{\micro\second} median cost of full client verification across the whole measured range.

caught by the owner's self-check and peer warning within one or two epochs. The four residual
threats are not cryptographic weaknesses. One is inherent to the semi-trusted-server model: the
operator necessarily learns which label belongs to which user, an information-disclosure residual
shared by the surveyed key-transparency deployments, including CONIKS~\cite{melara2015coniks}, and not
addressed by ACKA~\cite{dowling2023acka}, which abstracts the log behind a security definition rather
than building a distrusted one. The other three are availability functions the proof-of-concept
does not implement (write rate-limiting, a published-epoch staleness timeout, and a gossip
transport that would surface proof-omission), each a deployment-layer engineering task
(\cref{ch:discussion}) rather than a flaw in the construction. (A2's write censorship is, by
contrast, detected: the compound signal, a key mismatch from the self-check together with a
proof-verified \emph{absence} of the warning, is a strong indication of compromise. Deleting a
warning \emph{after} it commits is tampering rather than censorship, and is separately addressed by the
write-once policy and the per-epoch transition audit, with the writer's persistence evidence available
as a tested reference component; see \cref{app:algorithms}.)

\subsection{Attack Routes and Detection Controls}\label{ssec:eval-attacktree}

\Cref{fig:eval-attacktree} groups the evaluated scenarios by their role. Server substitution (A1), a
network man-in-the-middle attack (A3), and malicious rotation (A5) are independent ways of causing a
client to accept an attacker-controlled key. The OR relationship indicates that any one of these
routes can expose message plaintext if the substitution succeeds. Each route is paired with the
control that detects it.

A2 and A4 instead attempt to conceal an attack. A2 suppresses the shared warning, while A4 presents
different signed heads to different vantage points. The former is exposed by a key mismatch together
with the proof-verified absence of the warning; the latter by comparing signed heads from independent
vantage points.

These guarantees depend on the assumptions of \cref{ch:threat}. The warning-channel cases require
honest establishment and active monitoring; detecting A4 additionally requires a valid head from an
honest independent vantage. Under these conditions every in-scope route produces a warning or
rejecting verdict. Endpoint compromise (X1) remains outside the directory threat model.

\subsection{Residual Risks and Security Position}\label{ssec:eval-posture}

The overall security position follows from the design guarantees of \cref{ch:design}, the adversarial evidence of this section, and the component measurements above. The marginal in-memory warning-slot read (M5)
costs on the order of a microsecond of server-side work (\SI{1.62}{\micro\second} clean,
\SI{1.72}{\micro\second} attacked); end-to-end detection latency, which additionally requires the one
or two verified lookups, network transport, monitor polling, and epoch timing that M5 does not measure, was
not quantified. No false alarms were observed over \num{1000} clean deterministic sessions (M6). The
residual risks of \cref{ssec:eval-stride} are one semi-trusted-server limitation (the
label$\leftrightarrow$user mapping, outside what any transparency layer removes) and three availability
functions left to a production deployment. These results should be considered against current
deployment practice: the
deployed WhatsApp AKD ships with client key-history monitoring not yet enabled and directs the user to
verify the session \emph{manually} with the contact when an automatic check fails~\cite[pp.~5,
10]{whatsapp2023whitepaper}, and unprompted users rarely locate and complete such a manual ceremony
(\cref{ssec:eval-detection}). DUET instead provides automatic, in-band detection that needs no user
action.

\section{Implications for Deployment}\label{sec:eval-deploy}

The measurements above bear directly on whether a design of this kind could be adopted by a
production messenger such as Signal, whose own key-transparency server this work was built
against~\cite{signal-kt-server}. This section draws out those implications as measured comparisons
with their caveats attached, not as recommendations.

On the client, the cost is small and grows far more slowly than the service. Full verification is
$\approx$\SI{128}{\micro\second} at $N\le10^4$ and \SI{147.1}{\micro\second} at $10^7$
(\cref{ssec:eval-latency,ssec:eval-scale}),
and a lookup proof is \num{817}\,bytes median at $10^6$ labels (\cref{ssec:eval-scale}): at rough size
parity with CONIKS and, on the prefix-proof sibling representation alone, roughly $9\times$ smaller
than Signal's fixed \num{256}-sibling copath (\cref{sec:eval-compare}). A client offline for a month catches up in a single \num{320}\,byte proof
rather than the approximately \num{222}\,kB that the synthetic one-proof-per-epoch baseline costs over the same
window (\cref{ssec:eval-catchup}); for comparison, CONIKS's published per-epoch monitoring costs
imply approximately \num{530}\,kB for the same month (\cref{sec:eval-compare}). This matters most for
the intermittently connected mobile clients a messenger must serve. The measured components are sub-millisecond local
verification and sub-kilobyte per-lookup proofs; an isolated in-process \texttt{KTClient.detectMitm} check performs one or two such lookups (their combined bandwidth and end-to-end latency were not measured), and a full monitor pass adds the own-identity check and, where applicable, catch-up and continuous-mode verification. In exchange, the design is
intended to replace a manual ceremony which, as \cref{ssec:eval-detection} discusses, most unprompted
users never reliably locate and complete.

On the server, the results require more qualification, and those qualifications are exactly what a production
deployment would have to engineer away. Two costs stand out. First, the epoch commit is the one
operation that grows with $N$ ($\approx O(N)$, \SI{5.92}{\milli\second} at $10^4$,
\cref{ssec:eval-throughput}), because the current server deep-clones its committed snapshot; a
copy-on-write tree would reduce this to $O(\lg N)$ per modified label ($O(k \lg N)$ for an epoch's $k$ updates) and is the single most valuable server-side change.
Second, the per-lookup and per-rotation VRF prove (\SI{117.4}{\micro\second} measured in isolation,
\cref{tab:bench-maint}) dominates those
paths only because the benchmark re-evaluates the VRF for an unchanged identifier; a deployed server
would cache the label and pay it once. Beyond compute, the scale run exposes the memory limit: a
$10^7$-label tree leaves a $\approx$\num{20.8}\,GB resident set on one machine (\cref{ssec:eval-scale}), so a real
deployment must move to the persistent, sharded storage of the SEEMless--Parakeet lineage that this
in-memory prototype deliberately does not model.

Finally, the two operating modes bound the deployment choice rather than forcing it. Session mode is
the lower-write configuration proposed as the deployment default (one directory write per signed-pre-key rotation, at parity with existing
key-transparency systems) while continuous mode offers finer-grained, ACKA CEA-style detection at a
write amplification of $\approx 720\times$ under the benchmark model with hourly epochs. The ratio scales
with ratchet cadence rather than sitting at a fixed cap (\cref{ssec:eval-modes}). The measured
verification path meets the latency target, but the $O(N)$ epoch commit, the memory footprint,
persistence, and networked operation remain deployment limitations rather than solved problems.
Before a design of this kind could ship it would need the engineering work set out in
\cref{ch:discussion}: authenticated writes on the directory API, persistent sharded storage, and
narrowing the operator's label$\leftrightarrow$user query-privacy residual (\cref{ssec:eval-stride})
with a privacy-preserving lookup design (an OPRF hides the queried identity; requester unlinkability additionally needs an anonymizing transport, \cref{ch:discussion}). While those engineering items remain open, the component measurements show the cryptographic
verification path meets the latency and proof-size targets the chapter set out to test.
