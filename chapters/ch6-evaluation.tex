\chapter{Evaluation}\label{ch:eval}

This chapter evaluates the implementation described in \cref{ch:impl} against the goals and threats
defined in \cref{ch:threat}. It examines proof size and verification cost, offline catch-up,
scalability, the trade-off between session and continuous modes, comparisons with prior systems, and
the coverage of the security controls.

% ============================================================================
\section{Methodology}\label{sec:eval-method}

The evaluation addresses four questions derived from the design claims. All measurements use fixed
baselines and a controlled experimental environment.

\emph{Does detection change the size of an individual proof?} The warning check is an additional
raw-label lookup that reuses the prefix-tree and log-proof structures of a key lookup. The claim would
fail if enabling detection enlarged or restructured an individual proof
(\cref{ssec:eval-sizes,ssec:eval-detection}).

\emph{Does client verification remain inexpensive as the directory grows?} The claim would fail if
full client verification grew in proportion to $N$ or exceeded the sub-millisecond target
(\cref{ssec:eval-latency,ssec:eval-scale}).

\emph{Can an offline client re-synchronize with one proof rather than one per missed epoch?} The claim
would fail if the client still had to fetch a proof per epoch or if the windowed proof grew linearly
with the missed-epoch count $W$ (\cref{ssec:eval-catchup}).

\emph{Are the evaluated substitution attacks detected without alarms on the enumerated clean workflows?} A
missed attack in the adversarial suite would refute the detection claim. M17 separately checks that
every enumerated clean workflow produces the expected non-alarm verdict
(\cref{ssec:eval-detection,sec:eval-security}).

Measurements are grouped into seventeen metric families, \emph{M1}--\emph{M17}.
\Cref{tab:eval-map} defines each family, its baseline, and where its result is reported. M1--M13 follow
the chapter's progression from proof size to operating modes. M14--M17 extend the earlier families and
are reported with the result they strengthen.\footnote{The Rust harness uses the same numbering, so
each family can be traced to the corresponding benchmark group in \cref{app:benchmarks}.}

Three configurations recur throughout the chapter. The \emph{single-index} reference is a plain
log-inclusion proof. The \emph{VRF-indexed} configuration is the identity lookup performed through
\texttt{search\_by\_user\_id}. The harness records it under the historical identifier
\texttt{dual\_index}. The \emph{windowed} configuration adds windowed consistency verification.
These are benchmark configurations rather than a complete mechanism-level ablation.

The raw dual-index warning path instead calls \texttt{search(label)} and omits the \num{80}-byte VRF
proof. M16 measures its verified detector branches, while M13 and M15 measure the
session-versus-continuous trade. M11 alone uses the \emph{no-KT floor}, a synthetic identity-hash
comparison rather than a mechanism-level baseline (\cref{ssec:eval-throughput}). The measurements
therefore bound the relevant costs without treating a configuration label as an isolated mechanism.

Timings are recorded in Criterion reports and by a manual harness. The manual harness records the
median and 95th percentile from \num{2000} sequential in-process iterations per operation. The thesis
uses these as descriptive sample statistics and does not infer a confidence interval for a mean.
Measurements near the platform's timer resolution, including the
\SIrange{0.1}{0.3}{\micro\second} M4 windowed-generation values, are treated as coarse hot-path
observations.

Proof sizes are exact and seed-deterministic. M7 instead reports distributions over \num{1000} random
lookups per $N$. Fixed cryptographic and sampling seeds support reproducing the results, following the procedure in
\cref{sec:impl-repro}. The benchmark host, software versions, and the complete commands to reproduce
the runs are reported in \cref{app:benchmarks}. Body timings are
rounded to $0.1\,\si{\micro\second}$. Separate benchmark contexts shift some component medians by a few
percent, so the chapter quotes the in-path figures and does not attribute those small differences to
the mechanism.

Three limitations bound the interpretation of the numbers. First, the server is in-memory and
single-machine, so the absolute latencies exclude database and network costs. Second, the
single-epoch microbenchmarks carry no log-inclusion path. M14 measures the additional history term and
confirms its $32\lceil\lg E\rceil$-byte bound (\cref{ssec:eval-sizes}). Third, the operation-rate
figures are single-thread per-operation costs rather than parallel scaling. Cross-system timings in
\cref{sec:eval-compare} come from different hardware, scales, and storage models and are treated as
order-of-magnitude only.

\section{Microbenchmarks}\label{sec:eval-micro}

This section reports the core per-lookup costs on a directory of up to $10^6$ labels. It measures
proof size, generation and verification time, offline catch-up bandwidth, the local cost of the two
detector branches, and the expected verdicts for enumerated clean workflows.

\subsection{Lookup Proof Size and History Depth (M1, M14)}\label{ssec:eval-sizes}

Lookup-proof size determines the bandwidth added to a key fetch. \Cref{tab:eval-sizes} reports the
implemented VRF-indexed lookup and a dense Merkle-log inclusion proof over the same number of user
entries. The DUET proof contains a prefix proof, an \num{80}-byte VRF proof, and log inclusion. The
reference contains only the dense-log path. The table measures VRF-indexed identity lookups. Raw
dual-index warning lookups carry no VRF proof. Each row is one seed-deterministic path. M7
(\cref{ssec:eval-scale}) supplies the sampled distribution. A prefix proof carries one hash per
non-empty sibling on the label's path, whose number $h$ has expected value $\approx\lceil\lg N\rceil$,
so both objects grow logarithmically in $N$ as the sparse-tree design predicts
(\cref{ssec:design-structures}).

The VRF-indexed lookup has a fixed \num{177}-byte component. This consists of the
\num{80}-byte ECVRF proof defined by RFC~9381~\cite{rfc9381}, a \num{32}-byte label, a
\num{32}-byte value, a one-byte leaf-kind commitment, and a \num{32}-byte sibling bitmap. Each
prefix or log hash adds \num{32} bytes, giving
\begin{equation}\label{eq:eval-proofsize}
  |\pi| \;=\; 32h \;+\; 32h_{\mathrm{log}} \;+\; 177 \ \text{bytes},
  \qquad \mathbb{E}[h]\approx\lceil\lg N\rceil,\quad h_{\mathrm{log}}\le\lceil\lg E\rceil,
\end{equation}
where $h$ is the number of non-empty siblings on the queried label's path and
$h_{\mathrm{log}}$ is the current root's log-inclusion path length. The current directory root is
the final log leaf (\cref{ssec:design-verify}), so
$h_{\mathrm{log}}=\mathrm{popcount}(E-1)$. It is at most $\lceil\lg E\rceil$ and can be smaller.
Raw-label warning responses omit the VRF component and may carry a differently sized value. The
fixed constant therefore describes the VRF-indexed key lookup, not every response. The
$O(\lg N + \lg E)$ scaling of
\cref{eq:eval-proofsize} is plotted in
\cref{fig:eval-sizes-plot}. The $10^6$ row reads \num{913}\,bytes because the single seeded leaf's
path carries $h=\num{23}$ non-empty siblings. The distribution median over \num{1000} random lookups
at $10^6$ is \num{817}\,bytes (\cref{ssec:eval-scale}). The distribution median is
therefore reported in the remainder of this chapter, since it reflects the
proof size a typical lookup incurs rather than the depth of one particular seeded leaf. The
dual-index mechanism adds no fields to the key-lookup proof. Its warning check is a separate
raw-label lookup with its own response shape, not an enlargement of the identity proof.

M14 measures the history term that is absent from the single-epoch rows. It grows the committed log
through $E\in\{1,16,256,1024\}$ epochs at $N=10^3$ and $N=10^4$. The observed paths contain
$\{0,4,8,10\}$ hashes, adding $\{0,128,256,320\}$ bytes. These values match the RFC~9162
Merkle-log bound~\cite{rfc9162}. Directory size and history depth contribute independently
(\cref{app:benchmarks}), which confirms the $O(\lg N+\lg E)$ proof-size claim. The CONIKS comparison
continues to use the convention-matched single-epoch proof and reports the history term separately.

M3, the last row, measures the complete signed-head lookup-verification path, also called full
client verification. It includes VRF label binding, value binding, prefix-root recomputation, log

directory (\cref{ssec:eval-scale}). Its dominant cost, the \SI{75.0}{\micro\second} VRF verification,
is independent of directory size. The \SI{25.9}{\micro\second} prefix recomputation grows only with
proof depth. The complete check is therefore well below the sub-millisecond target and includes the
VRF step that CONIKS does not include in its published timing.

The server-side full search is also near-flat over this range because the compressed-leaf chain is
memoized (\cref{sec:impl-modules}). It reads \SI{111.2}{\micro\second}
at $N=10^3$ and \SI{111.6}{\micro\second} at $N=10^4$. The scale run's search median reads
\SI{132.7}{\micro\second} at $N=10^6$ and \SI{441.7}{\micro\second} at $N=10^7$
(\cref{ssec:eval-scale}). The median is approximately flat through $10^6$ and then rises at $10^7$.
Possible contributors are the wider proof and the different measurement context of the scale-up
harness. The experiment does not isolate their effects.

\subsection{Offline Catch-Up Bandwidth (M4)}\label{ssec:eval-catchup}

The bandwidth a client spends after being offline is where the windowed-consistency policy of
\cref{ssec:design-catchup} yields its largest saving over a repeated-proof workload. The baseline
here is synthetic. It re-fetches one current-head-anchored consistency proof for each of the $W$
missed epochs. The windowed client instead verifies a single distant-head proof spanning the whole
gap, which RFC~9162 supports directly~\cite{rfc9162}. The saving is therefore in the number of
proofs a monitoring policy chooses to fetch, not a cost RFC~9162 forces on an offline client.
\Cref{tab:eval-catchup} reports both as the offline window $W$ grows. Because catch-up proofs are
taken over the epoch log, one leaf per epoch, their size is independent of the number of users
$N$. The table therefore holds for every $N$ measured.

Two properties bound the interpretation of the ratio. First, the baseline is synthetic. The harness
issues $W$ current-head-anchored consistency proofs, modelling a client that re-fetches a proof
against the latest head on each of $W$ occasions.\footnote{It is one baseline among several, not the
cost of generic sequential catch-up. A client verifying adjacent $e \to e+1$ transitions is another
reasonable strategy and would use smaller individual proofs. The exact ratio is therefore specific
to this baseline. The proof-count comparison, $O(1)$ against $O(W)$, does not depend on that choice.}
Second, the byte figures are \emph{raw consistency-path hash bytes}. The harness counts path
length times the \num{32}-byte hash size. A deployment serializes these (the reference server sends
hex-encoded JSON with framing and length fields), so serialized network bandwidth was not measured
and would be larger on both sides of the comparison.

The byte saving grows approximately linearly with the window, measured as $\approx0.97W$
(\cref{fig:eval-catchup-plot}). At $W=720$, the windowed path carries \num{320} bytes instead of

because it is specific to the synthetic baseline.

The generation body has a median of \SI{0.3}{\micro\second} for the windowed proof and
\SI{197.0}{\micro\second} for the repeated baseline. This is a separate timing result and its quotient
is only approximate because the windowed value is close to the reporting resolution. Together, the
measurements confirm that one windowed proof replaces $W$ repeated proofs. This addresses the
monitoring-bandwidth extension identified by CONIKS~\cite{melara2015coniks}.

\subsection{Detector-Branch Latency and Clean-Session Coverage (M16, M17)}\label{ssec:eval-detection}

M16 reconstructs in Rust the verified operations performed by two branches of the isolated
\texttt{KTClient.detectMitm} helper (\cref{sec:impl-signal}). The timed body performs raw-label
search, proof verification, and value comparison without the VRF step measured by M3. It does not
time the TypeScript implementation directly.

On the early-return branch, a mismatching owner value settles the verdict after one verified lookup.
The median is \SI{27.8}{\micro\second}, with a 95th percentile of
\SI{28.8}{\micro\second}, at $N=10^4$. On the clean-matching branch, the owner slot contains the
expected key and the helper also verifies that the warning slot is empty. This two-lookup branch has a
median of \SI{31.1}{\micro\second} and a 95th percentile of
\SI{32.7}{\micro\second}. The empty warning result must be proof-verified, because accepting an
unproven empty response would let the server conceal a committed warning.

These are local Rust component costs. End-to-end detection additionally includes the TypeScript
runtime, HTTP transport, background polling, registration, and network round trips. A matching or verifiably empty owner slot proceeds to the warning-slot
lookup, whereas an owner-slot mismatch returns after the first lookup. The complete networked
background monitor performs additional catch-up, owner-, peer-, and warning-slot checks.

M17 checks the expected non-alarm behaviour of seven honest workflows: first registration, an
established session with the expected key, a proven-empty warning slot, repeated verification of a
valid state, valid log growth under a correct consistency proof, multiple honest continuous-mode
epochs, and agreeing cross-vantage heads. Named tests in the relevant suites assert each outcome
(\cref{app:tests}). M17 is therefore functional coverage of the enumerated clean workflows, not an
estimate of a population-wide false-alarm rate.

signed-head lookup verification against a synthetic one-hash floor. It excludes transport,
X3DH/PQXDH, and session establishment. This subsection focuses on the maintenance costs that limit
the single-machine prototype.

Key rotation is approximately unchanged over the measured range. Its

not measured here.

persistent tree updates to target $O(\lg N)$ work per modified label, or $O(k\lg N)$ for $k$
updates.

The scale run exposes the corresponding memory limit. Building the $10^7$-label tree takes about
26 minutes and leaves a \SI{21.3}{\giga\byte} resident set (\cref{tab:bench-scale}). Persistent and
distributed storage remain outside this in-memory evaluation.

\subsection{Auditor Cost (M12)}\label{ssec:eval-auditor}

M12 measures a local signature-and-consistency kernel rather than the complete networked audit. It
times an STH signature check, consistency-proof generation and verification, and a fork check against
one observed head. The first body has a median of \SI{28.6}{\micro\second} at $N=10^4$. The
one-head fork check has a median of \SI{27.1}{\micro\second} and a 95th percentile of
\SI{33.1}{\micro\second}. Since proof generation and verification are timed together, the first
figure is a conservative upper proxy for verification alone.

The measurement excludes network transfer, epoch-delta retrieval, committed-root inclusion
verification, and the full \texttt{audit\_epoch} transition replay. That replay applies each
disclosed update to a candidate replica. The fork-check figure also does not represent a mature
auditor with a long observation history. The implemented \texttt{detect\_fork} scans the retained
heads, whereas M12 seeds exactly one.

\subsection{Session versus Continuous Mode (M13, M15)}\label{ssec:eval-modes}

Session mode writes one directory entry per signed-pre-key rotation. Continuous mode writes one per
ratchet epoch to provide the finer-grained CEA check (\cref{ssec:design-modes}). M13 measures a
single label-bound proof generation and verification in each mode. The medians are
\SI{27.3}{\micro\second} for session mode and \SI{27.7}{\micro\second} for continuous mode
(\cref{app:benchmarks}). Their \SI{0.4}{\micro\second} difference is within run-to-run variation, so
no ordering is inferred.

Both M13 bodies include server-side proof generation and client-side verification of the value,
prefix root, and log inclusion. They exclude label derivation, the VRF step that these
client-derived-label paths do not use, and the signed-tree-head signature check included in M3. The
comparison therefore isolates the corresponding label-bound proof operation rather than a complete
client lookup.

M15 tests whether a longer continuous-mode history changes that operation. It evolves a conversation
through $K\in\{1,10,100,720\}$ ratchet epochs, then compares the final-epoch CEA check with a
session-mode raw lookup on the same log. Each series remains flat as $K$ grows, which establishes
depth independence. Their pointwise difference is at most \SI{0.1}{\micro\second}, including at $K=720$
on a log with more than ten thousand committed entries. That delta bounds the additional
fingerprint-comparison work and is not evidence of a history-depth cost. The full
$K$-by-rotation-cadence grid is reported in \cref{app:benchmarks}.

The material difference between the modes is therefore write frequency. \Cref{tab:eval-modes}
reports the writes over a conversation of $E$ hourly epochs, assuming one signed-pre-key rotation
every 30 days ($R=720$).

720 (1 month)  & 720   & 1 & $720\times$ \\
4{,}320 (6 months) & 4{,}320 & 6 & $720\times$ \\

Under this model, the ratio grows with $E$ until the first rotation and then settles at
$720\times$. This plateau follows from the assumed hourly epoch and 720-hour rotation. It is not a
deployment bound. In a live Double Ratchet, the governing quantity is the number of ratchet epochs
per signed-pre-key rotation, which varies with message activity.

The benchmark uses a simulated per-epoch secret rather than a live Double-Ratchet output. It measures
the transparency-layer work associated with each epoch, not the ratchet's key agreement. Both modes
use the same label-bound verifier, so the comparison does not favour either path by omitting the
label-binding check.

Four claims follow from the comparison. For each cross-system figure, the text states explicitly
whether it is published or derived, and from what.

First, the implemented (VRF-indexed) lookup proof is at rough size parity with CONIKS at matched
directory size, the like-for-like comparison since CONIKS lookups are likewise VRF-indexed. The raw
dual-index lookup used elsewhere in DUET carries no VRF proof and is correspondingly smaller. The
measured \num{817}-byte median at $N = 10^6$ (max \num{945}) is the prefix-proof payload plus the
\num{80}-byte ECVRF proof, measured under a single-epoch log. It excludes the signed tree head, the
JSON serialization framing, and the epoch-log inclusion path, which is empty at one epoch and grows
to at most $32\lceil\lg E\rceil$ bytes over $E$ epochs in a deployment. CONIKS publishes \num{1216}\,bytes at
$N = 2^{32}$. Instantiating CONIKS's own per-lookup accounting (one \num{32}-byte hash per tree level
plus one, a \num{96}-byte VRF proof, and its \num{64}-byte signed-tree-root
signature~\cite[\S5.3, Table~1]{melara2015coniks}) at $N = 10^6$ gives $32 \cdot 21 + 96 + 64 =
832$\,bytes, or \num{768}\,bytes with the signature excluded. The paper itself states no number at
$10^6$. On the same convention as this chapter's measurement, proof and VRF without a signature, DUET's
\num{817}\,bytes sits within \num{7}\% of CONIKS's \num{768}\,bytes. This is rough parity, with DUET
marginally larger on the raw proof. This VRF-indexed identity lookup does not itself carry the
dual-index warning mechanism. Detection is supplied separately through additional raw-label lookups
that reuse the same prefix-tree and log-proof structure without the VRF component (\cref{sec:design-dual}),
none of which enlarges an individual proof. No
wire-format advantage is claimed here. A full DUET lookup response also returns the signed tree head \emph{per
lookup} (\cref{sec:impl-signal}), which this proof-body comparison excludes on both sides.

Second, restricted to the prefix-proof sibling representation, DUET's bitmap-compressed proof carries
roughly one-ninth the sibling-hash bytes of Signal's fixed \num{256}-sibling copath at the measured
sizes. This is a like-for-like comparison of one component, not a whole-response wire-format claim.
Signal's key-transparency server pads every prefix proof to the full \num{256}-sibling copath
($256 \times 32 = \num{8192}$\,bytes) with seed-derived stand-in hashes, and its verifier
(\texttt{evaluateProof} in \texttt{tree/prefix/verify.go}) rejects any proof that does not contain
exactly \num{256} siblings of \num{32}\,bytes each~\cite{signal-kt-server}. DUET's prefix proof
instead ships only the non-empty siblings plus a \num{32}-byte bitmap. Taking DUET's \emph{whole}
lookup proof (prefix payload plus the \num{80}-byte VRF proof) as a conservative upper bound on its
prefix component gives $8192/945 = 8.7\times$ at the $10^7$ median and $8192/817 = 10.0\times$ at
$10^6$, so the prefix-only advantage is at least this large. The padding is a deliberate trade of
bandwidth for the hiding of tree density, which DUET's bitmap instead reveals, so the comparison is
$\sim$$9\times$ sibling-hash bytes in exchange for $\sim\lceil\lg N\rceil$ bits of density metadata.
It does not net against the signed tree head, which a full DUET response carries per lookup
(\cref{sec:impl-signal}) and which Signal's \num{8192}-byte copath figure excludes on both sides.
SEEMless's measured $\approx$8.6\,kB lookup proofs at $10^7$~\cite[p.~12]{chase2019seemless} confirm
that both deployed-lineage systems ship $\sim$8\,kB prefix proofs.

Third, offline catch-up at $W = 720$ costs \num{320}\,bytes against approximately \num{530}\,kB for
CONIKS-style per-epoch monitoring over the same window. The \num{530}\,kB figure is derived from
CONIKS's published per-epoch monitoring proof of $\approx$\num{736}\,bytes~\cite[Table~1]{melara2015coniks}:
$720 \times 736 = 529{,}920$\,bytes, equivalently thirty times its published \num{17.6}\,kB daily
cost. The per-epoch figure assumes CONIKS's own parameterization ($\approx 2^{21}$ directory changes
per epoch at $N \approx 2^{32}$), so the derived total is indicative rather than exact. At CONIKS's
stated parameterization it is over three orders of magnitude larger than the windowed proof
($529{,}920/320 \approx 1{,}656\times$).

Finally, full client verification stays below \SI{150}{\micro\second} through $10^7$ labels. CONIKS
reports \SI{159}{\micro\second} to verify the authentication path at $N = 10^7$ and approximately
\SI{400}{\micro\second} to verify the signed-tree-root signature, and reports no VRF-verification
time~\cite[\S5.3]{melara2015coniks}. The comparison must be taken at matched scale, so it is the $10^7$
median of \SI{139.2}{\micro\second} that belongs beside CONIKS's published figures, not the
$\approx$\SI{128}{\micro\second} measured at $N \le 10^4$. At that scale DUET's measured value is
lower than the published CONIKS figure and includes the VRF verification that CONIKS does not report.
The hardware and methods differ, however, so the values do not support a direct performance ratio.
The result established on this hardware is the sub-\SI{150}{\micro\second} median cost of full client
verification across the measured range.

hardware, directory scales, and storage models. Cross-system timing comparisons are therefore
indicative only. Byte figures are compared after aligning the stated proof components. The benchmarks
in this thesis are single-machine and in-memory (\cref{sec:eval-method}).\end{quote}

live background monitor (\cref{app:algorithms}).

\subsection{Residual Risks and Security Position}\label{ssec:eval-posture}

The adversarial suite produces the expected verdict for every enumerated scenario, and M17 covers
seven honest workflows without an alarm. Overall, the design guarantees and adversarial results show
that, for an honestly established and actively monitored conversation, the prototype automatically
performs the key and proof checks defined by the design. When a check rejects the directory response,
the client displays a warning. The component measurements quantify the local work of the evaluated
branches rather than end-to-end detection latency. The current integration does not block session
establishment.

M16 measures the two isolated detector branches as local Rust component work
(\cref{ssec:eval-detection}). It does not measure end-to-end detection latency, which also depends on
transport, polling, and epoch timing. The remaining risks are the
operator's knowledge of the account-to-label association and three unimplemented availability
controls. These limitations do not change the demonstrated detection result, but they constrain what
can be claimed for a production service.

\section{Implications for Deployment}\label{sec:eval-deploy}

The measurements identify both feasible client-side components and unresolved server-side work for a
messenger such as Signal~\cite{signal-kt-server}.

For a VRF-indexed identity lookup, median full verification remains below \SI{150}{\micro\second}
through $10^7$ labels (\cref{ssec:eval-latency,ssec:eval-scale}), and the proof is sub-kilobyte. It is
at rough size parity with the aligned CONIKS proof, while DUET's compressed prefix component is much
smaller than Signal's fixed \num{256}-sibling copath (\cref{sec:eval-compare}).

Offline catch-up has a different cost profile. The windowed client fetches one proof for the missed
window rather than one per epoch (\cref{ssec:eval-catchup,sec:eval-compare}). This one-proof result is
particularly relevant to intermittently connected clients.

The warning detector uses raw-label lookups rather than the VRF-indexed identity proof. M16 measures
one- and two-lookup Rust reconstructions of two isolated \texttt{KTClient.detectMitm} branches.
Their combined bandwidth and end-to-end latency were not measured. A complete background-monitor pass
also performs owner and peer checks and may perform catch-up or continuous-mode verification.

The server results expose prototype constraints. Epoch commit grows with the stored snapshot because
the current implementation deep-clones it (\cref{ssec:eval-throughput}). \Cref{ch:discussion} proposes
persistent tree updates targeting $O(\lg N)$ work per modified label, not implemented or measured here.
The in-memory tree also grows large at CONIKS scale (\cref{ssec:eval-scale}). Production operation
therefore requires persistent storage, distribution, concurrency testing, and networked measurements
that this evaluation does not provide.

The two modes expose a separate deployment trade-off. Session mode writes once per signed-pre-key
rotation, whereas continuous mode writes once per ratchet epoch for finer-grained CEA checking and
therefore performs substantially more writes (\cref{ssec:eval-modes}). The exact ratio is determined by
message activity and rotation cadence in a live system, not a fixed deployment value.

Further work also includes authenticated write ownership and stronger query privacy
(\cref{ch:discussion}). An OPRF-based design could hide the raw lookup identity from the service
performing the oblivious evaluation. It would not by itself hide which pseudonymous entry is fetched
or who issued the request. Those properties require additional private-retrieval and network-anonymity
mechanisms. The component measurements show that the implemented client-side proof formats and
cryptographic checks meet the chapter's size and latency targets. Networked operation was not
measured, and persistent storage is not implemented.
