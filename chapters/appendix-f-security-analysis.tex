\section{Warning-Suppression Safeguards}\label{sec:sec-suppression}

The append-only log constrains the \emph{history of committed roots} but not the \emph{contents} of
successive directory states. Within
any epoch whose tree includes the warning leaf, the server cannot answer a warning-slot query with
``absent'': non-inclusion must be \emph{proven} (\cref{ssec:design-verify}), and a valid
non-inclusion proof against a root whose tree contains the leaf would require a hash collision.
Across epochs, however, nothing in the log alone prevents a malicious server from building the
\emph{next} epoch's prefix tree without a leaf that the previous epoch's tree contained, and then
proving that leaf's non-inclusion honestly against the new committed root. Every log consistency
proof would continue to verify, because the log records only that roots were appended, not that the
directory evolved admissibly between them. Three safeguards close this gap.

\begin{enumerate}
\item \textbf{Write-once labels.} Dual-index and CEA labels (\cref{ssec:design-modes}) are
write-once: the server's update interface rejects a write to an occupied label in these families,
and the honest interface never removes or modifies an occupied label in a subsequent epoch. The policy is bound into
the signed configuration hash of \cref{eq:design-sth}, so a server that changes the policy alters the
signed commitment and is rejected by a client that checks the expected configuration.
\item \textbf{Transition audit.} The write-once policy binds an honest server. To bind a malicious
one, the auditor verifies each epoch. For each committed epoch the server discloses the ordered update
set and the committed root. The auditor applies the declared operations to its own copy of the
previous committed state (insertions of previously absent labels and, for key rotation, declared
in-place rotations whose disclosed old value must match the leaf being replaced), verifies that nothing
beyond the declared operations changed (the delta format cannot express a deletion), and accepts only
when the recomputed root equals the committed root. The epoch root's inclusion in the append-only log
binds the accepted transition to the signed history.
Each leaf commits its $\mathit{kind}$, \textsc{mutable} (the global-VRF identity slots, which the server
may rotate) or \textsc{immutable} (the raw dual-index, CEA, and warning labels, which are write-once),
bound into the leaf hash as $\Hleaf(\mathit{kind} \concat \mathit{label} \concat \mathit{value})$,
so the kind is authenticated by the very inclusion proof that authenticates the value and the server
cannot relabel it. The auditor therefore \emph{distinguishes} the two families: it accepts a declared
in-place rotation only on a mutable leaf, and \textbf{rejects any rotation of an immutable leaf
outright} (as well as any rotation that misdeclares the leaf's kind). An adversary that has
compromised the pre-shared state and tries to overwrite a committed CEA fingerprint $F_t$ with one
over its injected key must route the write through the privileged interface and declare it as a
rotation. Since the target leaf is immutable, the transition audit rejects that rotation, so the
epoch fails the auditor's validation and raises an alarm. Entry immutability is thus enforced
\emph{as an auditor acceptance condition}: an immutable-leaf rotation is detected and rejected, not merely surfaced. The owner-side self-checks remain as defence
in depth for the dual-index labels: a replaced lookup slot fails the owner's self-check and a
replaced warning slot still alerts (any value at the slot alerts). But note the CEA fingerprint
overwrite is one the receiver's per-epoch verdict alone \emph{cannot} catch under a pre-shared-state
compromise (the substituted fingerprint matches what the victim recomputes for the injected key), so
it is the auditor's rejection of the immutable-leaf rotation, and the alarm it raises, that closes it. The IETF
KeyTrans protocol assigns this update-validity role to third-party auditors. Its
\texttt{AuditorUpdate} structure carries each log entry's added and removed prefix leaves with a
proof against the prior tree, allowing the auditor to recompute both roots of the
transition~\cite[Section~15.2]{ietf-keytrans-protocol}. A deletion or overwrite therefore cannot be committed
without either failing the auditor's validation and raising its alarm, or presenting the auditor a transition that
fails to replay.
\item \textbf{Persistence check.} Independently of any auditor, the writer of a warning retains the
inclusion proof and signed tree head of the epoch at which its warning committed, and the persistence
check re-verifies the warning's inclusion on a later head. In the prototype this check is implemented
and separately unit-tested as a persistence component. It is not wired into the live background monitor
(\cref{alg:detect}). If the leaf later disappears,
the writer holds an inclusion proof under $\STH_w$, a non-inclusion proof under
a later $\STH_t$, and a valid consistency proof from $\STH_w$ to $\STH_t$: together these three proofs
constitute publicly verifiable evidence, attributable to the server's signing key, that the server
deleted a committed leaf, since all three verify against heads the server itself signed.
\end{enumerate}

The persistence check gives the warning's \emph{writer} evidence of deletion but does not alert a
\emph{peer} that missed the warning. The transition audit independently detects the deletion during
epoch validation. With these safeguards in place, the server's only remaining suppression strategy is
refusal. It can withhold the lookup, the epoch, or the auditor's disclosure, whether for all clients
or selectively for the one revealed warning label. Either way the refusal is observable, since a
client treats anything other than a proof-verified response as a failed check instead of a clean
absence. A refusal therefore never masquerades as a verified absence. The prototype reports an
unreachable or withheld response as an unavailable check (amber), while a malformed, invalid, or
mismatching response rejects as a failed check (red). Neither verdict attributes a specific cause. The \hyperref[sc:threat-a2]{A2}
warning-censorship signal combines a key
mismatch with \emph{proof-verified} warning absence. All three safeguards are
represented in the prototype. The write-once policy and transition audit run live. The persistence
check is implemented and separately unit-tested but is not wired into the background
monitor (\cref{ch:impl}, \cref{alg:detect}).
The prototype does not implement account-layer authentication of raw-label writes (proof of raw-label
ownership). Without it, the write-once policy still binds an honest server and the transition audit
still binds a malicious one, but a malicious client could pre-emptively occupy a currently empty peer
slot, which the owner's label-bound self-check and the resulting peer warning then catch after the
fact (\cref{ch:discussion}).

Detection is bidirectional, which matters for the offline case. The victim's own-key self-check
publishes the warning when the victim notices the wrong key under its own name. In addition, a peer
that has trust-on-first-use-pinned the victim's key detects a substituted peer slot and publishes the
warning on the victim's behalf, so an offline victim is still covered. For a server-side substitution
(\hyperref[sc:threat-a1]{A1}), where the server makes the served bundle agree with the log, a peer comparing the freshly
served bundle against the log sees no mismatch. Detection can occur through the victim's own-key
self-check or through a peer that has already trust-on-first-use-pinned the victim's key. For A1b,
the peer's background monitor performs this comparison on every tick. For A1a, the comparison occurs
when the peer next retrieves the victim's global identity key. Only against a pre-first-contact substitution, where no peer
has yet pinned a key, is the victim's self-check the sole detector. The residual limitation is the
trust-on-first-use caveat of \cref{sec:threat-fair}, since a substitution that predates first contact
pins the incorrect key.

The closest related design, KTACA, uses anonymous client auditing to provide automatic
detection~\cite{yadav2022fakekey}. Parakeet argues that anonymous lookups conflict
with its requirement that only authenticated and permitted users may
query~\cite{malvai2023parakeet-eprint}. The derived, pre-use unpredictable labels used here obtain the
same peer-facing detection without anonymity infrastructure.

\section{STRIDE Threat Analysis}\label{sec:sec-stride}

The threat analysis applies STRIDE~\cite{stride} to the server (Merkle log, prefix tree, signed
tree head), the client (registration, verification, warning monitor), and the auditor. Of twenty threats, sixteen are
addressed by an implemented control and four are residual. The control column distinguishes attacks
that are cryptographically prevented from those detected after they are attempted. Forgery of a VRF
label, a Merkle proof, or a signature is cryptographically prevented, whereas several actions a malicious
server can still attempt (planting a first-write registration, censoring a warning, or fabricating a
divergent head) are not prevented but detected by the transparency log, the warning channel, or the
cross-vantage auditor. \Cref{tab:eval-stride} gives the summary, and
the per-category detail follows in \cref{tab:stride-s,tab:stride-t,tab:stride-r,tab:stride-i,tab:stride-d,tab:stride-e}.

A threat is counted \emph{addressed} when an implemented control prevents or detects the main
attack outcome, even where a limitation remains. It is counted \emph{residual} when no implemented
control addresses that outcome. Observability of an availability failure (for instance, a client
seeing that a server refuses to serve) does not by itself count as addressing it. The Residual column
records both cases: the four counted residual threats are \emph{italicized}, while upright entries
are limitations of rows that are counted addressed.

The forgery threats are assessed under the hash and signature assumptions in \cref{sec:def-primitives}.

The four residuals arise from the trust model and deployment requirements. One follows from the
operator's position in the trust model: the operator learns the association between an account and its VRF-derived
identity label. The same property follows in CONIKS, where the provider computes the VUF-derived
index~\cite[Section~3.4]{melara2015coniks}, and in IETF KeyTrans, where each prefix-tree search key

three concern availability: write flooding, withheld epoch publication, and withheld proofs. These
deployment tasks are discussed in \cref{ch:discussion}.

The \hyperref[sc:threat-a2]{A2 warning-censorship scenario} is distinct from those availability
residuals. Its pre-commit compound signal and transition-audit detection are established in
\cref{sec:sec-suppression}. \Cref{alg:detect} shows the separately tested persistence component,
which is not wired into the live background monitor.

\section{Attack Routes and Detection Timeline}\label{sec:sec-routes}

\Cref{fig:eval-attacktree} is a threat-to-control map that groups the evaluated scenarios by their role. Server substitution (A1), a
network man-in-the-middle attack (A3), and malicious rotation (\hyperref[sc:threat-a5]{A5}) are independent ways of causing a
client to accept an attacker-controlled key. The OR relationship indicates that any one of these
routes can expose message plaintext if the substitution succeeds. Each route is paired with the
control that detects it.

The A2 warning-censorship scenario and A4 split-view equivocation are concealment attempts. A2 suppresses the shared warning, while A4 presents
different signed heads to different vantage points. A key mismatch together with proof-verified
warning absence exposes A2. Comparing signed heads from independent vantage points exposes A4.

These guarantees depend on the assumptions of \cref{ch:threat}. The warning-channel cases require
honest establishment and active monitoring. Detection of A4 split-view equivocation also requires a valid head from an
honest independent vantage. Under these conditions every attack route covered by the threat model produces a warning or
rejecting verdict. Endpoint compromise (X1) remains outside the directory threat model.
