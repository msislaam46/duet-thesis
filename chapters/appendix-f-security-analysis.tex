\section{Warning-Suppression Safeguards}\label{sec:sec-suppression}

The append-only log constrains the \emph{history of committed roots} but not the \emph{contents} of
successive directory states. Within
any epoch whose tree includes the warning leaf, the server cannot answer a warning-slot query with
``absent'': non-inclusion must be \emph{proven} (\cref{ssec:design-verify}), and a valid
non-inclusion proof against a root whose tree contains the leaf would require a hash collision.
Across epochs, however, nothing in the log alone prevents a malicious server from building the
\emph{next} epoch's prefix tree without a leaf that the previous epoch's tree contained, and then
proving that leaf's non-inclusion honestly against the new committed root; every log consistency
proof would continue to verify, because the log records only that roots were appended, not that the
directory evolved admissibly between them. Three safeguards close this gap.

\begin{enumerate}
\item \textbf{Write-once labels.} Dual-index and CEA labels (\cref{ssec:design-modes}) are
write-once: the server's update interface rejects a write to an occupied label in these families,
and the honest interface never removes or modifies an occupied label in a subsequent epoch. The policy is bound into
the signed configuration hash of \cref{eq:design-sth}, so a server that changes it breaks its own
signature for any client that recomputes the commitment.
\item \textbf{Transition audit.} The write-once policy binds an honest server; to bind a malicious
one, the auditor verifies it per epoch. For each committed epoch the server discloses to the auditor
the epoch's update set together with proofs against the previous committed root; the auditor
recomputes the previous root, replays the declared operations (insertions of previously absent
labels and, for key rotation, declared in-place rotations whose disclosed old value must match the
leaf being replaced), verifies that nothing beyond the declared operations changed (the delta
format cannot express a deletion), and checks that the result equals the newly committed root.
Each leaf commits its \emph{kind}, \emph{mutable} (the global-VRF identity slots, which the server
may rotate) or \emph{immutable} (the raw dual-index, CEA, and warning labels, which are write-once),
bound into the leaf hash as $\Hash(\mathit{kind} \concat \mathit{label} \concat \mathit{value})$,
so the kind is authenticated by the very inclusion proof that authenticates the value and the server
cannot relabel it. The auditor therefore \emph{distinguishes} the two families: it accepts a declared
in-place rotation only on a mutable leaf, and \textbf{rejects any rotation of an immutable leaf
outright} (as well as any rotation that misdeclares the leaf's kind). An adversary that has
compromised the pre-shared state and tries to overwrite a committed CEA fingerprint $F_t$ with one
over its injected key must route the write through the privileged interface and declare it as a
rotation; because the target leaf is immutable the transition audit rejects that rotation, so the
epoch fails the auditor's validation and raises an alarm. Entry immutability is thus enforced
\emph{as an auditor acceptance condition}: an immutable-leaf rotation is detected and rejected, not merely surfaced. The owner-side self-checks remain as defence
in depth for the dual-index labels: a replaced lookup slot fails the owner's self-check and a
replaced warning slot still alerts (any value at the slot alerts). But note the CEA fingerprint
overwrite is one the receiver's per-epoch verdict alone \emph{cannot} catch under a pre-shared-state
compromise (the substituted fingerprint matches what the victim recomputes for the injected key), so
it is the auditor's rejection of the immutable-leaf rotation, and the alarm it raises, that closes it. This is
the update-validity role the IETF KeyTrans protocol assigns to third-party auditors, whose
\textsf{AuditorUpdate} structure carries each log entry's added and removed prefix leaves with a
proof against the prior tree, so that the auditor can recompute both roots of the
transition~\cite{ietf-keytrans-protocol}. A deletion or overwrite therefore cannot be committed
without either failing the auditor's validation and raising its alarm, or presenting the auditor a transition that
fails to replay.
\item \textbf{Persistence check.} Independently of any auditor, the writer of a warning retains the
inclusion proof and signed tree head of the epoch at which its warning committed, and the persistence
check re-verifies the warning's inclusion on a later head. In the prototype this check is implemented
and unit-tested as a reference component; it is not wired into the live background monitor
(\cref{alg:detect}). If the leaf later disappears,
the writer holds an inclusion proof under $\mathit{sth}_t$, a non-inclusion proof under
$\mathit{sth}_{t'}$, and a valid consistency proof from $t$ to $t'$: together these three proofs
constitute publicly verifiable evidence, attributable to the server's signing key, that the server
deleted a committed leaf, since all three verify against heads the server itself signed.
\end{enumerate}

The persistence check gives the warning's \emph{writer} evidence of deletion but does not alert a
\emph{peer} that missed the warning. The transition audit independently detects the deletion during
epoch validation. With these safeguards in place, the server's only remaining suppression strategy is
refusal. It can withhold the lookup, the epoch, or the auditor's disclosure, whether for all clients
or selectively for the one revealed warning label. Either way the refusal is observable, since a
client treats anything other than a proof-verified response as a failed check rather than a clean
absence. A refusal therefore never masquerades as a verified absence. The prototype reports it as an
unavailable check (amber, not red), without attributing its cause. The A2 signal proper is the key
mismatch together with a \emph{proof-verified} absence of the warning. All three safeguards are
implemented. The write-once policy and the transition audit run live, the first enforced by the
server's raw-label update interface, the second by the auditor replaying each epoch's declared update
set. The persistence check is a tested reference component (\cref{ch:impl}, \cref{alg:detect}).
The prototype does not implement account-layer authentication of raw-label writes (proof of raw-label
ownership). Without it, the write-once policy still binds an honest server and the transition audit
still binds a malicious one, but a malicious client could pre-emptively occupy a currently empty peer
slot (\cref{ch:discussion}).

\section{STRIDE Enumeration}\label{sec:sec-stride}

The STRIDE enumeration covers the server (Merkle log, prefix tree, signed tree head), the client
(registration, verification, warning monitor), and the auditor. Of twenty threats, sixteen are
addressed by an implemented control and four are residual. The control column distinguishes attacks
that are cryptographically prevented from those detected after they are attempted. Forgery of a VRF
label, a Merkle proof, or a signature is cryptographically prevented, whereas several actions a malicious
server can still attempt (planting a first-write registration, censoring a warning, or fabricating a
divergent head) are not prevented but detected by the transparency log, the warning channel, or the
cross-vantage auditor. \Cref{tab:eval-stride} gives the summary, and
the per-category detail follows in \cref{tab:stride-s,tab:stride-t,tab:stride-r,tab:stride-i,tab:stride-d,tab:stride-e}.

A threat is counted \emph{addressed} when an implemented control prevents or detects the principal
attack outcome, even where a limitation remains; it is counted \emph{residual} when no implemented
control addresses that outcome. Observability of an availability failure (for instance, a client
seeing that a server refuses to serve) does not by itself count as addressing it. The Residual column
records both cases: the four counted residual threats are \emph{italicized}, while upright entries
are limitations of rows that are counted addressed.

The forgery threats are addressed under the assumptions stated in
\cref{sec:threat-assumptions}. These include ECVRF label binding, SHA-256, Ed25519, the append-only
log, and client-side proof verification. Key substitution is detected by the controls evaluated in
\cref{sec:eval-security}.

One residual follows from the semi-trusted-server model. The operator learns the association between
an account and its VRF-derived identity label. This query-privacy limitation is also present in the
surveyed key-transparency deployments, including CONIKS~\cite{melara2015coniks}. ACKA does not address
it because its security model abstracts the log behind the $\Log$ interface~\cite{dowling2023acka}.
The other three residuals concern availability. The prototype does not implement write rate
limiting, a published-epoch staleness timeout, or a gossip transport that exposes proof omission.
These are deployment tasks discussed in \cref{ch:discussion}.

A2 is different from those residuals. If a warning write is censored before commitment, a key
mismatch together with proof-verified warning absence raises the compound alarm. If a committed
warning later disappears, the invalid transition is detected by the transition audit. The separate
persistence component can retain evidence of that disappearance, although it is not wired into the
live background monitor (\cref{alg:detect}).

The four residual risks are of two kinds, and none is a cryptographic weakness. One is inherent to the
semi-trusted-server model: the operator necessarily learns the label-to-user mapping (Information
Disclosure), a residual shared by the standard key-transparency literature (CONIKS~\cite{melara2015coniks},
the IETF Key Transparency architecture~\cite{ietf-keytrans-protocol}) and not addressed by
ACKA~\cite{dowling2023acka}, which abstracts the log behind a security definition rather than
building a distrusted one. The other three are availability functions the proof-of-concept does not
implement: write rate-limiting, a published-epoch staleness timeout, and a gossip transport for
proof-omission. Each is a deployment-layer engineering task rather than a gap in the scheme
(\cref{ch:discussion}).

\section{Attack Routes and Detection Timeline}\label{sec:sec-routes}

\Cref{fig:eval-attacktree} groups the evaluated scenarios by their role. Server substitution (A1), a
network man-in-the-middle attack (A3), and malicious rotation (A5) are independent ways of causing a
client to accept an attacker-controlled key. The OR relationship indicates that any one of these
routes can expose message plaintext if the substitution succeeds. Each route is paired with the
control that detects it.

A2 and A4 instead attempt to conceal an attack. A2 suppresses the shared warning, while A4 presents
different signed heads to different vantage points. A key mismatch together with proof-verified
warning absence exposes A2. Comparing signed heads from independent vantage points exposes A4.

These guarantees depend on the assumptions of \cref{ch:threat}. The warning-channel cases require
honest establishment and active monitoring. Detecting A4 additionally requires a valid head from an
honest independent vantage. Under these conditions every attack route covered by the threat model produces a warning or
rejecting verdict. Endpoint compromise (X1) remains outside the directory threat model.
