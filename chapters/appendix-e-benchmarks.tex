\chapter{Full Benchmark Results}\label{app:benchmarks}

This appendix reproduces the complete aggregate benchmark tables summarized in \cref{ch:eval}. All reported values are
from recorded runs on the single environment below: the $10^7$ run supplies the timing
corpus and M7, and the full-grid run supplies the M14--M16 families. Sizes are exact and
seed-deterministic, and timings are reported as the median and 95th percentile. The metric families M1--M17 and the baseline configurations (\emph{no-KT floor}, \emph{single-index}, \emph{dual-index}, and \emph{windowed}) are defined in \hyperref[sec:bench-defs]{the definitions below}. The code$\to$group$\to$CSV mapping for reproducing each row is given in
\cref{sec:bench-repro}.

Each benchmark setup constructs fresh in-memory state, so no directory state carries between runs.
The fixed VRF and lookup-sampling seeds in \cref{tab:bench-env} make the directory layout and sampled
labels reproducible.

\phantomsection\label{sec:bench-defs}
\section*{Metric and Baseline Definitions}

The seventeen metric families referenced throughout \cref{ch:eval} are as follows.

\begin{description}\itemsep2pt
\item[M1] Lookup proof size in bytes and path length in hashes.
\item[M2] Server-side latency for generating a lookup proof.
\item[M3] Client-side lookup verification latency, reported as prefix-only, VRF-only,
  and full signed-head lookup verification.
\item[M4] Sequential and windowed catch-up proof bytes and proof-generation latency
  as a function of $W$.
\item[M5] The marginal cost of one unverified warning-slot read, reported as a component
  measurement.
\item[M6] Clean-session false-alarm count from the original deterministic experiment,
  retained for reproducibility.
\item[M7] Proof-size and verification distributions, together with resident set size
  after build, over $1{,}000$ random lookups at $N=10^{6}$ and $N=10^{7}$.
\item[M8] Per-operation lookup and update latency, from which a single-thread rate is derived.
\item[M9] Maintenance cost: key rotation and epoch commit.
\item[M10] VRF prove and verify in isolation.
\item[M11] One signed-head lookup verification corresponding to the verification performed
  at the peer-key-retrieval boundary.
\item[M12] STH signature verification, consistency-proof generation and verification, and
  a fork check against one observed head.
\item[M13] Session-mode versus continuous-mode write counts and verification cost.
\item[M14] The history-depth term in proof size and verification latency.
\item[M15] Continuous-mode verification over ratchet depth and the analytic
  write-amplification grid.
\item[M16] Synthetic timings in the Rust implementation for the early-return and clean-match
  detection paths.
\item[M17] Clean-session verdict coverage (functional, no timing).
\end{description}

\medskip\noindent
The measurements use four baseline configurations. \emph{No-KT floor} denotes
M11's local identity-key hash operation without a key-transparency lookup.
\emph{Single-index} denotes the Merkle-log-only comparison, with no prefix
tree or warning slot. \emph{Dual-index} denotes the prefix-tree-and-log
configuration used for the lookup and warning mechanisms.
\emph{Windowed} adds the consistency proofs used for offline catch-up.

Several methodology caveats were recorded with the run. The server is in-memory, with no network and
no database. Proof sizes in the M1 and M7 families are measured on a single-epoch log, so a deployed
$E$-epoch log adds up to $32\lceil\lg E\rceil$ bytes to each lookup proof. The M14 sweep measures that
multi-epoch term directly (\cref{sec:bench-newfamilies}). Memory is resident set size after build, not peak.
The operation-rate figures are single-thread per-operation costs. The SHA-NI row is reported because it affects portability: the SHA-256 implementation dispatches to
the hardware instruction at run time, so a host without it takes a software path for every hash, and
the hash-bound operations (the prefix and full verify, detection, the M8 update, M9, and M13)
would be materially slower there, while the VRF-bound operations, where SHA-256 is off the critical
path, would be largely unaffected. The timings below characterize this configuration, and pinning the
toolchain does not make them portable. The proof sizes are computed quantities and are therefore
hardware-independent.

Per-check verification cost is $27.3\,\si{\micro\second}$ in session mode and

verifier (\texttt{verify\_search\_result\_raw\_for}), so the two medians are directly comparable under the same local verifier. The
continuous-mode setup folds a simulated per-epoch ratchet secret that is distinct from the
authenticated public ratchet key (ACKA's $I$ versus $T$). It is a stand-in for a live Double-Ratchet
DH output, so the figure captures the transparency-layer cost of an epoch, not the ratchet's own key
agreement.

single-thread rate is derived. \texttt{M11\_handshake\_overhead} measures, in Rust, one signed-head lookup
