\chapter{Full Benchmark Results}\label{app:benchmarks}

This appendix reports the complete aggregate benchmark tables summarized in \cref{ch:eval}. All
values come from the recorded runs on the environment below. The large-directory run supplies M7,
while the full-grid run supplies M14--M16. Proof sizes are exact for the fixed seeds. Timings are
reported as medians and 95th percentiles for the recorded environment. The metric families M1--M17
and the baseline configurations are defined below, while \cref{sec:bench-repro} maps each metric to
its benchmark group and CSV source.

Each benchmark setup constructs fresh in-memory state, so no directory state carries between runs.
The fixed VRF and lookup-sampling seeds in \cref{tab:bench-env} make the directory layout and sampled
labels reproducible.

\phantomsection\label{sec:bench-defs}
\section*{Metric and Baseline Definitions}

The seventeen metric families referenced throughout \cref{ch:eval} are as follows.

\begin{description}\itemsep2pt
\item[M1] Lookup proof size in bytes and path length in hashes.
\item[M2] Server-side latency for generating a lookup proof.
\item[M3] Client-side lookup verification latency, reported as prefix-only, VRF-only,
  and full signed-head lookup verification.
\item[M4] Synthetic repeated-proof and windowed catch-up proof bytes and
  proof-generation latency as a function of $W$.
\item[M5] Label derivation and one unverified warning-slot read, reported as a component
  measurement.
\item[M6] Warning-slot occupancy rate across \num{1000} deterministic clean-session fixtures.
  The recorded rate is zero.
\item[M7] Proof-size and verification distributions, together with resident set size
  after build, over $1{,}000$ random lookups at $N=10^{6}$ and $N=10^{7}$.
\item[M8] Per-operation lookup and update latency, from which a single-thread rate is derived.
\item[M9] Maintenance cost: key rotation and epoch commit.
\item[M10] VRF prove and verify in isolation.
\item[M11] One signed-head lookup verification corresponding to the verification performed
  at the peer-key-retrieval integration point.
\item[M12] STH signature verification, consistency-proof generation and verification, and
  a fork check against one observed head.
\item[M13] Session-mode versus continuous-mode write counts and verification cost.
\item[M14] The history-depth term in proof size and verification latency.
\item[M15] Continuous-mode verification over ratchet depth and the analytic
  write-amplification grid.
\item[M16] Local timings for reconstructed owner-mismatch and clean-match detection paths in the
  \texttt{duet} crate.
\item[M17] Clean-workflow verdict coverage (functional, no timing).
\end{description}

\medskip\noindent
The measurements use four baseline configurations. \emph{No-KT floor} denotes
M11's local identity-key hash operation without a key-transparency lookup.
\emph{Single-index} denotes the Merkle-log-only comparison, with no prefix
tree or warning slot. \emph{Dual-index} denotes the prefix-tree-and-log
configuration used for the lookup and warning mechanisms.
\emph{Windowed} adds the consistency proofs used for offline catch-up.

Several methodology caveats were recorded with the run. The server is in-memory, with no network and
no database. Proof sizes in the M1 and M7 families are measured on a single-epoch log, so a deployed
$E$-epoch log adds up to $32\lceil\lg E\rceil$ bytes to each lookup proof. The M14 sweep measures that
multi-epoch term directly (\cref{sec:bench-newfamilies}). Memory is resident set size after build, not peak.
The operation-rate figures are single-thread per-operation costs. The SHA-NI row is retained
because the SHA-256 implementation may use hardware instructions on this host and a software path
on a host without them. This evaluation did not compare the two paths and therefore does not
quantify their performance difference. The timings below apply to the recorded configuration.
Proof sizes are computed quantities and do not depend on the hardware.

The sampling parameters are as follows. The manual timing CSV uses \num{2000} sequential iterations
for every recorded operation except the M9 epoch commit, which uses \num{200}. The M7 experiment
samples \num{1000} random lookups at each directory size. M14 uses \num{500} lookups per grid point
for proof-size distributions and \num{1000} iterations for verification timings. M15 uses
\num{1000} iterations per mode and ratchet depth, while M16 uses \num{2000}. These are descriptive
statistics for the recorded run.

\section{Published Comparison Details}\label{sec:bench-comparison}

The quantities compared in \cref{sec:eval-compare} use different proof formats, implementations,
hardware, and measurement boundaries. This section gives the published source values and the
calculations used to obtain the matched quantities.

\paragraph{Lookup Proof Size.}
CONIKS calls each signed directory commitment a signed tree root (STR). Table~1 counts one
verifiable unpredictable function (VUF) proof, one STR signature, and approximately $\lg N+1$
authentication-path hashes. It reports \num{1216}\,bytes for the elliptic-curve configuration at
$N\approx2^{32}$. Using the same accounting at $N\approx10^6$ gives
$\lceil\lg N\rceil+1=21$ hashes and a total of
$32\times21+96+64=832$ bytes, or \num{768}\,bytes when the signature is
excluded~\cite[Section~5.3 and Table~1]{melara2015coniks}. DUET's \num{817}-byte median also
excludes its signed head and carries no log-inclusion term, because M7 uses a single-epoch log and
M14 measures that term separately. It is approximately 6.4 percent larger than this matched CONIKS
quantity.

Signal's prefix verifier uses a \num{32}-byte index and requires one sibling hash for each of its
\num{256} bits. Since each sibling hash contains \num{32}\,bytes, the fixed copath contains
$256\times32=\num{8192}$ bytes. This total excludes the VRF proof and signed-head
fields~\cite{signal-kt-server}. The copath is approximately 10.0 times DUET's \num{817}-byte median at
$N=10^6$ and 8.7 times its \num{945}-byte median at $N=10^7$. These ratios compare Signal's
sibling copath with DUET's serialized lookup proof. They are not ratios between complete responses.

SEEMless reports an average query-proof size of approximately 8.6\,kB for 10 million users. The
reported proof includes the username and public key, a commitment and its opening, a VRF proof, and
authentication-path material. Its construction uses three authentication paths for each
query~\cite{chase2019seemless}. This result provides additional context but is not directly
matched to the DUET or Signal quantities.

\paragraph{CONIKS Routine Monitoring and Missed Epochs.}
CONIKS reduces routine monitoring bandwidth by returning the STR signature and only the
authentication-path hashes that changed during the epoch. Its performance evaluation derives
an average of \num{736}\,bytes per epoch and reports approximately \num{19.1}\,kB per
day~\cite[Section~5.3]{melara2015coniks}. Table~1 of the same paper instead gives
\num{726}\,bytes per epoch and \num{17.6}\,kB per day for the same elliptic-curve
configuration~\cite[Table~1]{melara2015coniks}. The \num{726}-byte table entry does not match the
expression $64+\lg(n)\times32$ in Section~5.3. Under that section's assumption that
$n\approx2^{21}$, the expression evaluates to
\num{736}\,bytes~\cite[Section~5.3]{melara2015coniks}. The main chapter therefore uses
only the conclusion supported by both presentations: the reported routine-monitoring cost is less
than 20\,kB per day.

For a client that has missed several epochs, CONIKS requires a series of checks connecting the
previously verified inclusion proofs and signed tree roots to the more recent
proofs~\cite{melara2015coniks}. The paper does not provide a total byte cost for a
$W=720$ missed window. If the reported \num{736}-byte average routine-monitoring cost were applied
to each of the \num{720} missed epochs, the resulting checks would total
\num{529920}\,bytes. This is an illustrative calculation, not a published CONIKS catch-up result.
The \num{736}-byte CONIKS value includes signed-root signatures and compressed changed
authentication paths, while DUET's
\num{320}-byte M4 value counts raw consistency-path hashes and excludes serialization and
transport. Therefore, this calculation shows how repeated checks can accumulate but is not used to
calculate a direct byte ratio against DUET.

Signal defines a \texttt{MonitorV2} endpoint whose request carries entry positions, commitment
indices, and consistency parameters. The cited repository does not publish a matched byte total for
a $W=720$ offline window~\cite{signal-kt-server}.

\paragraph{Client-Verification Timing.}
At $N=10^7$, CONIKS reports \SI{159}{\micro\second} for authentication-path verification and
approximately \SI{400}{\micro\second} for signature verification. These reported components give a
path-and-signature subtotal of approximately \SI{559}{\micro\second}. The source states that lookup
verification also requires one VUF verification but does not report its time
separately~\cite[Section~5.3]{melara2015coniks}. At the same directory size, DUET's median is
\SI{139.2}{\micro\second} and includes VRF, prefix, log-inclusion, and signed-head verification. The
implementations, hardware, and workloads differ. Thus, these values provide published context and do
not establish a controlled speed comparison.

\section{Reproducing Each Metric}\label{sec:bench-repro}

\Cref{tab:bench-repro} maps every metric family to the benchmark group, computation, or test that
produces it and to the CSV source or test command that records it. Therefore, each reported row can
be regenerated and located. The
harness lives in \texttt{benches/kt\_bench.rs}. Run it via \texttt{run-benches.ps1} (the scale family
M7 runs only with \texttt{-ScaleOnly} / \texttt{KT\_BENCH\_LARGE\_N=1}). Sizes are seed-deterministic
and must reproduce byte-for-byte. Timing values may vary with the
measurement environment.
