\chapter{Design}\label{ch:design}

This chapter presents DUET's architecture, dual-index warning scheme, windowed consistency proof, and
instantiation of ACKA. \Cref{app:algorithms} gives the pseudocode, and \cref{ch:eval} evaluates the
associated costs.

\paragraph{Notation.} The construction uses SHA-256 with RFC~6962 leaf and node tags, byte-string
concatenation $\concat$, and fixed-width service identifiers. \Cref{sec:def-primitives}
defines the primitives and encodings used below.

\section{Architecture}\label{sec:design-arch}

The architecture combines three authenticated data structures, with each layer authenticating the
one below (\cref{fig:design-arch}). The prefix tree stores the
current directory state, the append-only log records every committed version of that state, and the
signed tree head authenticates the latest log root. Together, they follow the combined-tree design of
the IETF Key Transparency working group (\cref{ssec:bg-keytrans}). Lookups are served against the \emph{last
committed epoch}, never the live tree. Only a committed prefix root has been appended to the log and
can therefore be linked by an inclusion proof to a signed tree head.

\centering
\input{figures/tikz/fig-design-arch}
\caption[The authenticated directory core.]{The authenticated directory core. The prefix tree,
Merkle log, and signed tree head form the commitment chain. The VRF derives global directory
labels.}
\label{fig:design-arch}
\end{figure}

\subsection{The Three Structures}\label{ssec:design-structures}

The prefix tree stores label-to-value bindings. Global identity slots use VRF-derived labels, while
the clients derive conversation lookup, warning, and continuous-mode labels from shared state. Each
committed prefix root becomes one leaf of an append-only Merkle log, and an Ed25519 signed tree head
authenticates the latest log root. A lookup is accepted only after its prefix proof, the committed
prefix root's log inclusion, and the signed head have all verified.

\paragraph{Why a VRF?} The VRF implements G3 (Directory Privacy)
(\cref{sec:threat-goals}). The operator holds the VRF secret key and maps a user
identifier to a pseudorandom label, attaching a proof that the label was computed
correctly. A client verifies that proof against the operator's public key but cannot
itself compute or predict any other label (\cref{ssec:bg-ct2kt}). The labels are thus
deterministic for the operator yet unpredictable to outsiders, which prevents an
observer from enumerating the directory.

\subsection{Epoch Lifecycle: Update, Commit, and the Signed Tree Head}\label{ssec:design-epoch}

An $\textsf{update}(\mathit{label},\mathit{value})$ changes one path in the current 256-level sparse
tree. A later $\textsf{commit\_epoch}()$ appends the resulting root to the log, snapshots that state
for lookups, and signs the new head. Lookups are served only against the last committed snapshot.

The signed message is:
\begin{equation}\label{eq:design-sth}
  \mathit{epoch} \concat \mathit{tree\_size} \concat \mathit{root} \concat
  \mathit{timestamp} \concat \Hash(\mathit{config}),
\end{equation}
where $\Hash(\mathit{config}) = \Hash(\mathit{pk}_{\mathsf{vrf}} \concat
\mathit{pk}_{\mathsf{sth}} \concat \mathit{suite} \concat \mathit{version} \concat
\mathit{epoch\_interval} \concat \mathit{raw\_label\_policy})$ binds the write-once raw-label policy so
the server cannot silently relax it. In \cref{eq:design-sth}, the epoch, log size, root, timestamp,
and configuration hash bind the head to one directory state and one parameter set. The client must
additionally apply a freshness policy, which the prototype does not yet implement. The full field
rationale and configuration-substitution cases are given in \cref{sec:design-detail-sth}.

\subsection{The Client Verification Chain}\label{ssec:design-verify}

A client verifies every response against the signed head through the six checks in
\cref{fig:design-verify}. Global identity lookups include the VRF check, whereas client-derived raw
labels begin with the requested-label binding. The returned head must equal the independently
verified current head or the new head accepted during catch-up. The prefix root must also be the
latest log leaf under that head, preventing acceptance of a stale committed snapshot.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-verify}
\caption[The six-step client verification chain.]{The six-step client verification chain. Every lookup is checked locally
against a signed root.}
\label{fig:design-verify}
\end{figure}

The Rust and TypeScript implementations enforce the same chain. The full-verification measurement in
\cref{ch:eval} includes every check. \Cref{sec:design-detail-sth} examines signed-head freshness and
binding in greater detail.

\section{The Dual-Index Warning Scheme}\label{sec:design-dual}

The dual-index scheme meets the in-band peer-warning requirement of \cref{ssec:bg-implications} and so
achieves G1 (Key-Substitution Detection) against the substitution attacks
\hyperref[sc:threat-a1]{A1}, \hyperref[sc:threat-a3]{A3}, and \hyperref[sc:threat-a5]{A5}. An in-band
warning channel flags a server-side slot substitution (A1) and its continuous-mode counterpart (A5).
The secret-derived dual-index labels detect a network man-in-the-middle (A3), because an attacker with
a different shared secret derives disjoint labels, so the proof-verified lookup returns non-inclusion.
A comparison with the peer's global VRF-anchored directory entry also detects pre-emptive occupation
of the expected slot, because an attacker-controlled value cannot match the authenticated global key.

\subsection{Label Derivation}\label{ssec:design-labels}

The dual-index scheme allocates three directory slots to each conversation: two lookup
slots (one per party) and one shared warning slot (\cref{fig:design-dualindex}).
Alice and Bob derive these slot labels from the X3DH/PQXDH shared secret $\sharedS$
(\cref{ssec:bg-x3dh}) using HKDF-SHA256 as specified in RFC~5869~\cite{rfc5869}, the same
key-derivation function Signal already uses elsewhere:
\begin{equation}\label{eq:design-labels}
\begin{aligned}
  \mathit{PRK} &= \HKDFex(\text{salt} = \text{\texttt{"duet-dual-index"}},\ \sharedS)\\
  \ell_{\mathsf{self}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{self}} \concat \mathit{id}_{\mathsf{peer}},\ 32\big)\\
  \ell_{\mathsf{peer}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{peer}} \concat \mathit{id}_{\mathsf{self}},\ 32\big)\\
  \ell_{\mathsf{warn}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"warning"}} \concat \min(\mathit{id}_\A, \mathit{id}_\B) \concat \max(\mathit{id}_\A, \mathit{id}_\B),\ 32\big).
\end{aligned}
\end{equation}
In \cref{eq:design-labels}, $\mathit{PRK}$ is the extracted pseudorandom key. Directional identity ordering gives each party
a separate lookup slot, while canonical ordering gives both parties the same warning slot. Every
output is 32 bytes. The Rust and TypeScript implementations are checked for byte-for-byte agreement on
these derivations (\cref{sec:tests-xlang}). \Cref{fig:design-dualindex} shows the two directional
lookup slots and shared warning slot.

\begin{figure}[ht]
\centering
\input{figures/tikz/fig-design-dualindex}
\caption[The dual-index scheme's three derived slots.]{Two lookup slots and a shared warning slot
are derived from the conversation secret $\sharedS$. HKDF-Extract produces $\mathit{PRK}$.
Three domain-separated HKDF-Expand operations then produce $\ell_{\mathsf{self}}$,
$\ell_{\mathsf{peer}}$, and $\ell_{\mathsf{warn}}$. Alice and Bob share $\sharedS$, so both parties derive

\end{figure}

\subsection{The Three Security Properties}\label{ssec:design-properties}

The derivation establishes three properties on which detection rests.

\paragraph{Symmetry.} From Alice's and Bob's respective viewpoints, the directional lookup
derivation ensures $A.\ell_{\mathsf{self}} = B.\ell_{\mathsf{peer}}$ and $A.\ell_{\mathsf{peer}} =
B.\ell_{\mathsf{self}}$, while the canonical identity ordering gives $A.\ell_{\mathsf{warn}} =
B.\ell_{\mathsf{warn}}$. The two parties therefore agree on the two directional lookup slots and the
shared warning slot they both monitor.

\paragraph{Pre-Use Unpredictability.} The server does not hold $\sharedS$, so the HKDF outputs are
pseudorandom from the server's perspective and it cannot distinguish $\ell_{\mathsf{warn}}$ from
any other leaf in the tree. It can therefore neither pre-position a value on the warning slot nor
recognize and selectively censor it. This protection holds until the label is first queried. After
first use the operator can associate a conversation's labels, and those consequences are handled by
the write-once policy, the transition audit, and the persistence check (\cref{ssec:design-detection}).

\paragraph{Scope of the Warning Channel.} The shared warning channel applies only after an honest
X3DH/PQXDH handshake has established a common secret. It covers A1 and A5 for established pairs.
First-contact A3 is detected through divergent labels and comparison with the peer's global VRF-bound
entry, while a substitution that predates an honest baseline remains the TOFU boundary
(\cref{sec:threat-fair}).

\subsection{Detection and the Bidirectional Warning}\label{ssec:design-detection}

On detecting a suspicious key at a lookup slot, the client writes a warning payload to
$\ell_{\mathsf{warn}}$. Both parties' background monitors read this slot on their next check and
raise a warning. The payload carries a MAC under a key derived from the shared secret and the
canonically ordered identities
($\HKDFexp(\mathit{PRK}, \text{\texttt{"warn-mac"}} \concat \min(\mathit{id_A},\mathit{id_B}) \concat \max(\mathit{id_A},\mathit{id_B}), 32)$).
Only the two conversation parties can produce or verify this MAC. The warning label is unpredictable
to the operator until one party reveals it in a request, so any \emph{unauthenticated} value returned
at that location is itself suspicious and still raises a warning. After the operator observes the
label, a valid MAC shows that a holder of the shared key produced the value rather than the operator.
Since both parties derive the same key, it does not identify the writer (\cref{ssec:design-properties}).

An append-only log authenticates committed roots but does not by itself constrain directory
transitions. DUET therefore combines write-once labels, per-epoch transition auditing, and retained
persistence evidence. \Cref{sec:sec-suppression} gives the full suppression and offline-detection
analysis, including the \hyperref[sc:threat-a2]{A2} compound condition and the treatment of refused responses.

\subsection{Shared-Label Consistency}\label{ssec:design-consistency}

Alice's peer lookup and Bob's self-check use the same directional label. Under one signed head that
label cannot authenticate two different values, even if the conversation secret is known.
\Cref{lem:dualindex-consistency} states the same-head result, while
\cref{def:g1-consistency} covers the surrounding detection cases. The same-head result does not cover
warning publication, changes across epochs, offline catch-up, or equivocation. Those cases rely on
warning persistence, transition auditing, windowed consistency, and cross-vantage comparison.

CEA authenticates a fingerprint stored at an entry. The dual-index construction determines the
conversation-derived locations at which entries and warnings are stored. A complete combined proof
remains future work (\cref{ch:discussion}).

\subsection{Session and Continuous Authentication Modes}\label{ssec:design-modes}

In \emph{session mode}, labels derive from the initial X3DH or PQXDH secret, and each slot stores the
identity key. A party re-registers when its signed pre-key rotates. The remaining handshake values are
not logged separately, but they contribute to the shared secret from which the labels derive.
\Cref{tab:design-x3dh-coverage} summarizes this coverage.

\emph{Continuous mode} follows ACKA's CEA construction. At epoch $t$, each party derives a shared label
$L_t$ and a directional fingerprint $F_t$ from the current chained state and public ratchet key, then
mixes the secret epoch input $I_t$ into the next state:
\begin{equation}\label{eq:design-cea}
\begin{aligned}
  L_t &= \Hash\!\big(k_t \concat \min(\mathit{id}_\A, \mathit{id}_\B) \concat \max(\mathit{id}_\A, \mathit{id}_\B) \concat t\big),\\
  F_t &= \Hash\!\big(\KDF(k_t,\ \mathit{id}_{\mathsf{sender}} \concat \mathit{id}_{\mathsf{peer}} \concat t) \concat T_t\big),\\
  k_{t+1} &= \KDF\!\big(k_t,\ \KDF(I_t, \text{\texttt{"CEA"}})\big) \qquad (\KDF = \text{HMAC-SHA256, a PRF}).
\end{aligned}
\end{equation}
In \cref{eq:design-cea}, both parties derive the same $L_t$, while $F_t$ binds the sender and public ratchet key. The sender
checks that the label is empty before writing, and the receiver advances only after a
\textsc{Consistent} verdict. An occupied label or mismatching fingerprint produces a warning and
leaves the chain unchanged. \Cref{sec:design-detail-cea} gives the full operation ordering and explains
how DUET's single-value directory implements ACKA's detection objective.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-design-modes}
\caption[Session mode versus continuous mode.]{Session mode derives labels from the initial secret
$\sharedS$ and registers the identity key once per pre-key rotation. Continuous mode derives a
label and fingerprint from the pre-update state $k_t$ at every epoch and authenticates the public

\label{fig:design-modes}
\end{figure}

\Cref{fig:design-modes} contrasts the two authentication modes. Session mode authenticates the
identity binding with one write per signed-pre-key rotation.
Continuous mode authenticates each ratchet epoch but writes once per epoch. Both share the directory,
signed heads, and warning channel. The prototype uses a deterministic conversation-secret stand-in
and a seeded ratchet simulation, and its synchronous CEA chain does not yet handle skipped
ratchet epochs. Production integration must obtain Signal's live conversation secret and add explicit
epoch and skipped-state handling (\cref{ch:discussion}).

\section{Windowed Consistency Proofs}\label{sec:design-windowed}

\subsection{The Catch-Up Problem and the Bound}\label{ssec:design-catchup}

The windowed proof implements G2. A client returning after $W$ epochs requests one RFC~9162
consistency proof between its last trusted log size $m$ and the current size $n$, rather than one
proof for each intermediate epoch~\cite{rfc9162}. Its size is bounded by:
\begin{equation}\label{eq:design-proofsize}
  |\pcons(m, n)| \le \lceil \log_2 m \rceil + \lceil \log_2 n \rceil \quad\text{hashes},
\end{equation}
The bound in \cref{eq:design-proofsize} covers one consistency proof between the trusted and new
heads. The client accepts only if the new signed head is an append-only extension of the trusted head. The
warning-slot lookup occurs in the same synchronization workflow and does not change the asymptotic
bound. \Cref{lem:windowed-size} states the result, and \cref{alg:client} gives the procedure.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-design-windowed}
\caption[Windowed offline catch-up.]{Offline catch-up over $W=n-m$ epochs. The upper arcs show
the synthetic evaluation baseline, which verifies one consistency proof per missed epoch at
$O(W\log n)$. The lower arc shows the RFC~9162 windowed approach, which requests one
consistency proof between the trusted head at $m$ and the current head at $n$. Its proof size is
logarithmic in the log size.}
\label{fig:design-windowed}
\end{figure}

\Cref{fig:design-windowed} contrasts one windowed proof with repeated per-epoch proofs. Endpoint
consistency alone cannot expose a substitution inserted and reverted inside the offline
window. Detection of such a transient attack therefore depends on a peer observing the substituted
key and committing a warning. A committed warning is protected by three safeguards. Write-once enforcement prevents replacement of
an occupied slot, the transition audit rejects an invalid declared change, and persistence evidence
exposes a later removal from the committed history. If the operator censors the write in the first
place, the distant-head proof still establishes append-only consistency but cannot exclude that
transient substitution. The complete argument is given in
\cref{sec:design-detail-window}.

\subsection{Worked Parameterization}\label{ssec:design-param}

For $N=10^7$ users, let $c=5$ be the active conversations per user and $r=30$ days the signed-pre-key
rotation period. With hourly epochs, the illustrative directory carries about 50 million
user--conversation lookup entries and a returning client may miss $W=r\cdot24=720$ epochs.
Each conversation also allocates one shared warning label, normally unwritten. Amortized over the
illustrative 30-day rotation period, the lookup entries are about 1.67~million directory updates per
day, or roughly $69{,}400$ updates folded into each hourly epoch commit (the log itself
gains one leaf per epoch regardless of update volume, \cref{ssec:design-epoch}).
\Cref{ch:eval} evaluates this parameterization.

\section{Instantiating ACKA}\label{sec:design-acka}

ACKA composes continuous key agreement, CEA, and an abstract secure-log interface
$\Log$~\cite{dowling2023acka}. DUET instantiates $\Log$ with the prefix tree, Merkle log, signed heads,
consistency and exclusion proofs, write-once raw labels, and transition validation. Continuous mode
retains ACKA's per-epoch label-and-fingerprint construction.

ACKA and DUET represent a label's history differently. ACKA detects impersonation when conflicting
fingerprints appear at one label, whereas DUET stores one immutable value per label. DUET therefore
detects an earlier adversarial post through the sender's occupancy check and a later overwrite through
transition auditing. The receiver's per-epoch check alone does not cover the overwrite case, so that
case depends on the audit. A complete proof that this representation preserves ACKA's guarantees
remains future work.

DUET additionally supplies conversation-derived lookup labels and a shared warning slot, windowed
catch-up, and cross-vantage fork detection. These additions address malicious directory behaviour,
peer notification, and offline recovery beyond ACKA's assumed log. The complete
component mapping is in \cref{tab:design-acka}.

\paragraph{Directory Structure.} A sparse binary Merkle tree gives uniform node semantics and
first-class non-inclusion for an empty warning slot. Path compression keeps transmitted proof size
dependent on populated prefix depth, while binary branching avoids the wider copaths and encodings of
an $n$-ary trie. Accumulators would make the required non-membership proof more expensive.

\paragraph{Global-Label Derivation.} Global slots use ECVRF-EDWARDS25519-SHA512-TAI rather than a bare
hash. The VRF therefore provides publicly verifiable outsider-enumeration resistance and matches Signal's deployed
suite~\cite{rfc9381,signal-kt-server}.

\paragraph{Combined Prefix-Plus-Log Stack.} The prefix tree authenticates the present directory,
while the log authenticates its history. One structure alone would not provide both lookup proofs and
the consistency evidence required by windowed catch-up and cross-vantage fork detection. The extra
cost is one log-inclusion path, quantified in \cref{ch:eval}. The combined stack provides one authenticated
chain from a directory entry to a signed history and retains direct non-inclusion proofs for the
warning slot. \Cref{sec:design-detail-alternatives} compares the alternatives, and
\cref{tab:threat-goals} maps the choices to the security requirements.
