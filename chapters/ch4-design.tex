\chapter{Design}\label{ch:design}

This chapter presents DUET's architecture, dual-index warning scheme, windowed consistency proof, and
instantiation of ACKA. \Cref{app:algorithms} gives the pseudocode, and \cref{ch:eval} evaluates the
associated costs.

\paragraph{Notation.} The construction uses SHA-256 with RFC~6962 leaf and node tags, byte-string
concatenation $\concat$, and fixed-width account identifiers. \Cref{sec:def-primitives}
defines the primitives and encodings used below.

\section{Architecture}\label{sec:design-arch}

DUET follows the IETF Key Transparency combined-tree design described in
\cref{ssec:bg-keytrans}. \Cref{fig:design-arch} shows its three-layer commitment chain.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-arch}
\caption[The authenticated directory core.]{The authenticated directory core. The prefix tree,
Merkle log, and signed tree head form the commitment chain. The VRF derives global directory
labels.}
\label{fig:design-arch}
\end{figure}

\subsection{The Three Structures}\label{ssec:design-structures}

The prefix tree stores label-to-value bindings. Global identity slots use VRF-derived labels, while
clients derive conversation lookup, warning, and continuous-mode labels from shared state. Each
committed prefix root becomes a leaf of the append-only Merkle log, and an Ed25519 signature on the
tree head authenticates the latest log root. A lookup is accepted only after the client verifies the
prefix proof, the prefix root's inclusion in the log, and the signed head.

\paragraph{Why a VRF?} The VRF implements G3 (Directory Privacy)
(\cref{sec:threat-goals}). The directory operator holds the VRF secret key and maps a user
identifier to a pseudorandom label, attaching a proof that the label was computed
correctly. A client verifies that proof against the operator's public key but cannot compute other
labels locally (\cref{sec:def-vrf}). The labels are deterministic for the operator but
pseudorandom to an observer of the published directory, protecting identifiers against offline
enumeration.

\FloatBarrier
\subsection{Epoch Lifecycle: Update, Commit, and the Signed Tree Head}\label{ssec:design-epoch}

An update operation changes one path in the current 256-level sparse
tree. A subsequent $\textsf{CommitEpoch}()$ appends the resulting prefix root to the log,
snapshots the tree for later lookups, and signs the new head. Lookups use only the last committed
snapshot. The live tree is not queried because its root has not yet been included in the log
authenticated by a signed head.

The signed message is:
\begin{equation}\label{eq:design-sth}
  \mathit{epoch} \concat \mathit{tree\_size} \concat \mathit{root} \concat
  \mathit{timestamp} \concat \Hash(\mathit{config}).
\end{equation}
In \cref{eq:design-sth}, $\Hash(\mathit{config}) = \Hash(\mathit{pk}_{\mathsf{vrf}} \concat
\mathit{pk}_{\mathsf{sth}} \concat \mathit{suite} \concat \mathit{version} \concat
\mathit{epoch\_interval} \concat \mathit{raw\_label\_policy})$ binds the VRF and signing keys,
suite, version, epoch interval, and write-once raw-label policy into the signed head. A client
recomputes this commitment from its expected keys and constants and rejects a mismatch, while the
transition audit replays each epoch's declared changes against the committed roots to check that the
policy was followed. The signed timestamp allows a client to apply a freshness policy, although
implementing that policy is outside the scope of this thesis. The full field rationale and
configuration-substitution cases are given in \cref{sec:design-detail-sth}.

\subsection{The Client Verification Chain}\label{ssec:design-verify}

A client verifies each lookup response through applicable checks shown in
\cref{fig:design-verify}. A global identity lookup binds the proof label to the verified VRF output.
For a client-derived raw label, the proof must be bound to the requested label. An occupied raw slot is
accepted only if its committed entry is immutable. The signed head for the result must have a valid
signature and belong to the client's accepted append-only history. The prefix root must also be the
latest log leaf under that head, preventing acceptance of an older committed directory state.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-design-verify}
\caption[The six-step client verification chain.]{The six-step client verification chain. Every
lookup is checked locally against a verified signed tree head. Here, $\pprefix$ denotes the
prefix-tree proof returned with the lookup, $\pvrf$ denotes the VRF proof for a global lookup, and
$\beta$ is the verified VRF output.}
\label{fig:design-verify}
\end{figure}

The \texttt{duet} crate provides the proof and signed-head verification functions. The Signal
Desktop client applies this verification chain to lookup responses.
\Cref{sec:design-detail-sth} examines signed-head freshness and binding in greater detail.

\section{The Dual-Index Warning Scheme}\label{sec:design-dual}

The dual-index scheme provides the in-band peer-warning channel required by
\cref{ssec:bg-implications} and supports G1 (Key-Substitution Detection) for established
conversations.

\subsection{Label Derivation}\label{ssec:design-labels}

The dual-index scheme allocates three directory slots to each conversation: one lookup slot for each
party and one shared warning slot (\cref{fig:design-dualindex}). Alice and Bob derive the three
labels from the X3DH/PQXDH shared secret $\sharedS$ (\cref{ssec:bg-x3dh}) using the HKDF-SHA256
Extract and Expand steps~\cite[Sections~2.2--2.3]{rfc5869}:
\begin{equation}\label{eq:design-labels}
\begin{aligned}
  \mathit{PRK} &= \HKDFex(\text{salt} = \text{\texttt{"duet-dual-index"}},\ \sharedS)\\
  \ell_{\mathsf{self}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{self}} \concat \mathit{id}_{\mathsf{peer}},\ 32\big)\\
  \ell_{\mathsf{peer}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{peer}} \concat \mathit{id}_{\mathsf{self}},\ 32\big)\\
  \ell_{\mathsf{warn}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"warning"}} \concat \min(\mathit{id}_{\mathsf{self}}, \mathit{id}_{\mathsf{peer}}) \concat \max(\mathit{id}_{\mathsf{self}}, \mathit{id}_{\mathsf{peer}}),\ 32\big).
\end{aligned}
\end{equation}
In \cref{eq:design-labels}, $\mathit{PRK}$ is the extracted pseudorandom key. The fixed-width
identifier encoding makes the concatenated identity fields unambiguous without separate length
prefixes. Directional identity ordering produces one lookup label for each party, while canonical
ordering produces the same warning label for both. Each label is 32 bytes. Cross-implementation
vectors require the \texttt{duet} crate and Signal Desktop client to derive identical bytes
(\cref{sec:tests-xlang}). \Cref{fig:design-dualindex} shows the derivation from Alice's viewpoint.

\begin{figure}[ht]
\centering
\input{figures/tikz/fig-design-dualindex}
\caption[The dual-index scheme's three derived slots.]{Dual-index label derivation from the
conversation secret $\sharedS$, shown from Alice's viewpoint. HKDF-Extract produces
$\mathit{PRK}$, and three domain-separated HKDF-Expand operations produce Alice's lookup label,
Bob's lookup label, and the shared warning label. Bob reverses the directional identity order,
which swaps the two lookup roles while preserving the warning label.}

\end{figure}

\subsection{Security Properties}\label{ssec:design-properties}

\paragraph{Symmetry.} From Alice's and Bob's respective viewpoints, the directional lookup
derivation ensures $\ell^\A_{\mathsf{self}} = \ell^\B_{\mathsf{peer}}$ and
$\ell^\A_{\mathsf{peer}} = \ell^\B_{\mathsf{self}}$, while the canonical identity ordering gives
$\ell^\A_{\mathsf{warn}} = \ell^\B_{\mathsf{warn}}$. The two parties therefore agree on the two
directional lookup slots and the shared warning slot they both monitor. Since a signed head
commits to one directory root, valid proofs under that head cannot bind the same directional lookup
slot to two different keys, even if the conversation secret is known.
\Cref{lem:dualindex-consistency} states this result, and \cref{def:g1-consistency} explains its role
in the broader G1 key-substitution requirement.

\paragraph{Pre-Use Unpredictability.} Before a conversation label is used, the operator does not
know the high-entropy secret $\sharedS$. Under the HKDF assumption, the outputs are
pseudorandom from the operator's perspective. Therefore, the operator cannot derive or recognize the
warning label except with negligible probability and cannot identify its slot in advance to
pre-position a value or selectively censor it. A read or write reveals the label to the operator and
ends this protection. The controls that apply after disclosure are described in
\cref{ssec:design-detection}.

\paragraph{Scope of the Warning Channel.} The shared warning channel applies only after an honest
X3DH/PQXDH handshake has established a common secret. For established pairs, it covers the
\hyperref[sc:threat-a1]{A1 key-substitution scenario} and the
\hyperref[sc:threat-a5]{A5 malicious key-rotation scenario}. When the directory is honest,
comparison with the peer's global VRF-bound identity entry detects a first-contact
\hyperref[sc:threat-a3]{A3 substitution}, while the resulting peer-slot absence provides only
supporting evidence of that substitution. The warning channel therefore assumes an honest baseline,
subject to the TOFU limitation in \cref{sec:threat-fair}.

\subsection{Detection and the Bidirectional Warning}\label{ssec:design-detection}

A client writes a warning payload to $\ell_{\mathsf{warn}}$ when its own lookup slot does not
contain its local identity key or when a peer's lookup slot contains a key different from the peer
identity key already pinned by the client. Either party can write the warning, and both background
monitors read the shared slot.

The warning payload carries a MAC under a key derived from the shared secret and the canonically
ordered identities
($\HKDFexp(\mathit{PRK}, \text{\texttt{"warn-mac"}} \concat
\min(\mathit{id}_{\mathsf{self}},\mathit{id}_{\mathsf{peer}}) \concat \max(\mathit{id}_{\mathsf{self}},\mathit{id}_{\mathsf{peer}}), 32)$).
While their endpoints remain uncompromised, only Alice and Bob can derive this key. A valid MAC
shows that a holder of the shared key produced the warning but does not identify which party wrote
it. Any value at the warning slot causes an alert, so a value without a valid MAC is reported as
unauthenticated and still raises a warning.

An append-only log authenticates committed roots but does not establish that directory transitions
are valid. Therefore, DUET uses write-once entries for the dual-index and warning slots, per-epoch
transition auditing, and retained persistence evidence. \Cref{sec:sec-suppression} analyses warning
suppression and offline detection, including the compound signal for
\hyperref[sc:threat-a2]{A2 warning censorship} and the handling of refused responses.

\subsection{Session and Continuous Authentication Modes}\label{ssec:design-modes}

DUET supports two authentication granularities. Session mode authenticates the identity binding for a
conversation, while continuous mode uses ACKA's continuous entity authentication (CEA) to authenticate
later public ratchet keys.

In \emph{session mode}, labels derive from the X3DH or PQXDH secret established for the conversation,
and each party registers its identity key at its own derived lookup slot. Each new conversation
secret produces a new set of lookup and warning labels. The remaining handshake values are not logged
separately, but they contribute to the shared secret from which the labels derive.
\Cref{tab:design-x3dh-coverage} summarizes this coverage.

\emph{Continuous mode} follows ACKA's CEA construction. At epoch $t$, each party derives a shared label
$L_t$ and a directional fingerprint $F_t$ from the current chained state and public ratchet key, then
mixes the secret epoch input $I_t$ into the next state:
\begin{equation}\label{eq:design-cea}
\begin{aligned}
  L_t &= \Hash\!\big(k_t \concat \min(\mathit{id}_{\A}, \mathit{id}_{\B}) \concat \max(\mathit{id}_{\A}, \mathit{id}_{\B}) \concat t\big),\\
  F_t &= \Hash\!\big(\KDF(k_t,\ \mathit{id}_{\mathsf{sender}} \concat \mathit{id}_{\mathsf{peer}} \concat t) \concat T_t\big),\\
  k_{t+1} &= \KDF\!\big(k_t,\ \KDF(I_t, \text{\texttt{"CEA"}})\big) \qquad (\KDF = \text{HMAC-SHA256, a PRF}).
\end{aligned}
\end{equation}
In \cref{eq:design-cea}, both parties derive the same $L_t$, while $F_t$ binds the sender's
identity and public ratchet key $T_t$ to that epoch. The sender writes $F_t$ only after a verified
non-inclusion proof shows that $L_t$ is empty and advances only after a verified read-back confirms
the committed fingerprint. The receiver advances only when a verified lookup
returns the expected $F_t$, producing a \textsc{Consistent} verdict. A persistent absence after the
retry window produces \textsc{NotPosted}, while a different fingerprint produces \textsc{Fork} and
causes the receiver to attempt to publish a shared warning. Neither outcome advances the state.
\Cref{fig:design-modes} contrasts the two modes and shows these sender and receiver outcomes.
\Cref{sec:design-detail-cea} gives the full operation ordering and explains how DUET's single-value
directory implements ACKA's detection objective.

\section{Windowed Consistency Proofs}\label{sec:design-windowed}

\subsection{The Catch-Up Problem and the Bound}\label{ssec:design-catchup}

The windowed proof implements G2 (Consistency Across Offline Windows). A returning client that
retains a trusted head requests one RFC~9162 consistency proof $\pcons(m,n)$ from its last verified
log size $m$ to the current size $n$~\cite[Section~2.1.4]{rfc9162}. Its size is bounded by:
\begin{equation}\label{eq:design-proofsize}
  |\pcons(m, n)| \le \lceil \log_2 m \rceil + \lceil \log_2 n \rceil
  \quad\text{hashes}.
\end{equation}
The bound in \cref{eq:design-proofsize} covers one consistency proof between the trusted and current
heads. The client accepts only when the current signed head is an append-only extension of the
trusted head. The warning-slot lookup follows this consistency check as a separate verified lookup.
It is not part of $\pcons(m,n)$ and does not alter its size bound.
\Cref{lem:windowed-size} provides the proof sketch, and \cref{alg:client} gives the client procedure.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-design-windowed}
\caption[Windowed offline catch-up.]{Offline catch-up over $W=n-m$ missed epochs. The upper arcs
represent the synthetic evaluation baseline, which verifies one consistency proof for each missed
epoch at $O(W\log n)$. The lower arc represents one RFC~9162 consistency proof between the trusted
head at $m$ and the current head at $n$~\cite[Section~2.1.4]{rfc9162}. Its size is logarithmic in
the endpoint log sizes.}
\label{fig:design-windowed}
\end{figure}

As shown in \cref{fig:design-windowed}, the windowed proof verifies consistency between the retained
trusted head and the current head, but it does not inspect every intermediate directory state.
Detecting a substitution inserted and reverted within the offline window through the returning
client's catch-up path therefore depends on a peer observing it and committing a warning. If the
directory operator censors the warning before it is committed, the consistency proof can still
verify append-only growth between the endpoint heads without revealing the substitution. The
safeguards that apply after commitment are described in \cref{ssec:design-detection}, while
\cref{sec:design-detail-window} gives the complete supporting argument.

\subsection{Worked Parameterization}\label{ssec:design-param}

For an illustrative analytic model, let $n_{\mathsf{users}}=10^7$ be the number of users, let $c=5$ be the active
conversations per user, and let $R=30$ days be the assumed interval between new session-mode
conversation secrets. The model uses hourly epochs~\cite[Section~5.3]{melara2015coniks}. This gives
$n_{\mathsf{users}}c/2=25$ million conversations and $n_{\mathsf{users}}c=50$ million directional lookup slots. A client offline for
30 days misses $W=720$ hourly epochs.

Each conversation also derives one warning label, but its slot remains absent until a warning is
written. Under the assumed session interval, new conversation secrets produce about $1.67$ million
directional-slot writes per day, or approximately $69{,}400$ per hourly epoch on average. The log
adds one leaf per epoch regardless of the number of directory writes
(\cref{ssec:design-epoch}). \Cref{ch:eval} evaluates these parameters.

\section{Instantiating ACKA}\label{sec:design-acka}

DUET instantiates ACKA's generic $\Log$ interface~\cite[Section~2.3]{dowling2023acka} using the
verifiable directory described in \cref{ssec:design-structures}. \Cref{tab:design-acka} maps the
underlying CKA, CEA, and $\Log$ components onto this design, while \cref{ssec:design-modes} gives
the continuous-mode operation.

ACKA and DUET handle values at a label differently. ACKA's log query returns all fingerprints
stored at a label~\cite[Section~2.3]{dowling2023acka}, while DUET's raw-label interface stores one
immutable value at each label. Therefore, the sender verifies that its epoch label is empty before
writing. This pre-write check detects an earlier adversarial post. Transition auditing rejects a
later overwrite within the audited history, including one attempted after the receiver has accepted
that epoch.

ACKA's $\Log$ interface also requires verification of append-only consistency between two log
views~\cite[Section~2.3]{dowling2023acka}. DUET provides append-only verification through Merkle
consistency proofs and detects divergent signed views through the auditor's comparison of signed
heads. Moreover, the shared warning slot and windowed catch-up described in
\cref{ssec:design-detection,sec:design-windowed} add peer notification and offline catch-up to this
instantiation.

\section{Design Decisions and Alternatives}\label{sec:design-decisions}

The directory structure, global-label derivation, and combined prefix-plus-log construction are the
three choices that most affect the system's behaviour.

\paragraph{Directory Structure.} DUET uses a path-compressed sparse binary Merkle prefix tree
because the warning channel requires verifiable inclusion and non-inclusion, including proof that
the warning slot is empty. Path compression collapses single-child chains in sparsely populated
regions, while the compressed proof transmits only the non-empty sibling hashes.

\paragraph{Global-Label Derivation.} Global slots use the
ECVRF-EDWARDS25519-SHA512-TAI VRF ciphersuite to make label derivation verifiable and protect
published labels from outsider enumeration, as required by G3 (Directory
Privacy)~\cite[Sections~1 and 3.4]{rfc9381}. The selected ciphersuite also matches Signal's
key-transparency implementation~\cite{signal-kt-server}.

\paragraph{Combined Prefix-Plus-Log Stack.} The prefix tree authenticates current lookup results,
while the append-only log supplies the history required for windowed catch-up and transition
auditing. Therefore, each lookup includes one additional log-inclusion path. The cost of this path
is evaluated in \cref{ch:eval}.

\Cref{sec:design-detail-alternatives} compares the rejected alternatives and their trade-offs.
\Cref{tab:design-decisions} summarizes these choices and the remaining design decisions with their
cited precedents and technical basis.
