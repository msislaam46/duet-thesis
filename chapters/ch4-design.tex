\chapter{Design}\label{ch:design}

This chapter presents the proposed design. \Cref{sec:design-arch} introduces the
overall architecture and its three authenticated data structures.
\Cref{sec:design-dual,sec:design-windowed} present the two main mechanisms proposed
in this thesis, the dual-index warning scheme and windowed consistency proofs.
\Cref{sec:design-acka} explains how the complete design instantiates ACKA, and
\cref{sec:design-decisions} justifies the principal design decisions. The
constructions are given here at the level of structure and rationale. The full
pseudocode is in \cref{app:algorithms}, and every cost claimed in passing is
measured in \cref{ch:eval}.

\paragraph{Notation.} Hashing is domain-separated in the manner of RFC~6962
(\cref{ssec:bg-merkle}): $\Hash_{\mathsf{leaf}}(x) = \Hash(\mathtt{0x00} \concat x)$
and $\Hash_{\mathsf{node}}(l, r) = \Hash(\mathtt{0x01} \concat l \concat r)$, with
$\Hash$ instantiated as SHA-256 and $\concat$ denoting byte concatenation; the empty
position has the constant default hash $\Hash(\varepsilon)$. The prefix tree and the log
use these same leaf and node tags; cross-tree confusion is not exploitable here, since
prefix roots appear only as log leaf data and log roots only in signed tree heads, but a
production deployment should apply distinct per-structure tags as defence in depth.
Identities are treated as fixed-width service identifiers, so concatenations of identity and
label material are unambiguous without explicit length prefixes.

\section{Architecture}\label{sec:design-arch}

The proposed architecture is built around three authenticated data structures
arranged in layers, where each layer authenticates the one below (\cref{fig:design-arch}). The
prefix tree stores the current directory state, the append-only log records every
committed version of that state, and the signed tree head authenticates the latest
log root. Together, these three authenticated data structures provide authenticated
lookups (prefix tree), append-only history (Merkle log), and publicly verifiable
commitments (signed tree head).

This is the ``combined tree'' design of the IETF Key Transparency working group
(\cref{ssec:bg-keytrans}): one authenticated dictionary holds the directory, an
append-only log records every committed state of that dictionary, and the head of the
log is published as a signed commitment. Lookups are served against the \emph{last
committed epoch}, never the live tree:
only a committed prefix root has been folded into the log, so only a committed root
can be tied, through one chain of proofs, back to a signed head.

\subsection{The Three Structures}\label{ssec:design-structures}

The three structures operate as a stack, and every lookup verification is rooted in
all three structures: a lookup is checked against the prefix tree, whose root is checked
against the log, whose head is checked against the signed commitment
(\cref{ssec:design-verify}).

\paragraph{Prefix Tree.} The directory is a sparse binary Merkle tree that maps each
256-bit \emph{label} to a \emph{value}; for a user-identity entry, the value is an
identity public key. The label is the position of the entry in the tree, derived
rather than chosen, and it comes in two families: a \emph{global slot}, computed
server-side as a VRF over the user identifier, and the per-conversation
\emph{dual-index slots}, computed client-side from the shared secret
(\cref{sec:design-dual}).

\paragraph{Append-Only Log.} Each committed prefix-tree root is appended to a Merkle
log (\cref{ssec:bg-merkle}) as a single leaf $\prefroot{t}$. The log therefore records
every committed directory state, and a consistency proof certifies that this
history has only ever grown. Nothing previously committed has been modified,
deleted, or reordered.

\paragraph{Signed Tree Head.} Each epoch, the root of the log is signed with Ed25519
and published as the STH. This gives clients and auditors a single authenticated value
that commits to the whole directory and its history. It is the anchor against which
every lookup is ultimately checked.

\paragraph{Why a VRF?} The VRF carries the directory-privacy goal G3
(\cref{sec:threat-goals}). The operator holds the VRF secret key and maps a user
identifier to a pseudorandom label, attaching a proof that the label was computed
correctly; a client verifies that proof against the operator's public key but cannot
itself compute or predict any other label (\cref{ssec:bg-ct2kt}). The labels are thus
deterministic for the operator yet unpredictable to outsiders, which prevents an
observer from enumerating the directory.

\subsection{Epoch Lifecycle: Update, Commit, and the Signed Tree Head}\label{ssec:design-epoch}

The directory evolves in epochs. An $\textsf{update}(\mathit{label}, \mathit{value})$
mutates the live prefix tree in place, re-hashing only the dirty leaf-to-root path, so
a single update is $O(\log N)$ rather than $O(N)$.

A $\textsf{commit\_epoch}()$ then closes the epoch. It reads the current prefix-tree
root, appends it to the log as the next leaf, recomputes the log root, snapshots the
committed tree so that subsequent searches are served against a frozen state, and signs
the new head.

The contents of the signed tree head determine exactly what the signature
authenticates. The STH signs, under Ed25519, the 88-byte little-endian message
\begin{equation}\label{eq:design-sth}
  \mathit{epoch} \concat \mathit{tree\_size} \concat \mathit{root} \concat
  \mathit{timestamp} \concat \Hash(\mathit{config}),
\end{equation}
where $\Hash(\mathit{config}) = \Hash(\mathit{pk}_{\mathsf{vrf}} \concat
\mathit{pk}_{\mathsf{sth}} \concat \mathit{suite} \concat \mathit{version} \concat
\mathit{epoch\_interval} \concat \mathit{raw\_label\_policy})$, the trailing byte binding the
write-once raw-label policy (C2/H3) so the server cannot silently relax it. Each field of \cref{eq:design-sth} is necessary for a different aspect of the verification procedure. The $\mathit{tree\_size}$ is
required by the inclusion and consistency verifiers. Signing the $\mathit{timestamp}$
means STH freshness cannot be forged, and the trailing $\Hash(\mathit{config})$ is a
CONIKS-style policy commitment (the field CONIKS calls $P$) that binds the provider's
parameters into the signature. With it, the server cannot silently swap its VRF key,
its signing key, the ciphersuite, the protocol version, or the epoch cadence, or
serve different parameters to different clients, because any client that recomputes
$\Hash(\mathit{config})$ from the parameters it expects will reject the mismatch. A
parameter substitution thus becomes a signed, monitorable, equivocation-detectable act
rather than a silent one.

\subsection{The Client Verification Chain}\label{ssec:design-verify}

A client accepts no server response without independently verifying it: every lookup is
ultimately authenticated against a signed tree head. Each verification traverses the same three-layer architecture
introduced in \cref{sec:design-arch}: first the prefix tree, then the append-only log,
and finally the signed tree head. The verification chain is the five-step pipeline of
\cref{fig:design-verify}.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-verify}
\caption[The five-step client verification chain.]{The five-step client verification chain. Every lookup is checked locally
against a signed root.}
\label{fig:design-verify}
\end{figure}

Step~1 is the anti-substitution binding on the global path: it ties the queried
identity, through the VRF, to the exact slot the proof speaks about. It is skipped on
the dual-index path, where the client derived the label itself from the shared secret
and so needs no server-supplied VRF proof to know which slot to read. Step~3 anchors the
whole chain to a signed head, and the head verified there must be the same head against
which the inclusion proof of step~5 is checked; a proof against an unsigned or stale head
is refused. Concretely, the client requires the head returned alongside the proof to be identical
to the head it independently obtained and verified: the latest head it fetched, or, during
catch-up, the new head whose append-only consistency with its last trusted head it has just
verified. A response anchored to any other head is rejected even if that head carries a valid
signature, since a validly signed but stale or forked head is precisely what the equivocation
adversary of attack A4 would supply. Steps~4 and~5 are the two layers of the combined tree: the prefix proof shows
the entry is at its label in the dictionary, and the log-inclusion proof shows that
dictionary state is the one the signed head commits to. Because each commit appends the
new directory root as the log's \emph{last} leaf, step~5 additionally pins the inclusion to
that latest leaf ($\mathit{leaf\_index} = \mathit{tree\_size} - 1$ at exactly the signed
size): a genuine inclusion proof for an \emph{earlier} leaf still verifies against the
current log root, so without this pin a server could answer with a stale directory snapshot
(one predating a warning, say) under the current signed head. Inclusion proves
membership, not \emph{currency} (RFC~9162 §2.1.3.2); the currency pin closes that gap. This is the combined-tree
semantics of the Key Transparency draft (\cref{ssec:bg-keytrans}).

The verification work is split across the implementation as follows. In the Rust reference,
\texttt{verify\_search\_result} performs the VRF, value, prefix-root, and log-inclusion
checks (1, 2, 4, 5), and the head-bound wrapper \texttt{verify\_search\_result\_against} adds
step 3 together with the equality binding of the returned head to the caller's independently
verified head and the latest-leaf currency pin, so a validly signed but stale or forked head
(or a genuine proof for an older leaf under the current head) is rejected. The live TypeScript client folds the signature check
and the same currency pin into \texttt{verifyChain}, so every lookup enforces all five. The ``full client verification''
benchmarked in \cref{ch:eval} is the complete five-step chain.

\section{The Dual-Index Warning Scheme}\label{sec:design-dual}

The dual-index warning scheme closes Problem~1 of \cref{sec:bg-open} (the absence of
an in-band peer-warning channel) and so realizes goal G1 against the substitution
attacks A1, A3, and A5 of \cref{ch:threat}.

\subsection{Label Derivation}\label{ssec:design-labels}

The dual-index scheme allocates three directory slots to each conversation: two lookup
slots (one per participant) and one shared warning slot (\cref{fig:design-dualindex}).
Alice and Bob derive these slot labels from the X3DH/PQXDH shared secret $\sharedS$
(\cref{ssec:bg-x3dh}) using HKDF-SHA256 (RFC~5869), the same key-derivation function
Signal already uses elsewhere:
\begin{equation}\label{eq:design-labels}
\begin{aligned}
  \mathit{PRK} &= \HKDFex(\text{salt} = \text{\texttt{"duet-dual-index"}},\ \sharedS)\\
  \ell_{\mathsf{self}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{self}} \concat \mathit{id}_{\mathsf{peer}},\ 32\big)\\
  \ell_{\mathsf{peer}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"lookup"}} \concat \mathit{id}_{\mathsf{peer}} \concat \mathit{id}_{\mathsf{self}},\ 32\big)\\
  \ell_{\mathsf{warn}} &= \HKDFexp\!\big(\mathit{PRK},\ \text{\texttt{"warning"}} \concat \min(\mathit{id}_\A, \mathit{id}_\B) \concat \max(\mathit{id}_\A, \mathit{id}_\B),\ 32\big).
\end{aligned}
\end{equation}
In \cref{eq:design-labels}, $\mathit{PRK}$ is the extracted pseudorandom key; $\mathit{id}_{\mathsf{self}}$ and
$\mathit{id}_{\mathsf{peer}}$ are the deriving party's own and peer identifiers; $\min$
and $\max$ impose a canonical order on the two identities (comparing their fixed-width
byte representations lexicographically), and each label is a 32-byte
(256-bit) output, matching the prefix tree's label width. The identifiers are ordered
canonically \emph{only} for the warning label, so that both parties compute the same
$\ell_{\mathsf{warn}}$; the two lookup labels are deliberately asymmetric, so that each
party's key occupies its own slot. There are therefore three labels, not two: both
parties' keys coexist in the directory, and the shared warning slot sits alongside them.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-dualindex}
\caption[The dual-index scheme's three derived slots.]{The dual-index scheme: the two lookup slots (one per participant) and the shared
warning slot are all derived by HKDF from the conversation's shared secret $\sharedS$. Because
both parties hold the same $\sharedS$, they derive the identical warning label $\ell_{\mathsf{warn}}$,
so a warning written by either party surfaces in a slot both sides read; a party holding a different secret
$\sharedS'$ derives a disjoint set of labels and cannot reach these slots.}
\label{fig:design-dualindex}
\end{figure}

This corrects two simplifications that appeared in early descriptions of the scheme: it
uses HKDF rather than a bare hash of $\sharedS$, and it uses three labels with canonical
ordering applied to the warning label alone. Cross-implementation test vectors verify the
byte-for-byte equivalence of the derivation across the Rust and TypeScript implementations
(\cref{app:algorithms}).

\subsection{The Three Security Properties}\label{ssec:design-properties}

The derivation gives the scheme three properties on which detection rests.

\paragraph{Symmetry.} Under the canonical ordering, $A.\ell_{\mathsf{self}} =
B.\ell_{\mathsf{peer}}$, $A.\ell_{\mathsf{peer}} = B.\ell_{\mathsf{self}}$, and
$A.\ell_{\mathsf{warn}} = B.\ell_{\mathsf{warn}}$, so the two parties agree on which slot
each key lives in and, crucially, on the one warning slot they both watch.

\paragraph{Unlinkability.} The server does not hold $\sharedS$, so the HKDF outputs are
pseudorandom from the server's perspective and it cannot distinguish $\ell_{\mathsf{warn}}$ from
any other leaf in the tree; it can therefore neither pre-position a value on the warning
slot nor recognize and selectively censor it. This property must be stated with its precise scope:
it holds up to the moment a label is first used. Any lookup or write necessarily reveals the queried
label to the operator, and repeated monitoring reveals which labels are read together, so after
first use the operator can associate the three labels of a conversation with the clients that query
them. What the scheme relies on is therefore unpredictability \emph{before} first use (the server
cannot pre-position a value on a slot whose label it cannot compute), while the consequences of
what the server learns \emph{after} first use are addressed by the write-once policy, the transition
audit, and the persistence check of \cref{ssec:design-detection}.

\paragraph{Scope of the Warning Channel.} The bidirectional warning defends a conversation
\emph{after} its X3DH/PQXDH handshake has completed honestly, so that Alice and Bob hold a genuine
shared secret $\sharedS$ the server never learns. This is the threat it targets: a malicious server
(or network) substituting a key for an \emph{already-established} pair (attacks A1, A5). It does
\emph{not} claim to catch a man-in-the-middle interposed \emph{during} first contact. If the
adversary sits in the handshake itself, Alice and Bob complete \emph{separate} handshakes with the
adversary and never share a single $\sharedS$, so no common rendezvous label exists; that case is the
trust-on-first-use boundary (\cref{sec:threat-fair}), and it is caught, if at all, by the global
VRF-slot check against the log (attack A3), which needs no shared secret, not by the warning
channel. The novelty claimed here is precisely the post-establishment peer warning, which
self-monitoring key transparency does not surface to the other party.

\paragraph{Tripwire.} Within that scope, a substituted key implies a different shared secret $\sharedS$,
hence disjoint labels, so a peer lookup either misses the slot the impersonator never
wrote to, or a warning write lands in a slot the impersonator could not predict. The guarantee that
a committed warning then \emph{stays} visible is not automatic. It is supplied by the write-once
policy, the transition audit, and the persistence check introduced in
\cref{ssec:design-detection}.

\subsection{Detection and the Bidirectional Warning}\label{ssec:design-detection}

On detecting a suspicious key at a lookup slot, a party writes data to
$\ell_{\mathsf{warn}}$; both parties' background monitors read $\ell_{\mathsf{warn}}$
on their next check and raise an alert. To make warnings distinguishable from noise, the
warning payload is authenticated: the writer appends a MAC computed under a key derived from the
shared secret with the two identities in canonical order
($\HKDFexp(\mathit{PRK}, \text{\texttt{"warn-mac"}} \concat \min(\mathit{id_A},\mathit{id_B}) \concat \max(\mathit{id_A},\mathit{id_B}), 32)$),
which only the two conversation parties can produce or verify. Any \emph{unauthenticated} value found at the slot still
raises an alert (since no third party should be able to reach the slot at all, unauthenticated
data there is itself evidence of misbehaviour), but the MAC lets the peer distinguish an authentic
warning from an injected one, which matters because the operator learns the label the first time the
slot is read (\cref{ssec:design-properties}) and could thereafter write to it.\footnote{The payload
MAC is wired end-to-end: the warning write path seals the alert (\texttt{seal\_warning}) and the read
path opens it (\texttt{open\_warning}) in both the Rust reference and the TypeScript client, and a
cross-implementation vector locks the sealed-payload bytes across the two implementations (alongside
the existing roundtrip and injection-rejection unit tests). The tripwire itself does not depend on the
MAC (any value at the slot still raises an alarm), so the MAC only classifies authorship: an
opened payload is an authentic peer warning, and a value that fails to open is flagged as
unauthenticated (possible operator injection) but still alarms.}

The suppression argument requires care, because the append-only property of the log constrains the
\emph{history of committed roots}, not the \emph{contents} of successive directory states. Within
any epoch whose tree includes the warning leaf, the server cannot answer a warning-slot query with
``absent'': non-inclusion must be \emph{proven} (\cref{ssec:design-verify}), and a valid
non-inclusion proof against a root whose tree contains the leaf would require a hash collision.
Across epochs, however, nothing in the log alone prevents a malicious server from building the
\emph{next} epoch's prefix tree without a leaf that the previous epoch's tree contained, and then
proving that leaf's non-inclusion honestly against the new committed root; every log consistency
proof would continue to verify, because the log records only that roots were appended, not that the
directory evolved admissibly between them. Three safeguards close this gap.

\begin{enumerate}
\item \textbf{Write-once labels.} Dual-index and CEA labels (\cref{ssec:design-modes}) are
write-once: the server's update interface rejects a write to an occupied label in these families,
and an occupied label is never removed or modified in a subsequent epoch. The policy is bound into
the signed configuration hash of \cref{eq:design-sth}, so a server that changes it breaks its own
signature for any client that recomputes the commitment.
\item \textbf{Transition audit.} The write-once policy binds an honest server; to bind a malicious
one, the auditor verifies it per epoch. For each committed epoch the server discloses to the auditor
the epoch's update set together with proofs against the previous committed root; the auditor
recomputes the previous root, replays the declared operations (insertions of previously absent
labels and, for key rotation, declared in-place rotations whose disclosed old value must match the
leaf being replaced), verifies that nothing beyond the declared operations changed (the delta
format cannot express a deletion), and checks that the result equals the newly committed root.
Each leaf commits its \emph{kind}, \emph{mutable} (the global-VRF identity slots, which the server
may rotate) or \emph{immutable} (the raw dual-index, CEA, and warning labels, which are write-once),
bound into the leaf hash as $\Hash(\mathit{kind} \concat \mathit{label} \concat \mathit{value})$,
so the kind is authenticated by the very inclusion proof that authenticates the value and the server
cannot relabel it. The auditor therefore \emph{distinguishes} the two families: it accepts a declared
in-place rotation only on a mutable leaf, and \textbf{rejects any rotation of an immutable leaf
outright} (as well as any rotation that misdeclares the leaf's kind). An adversary that has
compromised the pre-shared state and tries to overwrite a committed CEA fingerprint $F_t$ with one
over its injected key must route the write through the privileged interface and declare it as a
rotation; because the target leaf is immutable the transition audit rejects that rotation, so the
epoch fails to replay and loses the auditor's counter-signature. Entry immutability is thus enforced
\emph{structurally at the auditor}, not merely surfaced. The owner-side self-checks remain as defence
in depth for the dual-index labels: a replaced lookup slot fails the owner's self-check and a
replaced warning slot still alerts (any value at the slot alerts). But note the CEA fingerprint
overwrite is one the receiver's per-epoch verdict alone \emph{cannot} catch under a pre-shared-state
compromise (the substituted fingerprint matches what the victim recomputes for the injected key), so
it is precisely the auditor's structural rejection of the immutable-leaf rotation that closes it. This is exactly
the update-validity role the IETF KeyTrans protocol assigns to third-party auditors, whose
\textsf{AuditorUpdate} structure carries each log entry's added and removed prefix leaves with a
proof against the prior tree, precisely so that the auditor can recompute both roots of the
transition~\cite{ietf-keytrans-protocol}. A deletion or overwrite therefore cannot be committed
without either forgoing the auditor's counter-signature or presenting the auditor a transition that
fails to replay.
\item \textbf{Persistence check.} Independently of any auditor, the writer of a warning retains the
inclusion proof and signed tree head of the epoch at which its warning committed, and its background
monitor re-verifies the warning's inclusion on every subsequent check. If the leaf later disappears,
the writer holds an inclusion proof under $\mathit{sth}_t$, a non-inclusion proof under
$\mathit{sth}_{t'}$, and a valid consistency proof from $t$ to $t'$: together these three artefacts
constitute non-repudiable, publishable evidence that the server deleted a committed leaf, since all
three verify against heads the server itself signed.
\end{enumerate}

The residual asymmetry should be stated explicitly. The persistence check converts deletion from a
silent act into one that the warning's \emph{writer} detects and can prove; it does not, by itself,
alert a \emph{peer} who had not yet read the warning during the window in which it was visible. It
is the transition audit that closes this residual, because an auditor that validates every epoch's
update set detects the deletion independently of either party. With these safeguards in place, the
server's only remaining suppression strategy is to refuse service entirely (to decline lookups,
withhold epochs, or withhold the auditor's disclosure), producing an observable denial of service,
which is itself a signal (attack A2). All three safeguards are implemented in the prototype: the
write-once policy is enforced by the server's raw-label update interface, the transition audit by the
auditor replaying each epoch's declared update set against the committed root, and the persistence
check by the writer retaining a committed warning's inclusion proof and assembling deletion evidence
on any later disappearance (\cref{ch:impl}). The one element left to deployment is
authenticated writes (account-layer proof of raw-label ownership), without which the write-once
policy still binds an honest server and the transition audit still binds a malicious one, but a
malicious client could squat an as-yet-empty peer slot (\cref{ch:discussion}).

Detection is bidirectional, which matters for the offline case. The victim's own-key
self-check publishes the warning when the victim notices the wrong key under its own
name; in addition, a peer that has trust-on-first-use-pinned the victim's key detects a
substituted peer-slot and publishes the warning on the victim's behalf, so an offline
victim is still covered. For a \emph{server-side} substitution (A1), where the server
makes the served bundle agree with the log, a peer comparing the freshly served bundle against the
log sees no mismatch; detection then comes either from the victim's own-key self-check or from a peer
that has already trust-on-first-use-pinned the victim's key and compares the substituted log value
against its pin. Only against a \emph{pre-first-contact} substitution, where no peer has yet pinned a
key, is the victim's self-check the sole detector. The
residual limitation is the trust-on-first-use caveat of \cref{sec:threat-fair}: a
substitution that predates first contact pins the incorrect key.

\subsection{Security Experiment and Detection Argument}\label{ssec:design-experiment}

The security goal of the dual-index scheme is formalized by the experiment
$\Expt{dual\text{-}det}{\Pi,\Adv}$ below, in which $\Pi$ denotes the dual-index scheme and
$\Adv$ a probabilistic polynomial-time adversary (written $\Adv$ rather than $\A$, which
already denotes Alice); the notation adapts ACKA's $\CEAsec$
experiment~\cite{dowling2023acka}. The experiment is run by a challenger that invokes
$\Adv$. The adversary controls the directory server and, following ACKA, even chooses the
session secret and identities, security rests on the consistency of the registered keys,
not on their secrecy. After the honest keys are registered, $\Adv$ publishes a directory
state and a signed tree head and answers each honest lookup with a value and proof of its
choosing. The adversary succeeds if an honest party accepts a substituted key while no
detection mechanism is triggered: both parties' self-checks pass and the warning slot is
provably empty.

\begin{exptbox}{Experiment $\Expt{dual\text{-}det}{\Pi,\Adv}(\secpar)$}
\small
\begin{enumerate}\setlength{\itemsep}{1pt}
  \item $(\sharedS, \mathit{id}_\A, \mathit{id}_\B, \mathit{pk}_\A, \mathit{pk}_\B) \gets \Adv(\secpar)$ \quad (the adversary's choice of secret, identities, and honest keys).
  \item The challenger derives $(\ell^\A_{\mathsf{self}}, \ell^\A_{\mathsf{peer}}, \ell_{\mathsf{warn}}) \gets \mathsf{Derive}(\sharedS, \mathit{id}_\A, \mathit{id}_\B)$; by symmetry $\ell^\A_{\mathsf{peer}} = \ell^\B_{\mathsf{self}}$ (\cref{ssec:design-properties}).
  \item The challenger registers the honest keys: $\mathit{pk}_\A$ at $\ell^\A_{\mathsf{self}}$ and $\mathit{pk}_\B$ at $\ell^\B_{\mathsf{self}}$.
  \item $\Adv$ publishes a directory state (prefix tree and log) and a signed tree head $\mathit{sth}$.
  \item $\mathit{pk}_{\mathsf{peer}} \gets \mathsf{VerLookup}(\ell^\A_{\mathsf{peer}}, \mathit{sth})$ \quad (Alice's lookup of Bob's key).
  \item $\mathit{pk}_{\mathsf{self}} \gets \mathsf{VerLookup}(\ell^\B_{\mathsf{self}}, \mathit{sth})$ \quad (Bob's self-check).
  \item $\mathit{warn} \gets \mathsf{VerWarn}(\ell_{\mathsf{warn}}, \mathit{sth})$ \quad (proven (non-)inclusion of the warning slot).
  \item \textbf{return}~$1$ if $\mathit{pk}_{\mathsf{peer}} \notin \{\bot, \mathit{pk}_\B\} \wedge \mathit{pk}_{\mathsf{self}} = \mathit{pk}_\B \wedge \mathit{warn} = \mathsf{absent}$; otherwise $0$.
\end{enumerate}
{\footnotesize $\mathsf{VerLookup}$ returns the committed value at a label, or $\bot$ if no
valid proof is supplied; $\mathsf{VerWarn}$ returns $\mathsf{absent}$ when the warning slot
is proven empty and $\mathsf{present}$ otherwise. Both run the verification chain of
\cref{ssec:design-verify} against $\mathit{sth}$.}
\end{exptbox}

The experiment models the state \emph{after} the honest party's monitor has reacted to a
substitution: on observing $\mathit{pk}_{\mathsf{peer}} \neq \mathit{pk}_\B$, the client
writes to $\ell_{\mathsf{warn}}$, so $\mathit{warn} = \mathsf{absent}$ holds only if the
adversary suppressed that write, which against a committed log requires a forged
non-inclusion proof. A multi-round interactive formulation that makes the
write-then-recheck explicit across epochs is left to future work.

\begin{definition}[Dual-detection security]
A dual-index scheme $\Pi$ is \emph{dual-detection-secure} if, for every probabilistic
polynomial-time adversary $\Adv$,
\[
  \advantage{dual\text{-}det}{\Pi,\Adv}(\secpar) \;=\;
  \Pr\!\big[\,\Expt{dual\text{-}det}{\Pi,\Adv}(\secpar) = 1\,\big] \;\le\; \negl(\secpar).
\]
\end{definition}

\paragraph{Detection Argument (Proof Intuition, Not a Full Reduction).} The symmetry of the derivation
(\cref{ssec:design-properties}) underpins the detection guarantee: the slot Alice reads for
Bob's key, $\ell^\A_{\mathsf{peer}}$, is exactly the slot Bob self-checks,
$\ell^\B_{\mathsf{self}}$. Under a single signed tree head, a valid inclusion proof binds
that label to one committed value, so a winning adversary must return
$\mathit{pk}_{\mathsf{peer}} \neq \mathit{pk}_\B$ to Alice while Bob's self-check at the same label still
yields $\mathit{pk}_\B$: two contradictory authenticated values for the same committed
label under one root, implying a violation of the collision resistance of the Merkle hash
construction. Suppressing the warning after a detected mismatch likewise requires a forged
non-inclusion proof. The remaining attack is equivocation, serving Alice and Bob
different signed heads (attack A4), which lies outside this experiment and is handled by
the cross-vantage auditor (goal G4). A fully quantified reduction with concrete
advantage bounds, and a unified treatment of the network and malicious-server adversaries,
is left to future work (\cref{ch:discussion}).

The dual-index mechanism complements rather than replaces CEA. $\CEA$ authenticates the
values stored at directory entries by deriving per-epoch fingerprints; the dual-index
scheme instead derives the directory labels from the shared secret, identifying the
directory locations at which those values are stored. The two mechanisms therefore address complementary aspects of
authentication: $\CEA$ authenticates entry contents, while the dual-index scheme
authenticates entry placement.

\subsection{Session and Continuous Authentication Modes}\label{ssec:design-modes}

The scheme described so far is the \emph{session mode}: the labels come from the
\emph{initial} X3DH secret $\sharedS$, the registered value is the \emph{identity key},
and a party re-registers only when its signed pre-key rotates. Session mode detects the
handshake-time attacks (server substitution (A1) and network man-in-the-middle (A3))
at the cost of one log write per pre-key rotation.

Alongside it, the system implements a \emph{continuous mode} that binds authentication to
the \emph{entire} continuous key agreement, following ACKA's example CEA construction
(\cref{sec:bg-acka}). Each ratchet epoch carries a \emph{public} ratchet key $T_t$ and a \emph{secret} epoch key
$I_t$ (a secret epoch key: ACKA's Signal mapping sets $I_t = ck$, Signal's chain key, itself a KDF
of the ratchet Diffie--Hellman output, whereas this PoC folds the raw DH output as a stand-in for
$ck$, see \cref{ch:discussion}). At epoch $t$ the party
computes, from the current chain state $k_t$ (with $k_0$ the state established by Setup), an evolving
label and a fingerprint that authenticates $T_t$, and only then folds the secret $I_t$ into the
chain to produce $k_{t+1}$:
\begin{equation}\label{eq:design-cea}
\begin{aligned}
  L_t &= \Hash\!\big(k_t \concat \min(\mathit{id}_\A, \mathit{id}_\B) \concat \max(\mathit{id}_\A, \mathit{id}_\B) \concat t\big),\\
  F_t &= \Hash\!\big(\KDF(k_t,\ \mathit{id}_{\mathsf{sender}} \concat \mathit{id}_{\mathsf{peer}} \concat t) \concat T_t\big),\\
  k_{t+1} &= \KDF\!\big(k_t,\ \KDF(I_t, \text{\texttt{"CEA"}})\big) \qquad (\KDF = \text{HMAC-SHA256, a PRF}).
\end{aligned}
\end{equation}
It registers the pair $(L_t \to F_t)$ of \cref{eq:design-cea} in the same log, one entry per ratchet epoch. The
label $L_t$ uses the canonical $\min/\max$ identity ordering (the same convention as the warning
label in \cref{eq:design-labels}), so both parties derive the identical label for an epoch and it
maps to a single log slot. The fingerprint $F_t$, by contrast, is \emph{directional}
($\mathit{id}_{\mathsf{sender}} \concat \mathit{id}_{\mathsf{peer}}$): the verifier recomputes it with the
party who sent that epoch's ratchet key first, which binds the fingerprint to the sender's public
key $T_t$ and lets a substituted key be detected at the shared label.

The ordering of operations within an epoch follows ACKA's composed construction
(their Figure~8) in three respects, each of which matters for correctness. First, the label and
fingerprint are computed over the \emph{current} (pre-update) state and the \emph{public} key, and
only then is the \emph{secret} $I_t$ folded into the chain; folding the secret epoch key rather than
the public ratchet key keeps the chain unpredictable to an adversary that has compromised the
pre-shared state: the property the unlinkability and forgery-resistance arguments need. The secret
is domain-separated before folding ($\KDF(I_t, \text{\texttt{"CEA"}})$, ACKA Figure~8): in a faithful
deployment $I_t$ is Signal's chain key $ck$, which also feeds the session-key derivation (the paper's $\KDF(I_t,
\text{\texttt{"CKA"}})$), so the \texttt{"CEA"} tag keeps the value folded into the transparency chain
independent of the session key: the key separation the security argument relies on. Second,
before posting, the sender checks that the label $L_t$ is unoccupied: ACKA specifies that ``the
sender will also check if the label has already been uploaded to the log with a fingerprint, which
would indicate an impersonation''~\cite{dowling2023acka}, and the sender advances its chain only
after its write is confirmed committed. Third, the receiver advances its chain only when a
verification returns \textsc{Consistent}: a detected fork halts the session (the state is not
carried across a fork), and a pending lookup (the sender's fingerprint not yet committed) leaves the
receiver's state untouched, so the check can be retried without desynchronizing the chain.

One representational point requires an explicit statement. ACKA's log stores a \emph{vector} of
fingerprints per label, and its receiver rejects unless exactly one fingerprint is present; the alarm
condition is two fingerprints at one label. Our directory stores exactly one value per label, so that
alarm condition maps onto two mechanisms instead: the honest sender's pre-post check fails against an
occupied label (the case in which the adversary posted first), and the transition audit
(\cref{ssec:design-detection}), which, because each leaf commits its mutable/immutable kind into
its hash, \emph{rejects any rotation of an immutable CEA label outright}, rejects the converse
case, in which an adversary \emph{overwrites} the honest fingerprint after it committed. Without this
committed immutability, an active man-in-the-middle that has compromised the pre-shared state
(exactly the adversary ACKA defends against, and one who can therefore derive $L_t$) could replace
the honest $F_t$ with a fingerprint over its injected key; the receiver's per-epoch check would pass
(the substituted fingerprint matches what it recomputes), so detection cannot rest on that verdict
and instead rests on the auditor's structural rejection. Entry immutability is thus
not an implementation detail but the property that lets ACKA's security argument carry over to this
instantiation, and, with the committed leaf kind, it is enforced auditably rather than assumed.

Detection then proceeds as in ACKA: an active man-in-the-middle that injects a forged ratchet key
$T'$ either posts under a label the impersonated party never derives (a different chain gives a
different $L_t$) or produces a conflicting fingerprint at the agreed label, caught epoch by
epoch. On a fork, continuous mode reuses the dual-index warning slot to alert the peer in
band, a composition ACKA itself does not provide.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-modes}
\caption[Session mode versus continuous mode.]{Session mode (left): labels derived from the initial secret $\sharedS$, at which
the identity key is registered once per pre-key rotation. Continuous mode (right): a chained secret
$k_0 \to k_1 \to k_2 \to \cdots$ producing one fingerprint per ratchet epoch.}
\label{fig:design-modes}
\end{figure}

The two modes differ in their authentication coverage and cost
(\cref{fig:design-modes}). \textbf{Session mode} authenticates at the level of the identity key,
with one write per pre-key rotation, and needs fewer directory writes and a smaller integration
surface than continuous mode; a production deployment still needs the hooks and safeguards of
\cref{ch:discussion}.
\textbf{Continuous mode} authenticates each ratchet epoch, with one write per epoch, and
detects the post-compromise active man-in-the-middle that is ACKA's principal security guarantee, at a substantially higher log-write rate. The two are modes of one system, sharing
the prefix tree, the log, the STH, and the warning channel; their cost is measured in
\cref{ch:eval}. Two limitations remain and are stated explicitly. First, in the prototype the chained
secret is advanced deterministically from the shared secret; a production binding would replace this
simulated epoch input with Signal's live Double Ratchet chain key $ck$, obtained together with the
public ratchet key $T_t$ at a DH-ratchet-step integration point, which is a distinct hook from the
session-establishment capture of the initial shared secret $\sharedS$ (\cref{ch:discussion}). Second, the construction inherits ACKA's
synchronous epoch model: the label chain advances in lockstep on both sides, so a ratchet message
that is lost before the receiver processes its epoch would leave the two chains permanently
divergent and every subsequent check failing. The Double Ratchet itself tolerates such loss through
skipped-message keys; a production binding would therefore need to carry explicit epoch indices and
a bounded skipped-epoch window in the same manner (\cref{ch:discussion}). Cross-implementation test
vectors verify byte-for-byte equivalence of the Rust and TypeScript CEA constructions.

\section{Windowed Consistency Proofs}\label{sec:design-windowed}

The windowed consistency proof closes Problem~2 of \cref{sec:bg-open}, the linear cost
of offline catch-up, and so realizes goal G2.

\subsection{The Catch-Up Problem and the Bound}\label{ssec:design-catchup}

A client returning after $W$ offline epochs must verify that the current directory state
is an append-only extension of the last state it previously trusted. A
straightforward approach verifies one consistency proof for every missed epoch, giving $W$
separate proofs and an overall verification cost of $O(W \cdot \log n)$. Successive
consistency proofs contain substantial overlap, making repeated verification redundant. Instead, the
client requests a single consistency proof spanning its previously trusted log size $m$
and the current log size $n$, returned together with the latest signed tree head.
RFC~9162 guarantees that such a proof has size
\begin{equation}\label{eq:design-proofsize}
  |\pcons(m, n)| \le \lceil \log_2 m \rceil + \lceil \log_2 n \rceil \quad\text{hashes},
\end{equation}
growing only logarithmically with the current log size $n = m + W$ rather than linearly
with the number of intermediate epochs (\cref{fig:design-windowed}). The bound in
\cref{eq:design-proofsize} is what bounds the window's cost: the client verifies the
proof against the signed root of that tree head, so the new state is accepted only if it
is a signed, append-only extension of the state already trusted. The catch-up cost
therefore depends only logarithmically on the sizes of the previously trusted and current
log states, rather than linearly on the number of missed epochs. The warning-slot lookup is
performed during the same synchronization exchange and so does not change the asymptotic
complexity. The proof sketch and the \textsf{WindowedCatchUp} procedure are given in
\cref{app:algorithms}.

\begin{figure}[t]
\centering
\input{figures/tikz/fig-design-windowed}
\caption[Windowed offline catch-up.]{Offline catch-up over a window $W = n-m$ epochs. The na\"ive approach verifies one
consistency proof per missed epoch (upper arcs, $O(W\log n)$); the windowed approach requests
a single RFC~9162 consistency proof spanning the previously trusted head $m$ and the current
head $n$ (lower arc), whose size is bounded by $\lceil\log_2 m\rceil + \lceil\log_2 n\rceil$
hashes, logarithmic in the log size rather than linear in $W$.}
\label{fig:design-windowed}
\end{figure}

Three observations qualify this claim. First, the windowed proof is a \emph{standard}
RFC~9162 consistency proof between two distant heads, not a new cryptographic object. Nor is the
idea of collapsing unchanged epochs itself new: CONIKS (\S6.3) explicitly \emph{proposes} skipping
missed epochs when a history structure proves no change, SEEMless makes monitoring cost depend on the
number of key updates rather than on elapsed epochs, and OPTIKS reduces unchanged-key monitoring to a
single proof. The contribution here is therefore not the mechanism but its concrete instantiation for
the \emph{offline-client} monitoring window (one consistency proof from the client's last
checkpoint to the current head) together with the measured saving in \cref{ch:eval}. Second, the
saving is linear in the window: the windowed proof replaces $W$ proofs with one. It is a reduction in
the number of proofs, not an improvement in the asymptotic complexity of an individual proof.

Third, and most importantly, the soundness of windowing must be argued rather than assumed, because
the key-transparency literature contains an established objection to exactly this shortcut. CONIKS's
monitoring cost is linear in the offline period precisely because a malicious provider could insert
a false binding at some epoch inside the window and revert it before the client returns; a client
that verifies only the consistency of the two endpoint heads and the current value at its own label
would miss such a transient substitution, which is why CONIKS concludes that inspecting only the
latest signed root is unsound (\cref{ssec:bg-vkd-academic}). That objection applies verbatim to any
windowed check, including this one, and we therefore state explicitly why it does not defeat this
design. A transient in-window substitution is profitable to the adversary only if it is
\emph{used}: a peer who initiates or continues the conversation during the window performs
pinned-key lookups at the dual-index slots (\cref{ssec:design-detection}) and, on a mismatch, writes
to the shared warning slot. Under the write-once policy, transition audit, and persistence check of
\cref{ssec:design-detection}, that warning outlives the attack, and the returning client's catch-up
procedure reads the warning slot in the same synchronization exchange, so the transient substitution
leaves a durable, in-band trace that the windowed client does see. Windowed catch-up therefore
preserves detection \emph{only when the warning commits}: if a monitoring victim or a pinned peer
detects the substitution and successfully writes it, the peer-writable, persistent warning channel
leaves a durable trace that survives the attack; in a directory without such a channel (CONIKS's,
for instance), the same windowing would weaken detection exactly as CONIKS's authors argue.
If the server censors that write within the window (the A2 threat of \cref{ch:threat}), the endpoint
consistency proof still establishes append-only consistency and cuts catch-up bandwidth, but it does
not by itself exclude every transient in-window substitution; the write-once, transition-audit, and
persistence-check machinery protects a warning only once it is committed. The two contributions are
in this sense mutually dependent rather than independent optimizations.

\subsection{Worked Parameterization}\label{ssec:design-param}

A concrete deployment shows the window is not hypothetical. Take $N = 10^7$ users, each
with about $c = 5$ active conversations, and signed pre-keys rotating every $r = 30$ days.
Writing one entry per conversation gives on the order of 50~million prefix-tree labels;
amortized over the 30-day rotation period, this is about 1.67~million directory updates per
day, or roughly $69{,}400$ updates folded into each hourly epoch commit (the log itself
gains one leaf per epoch regardless of update volume; \cref{ssec:design-epoch}). A
client offline for a full rotation period faces a worst-case window of $W = r \cdot 24 =
720$ epochs. Under the naïve scheme this is 720 consistency proofs. Under the windowed
scheme it is one, of size $O(\log n)$ in the log size $n$. This is the parameterization carried into the
evaluation of \cref{ch:eval}.

\section{Instantiating ACKA}\label{sec:design-acka}

The ACKA framework (\cref{sec:bg-acka}) consists of three conceptual components:

\begin{itemize}
  \item \textbf{$\CKA$ (Continuous Key Agreement)}: used unmodified.
  \item \textbf{$\CEA$}: a primitive that derives per-epoch fingerprints and labels
  from public keying material and a chained secret state.
  \item \textbf{$\Logsec$}: an abstract secure log (append-only, with consistency and exclusion); its concrete realization left open.
\end{itemize}

The three mechanisms of this chapter, together with the cross-vantage auditor, form,
to our knowledge (we are aware of no prior published or open-source realization at the time of
writing), the first concrete instantiation of ACKA's abstract logging component
($\Logsec$) (\cref{sec:bg-acka}). The contribution is to
instantiate the component ACKA leaves abstract, $\Logsec$, with a concrete,
malicious-server-resistant verifiable key directory built on the IETF Key Transparency
specification~\cite{ietf-keytrans-protocol} and the lineage of Meta's
\texttt{akd} library~\cite{facebook-akd}, and to drive it in continuous mode so that the
$\CEA$ fingerprints are published epoch by epoch (\cref{ssec:design-modes}); the
mapping is summarized in \cref{tab:design-acka}.

\begin{table}[htbp]
\centering
\caption{Mapping the ACKA components onto their instantiation in this work.}
\label{tab:design-acka}
\small
\resizebox{\textwidth}{!}{%
\begin{tabular}{@{}llp{6.0cm}@{}}
\toprule
ACKA component & Role in the framework & Instantiation in this work \\
\midrule
$\CKA$    & continuous key agreement & Signal's Double Ratchet, used unmodified \\
$\CEA$ & per-epoch fingerprints / labels & dual-index labels (session) and CEA fingerprints (continuous), adding an in-band warning channel \\

Three deliberate departures from the paper are stated plainly, because each corresponds to one of
the ACKA limitations identified in \cref{sec:bg-acka}, and instantiating $\Logsec$ lets
us address it. First, where $\CEA$ authenticates fingerprints, the session-mode scheme
additionally derives \emph{labels} from the shared secret, adding the in-band
peer-warning channel ACKA lacks. Second, ACKA's combined $\mathsf{CKALOG}$ construction performs no
deferred verification, a client must verify each epoch as it arrives, whereas the
windowed consistency proof of \cref{sec:design-windowed} adds exactly the deferred,
batched catch-up an intermittently connected client needs. Third, ACKA assumes the log is
honest and provides no out-of-band cross-checking of tree heads; the cross-vantage auditor
of the threat model (goal G4, attack A4) adds equivocation detection on top of the
instantiated log. Closing these three gaps is what turns ACKA's abstract framework into a
deployable system.

\paragraph{Directory Structure.} The directory is a sparse binary Merkle tree rather
than an $n$-ary trie or a cryptographic accumulator. A binary tree gives uniform node
semantics, every internal node hashes exactly two children under the RFC~6962 node tag,
which keeps both the client verifier and the audit surface small, and it makes
non-inclusion a first-class, cheap proof: an absent label resolves to a default-hash path,
which is exactly what the warning tripwire (\cref{ssec:design-detection}) relies on to
prove a slot empty. An accumulator would shorten membership proofs but make the
non-membership proofs the warning channel needs substantially more expensive, and an
$n$-ary trie would complicate the copath encoding without reducing depth for 256-bit
labels. This is the structure used by CONIKS and the IETF Key Transparency design
(\cref{ssec:bg-keytrans}).

\paragraph{Global-Label Derivation.} Global slots are addressed by an ECVRF over the user
identifier rather than a bare hash. A bare hash would let any observer enumerate the
directory by guessing identifiers. The VRF instead makes labels pseudorandom to outsiders
yet publicly verifiable, so a client can confirm the operator computed the correct label
without being able to compute or predict any other (\cref{ssec:design-structures}). We use
ECVRF-EDWARDS25519-SHA512-TAI (RFC~9381) to match Signal's deployed keytrans VRF, so the
primitive cost is one the platform already pays.

\paragraph{Combined Prefix-Plus-Log Stack.} Authentication uses two trees, a prefix
tree for the current directory and an append-only log of its committed roots, rather
than a single structure. One tree alone would authenticate the present state but not its
history, leaving append-only violations undetectable. The log supplies exactly the
consistency proofs that windowed catch-up (\cref{sec:design-windowed}) and the
cross-vantage auditor (goal~G4) depend on. The cost is one extra log-inclusion path per
lookup, up to $32\lceil\lg E\rceil$ bytes, quantified in \cref{ch:eval}.
