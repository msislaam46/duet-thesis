\section{Signal Key Material and X3DH Mechanics}\label{sec:ext-signal}

Following the X3DH protocol used by Signal, a user publishes a long-term identity key, a signed
pre-key and its signature, and a set of one-time pre-keys~\cite[Sections~2.4 and 3.2]{x3dh}. A user $U$ generates a long-term identity key pair
$(\pkid{U},\skid{U})$, retains the secret key $\skid{U}$ locally, and publishes the corresponding
public identity key $\pkid{U}$. The user also publishes a medium-term signed pre-key $\spk{U}$
together with a signature $\sig{\spk{U}}$ produced under $\skid{U}$, and a batch of single-use
one-time pre-keys $\opk{U}{i}$. These public values are uploaded to the messaging server so that a
sender can initiate a session while the recipient is offline.

A Signal Safety Number combines the parties' long-term identity-key fingerprints for out-of-band
comparison~\cite{safetynumbers}. A signed pre-key is authenticated through its signature under the
identity key, but it is not included in the Safety Number itself. One-time pre-keys are unsigned and
have no individual authentication, although the identity-key and signed-pre-key terms bind the
handshake to the intended parties~\cite[Sections~3.2--3.3]{x3dh}. The Safety Number therefore does
not directly authenticate all the key material used together in a particular session. This
limitation in per-session coverage motivates the construction developed later in the thesis.

The Extended
Triple Diffie--Hellman (X3DH) protocol allows Alice to derive a shared secret
(denoted by $\sharedS$) with Bob even when Bob is offline, by combining Alice's
keys with the identity, signed pre-key, and one-time pre-key material published
by Bob. Following the X3DH specification~\cite[Section~2.4]{x3dh}, this thesis denotes identity keys by
$\xIK{}$, signed pre-keys by $\xSPK{}$, one-time pre-keys by $\xOPK{}$, and ephemeral keys by
$\xEK{}$. Thus, $\xIK{U}=\pkid{U}$, $\xSPK{U}=\spk{U}$, and
$\xOPK{U}=\opk{U}{i}$. Each notation denotes a public key whose corresponding private key is held by
its owner. Alice generates an ephemeral key $\xEK{\A}$ and computes the Diffie--Hellman
values in \cref{eq:bg-x3dh}.
\begin{equation}\label{eq:bg-x3dh}
\begin{aligned}
\mathrm{DH1}    &= \DH{\xIK{\A}}{\xSPK{\B}}, \\
\mathrm{DH2}    &= \DH{\xEK{\A}}{\xIK{\B}}, \\
\mathrm{DH3}    &= \DH{\xEK{\A}}{\xSPK{\B}}, \\
\mathrm{DH4}^{*} &= \DH{\xEK{\A}}{\xOPK{\B}}
   \qquad\text{(if the bundle contains a one-time pre-key)}, \\
\sharedS &= \KDF\!\left(\mathrm{DH1}\concat\mathrm{DH2}\concat\mathrm{DH3}
   \concat\mathrm{DH4}^{*}\right).
\end{aligned}
\end{equation}
Here, $\DH{X}{Y}$ denotes the Diffie--Hellman shared secret derived from the key pairs associated
with $X$ and $Y$, following the X3DH specification. The notation omits whether a party uses the
public or private component of each pair. $\KDF$ denotes a key-derivation function, $\concat$
denotes byte-string concatenation, and $\sharedS$ is the resulting shared secret. \Cref{ch:design}
uses this secret as an input to DUET's label derivation. Key authenticity must hold at this point.

The identity keys enter the shared secret through $\mathrm{DH1}$ and
$\mathrm{DH2}$: $\mathrm{DH1}$ combines Alice's identity key with Bob's signed
pre-key, and $\mathrm{DH2}$ combines Bob's identity key with Alice's ephemeral
key, so that both parties' long-term identities are bound into session
establishment. $\mathrm{DH3}$ and $\mathrm{DH4}^{*}$ incorporate Bob's signed
pre-key and one-time pre-key material, contributing forward secrecy, and the
fourth term is not included when no one-time pre-key is
available~\cite[Section~3.3]{x3dh}.

The resulting $\sharedS$ depends on Alice's identity and ephemeral keys and on Bob's identity key,
signed pre-key, and optional one-time pre-key. When Bob's genuine one-time pre-key is absent or
withheld, an attacker who substitutes Bob's identity key and a signed pre-key valid under that
identity can derive the resulting shared secret and impersonate Bob. DUET is designed to detect this
coordinated substitution. Substituting only the signed pre-key causes Alice's signature check to
fail because she verifies $\spk{\B}$ under $\pkid{\B}$ and aborts on failure. Substituting only the
one-time pre-key normally causes Alice and Bob to derive different secrets, so session establishment
fails and impersonation does not succeed. Not using the one-time pre-key weakens initial forward
secrecy but does not enable impersonation~\cite[Sections~3.3, 3.4, and 4.7]{x3dh}. \Cref{fig:bg-x3dh} shows the protocol sequence from
publication of Bob's pre-key bundle to Alice's initial message.

\begin{figure}[H]
\centering

\caption[X3DH message sequence.]{X3DH message sequence. Alice verifies Bob's signed pre-key,

Signal's post-quantum variant, PQXDH, additionally mixes in a key-encapsulation secret to protect
recorded traffic against a future ``harvest-now, decrypt-later'' attack~\cite[Section~4.7]{pqxdh}. The resulting shared secret then initializes the Double Ratchet, which
evolves the cryptographic state throughout the conversation and derives per-message encryption
keys~\cite[Sections~2.1--2.4]{doubleratchet}.

\section{Double Ratchet Mechanics}\label{sec:ext-ratchet}

The shared secret derived by X3DH or PQXDH initializes the Double Ratchet. The construction combines
a Diffie--Hellman ratchet, which mixes fresh Diffie--Hellman outputs into the root chain, with
sending and receiving key-derivation chains that derive a new message key for each
message~\cite{doubleratchet}. This provides forward secrecy and
post-compromise recovery. Learning the current chain state does not reveal earlier message keys.
Post-compromise recovery occurs after a fresh Diffie--Hellman output unknown to the attacker enters
the root chain, provided that the attacker no longer controls the
session~\cite[Section~8.2]{doubleratchet}. The active-adversary setting returns in
\cref{sec:bg-acka}. \Cref{fig:bg-ratchet} shows how the root, sending, and receiving chains
interact.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-bg-ratchet}
\caption[Double Ratchet key schedule.]{Double Ratchet key schedule. Each party maintains root,
sending, and receiving chains, while the figure follows one sending direction. A fresh
Diffie--Hellman output enters $\KDF_{RK}$, which produces the next root key and a chain key.
Each $\KDF_{CK}$ step produces the next chain key and one message
key. Message keys do not derive later keys and may be
retained temporarily for out-of-order delivery. The
labels $rk$, $ck$, and $mk$ denote root, chain, and message keys,
respectively~\cite[Sections~2.1--2.6]{doubleratchet}.}
\label{fig:bg-ratchet}
\end{figure}

\section{ACKA and Continuous Authentication}\label{sec:ext-acka}

A continuous key agreement (CKA) models key exchange as a sequence of updates. The participants
exchange new public key shares and derive a fresh symmetric key after each protocol
message. Signal's Double Ratchet is one of the ratcheting protocols
captured by this abstraction~\cite{dowling2023acka}.

ACKA combines a CKA with Continuous Entity Authentication (CEA) and a secure log. For each update,
CEA derives a label from the previous shared state and a fingerprint over the current public
keying material. The sender appends the label and fingerprint to the log, while the receiver queries
the expected label before accepting the update. The
log must be append-only and immutable, support label queries, and prove consistency between two
views. ACKA leaves its implementation generic and notes that it could use a blockchain or another
distributed-ledger protocol~\cite{dowling2023acka}.

ACKA considers an active man-in-the-middle after compromise of the shared state and long-term
authentication secrets. Its security experiment also allows the
adversary to control the sender's randomness and inject forged update
messages~\cite{dowling2023acka}.

Three differences clarify how DUET extends this framework. First, ACKA uses its secure log as an
additional channel that an active adversary cannot fully
control. In its composed construction, the receiver detects a
forged update. A sender can also detect an attack when its expected label is already occupied, after
which the paper suggests appropriate, likely out-of-band
action~\cite{dowling2023acka}. The paper does not define a conversation-specific
in-band mechanism through which a detecting party publishes a warning that the peer's monitor can
retrieve. DUET adds this shared warning channel. Second, ACKA authenticates successive CKA updates
in sequence and defines no windowed catch-up procedure. Third, although its log interface verifies
consistency between two views, the paper does not define a third-party auditor that compares signed
directory views. DUET's peer-warning, catch-up, and auditor mechanisms are specified in
\cref{ssec:design-detection,sec:design-windowed,alg:auditor}.

\section{Manual Verification Evidence}\label{sec:ext-usability}

Dowling and Hale observe that Signal's user-controlled comparison authenticates the state at session
initiation but not the current protocol state because the compared keys are not used in CKA
evolution. The same limitation applies to trust on first use, where the initial keys are assumed to
be valid but later protocol state is not re-authenticated~\cite{dowling2023acka}. Their
earlier MoDUSA construction instead derives per-epoch authentication keys and fingerprints over the
ratchet history. It detects an active man-in-the-middle during a session and supports repeated
authentication as the session continues~\cite[Sections~1 and 4]{dowling2020nocompromise}.
However, MoDUSA still requires users to initiate the comparison. Thus, it authenticates evolving
state without providing automatic re-authentication.

Dowling and Hale illustrate this limitation using a three-year communication period and a compromise
approximately one year into it. In their active-attacker example, the CKA exposes two years of data,
whereas the TLS case exposes one hour of data. The comparison assumes that the attack remains
undetected~\cite{dowling2023acka}.

Manual comparison also introduces a usability cost. In the first phase of one study, pairs were
asked to authenticate each other and ensure that no other party could read their messages, but were
not instructed to compare encryption keys. Only two of twelve pairs succeeded in locating and
completing the ceremony in at least one of WhatsApp, Viber, or Facebook Messenger. Across all
pair--application trials, the success rate was 14\%~\cite[Section~5]{vaziripour2017}.
Application-independent instructions about comparing encryption keys raised the overall success rate
to 78\%, while Viber reached 96\%~\cite[Section~6.1 and Table~2]{vaziripour2017}. Even with these instructions,
users took an average of 3.2 minutes to find the ceremony and a further 7.8 minutes to complete
it~\cite[Section~6.3]{vaziripour2017}.

The responses also showed limited understanding of the threat model. Among the 32 responses that did
not mention key verification, 28 (88\%) relied instead on features of the other person, such as
voice, appearance, or shared knowledge~\cite[Section~9]{vaziripour2017}. A man-in-the-middle attacker
was not explicitly identified as a possible attack vector. The authors suggest that a system such
as CONIKS could automate key discovery without relying on one trusted party while preventing a key
server from presenting inconsistent views without detection~\cite{vaziripour2017}.

\section{Merkle Commitments and Transparency Proofs}\label{sec:ext-merkle}

A hash commitment binds a publisher to a value through a short fingerprint. Publishing
$\Hash(D)$ commits the publisher to $D$. Under collision resistance, an efficient adversary cannot
find a distinct $D'\neq D$ such that $\Hash(D')=\Hash(D)$
(\cref{def:hash}).

RFC~9162 defines the Merkle Tree Hash over an ordered list of records
$D=(d_0,\ldots,d_{n-1})$. Each record has a leaf hash
$h_i=\Hleaf(d_i)=\Hash(\texttt{0x00}\concat d_i)$, while an internal node is
$\Hnode(l,r)=\Hash(\texttt{0x01}\concat l\concat r)$. These prefixes separate leaf hashes from
internal-node hashes and provide second-preimage resistance across the two node
types~\cite[Section~2.1.1]{rfc9162}. The recursively computed root
$\MTH(D)$ is a single hash that commits to the ordered list.

An inclusion proof for $d_i$ contains the additional tree nodes needed to reconstruct $\MTH(D)$
from $h_i$. The verifier combines these nodes according to the leaf index and tree size, then
accepts only if the reconstructed value equals the log root in the trusted signed tree
head~\cite[Section~2.1.3]{rfc9162}. For a tree of $n$ records, the proof contains at most
$\lceil\log_2 n\rceil$ hash values.

A consistency proof between an earlier tree of size $m$ and a later tree of size $n$ contains the
nodes needed to verify that the first $m$ records are identical in both trees. Therefore, it
establishes that the later tree is an append-only extension of the earlier tree. RFC~9162 bounds the
proof by $\lceil\log_2 n\rceil+1$ nodes~\cite[Section~2.1.4.1]{rfc9162}.
\Cref{fig:bg-merkle} illustrates the inclusion proof for one record.

the verifier computes $h_2=\Hleaf(d_2)$ and uses the shaded copath

\section{Verifiable-Key-Directory Building Blocks}\label{sec:ext-vkd-blocks}

VKD constructions combine private lookup labels with authenticated directory structures. CONIKS
describes its directory as a Merkle prefix tree, while SEEMless, Parakeet, and ELEKTRA define their
directory properties through variants of zero-knowledge sets (ZKS). The role of the VRF is described
in \cref{ssec:bg-ct2kt}.

\paragraph{Merkle Prefix Trees.} CONIKS stores bindings in a binary Merkle prefix tree indexed by
private lookup indices. Each branch follows one bit of the index. A membership proof contains the
authentication path from the matching leaf to the root. A proof of absence follows the queried index
to its longest matching prefix and ends at either an empty node or a leaf with a different
index~\cite[Sections~3.1--3.2]{melara2015coniks}.

Related constructions use different terminology and encodings. For example, SEEMless uses a
Persistent Patricia Trie to retain historical versions of its Append-Only Zero Knowledge Set
(aZKS) without maintaining a separate authentication structure for every
epoch~\cite[Section~6]{chase2019seemless}. Its Patricia trie is compressed because it contains no
empty nodes. This thesis uses \emph{path-compressed prefix tree} when single-child chains are
collapsed. The IETF KeyTrans draft also specifies a prefix tree and proof encodings for
inclusion and non-inclusion~\cite[Sections~3.3 and~12.2]{ietf-keytrans-protocol}.

\paragraph{Zero-Knowledge Sets.} A ZKS commits to a collection of label--value pairs and supports
membership and non-membership proofs without revealing information about the remaining collection.
These constructions define privacy relative to a leakage function that states what information the
proofs may reveal beyond the query result. SEEMless's aZKS extends the static primitive with
verifiable append-only updates and prevents an existing label from being modified or
deleted~\cite[Sections~2--3]{chase2019seemless}.

Parakeet's ordered ZKS (oZKS) additionally binds the order in which elements are inserted. Its
compaction extension first marks eligible elements for deletion through tombstoning and later
deletes the tombstoned elements~\cite[Sections~III-C and~IV]{malvai2023parakeet}. A rotatable ZKS
(RZKS) adds a separate post-compromise update that rotates the server key and restores privacy for
future updates after server-state compromise~\cite[Sections~1 and~3]{chen2022rzks}. ELEKTRA
uses RZKS as the authenticated directory underlying its multi-device
construction~\cite[Sections~1 and~3.1]{len2023elektra}.

\section{Equivocation and Split-View Detection}\label{sec:ext-splitview}

A consistency proof establishes that one log state extends another, but it does not show whether
every observer received that same state. A malicious directory operator may maintain two internally
consistent histories, presenting signed head $\STH^\A$ to Alice and a different $\STH^\B$ to Bob.
It may commit a legitimate key binding in one view and a substituted binding in the other. Both
clients' local inclusion and consistency checks may succeed. Therefore, detecting this split view
requires comparing signed heads through client gossip, an anonymous channel, or external
auditors~\cites[Section~4.1.4]{melara2015coniks}
[Sections~10.2 and~16]{ietf-keytrans-protocol}. This limitation of local verification motivates
DUET's split-view requirement in \cref{ssec:bg-implications}. \Cref{fig:bg-splitview} shows the two
views and their comparison.

\begin{figure}[H]
\centering
\input{figures/tikz/fig-bg-splitview}
\caption[The split-view (fork) attack.]{The split-view attack. A malicious directory operator
presents Alice and Bob with different but internally consistent signed heads. Two validly signed
heads of the same tree size with different roots provide direct evidence of equivocation. For
different tree sizes, the comparison requires a valid consistency proof. A missing or invalid proof
produces \textsc{ConsistencyUnverified} but does not establish equivocation.}

\section{Academic and Deployed Directory Systems}\label{sec:ext-vkd-survey}

\subsection{Academic VKD Constructions}

\paragraph{CONIKS.}
CONIKS provides the starting point for the academic designs considered here. It introduced a
transparency-based key-verification design using a Merkle prefix tree. It stores each binding at a
private lookup index derived through a verifiable unpredictable function and publishes a Signed
Tree Root (STR) at each epoch. Every STR commits to the current directory root and includes the hash
of the preceding STR~\cite[Sections~3.1 and~3.3--3.4]{melara2015coniks}. Clients monitor their own
bindings every epoch using logarithmic-size proofs. Under the paper's stated model, a provider with
approximately $2^{32}$ users requires a daily monitoring download below
20\,kB~\cite[Sections~4.1.3 and~5.3]{melara2015coniks}. Auditors verify the linear STR history, while
clients compare the provider's STR with one observed by an auditor to detect
equivocation~\cite[Section~4.1.4]{melara2015coniks}.

Three limitations of CONIKS are directly relevant to DUET. A returning client must perform a series
of checks covering the missed epochs~\cite{melara2015coniks}. Direct exchange of observed
STRs between clients remains future work~\cite[Section~4.1.4, footnote~5]{melara2015coniks}.
Finally, CONIKS can expose an attack but cannot stop a provider that accepts the resulting public
evidence~\cite[Section~2.1]{melara2015coniks}.

\paragraph{SEEMless.}
SEEMless builds on this key-directory model by formalizing the verifiable key directory (VKD)
abstraction through completeness, soundness, and simulation-based
privacy~\cite[Section~2]{chase2019seemless}. Its append-only zero-knowledge set (aZKS) stores
successive versions under distinct label--version pairs so that earlier changes remain in the
verified history. A \texttt{KeyHistory} query returns the values and epochs of the user's key
updates. Its cost depends mainly on the number of updates, while marker checks add overhead
logarithmic in the number of epochs~\cite[Sections~4.2--4.3]{chase2019seemless}. The client must
compare the returned history with the updates it made. Auditors verify update proofs between
adjacent epochs~\cite[Section~4.3]{chase2019seemless}. The paper assumes agreement on the published
commitment and suggests gossip or blockchain publication as possible
mechanisms~\cite[Section~2.1]{chase2019seemless}.

\paragraph{Parakeet.}
Parakeet addresses the storage growth of append-only history and the publication of consistent
commitments. It introduces compaction to limit storage
growth~\cite[Sections~III-C and~IV]{malvai2023parakeet} and uses a consensusless witness protocol
to distribute consistent commitments. The protocol assumes $3f+1$ witnesses, of which at most $f$
are faulty, and certifies an epoch commitment with signatures from a quorum of $2f+1$
witnesses~\cite[Sections~II-A and~V]{malvai2023parakeet}. Quorum intersection prevents two
conflicting commitments for the same epoch from both obtaining valid
certificates~\cite[Section~V-B]{malvai2023parakeet}. This introduces a distributed witness set as
an operational and trust assumption, while detecting an unauthorised key change still depends on
the client monitoring its own binding~\cite[Section~II-A]{malvai2023parakeet}.

\paragraph{ELEKTRA.}
ELEKTRA extends the VKD abstraction to multiple devices. Each account is represented by a keychain
containing device additions and revocations. Except for the first key and a full account reset, a
keychain change must be authenticated by an existing unrevoked device
key~\cite[Sections~1, 2.1, and~2.2]{len2023elektra}. Outside the first-key and full-reset cases, and
assuming consistency of the directory, a malicious provider cannot add a fabricated device key
without forging a device signature or compromising an existing device. Its \texttt{PCSUpdate}
operation uses a rotatable zero-knowledge set to rotate the server key and restore privacy after
server-state compromise~\cite[Sections~1 and~3.1]{len2023elektra}.

A full account reset invokes \texttt{AddFirstKey}, which appends another \texttt{AddFirst}
statement that contacts can detect when they query the keychain. The paper recommends showing an
urgent warning for this event~\cite[Section~2.2]{len2023elektra}. However, this warning concerns a
full account reset, not the substitution of an individual key.

\paragraph{OPTIKS.}
OPTIKS simplifies the two-tree structure used by SEEMless and Parakeet. The \emph{all tree} stores
every key version, while the \emph{old tree} stores versions that are no longer
current~\cite{optiks2024}. OPTIKS removes the old tree and instead proves freshness in the
remaining tree through membership of the current version and non-membership of the next version.
Since the two trees have approximately the same size, this reduces storage and update costs by
approximately half~\cite{optiks2024}. After checking a key once in the current time period,
the client needs only one non-membership proof if that key remains
unchanged~\cite[Section~5]{optiks2024}. However, the client must complete the required history
checks before data from an old time period is deleted~\cite[Section~5]{optiks2024}. OPTIKS does not
define a conversation-specific peer-warning channel for an individual key substitution.

\paragraph{PRISM.}
PRISM changes the monitoring model by allowing each client to verify the complete directory state.
It uses a zero-knowledge rollup in which a zero-knowledge virtual machine (zkVM) proves state
transitions over a Jellyfish Merkle tree. The resulting epoch proofs are published through a
data-availability layer, allowing light clients to verify the whole directory state instead of
monitoring only their own entries~\cite[Sections~1 and~4]{pusch2025prism}. PRISM identifies the
wider reliance of existing systems on external checks performed by users, gossiping clients,
blockchains, auditors, or witness committees~\cite{pusch2025prism}. The authors state that the
paper provides an overview and does not attempt a complete
specification~\cite{pusch2025prism}. Its construction relies on Celestia for ordered and
globally available data and uses a designated sequencer/prover to batch operations and generate
epoch proofs~\cite[Sections~3.2 and~4]{pusch2025prism}.

\paragraph{Merkle\texorpdfstring{$^2$}{2}.}
Merkle\textsuperscript{2} is a general transparency log system that the authors identify as
applicable to public-key transparency~\cite[Sections~I and~XI]{hu2021merkle2}. It nests two
authenticated structures: an outer chronological Merkle tree and a prefix tree committed by each of
its internal nodes~\cite[Section~IV]{hu2021merkle2}. This structure gives $O(\log^2 n)$ append cost, while a data
owner downloads only $O(\log^2 n)$ data for monitoring throughout the system's
lifetime~\cite[Table~I and Section~V]{hu2021merkle2}. The paper explains that VRF-derived indices
can reduce identifier leakage~\cite[Section~VII-B]{hu2021merkle2}. However, VRF is not implemented
as the evaluation concentrates on system performance instead of
privacy~\cite[Section~VIII]{hu2021merkle2}.

\subsection{Production VKDs and R\&D Projects}

\paragraph{WhatsApp Key Transparency (AKD).}
WhatsApp deploys an Auditable Key Directory at production scale, with signed directory roots and
retained audit material for independent consistency
checking~\cite{whatsapp2023whitepaper}. At the time of the whitepaper, WhatsApp clients did not yet
support key-history requests~\cite{whatsapp2023whitepaper}. A failed automatic check directs the user to verify the
session manually with the contact~\cite{whatsapp2023whitepaper}. The cited workflow
does not define the automatic in-band peer warning targeted by this thesis.

\paragraph{Signal Key Transparency.}
Signal's repository states that its implementation uses the IETF protocol with application-specific
modifications and exposes Search, Monitor, and audit interfaces. The stored
mappings associate an account identifier (ACI) with its identity key and associate a phone number or
username hash with the ACI. The verifier requires a full 256-sibling prefix copath. At 32 bytes per
sibling, this gives the fixed \num{8192}-byte copath used as a baseline in
\cref{ch:eval}~\cite{signal-kt-server}.

\paragraph{Proton Mail Key Transparency.}
ProtonKT applies a verifiable directory to email and reuses Certificate Transparency to support
consistency checking~\cite{goebel2023proton}. It supports owner and external auditing~\cite{goebel2023proton}.
Its warning model notifies the key owner but not the communication
partner~\cite{goebel2023proton}. The Proton thesis also describes the investigation
of KT warnings as an open user-experience
challenge~\cite{goebel2023proton}.

\paragraph{Google KT and Apple CKV.}
Google Key Transparency is an archived CONIKS-inspired implementation
project~\cite{google-kt}. Apple Contact Key Verification provides automatic verification of account
and device keys~\cite{apple-ckv}. Their relevant properties are summarized in
\cref{tab:bg-compare}.
