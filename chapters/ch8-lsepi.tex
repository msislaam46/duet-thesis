\chapter{Legal, Social, Ethical and Professional Issues}\label{ch:lsepi}

DUET processes account-linked key material, extends AGPL-covered software, and reports security
evidence that may influence deployment decisions. This chapter examines the resulting legal, social,
ethical, and professional responsibilities.

% ============================================================================
\section{Legal Issues}\label{sec:lsepi-legal}

The client work derives from libsignal and Signal Desktop, both distributed under the
AGPL-3.0~\cite{libsignal,signal-desktop,agpl3}. Conveying modified AGPL-covered code requires the
corresponding source to be provided under the licence. If a modified version is operated as a network
service that supports remote interaction, Section~13 additionally requires that interacting users be
offered the corresponding source. This prototype was evaluated locally rather than operated as a
public service. UK law protects software as a literary work, so upstream copyright and licence notices are retained rather than
rewritten~\cite{uk-software-copyright}. An upstream contribution would require signing Signal's contributor licence
agreement~\cite{signal-cla}, a route not taken here.

The project uses publicly documented cryptographic algorithms and open-source implementations. Public
availability does not by itself determine export-control classification, so this thesis makes no claim
that the implementation falls within a particular exemption~\cite{uk-cryptonote,uk-export-lists}. A
production release would require classification against the applicable control list and the guidance
current at that time. The directory stores pseudonymised identifiers, public keys, and epoch metadata,
never message content or plaintext identifiers. Pseudonymised data remains personal data under UK
GDPR, so this design is treated as processing personal data rather than
exempt~\cite{ico-pseudonymisation}. VRF-derived indices keep raw identifiers out of the published
tree and reduce direct identifier exposure, but they do not make the records anonymous. Production
use would require a data-protection assessment, a documented processing purpose and lawful basis,
restricted access to warning records, and defined retention periods~\cite{ico-data-principles}. Two residual exposures remain: the
query pattern visible to the operator (\cref{ch:discussion}) and the density metadata a
bitmap-compressed proof reveals (\cref{ch:eval}).

\section{Social and Ethical Issues}\label{sec:lsepi-social}

Undetected key substitution is a physical risk for journalists, activists, and others whose safety
depends on a conversation staying private. Automatic detection is intended in part to protect these
groups, making accurate reporting about what was built an ethical obligation. The
prototype runs on a single machine and in memory and uses a deterministic conversation-secret
stand-in and a seeded ratchet simulation (\cref{sec:impl-strategy}). It does not protect a client
whose endpoint is compromised (\cref{sec:threat-assumptions}). Overstating a security tool puts its
intended users at risk.

Ambiguous, excessive, or privacy-revealing warnings can themselves cause harm. An uninterpretable
warning causes alarm fatigue rather than protection. The interface
therefore uses amber for an unavailable directory and red only for a verified mismatch. A red warning
states that an integrity or consistency check failed without assigning a cause. Usability
testing, accessibility, escalation routes, and support paths are unaddressed here and named as future
work in \cref{ch:discussion}. Warning records also reveal who was warned and when, creating additional
metadata that requires protection.

The evaluation used synthetic accounts and neither recruited participants nor intercepted live
traffic (\cref{ssec:impl-demo}), so it was not a human-participant study. A deployment would need to
assess the unmeasured infrastructure, energy, and access costs of an independent second vantage.

\section{Professional Issues and Codes of Conduct}\label{sec:lsepi-prof}

The BCS Code of Conduct organizes obligations into public interest, professional competence and
integrity, duty to relevant authority, and duty to the profession~\cite{bcs-code}. The public
interest is served by stating the limits above as prominently as the results. Competence and
integrity are addressed by validating the project's ECVRF implementation against the RFC~9381 test
vectors and by disclosing in \cref{sec:impl-challenges} the defects corrected during development,
including a missing signed-head binding a passing test suite had not caught. Regular supervisory review, source
attribution, and compliance with the university's academic-integrity requirements address the duty to
the relevant authority. Separating measured prototype results from unimplemented production
requirements addresses the duty to the profession.

The IET Rules of Conduct impose corresponding duties~\cite{iet-conduct}. Through the Statement of Ethical Principles incorporated by Rule 2, the IET requires accuracy and
rigour, which is why every measurement in \cref{ch:eval} carries its scope. Rules 5 and 6 require working
within competence and maintaining knowledge, which is why the project's ECVRF implementation is checked against
the RFC~9381 vectors rather than assumed correct. Rule 26 requires that opinions state their
limitations, which is why the thesis states the assumptions and qualifications attached to its
security and performance claims. The defects found during development were confined to the prototype. No finding indicated a defect in
upstream Signal software. Any upstream defect would have been reported through Signal's security
vulnerability channel rather than published~\cite{signal-security-report}.
