\chapter{Implementation}\label{ch:impl}

The implementation has two components. The \texttt{duet} Rust crate provides the directory server,
cryptographic operations, an auditor process, and a benchmark harness. The client component,
implemented in TypeScript and integrated into Signal Desktop,
provides the verifier, background monitor, lifecycle hooks, and warning interface. This chapter
covers their architecture, integration, testing, and engineering challenges.

% ============================================================================
\section{Architecture and Language Choices}\label{sec:impl-strategy}

The \texttt{duet} Rust crate contains the directory server and cryptographic core, along with the
auditor process and benchmark harness. An initial Python version prototyped the core constructions
but was too slow for the required large-directory benchmarks. The measured implementation was
therefore rebuilt in Rust to use established cryptographic libraries for timing-sensitive operations
and support future integration with libsignal~\cite{libsignal}. Keeping the crate separate from
Signal Desktop also allows independent measurement.

The client component provides local proof verification, background monitoring, lifecycle hooks, and
the warning interface. Its verification and raw-label write paths are described in
\cref{ssec:impl-verifier}. Fixed vectors compare cryptographic outputs between the client component
and the \texttt{duet} crate, while the opt-in live integration tests, referred to as the wire-parity
suite, run the client verification code against responses from the directory server. The
verification chain is based on the IETF KeyTrans design~\cite{ietf-keytrans-protocol}. However,
differing prefix-proof encodings currently prevent interoperability with Signal's Go
key-transparency implementation~\cite{signal-kt-server}. \Cref{fig:impl-overview} shows the two
implementation components and the separate auditor process.

The directory server is an in-memory, single-machine prototype that clones the directory tree at
each epoch commit. The Signal integration uses a deterministic conversation-secret substitute and
seeded Double Ratchet simulation to test label derivation and CEA state transitions. The client
performs identity-key verification when Signal Desktop retrieves the peer's identity key. However,
production integration would require access to the live conversation secret and ratchet state from
libsignal, as discussed further in \cref{ch:discussion}.

\section{DUET Directory and Cryptographic Core}\label{sec:impl-modules}

Within the \texttt{duet} crate, the directory core combines a path-compressed sparse Merkle
directory, an append-only log with RFC~9162 consistency proofs~\cite[Section~2.1.4]{rfc9162}, and signed tree heads based on
the IETF KeyTrans model~\cite[Sections~3 and 11.2]{ietf-keytrans-protocol}. It also uses
ECVRF-EDWARDS25519-SHA512-TAI for global-label
derivation~\cite[Section~5.5]{rfc9381}. The crate implements DUET's dual-index construction, ACKA's
CEA construction~\cite[Section~5.1]{dowling2023acka}, the HTTP server, and the auditor process. The
\texttt{sha2}, \texttt{hkdf}, \texttt{ed25519-dalek}, and \texttt{curve25519-dalek} crates provide
the underlying hash, key-derivation, signing, and elliptic-curve operations. The \texttt{vrf} module
checks its curve encoding and proof verification against the RFC~9381 test
vectors~\cite[Appendix~B.3]{rfc9381}. \Cref{fig:impl-modules} shows the relationships among the
directory core, client component, and auditor, while \cref{tab:impl-modules} maps each module to its
standards basis and conformance evidence.

\subsection{Directory State and Cryptography}\label{ssec:impl-core-state}
\label{ssec:impl-core-crypto}

The directory materializes only populated prefix paths and compresses each proof with a 256-bit
bitmap. A compressed leaf terminates the fixed-depth tree walk early. Empty sibling hashes are
omitted from the transmitted proof. The implementation memoizes a small window of each compressed
leaf's empty-sibling hash chain when it is first needed, avoiding repeated computation on later
lookups. For a directory containing $N$ populated pseudorandom labels, a proof contains about
$\lceil \lg N \rceil$ non-empty sibling hashes. Tree-update work is separate. Updating $k$ labels visits at most $d=256$
tree levels per label, giving $O(kd)$ tree-update work. Since $d$ is fixed, this is $O(k)$ in $k$
and independent of $N$.

At an epoch commit, the server appends the current directory root to the log, clones the current
tree as the committed snapshot, and signs the resulting head. Clients verify lookup responses against
this signed state. The \texttt{dual\_index} module uses the \texttt{hkdf} crate with SHA-256 to
implement the extract-and-expand derivations in \cref{ssec:design-labels}~\cite[Sections~2--3]{rfc5869}.
The two lookup directions use opposite service-identifier orders under the \texttt{lookup} context,
while canonical identifier ordering under the \texttt{warning} context produces the shared warning
label. The \texttt{vrf} module implements ECVRF-EDWARDS25519-SHA512-TAI directly with
\texttt{curve25519-dalek} and \texttt{sha2}~\cite[Section~5.5]{rfc9381}, using the first 32 bytes of
$\beta$ as the prefix-tree label. A drawback of cloning the tree is that its cost grows with the
directory size. Further module and data-structure details are provided in
Appendix~\ref{sec:apiref-engineering}.

\subsection{Server, Auditor, and Benchmark Harness}\label{ssec:impl-core-server}
\label{ssec:impl-bench}

The HTTP server uses \texttt{axum} and \texttt{tokio} and holds the directory behind a single
\texttt{Arc<Mutex<KTServer>{}>}. This serializes access within the single-machine prototype. The public
interface provides registration, lookup, raw-label updates, consistency proofs, epoch deltas, and
epoch commits. The demonstration harness uses a separate privileged testing interface to overwrite or
delete entries and reset the server. A public write to an occupied dual-index, warning, or CEA label
returns \texttt{409 Conflict}. For the A4 split-view scenario, the demonstration harness uses the
privileged interface to stage a second signed-head view. The auditor runs as a separate process and
compares that view with the primary head to detect equivocation.

The auditor also verifies every committed directory transition. For each epoch, the
\texttt{/epoch-delta} endpoint returns the declared insertions and rotations, including the previous
value for every rotation. \Cref{fig:impl-transition-audit} shows the complete verification flow. The
auditor replays every unaudited delta on a temporary copy of its accepted directory state. It verifies
that each disclosed root is included in the signed log and that the replay reproduces that root. The
accepted directory state and cursor advance only after every unaudited epoch is verified and any available
signed-head comparison succeeds. The auditor's update flow is based on the IETF
\texttt{AuditorUpdate} pattern, in which the service operator sends an update for each new log entry
to a third-party auditor for
verification~\cite[Section~15.2]{ietf-keytrans-protocol}. However, DUET's delta format and
verification checks are specific to this implementation. Since deletion is not expressible in the
delta format, an undeclared deletion produces a root mismatch. A duplicate insert or immutable
rotation is rejected during replay. A separate persistence check provides additional deletion
evidence by combining an earlier inclusion proof, a later non-inclusion proof, and a consistency
proof between the signed heads. This check is independently tested but is not integrated into the
Signal Desktop monitor.

For performance evaluation, the benchmark harness calls the directory core directly within the same
process. Therefore, the reported timings cover local cryptographic and data-structure work and
exclude HTTP, Electron, persistent storage, and network costs. The measurement environment is
described in Appendix~\ref{sec:bench-env}, while Appendix~\ref{sec:bench-repro} gives the
reproduction procedure.

\section{Signal Desktop Integration}\label{sec:impl-signal}

The Signal Desktop verifier checks responses from the DUET directory server and reports results
through a conversation badge and banner. The badge starts grey (pending) and turns green only when
verification succeeds and the account-wide self-check is healthy. If the server is unreachable, the
badge remains pending and an amber availability banner appears. A proof failure, verified key
mismatch, proof-verified warning-slot value, or fail-closed operational timeout produces a red
badge and warning banner.

\subsection{Client Verification and Lifecycle}\label{ssec:impl-verifier}
\label{ssec:impl-hooks}

Node's cryptographic APIs provide SHA-256, SHA-512, HMAC-SHA256, Ed25519, and X25519, while the
ECVRF arithmetic is implemented in TypeScript. At Signal Desktop's peer-key-retrieval integration
point, the client applies the verification chain in \cref{ssec:design-verify} to the directory
lookup response and compares its verified value with the fetched identity key. An invalid or
missing signed head, a failed proof, or a key mismatch causes verification to fail. The prototype reports the resulting verdict but does not prevent session establishment.

The key-upload path registers the client's global identity binding, while the peer-key-retrieval
path verifies the fetched binding. Before these directory operations, Signal service-ID strings are
converted to canonical 16-byte account identifiers. A background monitor first checks the client's
own global VRF-derived identity entry. For each conversation, it then verifies append-only consistency, the
client's own lookup slot, the shared warning slot, and the peer's lookup slot, emitting a green
verdict only when all checks succeed and the global self-check is healthy. The warning slot is checked
before the peer slot, so a committed warning takes precedence over a pending or fail-closed
\texttt{NotPosted} verdict for an absent peer. A proof-verified peer-slot
absence remains pending for two checks. If the slot is still absent on the third check, the client
reports a fail-closed \texttt{NotPosted} timeout, since the peer may not yet have run the client. A
periodic lifecycle check stops monitoring deleted conversations, while archived conversations remain
monitored.

A warning payload carries a MAC under a key derived from the conversation secret. A valid MAC shows
that one of the parties produced the payload but does not identify the writer. DOM events carry
verdicts from the preload context to the user interface. Appendix~\ref{sec:apiref-hooks} lists the functions and
event names, while Appendix~\ref{sec:apiref-engineering} provides the implementation and engineering
details.

\subsection{End-to-End Demonstration}\label{ssec:impl-demo}

The demonstration uses two Signal Desktop clients with the DUET directory server, an auditor process,
and a privileged attack tool. It covers the two server-side key-substitution variants in
\hyperref[sc:threat-a1]{A1}. In the A1a global-slot variant, the attack tool replaces the mutable
global identity entry. The transition auditor accepts the declared rotation because this entry is
mutable, while the affected client's account-wide self-check detects the substitution and publishes
an authenticated warning that the peer reads from the shared slot. In the A1b session-slot variant,
the attack tool replaces an immutable dual-index session slot. The affected client's session monitor
detects the mismatch and publishes the peer warning, while the transition auditor rejects the
declared rotation because the slot is immutable.

\Cref{fig:impl-screens} shows both clients before and after the A1a substitution. The runs use two
researcher-controlled Signal accounts linked through Signal's production service and intercept no
third-party traffic. Additional console, command, and auditor evidence is provided in
Appendix~\ref{sec:apiref-demo}.

\section{Implementation Agreement and Security Testing}\label{sec:impl-tests}

Testing checks standards conformance, agreement between the \texttt{duet} crate and the Signal
Desktop client component, and the expected behaviour under the threat scenarios. Both ECVRF
implementations are checked against the RFC~9381 test
vectors~\cite[Appendix~B.3]{rfc9381}. Fixed vectors require byte-for-byte agreement for dual-index
labels, warning payloads, and CEA state evolution. The opt-in wire-parity suite checks the client
verification code against signed heads, VRF outputs, prefix-tree and log-inclusion proofs, and
consistency proofs returned by the directory server implemented in Rust.

The adversarial suite covers the honest baseline (A0), the attack scenarios (A1--A5), and the
endpoint-compromise boundary defined in \cref{sec:threat-scenarios}. These tests establish agreement
and the expected behaviour for the specified inputs only, without establishing equivalence over
every input. For A5 (malicious key rotation), predecessor cross-signature checking remains limited
to the \texttt{duet} crate's adversarial suite. The Signal Desktop client instead uses identity
re-fetch and the shared warning path without performing this check.
Appendix~\ref{sec:tests-adversarial} gives the individual adversarial outcomes, while
Appendix~\ref{sec:tests-evidence} describes the complete evidence structure and suite counts.

\section{Engineering Challenges}\label{sec:impl-challenges}

Three areas required substantial implementation changes. First, the client component's initial
ECVRF implementation produced different outputs from the \texttt{duet} crate as their
encode-to-curve steps differed. Both implementations were aligned with the
ECVRF-EDWARDS25519-SHA512-TAI suite and checked against the RFC test
vectors~\cite[Appendix~B.3]{rfc9381}. Each lookup response was also changed to carry a signed head
obtained under the same server lock. The verifier checks that the signed head's root matches the
root used for log-inclusion verification, preventing a valid proof from being paired with an
unsigned or unrelated head.

Second, registration and lookup initially used different encodings for Signal account identifiers.
Converting both paths to the canonical 16-byte account identifier removed that mismatch. Another
race condition arose when an epoch was committed between reading a signed head and requesting a
consistency proof. The client and auditor now request each proof using the size of the validated
signed head so that a later commit cannot change the proof's upper bound.

Third, Electron integration produced two delivery problems. First, dynamic imports split the
key-transparency code across bundles, so the complete key-transparency layer was kept in one bundle.
Second, context isolation prevents properties assigned in the preload context from being read by
the renderer. Therefore, verdicts are dispatched as DOM custom events on \texttt{window}, which
pass from the preload context to the renderer.
Appendix~\ref{sec:apiref-engineering} provides further details on bundling, deterministic keys,
reset behaviour, and fail-closed handling.
