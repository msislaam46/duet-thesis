\chapter{Implementation}\label{ch:impl}

The implementation has two components. The Rust component provides the directory, cryptographic
operations, auditor, and benchmarks. The TypeScript component embeds the client verifier in Signal
Desktop. This chapter covers their architecture, integration, parity testing, engineering
constraints, and reproducibility.

% ============================================================================
\section{Architecture and Language Boundary}\label{sec:impl-strategy}

The standalone \texttt{duet} crate implements the Rust component. An initial Python version
prototyped the core constructions but was too slow for the required large-directory benchmarks. The
measured implementation was therefore rebuilt in Rust, which also supports libsignal integration and
established cryptographic libraries for timing-sensitive operations. Rust allows the crate to be
measured independently of Signal and libsignal and is also used by the Parakeet and Meta AKD
implementations~\cite{malvai2023parakeet,facebook-akd}. \Cref{fig:impl-overview} shows the resulting
language and trust boundary.

The TypeScript layer implements the client-side proof checks and user-interface path. It verifies
prefix, log, VRF, and signed-head evidence locally, performs the required raw-label writes, and is
checked against Rust through fixed vectors and live wire-parity tests. The formats follow the IETF
KeyTrans design, but no Go interoperability is claimed because Signal and DUET deliberately use
different prefix-proof encodings~\cite{ietf-keytrans-protocol,signal-kt-server}.

The Rust service is an in-memory, single-machine prototype. The Signal integration uses a deterministic
conversation-secret stand-in and a seeded Double Ratchet simulation, which cover the construction and
wire format but not secrecy-dependent label unpredictability or real-ratchet security. The identity-key
path is not simulated: the verifier runs at Signal Desktop's real peer-key-retrieval
boundary. Production integration must obtain the live conversation secret and ratchet state from libsignal
(\cref{ch:discussion}).

\section{The Rust Cryptographic Core}\label{sec:impl-modules}

The \texttt{duet} crate implements a path-compressed sparse Merkle directory and signed tree heads
following the IETF KeyTrans model~\cite{ietf-keytrans-protocol}, an RFC~9162 append-only
log~\cite{rfc9162}, and ECVRF-EDWARDS25519-SHA512-TAI~\cite{rfc9381}. It also includes DUET's
dual-index construction, ACKA's CEA construction~\cite{dowling2023acka}, an HTTP server, and an
independent auditor. The crates \texttt{sha2},
\texttt{hkdf}, \texttt{ed25519-dalek}, and \texttt{curve25519-dalek} supply the standard primitives. The
project implements the ECVRF directly and checks it against the RFC~9381 test vectors.
\Cref{fig:impl-modules} shows the module structure, while \cref{tab:impl-modules} maps each module to
its standards basis and conformance evidence.

\subsection{Directory State and Cryptography}\label{ssec:impl-core-state}
\label{ssec:impl-core-crypto}

The directory materializes only populated prefix paths and bitmap-compresses proofs. A compressed leaf
terminates the otherwise fixed 256-bit walk. The implementation lazily memoizes a small window of each
compressed leaf's empty-sibling hash chain, avoiding repeated computation. Empty siblings are omitted
from the transmitted proof, which carries about $\lceil \lg N \rceil$ non-empty sibling hashes. Proof transmission and update cost have different
bounds. With the trie depth fixed at $d=256$, copying the affected paths for $k$ modified labels
costs $O(kd)$, which is $O(k)$ in $k$ and independent of $N$.

A committed epoch freezes a snapshot, appends its root to the log, and signs the resulting head.
Client recomputation checks each response without trusting the directory operator. HKDF-SHA256 derives
the two conversation-specific lookup labels and the shared warning label from the conversation secret
and the parties' service identifiers~\cite{rfc5869}. For global identity entries, the RFC~9381 ECVRF
derives a pseudorandom label from the user identifier and supplies a proof of correct
evaluation~\cite{rfc9381}. Epoch commitment deep-clones the current tree to form the committed
snapshot, so its copy cost grows with the directory size. Further module and data-structure details
are provided in \cref{sec:apiref-engineering}.

\subsection{Server, Auditor, and Benchmark Boundary}\label{ssec:impl-core-server}
\label{ssec:impl-bench}

An \texttt{axum} and \texttt{tokio} server holds the directory behind a single
\texttt{Arc<Mutex<KTServer>>} with no sharding, which is adequate for a single-machine prototype and is
one of the constraints \cref{ch:discussion} returns to. The server exposes public lookup and monitoring
operations plus a privileged unchecked-overwrite interface used only by the adversarial harness.
Write-once enforcement returns 409 Conflict when a dual-index, warning, or CEA label is already
occupied, so a replacement is refused, never silently applied. A separate \texttt{ureq} auditor
binary obtains signed heads from its own vantage.

Every commit publishes a declared set of inserts and rotations at an epoch-delta endpoint, and each
rotation discloses its prior value. \Cref{fig:impl-transition-audit} shows the resulting audit. The
auditor applies the declared set to a candidate replica and accepts only if the recomputed root equals
the committed root, which mirrors the \texttt{AuditorUpdate} role in the IETF architecture. Deletion is
not expressible in the delta format, so an omitted warning or an immutable-slot replacement makes the
roots diverge and is reported, not absorbed. A tested writer-side persistence component can
additionally combine an original inclusion proof, a later non-inclusion proof, and consistency between
the two signed heads into independently verifiable deletion evidence, but it is not yet wired into the
live monitor. Initial ownership of an empty raw label is not authenticated, so a malicious client can
still occupy an unclaimed slot first.

\section{Signal Desktop Integration}\label{sec:impl-signal}

The embedded TypeScript client verifies Rust directory responses and reports the result through a
conversation badge and banner. The interface starts grey (pending), turns green only when
verification succeeds and the account-wide self-check is healthy, shows an amber notice when a check
is unavailable, and shows a red warning after a proof failure, key mismatch, authenticated peer
warning, or the fail-closed operational timeout.

\subsection{Client Verification and Lifecycle}\label{ssec:impl-verifier}
\label{ssec:impl-hooks}

Node's cryptographic provider supplies SHA-256, SHA-512, HMAC-SHA256, Ed25519, and X25519, while the
ECVRF arithmetic is implemented in TypeScript. The client performs the complete verification chain of
\cref{ssec:design-verify} at Signal Desktop's own peer-key-retrieval boundary, on the real
identity-key path. Invalid or absent heads, proof failures, and key mismatches produce rejecting
verdicts. The integration reports the verdict but, by design in this prototype, does not block
session establishment.

The key-upload path registers identity material, while the peer-key-retrieval path verifies the
fetched binding. A background monitor first checks the
client's own global VRF-derived identity entry, then, per conversation, its owner, peer, and warning
slots, emitting a green verdict only when the global self-check is healthy. A proof-verified
peer-slot absence is reported as pending for the first checks and, after a fail-closed timeout, as
\texttt{NotPosted}, since it can also mean the peer has not yet run the client. A periodic sweep
drops conversations that have gone inactive, as on deletion, while retaining archived ones. A warning
payload carries an HKDF-derived MAC over the conversation secret,
so a client can tell a secret-holder's payload apart from one injected by the operator. Since both
parties derive the same MAC key, the MAC does not identify the writer. Signal service-ID strings are
converted to canonical 16-byte account identifiers at the integration boundary, and phone-number
identifiers are excluded. Verdicts cross Electron's isolated contexts through DOM events. The exact
functions, event names, and engineering record are in \cref{sec:apiref-hooks,sec:apiref-engineering}.

\subsection{End-to-End Demonstration}\label{ssec:impl-demo}

The demonstration uses two Signal Desktop clients with the Rust directory server, auditor, and a
privileged attack tool. It covers the two \hyperref[sc:threat-a1]{A1 key-substitution variants}.
In the A1a global-slot variant, the attack tool replaces the value in the mutable global identity
slot. The auditor accepts the declared rotation, while the affected client's self-check detects the
substituted key. In the A1b session-slot variant, the attack tool replaces the value in an immutable
dual-index session slot. The affected client publishes a warning that the peer reads from the shared
slot, and the auditor rejects the transition because that slot cannot be rotated.
\Cref{fig:impl-screens} shows both clients before and after the A1a substitution. The runs use two
researcher-controlled Signal accounts linked through Signal's production service and intercept no
third-party traffic. Additional console, command, and auditor evidence is provided in
\cref{sec:apiref-demo}.

\section{Cross-Implementation Testing and Parity}\label{sec:impl-tests}

RFC~9381 test vectors~\cite{rfc9381} check the ECVRF implementation. Fixed cross-language vectors
require byte-for-byte agreement for label derivation, warning payloads, and CEA evolution. A live
wire-parity suite checks the TypeScript verifier against signed heads, VRF outputs, Merkle proofs, and
consistency proofs produced by the Rust directory server. The Rust integration and cryptographic tests
use an in-process \texttt{KTServer} rather than a mock. The adversarial suite covers the honest
baseline (A0), global- and session-slot substitution (\hyperref[sc:threat-a1]{A1a and A1b}), warning
censorship (\hyperref[sc:threat-a2]{A2}), the first-contact substitution postcondition
(\hyperref[sc:threat-a3]{A3}), equivocation (\hyperref[sc:threat-a4]{A4}), key-rotation substitution
(\hyperref[sc:threat-a5]{A5}), and endpoint compromise (\hyperref[sc:threat-x1]{X1}). These tests show
agreement and the expected behaviour for the specified inputs, not equivalence over every input.
\Cref{sec:tests-evidence} gives the complete counts, names, and outcomes.

The Rust tests exhaustively cover every Merkle-log inclusion proof and consistency pair up to size 64,
with forged-proof rejection, not sampling. Auditor tests reject invalid
fork evidence and report genuine equivocation as \textsc{Fork}, while a divergent head with an invalid
signature is rejected rather than misclassified.

The TypeScript harness contains 180 Jest tests. Thirty-five embedded tests across six suites drive
realistic account identifiers through Signal Desktop's own integration boundary. The standalone,
embedded, and opt-in wire-parity suites are separate test
classes rather than one aggregate total. \Cref{sec:impl-repro} provides the complete reproduction
commands and environment.

\section{System-Wide Engineering Challenges}\label{sec:impl-challenges}

Three areas required substantial implementation changes. First, the initial TypeScript label stand-in did not agree with Rust's RFC~9381 ECVRF because their
encode-to-curve steps differed. Both implementations were aligned on the
ECVRF-EDWARDS25519-SHA512-TAI suite and checked against the RFC test
vectors~\cite[Appendix~B.3]{rfc9381}. Signed heads were also bound to each lookup response, preventing a valid proof
from being paired with an unsigned or unrelated head.

Second, registration and lookup originally encoded Signal account identifiers differently. Converting
the service-ID string once at the integration boundary gives both paths the same canonical 16-byte
input and excludes phone-number identifiers before processing. Concurrent registration separately
exposed a time-of-check race between reading the head and using it to bound a proof. Binding each
consistency proof to the already validated head size prevents a later commit from making the client or
auditor compare a proof against the wrong upper bound.

Third, Electron integration blocked reliable interface delivery. Dynamic imports split the
key-transparency code, so it was kept in one bundle. Context isolation blocked assignments to
\texttt{window} but allowed DOM events across the preload and renderer boundary. The application
exposes both a typed event bus and DOM custom events. Dispatching verdicts through both interfaces
resolved the delivery mismatch. The remaining bundling,
deterministic-state, and reset detail is described in \cref{sec:apiref-engineering}.

Within the uncompromised-endpoint assumption in \cref{sec:threat-assumptions}, directory-response
verification relies on the verifier, its cryptographic dependencies, the project's ECVRF implementation, and the
operator's two public keys, which are fetched once at initialization. The verifier returns a rejecting
verdict for invalid or absent signed heads, incorrect roots, missing inclusion proofs, mismatching labels,
and invalid VRF bindings. Availability
failures produce an amber notice rather than a red integrity warning, so an unreachable directory server is
never reported as an attack. The Signal integration currently reports these verdicts but leaves
session-blocking policy to future work.

Seeded server keys, a genesis epoch, and an administrative reset make the demonstration repeatable and
prevent an empty-log failure from leaving shared state unusable. The harness also recovers from a
poisoned mutex. Production handlers would still need explicit lock-failure recovery beyond these
demonstration safeguards.

\section{Reproducibility}\label{sec:impl-repro}

Fixed seeds set the VRF key, label placement, sampled users, and fresh server state per benchmark, so
no state carries between runs, while the live demonstration uses the administrative reset. The
environment record captures the hardware, operating system, compiler, and toolchain versions, and
\cref{sec:apiref-repo} gives the \texttt{cargo test} and \texttt{cargo bench} commands, repository
layout, and runner scripts.
