\chapter{Implementation}\label{ch:impl}

This chapter describes how the design of \cref{ch:design} was realized in software. It first
sets out the architecture and the language boundary between the two layers the system is built
from (\cref{sec:impl-strategy}). It then describes the cryptographic core, the standalone Rust
\texttt{kt} crate that holds the transparency log and all server-side components of the prototype
(\cref{sec:impl-modules}), followed by the client integration into Signal Desktop, written in
TypeScript (\cref{sec:impl-signal}). It then describes the cross-implementation testing and parity
that bridge the two independent implementations (\cref{sec:impl-tests}), the system-wide
engineering challenges resolved along the way (\cref{sec:impl-challenges}), and finally the steps
taken to make the results reproducible (\cref{sec:impl-repro}). The empirical evaluation of the
resulting system is deferred to \cref{ch:eval}.

\section{Architecture and Language Boundary}\label{sec:impl-strategy}

In this section we explain why the system is divided into two implementations and where the
boundary between them lies. This matters because the cryptographic core and the messaging-client
integration have very different requirements, and keeping them strictly apart is what lets each
be built, measured, and reasoned about on its own without the reader having to track which
environment is in view.

The cryptographic operations and the transparency log are isolated in a standalone Rust crate,
while the client-side verification and the user-interface hooks are integrated directly into
Signal Desktop's TypeScript codebase. The first layer is the \texttt{kt} crate. It is the reference implementation of the design, and it
is the implementation on which all measurements reported in \cref{ch:eval} are performed. Rust was
chosen for the measurement core because it is the language of the comparable production systems
(Parakeet and Meta's \texttt{akd} library are both Rust~\cite{malvai2023parakeet,facebook-akd})
and because it allows the directory to be built against the libsignal codebase~\cite{libsignal}
rather than as a separate model. The crate builds and tests without the rest of libsignal, which
isolates the measurement environment while preserving compatibility with libsignal's integration
interface. Its data structures and proof formats follow the KeyTrans draft and were designed by comparison
with Signal's own Go implementation~\cite{signal-kt-server}; the cryptographic primitives are
independently validated against the RFC test vectors (\cref{app:tests}). There is no executable
Go\,$\leftrightarrow$\,DUET interoperability test: the proof encodings differ deliberately
(Signal's are fixed-width, DUET's bitmap-compressed), so no wire-compatibility is claimed.

The second layer is an integration into the Signal Desktop client~\cite{signal-desktop}, written
in TypeScript. Its purpose is to demonstrate that the design runs end to end against real identity
keys inside the Signal Desktop client codebase, rather than solely within the benchmark harness. The client
is a pure verifier: it re-implements the same verification primitives (prefix-root recomputation,
Merkle inclusion, ECVRF, Ed25519) so that no trust is placed in the server, and the Rust and
TypeScript implementations are held to byte-for-byte agreement on the shared dual-index,
warning-MAC, CEA, signed-tree-head, ECVRF, and Merkle test vectors (\cref{sec:impl-tests}); the
deliberately different external wire formats are excluded.

The scope and limitations of each layer are explicitly bounded. The Rust crate is an in-memory,
single-machine artefact; it does not model a distributed or database-backed deployment, and the
consequences of that for the measurements are stated in \cref{ch:eval}. The Signal Desktop
integration demonstrates feasibility but carries two proof-of-concept stand-ins, both of which are
the in-protocol hooks left to future work in \cref{ch:discussion}: the per-conversation shared
secret is derived from a deterministic stand-in (\texttt{pocSharedSecret}) rather than bridged out
of libsignal's live X3DH state, and continuous mode is driven by a deterministically seeded
simulated Double Ratchet rather than the client's live ratchet. The stand-ins exercise the same
construction and wire format, but the security consequence must be stated plainly rather than glossed
as merely a different input source: \texttt{pocSharedSecret} is a \emph{public} function of the two
parties' identity keys, so unlike a real X3DH/PQXDH secret it is computable by the server (indeed by
anyone). Under the stand-in the derived labels are therefore \emph{predictable}, not unguessable, and
the secrecy-dependent guarantees, unlinkability of the slots and the server's inability to
pre-position a value on them (\cref{ssec:design-properties}), hold only once the genuine secret is
bridged in. What the prototype validates end-to-end is the construction, wire format, and detection
logic; those secrecy-dependent properties are argued against the design, not demonstrated by the
stand-in. As a further prototype boundary, the demo server treats mutex poisoning and VRF
encode-to-curve exhaustion (probability ${\approx}\,2^{-256}$ per attempt, over at most 256 attempts)
as fatal, aborting rather than degrading gracefully; a production service would surface these as
recoverable errors.

This separation is deliberate. Keeping the cryptographic core independent of the Signal Desktop
integration lets all measurements be performed on a standalone reference implementation while
interoperability with a production messaging client is validated independently, and it ensures
that the performance figures of \cref{ch:eval} are not distorted by Electron or user-interface
overhead. \Cref{fig:impl-overview} shows the implemented system as a whole: the TypeScript client
embedded in Signal Desktop, the Rust reference implementation that houses all server-side components of the
prototype (the prefix tree, the Merkle log, the signed-tree-head signer, the ECVRF, the dual-index
derivation, and the continuous-monitoring layer) reached over HTTP, and the independent Rust
auditor that polls the server's signed tree head and consistency proofs from a separate vantage
point. The remainder of this chapter follows the boundary the figure draws: \cref{sec:impl-modules}
details the Rust cryptographic core, \cref{sec:impl-signal} the TypeScript client, \cref{sec:impl-tests}
the parity regime that binds the two, and \cref{sec:impl-challenges} the engineering obstacles
overcome end to end.

\subsection{Sparse Merkle Tree and Log Implementation}\label{ssec:impl-core-state}

The directory's state lives entirely in memory, in the cooperating structures that mirror the
authenticated-data-structure stack of the design (\cref{ssec:design-structures}). The base
\texttt{hashing} module fixes the RFC~6962 leaf and node domain tags shared by both structures.
The \texttt{merkle\_log} module maintains the append-only log as a vector of hashes and implements
the RFC~9162 inclusion and consistency verifiers, each proof costing time logarithmic in the
number of entries. The \texttt{prefix\_tree} module implements the directory itself as a
path-compressed sparse Merkle tree, held as a pointer-based structure so that only the nodes
actually populated are materialized; each compressed leaf lazily memoizes the top of its
empty-sibling hash chain, so that serving a proof whose co-path meets a compressed leaf does not
recompute the up-to-256-level chain on every lookup. Its proofs are bitmap-compressed, and a client
recomputes the root from such a proof to check a lookup without trusting the server.

The whole of this state sits behind a single lock: the server serializes all access to one
\texttt{KTServer} instance through an \texttt{Arc<Mutex<KTServer>>}, so reads and writes are mutually
exclusive rather than sharded or replicated, the single-machine bound already set out in
\cref{sec:impl-strategy}. Over this state sits the cryptography that the design leans on most
heavily, which the next subsection describes.

\subsection{The ECVRF and Dual-Index Modules}\label{ssec:impl-core-crypto}

Three modules carry the heavier cryptography. The \texttt{vrf} module implements the
ECVRF-EDWARDS25519-SHA512-TAI construction of RFC~9381 (suite \texttt{0x03}), which produces the
verifiable pseudorandom labels used on the global-lookup path; the \texttt{dual\_index} module
derives the three labels $\ell_{\mathsf{self}}$, $\ell_{\mathsf{peer}}$, and $\ell_{\mathsf{warn}}$
from the shared secret by HKDF-SHA256 (RFC~5869), exactly as specified in
\cref{ssec:design-labels}, and the \texttt{cea} module realizes the continuous example construction
of the ACKA framework~\cite{dowling2023acka} that drives ongoing monitoring.

These modules rest on established cryptographic crates rather than custom implementations.
\texttt{sha2} provides SHA-256, \texttt{hkdf} the HKDF dual-index derivation, \texttt{ed25519-dalek}
the Ed25519 signing and verification of the signed tree head, and \texttt{curve25519-dalek} the
Edwards-curve arithmetic over which the ECVRF of RFC~9381 is implemented in-house; the ECVRF is the
only primitive written by hand, and it is validated against the published suite-\texttt{0x03} test
vectors (\cref{sec:impl-tests}). The implementation preserves the asymptotic complexity established
in the design (\cref{ch:design}): prefix-tree lookups, log inclusion and consistency proofs, and
their client-side verification remain logarithmic in the number of entries, while label derivation
and signature verification remain constant in directory size, the behaviour the evaluation of
\cref{ch:eval} measures directly. Computing labels and signing roots is one thing; answering clients
over the network is another, and it is the subject of the last subsection of the core.

\subsection{The HTTP Server and Auditor Binary}\label{ssec:impl-core-server}

Two binaries turn the library into running services. A standalone HTTP server, built on the
\texttt{axum} framework over the asynchronous \texttt{tokio} runtime, wraps the \texttt{KTServer}
and serves the lookup, monitoring, and consistency operations as JSON, alongside a privileged
testing interface used only by the adversarial scenario suite and the scripted attacker of the
end-to-end demonstration (\cref{sec:impl-tests,ssec:impl-demo}). An independent
auditor binary, a small \texttt{ureq} HTTP client, polls the signed tree head, verifies its Ed25519
signature, and checks append-only consistency on each new epoch, so that a forked or rewritten
history is caught from a second vantage point. A benchmark harness completes the set, driving the
measurements of \cref{ch:eval}; the endpoint list and request formats are given in
\cref{app:apiref} (the public, admin, hook, and event interfaces of
\cref{tab:apiref-public,tab:apiref-admin,tab:apiref-hooks,tab:apiref-events}, with the demonstration
screens of \cref{fig:demo-baseline,fig:demo-cmd,fig:demo-equivocation}), and the complete test
catalogue in \cref{app:tests}
(\cref{tab:tests-rust-prim,tab:tests-rust-server,tab:tests-rust-system,tab:tests-jest-wire,tab:tests-jest-unit,tab:tests-adversarial}).

The directory-immutability safeguards of \cref{ssec:design-detection} are implemented across these
components rather than left to deployment. The write-once policy lives in the server's raw-label
update path: a write to an already-occupied dual-index, CEA, or warning label is rejected (the public
\texttt{/update-raw} endpoint answers \texttt{409 Conflict}), while the privileged interface exposes
an explicit unchecked overwrite so the adversarial suite can play a malicious operator. Every commit
freezes a \emph{declared update set} (the epoch's inserts and rotations, each rotation disclosing
its prior value), which the server publishes at an \texttt{/epoch-delta} endpoint alongside the
committed directory root. The auditor consumes exactly this disclosure (\cref{fig:impl-transition-audit}): it maintains its own
mirror directory, replays each epoch's declared set, and checks the result against the committed root,
so a deletion (which the delta format cannot express) or an undeclared modification makes the replay
diverge and is caught, the role the IETF KeyTrans protocol assigns to third-party auditors through
its \textsf{AuditorUpdate} structure~\cite{ietf-keytrans-protocol}. Independently of any auditor, the
\texttt{monitor} module gives a warning's writer a persistence check: it retains the inclusion proof
and signed tree head of the epoch at which the warning committed and, on any later disappearance,
assembles the inclusion proof, the proven non-inclusion, and the consistency proof between the two
heads into a bundle that verifies against the server's own signatures. The warning payload itself
carries an HKDF-derived MAC (\cref{alg:dualindex}) so that a reader can distinguish a peer-authored
warning from one the operator injected once it has learned the slot's label. The single element left
to deployment is authenticated writes: without account-layer proof of raw-label ownership the
write-once policy still binds an honest server and the transition audit still binds a malicious one,
but a malicious client could squat an as-yet-empty peer slot (\cref{ch:discussion}).

The performance profile of the core follows from these choices. State is held entirely in memory, so
no disk or database access sits on the lookup path; prefix proofs are bitmap-compressed over a
path-compressed tree, so a proof carries only the siblings that actually exist. The Axum server
accepts connections concurrently, though accesses to the single in-memory \texttt{KTServer} are
serialized through one mutex; the client-side cryptographic verification of a response then proceeds
independently once the response is received. The one cost that is not sublinear
is the epoch commit, which snapshots the tree by a deep clone; \cref{ch:eval} quantifies it and
\cref{ch:discussion} notes the copy-on-write remedy.

\subsection{Benchmark Infrastructure}\label{ssec:impl-bench}

Because the evaluation of \cref{ch:eval} rests on the numbers this harness produces, its methodology
belongs here, with the results themselves deferred. Measurements are taken two ways. Criterion drives
the statistical benchmarks, warming up for a fixed interval and then collecting a configured number
of samples over a fixed measurement window (its sampling is parameterized, not stopped on any
convergence criterion), from which it derives confidence intervals by bootstrap resampling and
emits the full distribution; a lightweight companion harness times a fixed number of iterations
(\num{2000} per operation) against a monotonic clock and records the median, 95th percentile, and a
95\% confidence half-width \emph{of the mean} (normal approximation) to CSV. The companion medians
are the figures quoted in \cref{ch:eval}; no formal agreement test between the two is claimed, and
\cref{sec:eval-method} states what each statistic does and does not license.

Workloads are synthetic and deterministic. A directory of a configurable size $N$ is built by
inserting seeded pseudorandom users, and both the VRF key and the sampling generator are fixed to
constant seeds, so proof sizes are reproducible to the byte and timing samples are drawn from the
same users on every run. Timings are \emph{server-side}: the harness invokes the \texttt{KTServer}
directly, so an operation measures only its cryptographic work, with the \texttt{axum} HTTP transport
and the Electron client deliberately excluded: their overhead is not the quantity being
characterized, and separating them keeps the measurement of the design faithful. Memory is captured
separately as the resident set size after building the tree, via the \texttt{sysinfo} crate, and the
$10^7$-label runs used for comparison with CONIKS report distributions over a thousand random lookups per size. Each experiment
begins from fresh server state, an administrative reset rebuilds the directory from its seed, so
no residual state from a previous run can leak into a measurement.

Together the server, auditor, and benchmark harness are the whole of the Rust side. The client that
consumes their proofs (and that, crucially, must reproduce their cryptography exactly) is the
subject of the next section.

\section{Signal Desktop Integration}\label{sec:impl-signal}

Where the Rust crate is a server to be measured, the TypeScript layer is a verifier to be
deployed. It re-implements only what a client needs and places no trust in the server, and the
whole section is confined to the front end: what the client checks, and where it attaches to
Signal.

The integration follows a multi-actor architecture. A standalone Rust directory server and an
independent auditor run as separate processes and communicate with the client over HTTP; a
separate attacker process drives substitutions and equivocations against a privileged endpoint.
The TypeScript client is embedded in Signal Desktop. The system runs in two
modes: the standalone networked stack, driven from the command line, and the
networked-in-app mode in which the embedded client talks to the live Rust server, auditor, and
attacker from within the real user interface, enabled at runtime by setting a server URL.
\Cref{fig:impl-signal} shows the overall arrangement: the embedded client at the centre, the three
processes it exercises (the directory server, the auditor, and the attacker) and the badge
and banner through which verdicts reach the user, with the client verifying against the live
networked stack.

\subsection{The Client-Side Verifier}\label{ssec:impl-verifier}

The client places no trust in the server: it re-checks every proof itself, so its cryptography must
reproduce the Rust core exactly. It re-implements the same verification primitives (prefix-root
recomputation, Merkle inclusion, ECVRF, and Ed25519) and depends only on Node's built-in
\texttt{crypto} module for SHA-256, SHA-512, and X25519, with its ECVRF curve arithmetic
implemented in-house, so the embedded verifier adds no cryptographic dependency to the Signal
client. On every peer-key retrieval it runs the full verification chain of \cref{ssec:design-verify}
against the head the server returns, refusing any response whose signature, prefix root, or log
inclusion fails to check.

One behaviour of the verifier is worth drawing out, because it governs what the user sees: the
client distinguishes unavailability from attack. A server that is merely unreachable must not be
mistaken for an attacker, so an unreachable server raises a calm, amber unavailability notice and
never the red man-in-the-middle alarm, which is reserved for a server that responds and is caught
misbehaving. Where these checks attach to the messaging client, the points at which the verifier
is actually invoked, is the subject of the next subsection.

\subsection{Hooking the Signal Lifecycle}\label{ssec:impl-hooks}

The client attaches to three lifecycle points of the Signal client: the key-upload path, the
peer-key-retrieval path, and session establishment. The
peer-key-retrieval hook is the security-critical one, it runs the full verification chain
(\cref{ssec:design-verify}) on a peer's key before that key is accepted. On the Rust side, a
hook in libsignal's pre-key-bundle processing marks the point at which the live X3DH secret is
available: the place where the production binding of the real shared secret would attach, and
where the prototype instead substitutes its deterministic stand-in. Verdicts surface in the user
interface through a conversation-header badge (green when verified, red on a warning) and a
banner, driven by DOM events that signal a warning (a detected key substitution or
man-in-the-middle) and temporary unavailability. The concrete hook functions and event names are
listed in \cref{app:apiref}.

\Cref{fig:impl-verify} traces the exchange that the peer-key-retrieval hook performs. The client
requests the peer's key at its label, and the server replies with the value together with the
three artefacts that bind it: the prefix proof, the log-inclusion proof, and the signed tree
head. The client verifies all of these locally, it recomputes the prefix root from the
returned proof, checks that this root is included in the log, and validates the tree-head
signature, adding the VRF binding of the label on the global-lookup path. It then issues a second
lookup for the shared warning slot, whose proven inclusion or non-inclusion is what separates a
clean verdict from a warning. Any check that fails makes the verifier return a rejecting verdict
rather than a clean one, so a substituted key or a withheld warning cannot pass verification
silently; the prototype hook surfaces that verdict as a banner but does not itself yet block session
establishment (\cref{ssec:impl-demo}).

\subsection{End-to-End Demonstration}\label{ssec:impl-demo}

\Cref{fig:impl-e2e} gives the end-to-end account across the four roles (Alice and Bob, each a client
with its verifier embedded; the KT server; and the auditor). In the normal path Alice registers her
key and commits; Bob's verifier then performs three label-bound, proof-verified lookups (the peer
slot $\ell_A$ it retrieves Alice from, its own slot $\ell_B$, and the shared warning slot
$\ell_{\mathsf{warn}}$, which is verifiably empty) and returns \textsc{safe}, while the auditor
polls and replays to \textsc{consistent}. In the A1b branch the server overwrites Alice's own
dual-index slot $\ell_A$ (which is also Bob's peer slot): Alice's monitor reads the substituted value
against her pinned key, finds a mismatch, and writes the shared warning slot; Bob's monitor then reads
that warning and both clients go red. Independently, the auditor's transition replay rejects the
declared immutable rotation, so detection does not rest on the client path alone. The live run below
exercises it inside the real interface.

The integration runs as a live, multi-actor demonstration: two linked Signal Desktop clients, the
standalone Rust server, the auditor, and a scripted attacker, driven by the runner scripts of
\cref{app:apiref}. Its purpose is to show the detection surfaces firing inside the real user
interface rather than only in a benchmark. The clearest run is the dual-index substitution
(scenario A1b). The attacker overwrites the victim's per-conversation slot on the shared server; on the
victim's next monitor tick the own-key self-check fails, and the client writes the shared warning slot
once (its log records \texttt{WRITE warning slot label=a480\ldots}) and raises a red conversation
banner reading that its identity key was replaced. The peer client, monitoring the \emph{same} shared
label, reads it on its own next tick (\texttt{READ warning slot label=a480\ldots}, the identical hex)
and raises the matching red banner, so both sides are alerted whenever a monitoring victim or a
pinned peer detects the substitution and commits the warning (the conditional case argued in
\cref{ch:design}).
Independently of the clients, the auditor's per-epoch transition audit rejects this A1b overwrite: the
dual-index slot is immutable, so the declared in-place rotation is an \textsc{ImmutableRotation} the
replay refuses and the epoch alarms (\cref{fig:impl-auditor}). Its cross-vantage fork check separately
reports no equivocation, since A1b is a substitution rather than a split view. This is the opposite of
the global-slot case A1a, where the identity slot is mutable and a malicious rotation is a legal
declared operation the auditor cannot tell from an honest key change; there the auditor stays
\textsc{consistent} and detection rests on the client self-check alone. \Cref{fig:impl-screens} shows the resulting red banner on both
clients: the DevTools console beside each records the victim's \texttt{WRITE warning slot} and the
peer's \texttt{READ warning slot} at the \emph{identical} label, the bidirectional detection across
the two client instances.

\section{Cross-Implementation Testing and Parity}\label{sec:impl-tests}

The Rust cryptographic core of \cref{sec:impl-modules} and the TypeScript client of
\cref{sec:impl-signal} are two independent implementations of the same protocol, written in
different languages and for different purposes, one to be measured, one to be deployed. This
section connects them: it describes how the two are held to agreement on the protocol operations that
the shared vectors cover, and how the combined system is then tested against the threat model.

The two are pinned by a single cross-language contract. A fixed set of test vectors fixes the HKDF
dual-index derivation and the CEA construction byte-for-byte across the Rust and TypeScript
implementations, and the same discipline keeps their Ed25519 signed-tree-head and Merkle
computations in step, so any divergence on a covered operation-and-input vector surfaces as a vector
failure rather than passing silently; another input to the same operation can still diverge, so the
remaining behaviour is supported, not proved, by language-specific unit and
integration tests. This contract is the basis for treating the TypeScript client as a faithful
verifier of the Rust server's outputs on the covered operations; without it, agreement in one test
would be weak evidence of agreement in the next.

On top of that contract, testing is organized around two questions: whether each component
conforms to its specification, and whether the system as a whole detects the attacks of the threat
model. The first is addressed by unit and property tests close to the code; the second by an
adversarial scenario suite. \Cref{fig:impl-testing} summarizes the testing pipeline, from
specification conformance up to the end-to-end scenarios and performance benchmarks.

\centering
\input{figures/tikz/fig-impl-testing}
\caption[The testing pipeline.]{The testing pipeline: specification conformance against published vectors, per-module
unit and property tests, cross-language equivalence vectors, end-to-end adversarial scenarios,
and the performance benchmarks of \cref{ch:eval}.}
\label{fig:impl-testing}

On the \textbf{Rust} side, the core is covered by unit tests run under \texttt{cargo test}.
The Merkle log is tested exhaustively (every inclusion proof and every $(m,n)$ consistency
pair up to size 64, together with forgery attempts) so the RFC~9162 verifiers are checked
against their full small-input space rather than on a handful of cases. The prefix tree is
tested by recomputing the root from the compressed proof. The dual-index derivation is checked
against the cross-implementation HKDF vectors, and the VRF against the RFC~9381 suite-\texttt{0x03}
vectors. The server's signed tree head is tested for correct acceptance and for rejection of a tampered
or wrong-key signature. The auditor is tested for both honest audit and fork detection, including
the two cases that matter for soundness: that a genuine equivocation (one signer, two roots
at one epoch) is reported as a fork, and that a divergent head with an invalid signature is
correctly rejected rather than misclassified as a fork.

On the \textbf{TypeScript} side, the Signal Desktop client is covered by a Jest suite. A
wire-parity suite runs the client's full verification chain against the live Rust server,
confirming multi-entry inclusion, proven non-inclusion, the Ed25519 signed-tree-head check
(and its rejection of a tampered head), the VRF path, and windowed consistency. Unit suites
back a test double onto a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle
log, ECVRF, and Ed25519 signer) so the client runs against concrete cryptographic
implementations rather than stubs. These unit suites exercise key-substitution detection (the
lookup verdicts \texttt{SAFE}, key mismatch, and proven not-in-log), the own-key self-check
against a server overwrite, man-in-the-middle detection on a replaced lookup slot, and the
availability-versus-integrity routing that distinguishes an unreachable server from a detected
attack.

Finally, the adversarial scenario suite runs the attack taxonomy of \cref{ch:threat} end to end,
each scenario asserting the expected verdict and the epoch at which detection occurs. Implemented as
the Rust integration test \texttt{tests/adversarial.rs} (run with \texttt{cargo test --test
adversarial}), the automated suite covers every scenario: the A0 baseline, the two server-side
substitution variants A1a (global VRF slot) and A1b (dual-index session slot), the censorship,
network, and equivocation attacks A2--A4, the key-rotation substitution A5 (caught by identity-anchored
re-fetch and cross-signature), and the X1 endpoint-compromise case asserted as an out-of-scope
boundary, all eight passing. \Cref{tab:impl-t5a} records, for
representative correctness tests, the property checked and the threat or correctness
requirement it protects, and \cref{tab:impl-t5b} records the adversarial scenarios with their
expected and observed verdicts; the full results are reported in \cref{ch:eval}, and the
complete test catalogue is given in \cref{app:tests}.

\section{System-Wide Engineering Challenges}\label{sec:impl-challenges}

Building the system end to end surfaced obstacles at every layer. This section collects the most
instructive, each with the resolution adopted, grouped by where they arose: the protocol the two
implementations must agree on, the concurrency of a live multi-client deployment, the Electron
client integration, and the server's robustness under load.

\paragraph{Protocol: Verifiable-Random-Function Divergence.} The first working client computed
labels with an Ed25519-based stand-in, whereas the Rust implementation used the full ECVRF of
RFC~9381; the two could never agree. The TypeScript VRF was reimplemented as the complete
ECVRF-EDWARDS25519-SHA512-TAI suite and cross-validated against the same RFC~9381 test vectors as the
Rust implementation, after which both verify identically.

\paragraph{Protocol: Per-Lookup Head Binding.} An early version verified each lookup's proof against
the head the server returned with the search, but only checked the signed-tree-head signature once
per monitoring tick, not per lookup. A malicious server could therefore answer a single lookup
against a fabricated head, defeating warning-censorship detection. The server now returns the signed
tree head atomically with each search, and the client verifies the signature, requires the returned
root to match the signed head, and checks inclusion against that signed root, refusing any unsigned
or absent head.

\paragraph{Concurrency: Time-of-Check Races.} When two clients committed their startup registrations
concurrently, both the client's and the auditor's consistency checks produced spurious fork alarms,
because each fetched a signed tree head and then a consistency proof whose upper bound raced the
other client's commits. Tracking the log by size rather than epoch, and pinning the consistency
proof's upper bound to the size of the head being validated, removed the race; the same fix applied
to both verifiers.

\paragraph{Client Integration: Bundler Code-Splitting.} The most stubborn obstacle was the
application's bundler, which splits a chunk at every dynamic import. Loading the multi-module
networked layer through dynamic imports introduced initialization-order dependencies between bundles
that prevented reliable loading of the verification layer. The resolution was to remove every
dynamic import for the key-transparency code so that the whole layer lives in one bundle, with the
networked path made opt-in at runtime; its failure is caught separately and never affects the
messaging client itself.

\paragraph{Client Integration: Electron Context Isolation.} With context isolation enabled, property
assignments to \texttt{window} in the preload world are not visible to the renderer, so
console-injected helpers silently did nothing. DOM custom events on \texttt{window}, by contrast,
cross the boundary, which is exactly why the warning banner worked while the injected client
handle did not. The integration therefore routes all verdicts through custom events and registers
peers from within the preload world rather than relying on console helpers.

\paragraph{Client Integration: Event-Channel Mismatch.} Detection initially fired without updating
the user interface: the background monitor emitted on the client's typed event bus, but the badge
and banner listen for a DOM custom event. The fix was to dispatch both, mapping the verdict onto the
custom event the badge and banner already listened for.

\paragraph{Deployment: Operational Robustness.} Several issues appeared only in a live deployment: a
server that generated a fresh signing key on each launch invalidated every cached public key, fixed
by deriving the server's keys deterministically from a seed; a panic on a freshly emptied log
poisoned the shared mutex, after which the server rejected every subsequent request and brought
itself down, resolved by bootstrapping a genesis epoch at initialization, and the demonstration was
not reproducible because attack state persisted in memory, fixed by an administrative reset that
rebuilds the server from its seed. That last fix is also what makes the demonstration repeatable.

\paragraph{Trusted Computing Base and Fail-Closed Behaviour.} This paragraph states what must
be trusted. On the client, the trusted computing base is the verifier and the cryptographic crates it
calls (\cref{ssec:impl-core-crypto}) together with the operator's two public keys, the STH signing key
and the VRF key, pinned on first use; the server, the network, and the log are \emph{not} trusted, and
every answer they give is re-checked against those keys. The \emph{verifier} is fail-closed: any
failure (an invalid or absent signed-tree-head signature, a prefix root that does not recompute, a
missing log inclusion, a proof whose label does not match the one queried, or a VRF binding that
does not hold) yields a \emph{reject} verdict rather than falling through to acceptance. One
integration caveat must be stated plainly, because it is the boundary between what the verifier
guarantees and what the prototype currently enforces: in the present Signal Desktop prekey-bundle
hook (\cref{ssec:impl-hooks}) that reject verdict is surfaced \emph{advisorily}: the user is shown
the red warning, but the hook does not yet abort session establishment. Turning the hook fail-closed
(refusing the session on a red verdict rather than only warning) is a deployment policy decision
left to future work (\cref{ch:discussion}); the guarantee proven here is that the verifier never
\emph{accepts} a bad answer, not that the current integration blocks the session on one. Availability failures are the one
case deliberately \emph{not} treated as an attack: an unreachable server yields the amber notice of
\cref{ssec:impl-verifier}, never the red verdict. The prototype classifies an outage as an availability failure rather than as
successful verification, but it does not distinguish a benign outage from a malicious refusal to
serve; treating a persistent outage as suspicious is a deployment-policy decision left to future work. Hardening every request handler against
a poisoned lock, rather than relying on the genesis-epoch bootstrap above, is noted as a production
follow-up. These properties, and the reproducibility of the whole, are taken up next.

\section{Reproducibility}\label{sec:impl-repro}

The measurements of \cref{ch:eval} are made reproducible by pinning the environment and fixing the
cryptographic and sampling randomness. The toolchain version is recorded. The VRF
key and the sampling generator are seeded from fixed constants, so label placement and the
choice of sampled users are deterministic across runs. Each experiment begins from fresh server state
after an administrative reset, so no residual state carries between runs. The benchmark suite is
driven by single commands (\texttt{cargo test}, \texttt{cargo bench}), with the hardware, operating system, and
compiler version captured automatically into an environment record that accompanies the results. The
repository layout and the one-command runner scripts are listed in \cref{app:apiref}.
