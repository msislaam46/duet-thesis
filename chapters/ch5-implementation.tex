\chapter{Implementation}\label{ch:impl}

The implementation combines a Rust cryptographic core and directory with a TypeScript verifier
embedded in Signal Desktop. This chapter covers their architecture, integration, parity testing,
engineering constraints, and reproducibility.

% ============================================================================
\section{Architecture and Language Boundary}\label{sec:impl-strategy}

Because the cryptographic core and the Signal Desktop integration have different requirements, they
are maintained as separate implementations with a defined language boundary.

The cryptographic operations and the transparency log are isolated in a standalone Rust crate,
while the client-side verification and the user-interface hooks are integrated directly into
Signal Desktop's TypeScript codebase. The first layer is the \texttt{duet} crate. It is the reference implementation of the design, and it
is the implementation on which all measurements reported in \cref{ch:eval} are performed. Rust was
chosen for the measurement core because it is the language of the comparable production systems
(Parakeet and Meta's \texttt{akd} library are both Rust~\cite{malvai2023parakeet,facebook-akd}).
The crate is a standalone workspace with no libsignal dependency, which isolates the measurement
environment. A documentation-only sketch marks where a production libsignal binding could obtain the
live X3DH secret (\cref{ssec:impl-hooks}). The implemented integration instead attaches to Signal
Desktop's TypeScript key-upload and peer-key-retrieval paths. Its data structures and proof formats follow the KeyTrans draft and were designed by comparison
with Signal's own Go implementation~\cite{signal-kt-server}. The directly implemented ECVRF is
checked against the RFC~9381 test vectors~\cite{rfc9381} (\cref{tab:tests-rust-prim}). There is no executable
Go\,$\leftrightarrow$\,DUET interoperability test: the proof encodings differ deliberately
(Signal's are fixed-width, DUET's bitmap-compressed), so no wire-compatibility is claimed.

The second layer is an integration into the Signal Desktop client~\cite{signal-desktop}, written
in TypeScript. The client integration demonstrates the prototype's verification and in-band
warning path against Signal Desktop identity keys within the client codebase, rather than only
within the standalone harness. The client re-implements prefix-root recomputation, Merkle inclusion, ECVRF, and Ed25519. It
verifies returned bindings and proofs locally instead of relying on the server's assertion. It also
performs the client-originated writes required by the design, including registration at the
dual-index lookup slot and warning publication. Fixed vectors require byte-for-byte agreement for dual-index label
derivation, authenticated warning payloads, and CEA state evolution (\cref{sec:impl-tests}). A
separate live wire-parity suite checks whether the TypeScript verifier accepts the Rust directory
server's signed tree heads (STHs), ECVRF outputs, Merkle proofs, and windowed consistency proofs.

The Rust crate is an in-memory,
single-machine prototype. It does not model a distributed or database-backed deployment, and the
consequences of that for the measurements are stated in \cref{ch:eval}. The Signal Desktop
integration demonstrates feasibility but uses two proof-of-concept stand-ins. The per-conversation
shared secret is derived from the deterministic \texttt{pocSharedSecret} function rather than
obtained from libsignal's live X3DH state. Continuous mode also uses a deterministically seeded
simulated Double Ratchet instead of the client's live ratchet. Both stand-ins preserve the
construction and wire format. Replacing them with live conversation-secret and ratchet-state inputs
remains future work (\cref{ch:discussion}).

Because \texttt{pocSharedSecret} is a public function of the parties' identity keys, the server and
any external observer can compute it. The resulting labels are therefore predictable under the
stand-in. Pre-use label unpredictability and resistance to server pre-positioning
(\cref{ssec:design-properties}) require the live conversation secret. The prototype demonstrates the
construction, wire format, and detection logic. Evidence for the secrecy-dependent properties comes
from the design argument, since the public stand-in cannot demonstrate them.

The demo server also aborts on mutex poisoning and on exhaustion of all \num{256} VRF
encode-to-curve candidates. Under the model used here, the latter has aggregate probability
approximately $2^{-256}$. A production service would report both conditions as recoverable errors.

Separating the cryptographic core from Signal Desktop allows the Rust implementation to be measured
independently, while the client integration demonstrates control-flow feasibility.
\Cref{fig:impl-overview} shows the TypeScript client communicating with the Rust directory server
over HTTP. The Rust implementation contains the directory server and reference client constructions,
and the independent auditor obtains signed heads, epoch deltas, and consistency proofs from a
separate vantage. The following sections examine the Rust core, client integration, parity testing,
and engineering challenges.

\subsection{Sparse Merkle Tree and Log Implementation}\label{ssec:impl-core-state}

The directory's state lives entirely in memory, in the cooperating structures that parallel the
authenticated-data-structure stack of the design (\cref{ssec:design-structures}). The base
\texttt{hashing} module fixes the RFC~6962 leaf and node domain tags shared by both structures.
The \texttt{merkle\_log} module maintains the append-only log as a vector of hashes and implements
the RFC~9162 inclusion and consistency verifiers, each proof costing time logarithmic in the
number of entries. The \texttt{prefix\_tree} module implements the directory itself as a
path-compressed sparse Merkle tree, held as a pointer-based structure so that only the nodes
actually populated are materialized. Each compressed leaf lazily memoizes the top of its
empty-sibling hash chain, so that serving a proof whose co-path meets a compressed leaf does not
recompute the up-to-256-level chain on every lookup. Its proofs are bitmap-compressed, and a client
recomputes the root from such a proof to check a lookup without trusting the server.

A single \texttt{Arc<Mutex<KTServer>>} protects the server state, so reads and writes are serialized.
The prototype does not shard or replicate this state, consistent with the single-machine scope
established in \cref{sec:impl-strategy}.

\subsection{The ECVRF and Dual-Index Modules}\label{ssec:impl-core-crypto}

Three modules implement the main cryptographic operations. The \texttt{vrf} module implements the
ECVRF-EDWARDS25519-SHA512-TAI construction of RFC~9381 (suite \texttt{0x03}), which produces the
verifiable pseudorandom labels used on the global-lookup path. The \texttt{dual\_index} module
derives the three labels $\ell_{\mathsf{self}}$, $\ell_{\mathsf{peer}}$, and $\ell_{\mathsf{warn}}$
from the shared secret by HKDF-SHA256 (RFC~5869), exactly as specified in
\cref{ssec:design-labels}, and the \texttt{cea} module implements the continuous example construction
of the ACKA framework~\cite{dowling2023acka} that drives ongoing monitoring.

These modules delegate most standard primitives to established cryptographic crates. The ECVRF protocol is the exception, implemented directly as noted below.
\texttt{sha2} provides SHA-256, \texttt{hkdf} the HKDF dual-index derivation, \texttt{ed25519-dalek}
the Ed25519 signing and verification of the signed tree head, and \texttt{curve25519-dalek} the
Edwards-curve arithmetic over which the ECVRF of RFC~9381 is implemented in-house. The ECVRF is the
one hand-written primitive, checked against the published suite-\texttt{0x03} test
vectors (\cref{sec:impl-tests}). The implementation preserves the asymptotic complexity established
in the design (\cref{ch:design}). The prefix-tree walk covers a fixed 256-bit path. The expected
number of transmitted non-default siblings is approximately $\lceil\lg N\rceil$. Log inclusion and
consistency proofs and their verification are logarithmic in the log size. Label derivation and
signature verification are independent of directory size. \Cref{ch:eval} measures these costs.

\subsection{The HTTP Server and Auditor Binary}\label{ssec:impl-core-server}

Two binaries turn the library into running services. A standalone HTTP server, built on the
\texttt{axum} framework over the asynchronous \texttt{tokio} runtime, wraps the \texttt{KTServer}
and serves the lookup, monitoring, and consistency operations as JSON, alongside a privileged
testing interface used only by the adversarial scenario suite and the scripted attacker of the
end-to-end demonstration (\cref{sec:impl-tests,ssec:impl-demo}). An independent
auditor binary, a small \texttt{ureq} HTTP client, verifies signed-head growth and replays epoch
transitions along its own view. An independently obtained head additionally enables the cross-vantage
comparison needed to detect a consistent split view. A benchmark harness completes the set, driving the
measurements of \cref{ch:eval}. The public, admin, hook, and event interfaces are listed in
\cref{tab:apiref-public,tab:apiref-admin,tab:apiref-hooks,tab:apiref-events}.
\Cref{fig:demo-baseline,fig:demo-cmd,fig:demo-equivocation} show the demonstration screens. The
complete test catalogue is in \cref{app:tests}
(\cref{tab:tests-rust-prim,tab:tests-rust-server,tab:tests-rust-system,tab:tests-jest-wire,tab:tests-jest-unit,tab:tests-adversarial}).

The directory-immutability safeguards of \cref{ssec:design-detection} are enforced across these
components. The server enforces the write-once policy in its raw-label
update path. Thus, a write to an already-occupied dual-index, CEA, or warning label is rejected (the public
\texttt{/update-raw} endpoint answers \texttt{409 Conflict}), while the privileged interface exposes
an explicit unchecked overwrite so the adversarial suite can play a malicious operator. Every commit
freezes a \emph{declared update set} (the epoch's inserts and rotations, each rotation disclosing
its prior value), which the server publishes at an \texttt{/epoch-delta} endpoint alongside the
committed directory root. The auditor consumes exactly this disclosure (\cref{fig:impl-transition-audit}): it maintains its own
replica directory and replays each epoch's declared set. It accepts the epoch only if the replayed
root equals the committed root. A deletion, which the delta format cannot express, or an undeclared
modification makes the replayed root diverge and is therefore rejected. This corresponds to the
third-party auditor role in the IETF KeyTrans protocol, assigned through its \textsf{AuditorUpdate}
structure~\cite{ietf-keytrans-protocol}. Independently of any auditor, the
\texttt{monitor} module provides a writer-side persistence check. It retains the inclusion proof and
signed tree head from the epoch in which a warning commits. If that warning later disappears, the
module combines the original inclusion proof, the subsequent non-inclusion proof, and a consistency
proof between the two heads into a bundle that verifies against the server's own signed heads. Unit
tests cover this reference component, but the live background monitor currently implements only
detection and warning publication (\cref{alg:detect}). The warning payload itself
carries an HKDF-derived MAC (\cref{alg:dualindex}) so that a reader can distinguish a peer-authored
warning from one the operator injected once it has learned the slot's label. Authenticated ownership of raw-label writes is not implemented. The write-once policy still
constrains an honest server, and the transition audit detects invalid changes by a malicious one.
However, without account-layer authorization, a malicious client could occupy an unclaimed peer slot
before its legitimate owner writes to it. \Cref{ch:discussion} addresses this and the remaining
deployment work.

The performance profile of the core follows from these choices. State is held entirely in memory, so
no disk or database access sits on the lookup path. Prefix proofs are bitmap-compressed over a
path-compressed tree, so a proof carries only the siblings that actually exist. The Axum server
accepts connections concurrently, though accesses to the single in-memory \texttt{KTServer} are
serialized through one mutex. The client-side cryptographic verification of a response then proceeds
independently once the response is received. The one cost that is not sublinear
is the epoch commit, which snapshots the tree by a deep clone. \Cref{ch:eval} quantifies it and
\cref{ch:discussion} notes the copy-on-write remedy.

\subsection{Benchmark Infrastructure}\label{ssec:impl-bench}

The benchmark harness produces the measurements reported in \cref{ch:eval}. This subsection records
only its role and its measurement boundary. Timings are \emph{server-side}: the harness invokes the
\texttt{KTServer} directly, so an operation measures only its cryptographic work, with the
\texttt{axum} HTTP transport and the Electron client deliberately excluded, because their overhead is
not the quantity being characterized. Each benchmark constructs fresh seeded server state, while the
live demonstration uses the administrative reset. The benchmark runner executes the regular suite and
the scale-only $10^7$-label run (M7) separately and records the environment for the resulting corpus.
\Cref{sec:eval-method} states what each statistic does and does not license, and \cref{app:benchmarks}
gives the sampling procedure, the companion-harness statistics, the workload construction, and the
measurement environment.

\section{Signal Desktop Integration}\label{sec:impl-signal}

The TypeScript layer integrates verification into Signal Desktop. It re-implements only what a client
needs and verifies returned bindings and proofs locally rather than accepting them on the server's
assertion. This section covers what the client checks and where it attaches to Signal.

The prototype combines an embedded TypeScript client with a Rust directory server, a Rust auditor,
and a Node-based scripted attacker. It can be exercised from the command line or through Signal
Desktop. In the latter configuration, the embedded client communicates with the directory server
over HTTP after a server URL is configured. \Cref{fig:impl-signal} shows these components and the
badge and banner through which the client reports verdicts.

\subsection{The Client-Side Verifier}\label{ssec:impl-verifier}

The client repeats the Rust verification logic locally. Node's built-in \texttt{crypto} module
supplies SHA-256, SHA-512, HMAC-SHA256, Ed25519 verification, and X25519, while the ECVRF curve
arithmetic is implemented directly in TypeScript. The embedded verifier therefore adds no external
cryptographic library to Signal Desktop. On each peer-key retrieval for an account identifier (ACI),
the verifier checks the complete chain described in \cref{ssec:design-verify}. An invalid signature,
prefix root, or log-inclusion proof produces a rejecting verification verdict.

Client-visible verdicts distinguish unavailability from an integrity failure. A server that is merely unreachable must not be
mistaken for an attacker, so an unreachable server raises a calm, amber unavailability notice and
never the red warning, which is reserved for a proof or key-integrity failure or an
authenticated peer warning.

\subsection{Hooking the Signal Lifecycle}\label{ssec:impl-hooks}

The integration uses key-upload and peer-key-retrieval hooks together with a background monitor.
Peer identity material is recorded during key retrieval and through a periodic identity-record
sweep. No live session-establishment hook exposes the X3DH shared secret. The
peer-key-retrieval hook is the security-critical one: it runs the full verification chain
(\cref{ssec:design-verify}) on a peer's key at the retrieval boundary and reports the verdict. It
does not block session establishment. Blocking on a rejecting verdict remains a deployment-policy
decision (\cref{ssec:impl-demo,ch:discussion}). A documentation-only Rust module identifies the point at which a production libsignal binding could
obtain the live conversation secret. The prototype's TypeScript integration uses its deterministic
stand-in at the corresponding boundary. Verdicts appear in the user
interface through a conversation-header badge (green when verified, red on a warning) and a
banner, driven by DOM events that signal a warning (a detected key substitution or
man-in-the-middle) and temporary unavailability. The specific hook functions and event names are
listed in \cref{tab:apiref-hooks,tab:apiref-events}.

\Cref{fig:impl-verify} illustrates the matching branch of the networked \texttt{RemoteKTClient.detectMitm}
path. The client reads its own dual-index lookup slot $\ell_{\mathsf{self}}$, and the server replies
with the value together with the proofs that bind it: the prefix proof, the log-inclusion proof, and
the signed tree head. The client verifies all of these locally: it recomputes the prefix root from the
returned proof, checks that this root is included in the log, validates the tree-head
signature, and anchors the head as an append-only extension of its pinned baseline. Only when the
owner slot verifies and matches the client's own key does it issue a second
lookup for the shared warning slot, whose proven inclusion or non-inclusion separates a
clean verdict from a warning. The helper returns \texttt{null} when both lookups pass and a
\texttt{MitmWarning} when the owner slot is absent or mismatched, or when the warning slot is occupied.
A proof or head-anchoring failure causes the helper to throw. The live background monitor does not call
this helper directly: it implements the corresponding checks in \texttt{monitorConversation}
(\cref{alg:detect}), publishes warnings when required, and reports its own \texttt{MonitorVerdict} or
verification error through the client warning interface (\cref{ssec:impl-demo}).

\subsection{End-to-End Demonstration}\label{ssec:impl-demo}

The integration runs as a live, multi-actor demonstration: two linked Signal Desktop clients, the
standalone Rust server, the auditor, and a scripted attacker, driven by the runner scripts of
\cref{sec:apiref-repo}. Its purpose is to demonstrate the detection paths in the Signal user
interface rather than only in a benchmark. The clearest run is the dual-index substitution
(scenario A1b). The attacker overwrites the victim's per-conversation slot on the shared server. On the
victim's next monitor tick the own-key self-check fails, and the client writes the shared warning slot
once and raises a red conversation banner reading that its identity key was replaced. The peer client,
monitoring the \emph{same} shared label, reads it on its own next tick and raises the matching red
banner, so both sides are alerted whenever a monitoring victim or a pinned peer detects the
substitution and commits the warning (the conditional case argued in \cref{ch:design}).
Independently of the clients, the auditor's per-epoch transition audit rejects this A1b overwrite: the
dual-index slot is immutable, so the declared in-place rotation is an \textsc{ImmutableRotation} the
replay refuses and the epoch alarms (\cref{fig:impl-auditor}). Its cross-vantage fork check
reports no equivocation, since A1b is a substitution rather than a split view. This is the opposite of
the global-slot case A1a, where the identity slot is mutable and a malicious rotation is a legal
declared operation the auditor cannot tell from an honest key change, so there the auditor stays
\textsc{Consistent} and detection rests on the client self-check alone. \Cref{fig:impl-screens} shows
the resulting red banner on both clients. This is bidirectional detection across the two client
instances, and their DevTools consoles record the victim's warning-slot write and the peer's read at
the identical label (\cref{sec:apiref-demo}).

The byte-locked cross-language vectors provide direct evidence for the specified inputs and
operations. Tests over additional inputs support broader agreement but do not prove it.

\section{Cross-Implementation Testing and Parity}\label{sec:impl-tests}

The Rust core and TypeScript client independently implement the same protocol for different purposes.
Rust provides the measured reference implementation, while TypeScript provides the Signal Desktop
integration.

Fixed vectors require byte-for-byte agreement on dual-index label derivation, authenticated warning
payloads, and CEA state evolution. The live wire-parity suite also checks the TypeScript verifier
against signed tree heads, ECVRF outputs, Merkle proofs, and windowed consistency proofs produced by
the Rust directory server. A divergence within either covered test set causes the relevant test to
fail. Language-specific unit and integration tests provide supporting evidence for other inputs, but
they do not establish equivalence over the full input space. Agreement on the covered operations
supports treating the TypeScript client as a faithful verifier of the Rust directory server's outputs.

Testing provides five forms of evidence. Specification grounding states the required behaviour, and
unit and invariant tests assess individual components. Cross-language vectors check agreement between
the implementations. The adversarial scenario suite evaluates the combined system against the threat
model. Performance benchmarks support the cost claims in \cref{ch:eval}. \Cref{fig:impl-testing} maps
these forms of evidence.

On the \textbf{Rust} side, the core is covered by unit tests run under \texttt{cargo test}.
The Merkle log is tested exhaustively (every inclusion proof and every $(m,n)$ consistency
pair up to size 64, together with forgery attempts) so the RFC~9162 verifiers are checked
against their full small-input space rather than on a handful of cases. The prefix tree is
tested by recomputing the root from the compressed proof. The dual-index derivation is checked
against the cross-implementation HKDF vectors, and the VRF against the RFC~9381 suite-\texttt{0x03}
vectors. The server's signed tree head is tested for correct acceptance and for rejection of a tampered
or wrong-key signature. The auditor is tested for both honest audit and fork detection, including
the two cases that matter for soundness: that a genuine equivocation (one signer, two roots
at one epoch) is reported as a fork, and that a divergent head with an invalid signature is
correctly rejected rather than misclassified as a fork.

On the \textbf{TypeScript} side, the standalone verifier harness contains 116 Jest tests. Live
Rust--TypeScript wire parity is a separate opt-in target that requires the Rust server, and a normal
Jest run alone does not establish wire parity. When enabled, the wire-parity suite runs the client's
full verification chain against the live Rust server, confirming multi-entry inclusion, proven
non-inclusion, the Ed25519 signed-tree-head check (and its rejection of a tampered head), the VRF
path, and windowed consistency. The integration suite and the cryptographic unit suites run the
verifier against a real in-process \texttt{KTServer} (a genuine prefix tree, Merkle log, ECVRF, and
Ed25519 signer), so the client is checked against the implemented components rather than stubs, while
the remaining unit suites use controlled test doubles. Together they cover key-substitution detection (the
lookup verdicts \texttt{SAFE}, key mismatch, and proven not-in-log), the own-key self-check
against a server overwrite, man-in-the-middle detection on a replaced lookup slot, and the
availability-versus-integrity routing that distinguishes an unreachable server from a detected
attack. Beyond this harness, sixteen embedded tests in four Signal Desktop suites run under the
client's own test runner and drive realistic ACI strings through the same integration boundary the
live callers use (\cref{sec:tests-ts}).

Finally, the adversarial scenario suite runs the attack taxonomy of \cref{ch:threat} against the
implemented crate. Implemented as the Rust integration test \texttt{tests/adversarial.rs} (run with
\texttt{cargo test --test adversarial}), it covers A0, A1a, A1b, A2--A5, and X1 and asserts the
expected security outcome for each. The A1 variants additionally pin the warning epoch.
\Cref{tab:impl-t5a} records representative correctness tests and the requirement each protects, and
\cref{tab:tests-adversarial} records the adversarial scenarios with their expected and observed
verdicts. Both tables and the complete test catalogue are in \cref{app:tests}, and the measured
results are reported in \cref{ch:eval}.

\section{System-Wide Engineering Challenges}\label{sec:impl-challenges}

Building the system end to end revealed obstacles at every layer. The main engineering challenges
arose in protocol parity, identifier representation, concurrent multi-client operation, Electron
integration, and server robustness.

\paragraph{Protocol Parity.} Two protocol-parity problems had to be resolved. The first client used an Ed25519-based label
stand-in, while Rust used the complete RFC~9381 ECVRF, so their outputs could not agree. TypeScript
was therefore updated to implement the same ECVRF suite and checked against the RFC~9381 vectors. The
second problem concerned signed-head verification. An early client checked the head signature only
once per monitoring tick, allowing an individual lookup to be answered against a fabricated head. Each
search now returns its signed head atomically. The client verifies the signature, requires the
returned root to match that signed head, and checks the inclusion proof against that root.

\paragraph{Identifier Representation.} Signal represents ACIs and phone-number identifiers (PNIs) as service-ID strings. The dual-index and
CEA constructions accept only canonical 16-byte ACIs. The integration boundary converts an ACI
through libsignal and uses the resulting bytes for both registration and lookup. This keeps the VRF
input identical on both paths. PNIs are excluded before key-transparency processing. Standalone and
embedded tests cover this boundary.

\paragraph{Concurrency: Time-of-Check Races.} Concurrent client registration exposed a time-of-check race. The client and auditor could each fetch
a signed head and then request a consistency proof after another client had committed, causing the
proof's upper bound to exceed the head being checked. Tracking the log by size and binding the
proof's upper bound to the validated head prevented both the client and auditor from incorrectly
reporting a fork.

\paragraph{Electron Integration.} Three obstacles arose in embedding the client in Signal Desktop's
Electron runtime. The first was the application's bundler, which splits a chunk at every dynamic
import. Loading the multi-module networked layer through dynamic imports introduced
initialization-order dependencies between bundles that prevented reliable loading of the verification
layer. Every dynamic import for the key-transparency code was therefore removed, so the whole layer
now lives in one bundle, with the networked path made opt-in at runtime and its failure caught
separately so that it never affects the messaging client itself. The second was context isolation.
With it enabled, property assignments to \texttt{window} in the preload world are not visible to the
renderer, so console-injected helpers silently did nothing, whereas DOM custom events on
\texttt{window} cross the boundary. That is why the warning banner worked while the injected client
handle did not. The integration therefore routes all verdicts through custom events and registers
peers from within the preload world. The third was an event-channel mismatch. Detection initially
fired without updating the user interface, because the background monitor emitted on the client's
typed event bus while the badge and banner listen for a DOM custom event. The fix was to dispatch both
and map the verdict onto the custom event the badge and banner already listened for.

\paragraph{Operational Robustness and Determinism.} Several issues appeared only when the end-to-end
prototype was run. A server that generated a fresh signing key on each launch invalidated every
cached public key, which was fixed by deriving the server's keys deterministically from a seed. A
panic on a freshly emptied log poisoned the shared mutex, after which the server rejected every
subsequent request and brought itself down, which was resolved by bootstrapping a genesis epoch at
initialization. The demonstration was not reproducible because attack state persisted in memory, so
an administrative reset that rebuilds the server from its seed both fixes that and makes the
demonstration repeatable.

\paragraph{Trusted Computing Base and Fail-Closed Behaviour.} On the client, the trusted computing
base is the verifier implementation, its cryptographic dependencies, and the directly implemented
ECVRF (\cref{ssec:impl-core-crypto}), together with the operator's two public keys, the STH signing
key and the VRF key. Because the prototype obtains these keys from the service during initialization,
their initial authenticity remains a trust assumption, and independent authenticated provisioning is a
production requirement. Subject to that assumption, the server, the network, and the log are
\emph{not} trusted, and every response they give is re-checked against those keys.

The \emph{verifier} is fail-closed for integrity checks. Any cryptographic or proof-validation
failure (an invalid or absent signed-tree-head signature, a prefix root that does not recompute, a
missing log inclusion, a proof whose label does not match the one queried, or a VRF binding that does
not hold) yields a \emph{reject} verdict rather than falling through to acceptance.

The present Signal Desktop key-fetch hook (\cref{ssec:impl-hooks}) marks the boundary between what
the verifier guarantees and what the prototype currently enforces. The current key-fetch hook reports
explicit mismatches and proof failures as a red warning but does not abort bundle processing. Complete
error-to-UI routing and session-blocking enforcement remain prototype limitations, left to future
work (\cref{ch:discussion}).

Availability failures produce a separate client state. If the server cannot be reached, the client
displays the amber notice described in \cref{ssec:impl-verifier} and does not mark the key as
verified. The red warning is reserved for proof failures, key mismatches, and authenticated peer
warnings. The prototype cannot determine whether an outage is benign or deliberate, so the response
to persistent failures remains a deployment-policy decision. Production request handlers must also
recover from poisoned locks instead of relying only on the genesis-epoch bootstrap.

\section{Reproducibility}\label{sec:impl-repro}

Reproducibility of the measurements in \cref{ch:eval} depends on a recorded environment and
deterministic cryptographic and sampling inputs. Fixed seeds determine the VRF key, label placement,
and sampled users. Each benchmark begins from fresh seeded server state, so no residual state carries
between runs, while the live demonstration uses the administrative reset. The Rust tests and
benchmarks are run with \texttt{cargo test} and \texttt{cargo bench}, respectively. The environment
record captures the hardware, operating system, compiler, and toolchain versions. The repository
layout and the one-command runner scripts are listed in \cref{sec:apiref-repo}.
